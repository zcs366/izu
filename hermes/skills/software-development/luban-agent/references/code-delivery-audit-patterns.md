# 代码交付审计常见陷阱与实战案例

> 本文件记录2026年5月16日对P0（反馈闭环修复）+ P1（Session Checkpoint + 假引文检测器）代码交付的审计结果，可作为后续代码交付审计的陷阱清单。

## 陷阱一：JSON持久化无异常保护

**发现场景：** 审计 `izu-pipeline.py` 的 `load_manifest()` 函数

**症状：** 第104-105行：
```python
with open(latest) as f:
    manifest = json.load(f)
```
如果 `save_manifest` 在写入过程中crash（磁盘满、JSON序列化异常），文件可能写了一半（无效JSON），`json.load(f)` 直接抛 `json.JSONDecodeError`。**没有fallback处理。**

**修复：** 加 try/except，捕获 JSONDecodeError 后删掉损坏文件，返回 `(None, 0, {})` 降级为全量运行。

**原理：** 任何写文件的持久化操作（`save_manifest`、`save_step` 等），读取端都必须假设文件可能损坏。写端用临时文件 + 原子重命名（tempfile + os.rename）更安全，但最低要求是读端有降级路径。

## 陷阱二：串行URL存活检查阻塞

**发现场景：** 审计 `izu_citation_check.py` 的 `check_url_reachability()` 和 `izu-pipeline.py` 的 `code_fact_check_urls()`

**症状：**
- `check_url_reachability()` 超时10秒（行118），串行检查10个URL理论最长阻塞100秒
- `code_fact_check_urls()` 超时5秒但串行（行396），最多20个URL = 最长100秒
- `izu_fake_cite_check.py` 超时5秒，socket全局timeout=5（行28），串行检查

**修复（低优先级）：** 统一超时到5秒 + 使用 `concurrent.futures.ThreadPoolExecutor` 并行检查 + 设置全局 max_urls=10 上限。

**判断标准：**
- 当前生产环境没出问题 → ⚠️ 有风险但不阻塞
- 如果引文验证步骤是流水线的瓶颈（耗时拉长到分钟级）→ 🔴 需要立即优化

## 陷阱三：新写功能与已有功能的重叠

**发现场景：** 审计 `izu_fake_cite_check.py`（62行）vs `izu_citation_check.py`（402行）

**症状：** 两者都做URL存活检查（HEAD请求）。但`izu_fake_cite_check.py`额外检查arXiv ID格式和域名合理性，`izu_citation_check.py`额外做引文提取+断言一致性LLM验证。

**判断框架：**

| 重叠程度 | 判定 | 处理 |
|---------|------|------|
| >80%功能重叠 | ❌ 重复造轮子 | 删除一个，合并检查项 |
| 30-80%功能重叠但各有独特检查 | ⚠️ 可接受但建议整合 | 保留现状，或在下次重构时整合 |
| <30%功能重叠 | ✅ 各司其职 | 保持独立 |

当前判断：两者各约50%重叠，但各有独特检查项 → ⚠️ 可接受。

## 陷阱四：`--resume` 降级路径不完整

**发现场景：** 审计 `izu-pipeline.py` 主循环（行1276-1284）

**症状：** `load_manifest` 返回 `(None, 0, {})` 时降级为全量运行（行1278-1284）。旁路 `--from <步骤名>` 提供了另一个恢复方式（行1285-1286）。降级路径完整。

**但需要注意：** 如果manifest存在但`last_completed_step`是最后一个步（如"核"），`next_idx = steps.index(last_done) + 1` = 9（越界），遍历 `for i in range(9, 9)` 什么都不跑。这是正确的行为——所有步已完成，不需要再跑。不是bug。

## 陷阱五：cron prompt追加破坏原有逻辑

**发现场景：** 审计 cron job `65eba5595103`（论文日报）的prompt修改

**症状：** 尾部追加了「今日需关注3件事」板块。需要检查：
1. ✅ 是否用 `---` 分隔线与正文分离 → 是
2. ✅ 原有搜索逻辑（"搜索2-3篇→按skill格式输出→中文撰写"）是否原样保留 → 是
3. ✅ 兜底行为是否存在（"今日无紧急事项"）→ 是
4. ✅ 时间颗粒度是否匹配用户场景（3min/10min/30min）→ 是

**原则：** cron prompt追加内容时，永远用 `---` 分隔线 + 禁止修改原有搜索/产出指令 + 必须有兜底行为。

## 陷阱六：cron噪声与用户阅读能力错配

**发现场景：** 审计全部36条cron的交付渠道

**症状：** 36条cron中，每天可能推送10+条消息到军师的微信/Telegram。但用户日均可用时间约1小时（早上5:00-6:00看日报 + 碎片时间）。

**修剪方法论：**

1. **按活动度排序**：每条cron的 `completed` 次数
2. **按重叠度判断**：哪些cron在做类似的事（如论文日报 vs 管弦乐队Stage2-6）
3. **按废弃状态标记**：背后脚本已废弃/API key已失效的cron
4. **按用户消耗估算**：每cron产生的消息数 × 推送渠道数 = 每日消耗用户注意力
5. **保留高杠杆**：保留数据层面（论文日报）+ 保留营收相关（企业经营群报）+ 保留系统和安全相关（备份、升级、入库）

**实战示例：** 36→24条。砍掉6条管弦乐队Stage（脚本废弃+API失效）+ 4条个人周报（7天看不过来的压缩为3天）+ 2条对应提醒。日均消息从~14条降到~3条。
