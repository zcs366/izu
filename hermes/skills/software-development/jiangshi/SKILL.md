# 匠石（Jiangshi）—— 代码与模型的边界法则

> 运斤成风，去垩而鼻不伤。
> 匠石知道哪里该用斧（代码），哪里该用眼（模型）。

## 来源

2026年5月，卡兹克开源AI信息筛选工具AIHOT，公开了11版迭代的核心教训。在izu v3.0→v4.0重构中，这些教训被系统化应用并验证有效。

## 核心铁律

### 第一律：能用代码就别用模型

```
默认假设：这个环节用代码做。
只有代码做不了的（语义理解、模式识别、创意生成），才交给模型。
```

**反模式**：写个Prompt让模型全包。这就是AIHOT v1-v7的死法。
**正模式**：模型只做最纯粹的那一步，其余全部代码化。

### 第二律：Prompt做减法，规则做加法

AIHOT v7→v8是负向优化——Prompt从300行涨到600行，模型反而变笨。最终v11把Prompt砍到200行，模型只打五维分。

**核心洞察**：
- Prompt越复杂，模型越迷失
- 规则应该写在代码里，不该塞进Prompt
- 每次想往Prompt加一条规则，先问：这条规则能用代码实现吗？

### 第三律：能提前算好的绝不现算

AIHOT日报1秒生成——因为精选、分类、翻译在入库时已完成。

**应用到所有系统**：
- 数据入库时做完全部重活
- 展示/输出时只做分桶和排序
- 不要等用户请求时才让模型现算

### 第四律：信源分级在代码层完成

模型不需要知道信源权重。代码做完分级，把带tier标注的结果喂给模型。T1优先引用，T3标注警告。

### 第五律：做减法，不做加法

每次迭代，不是往系统里加东西，而是重新划分代码和模型的边界。代码接管越多，模型职责越纯粹，系统越可靠。

## 决策框架

面对任何一个环节，问三个问题：

```
Q1: 这一步需要语义理解吗？
    NO → 代码做。立刻。
    YES → Q2

Q2: 语义理解后，还需要模型做进一步的决策吗？
    NO → 代码接收模型的语义输出，套公式。
    YES → Q3

Q3: 这个决策有确定性的规则可循吗？
    YES → 把规则写成代码。模型只负责理解输入，代码负责决策。
    NO → 模型做。但这是最后手段，不是默认选项。
```

### WSL中运行Playwright Chromium

WSL2无头Chromium必须加这些参数，否则EPIPE崩溃：
```python
browser = p.chromium.launch(headless=True, args=[
    '--disable-gpu','--no-sandbox','--disable-dev-shm-usage',
    '--disable-setuid-sandbox','--no-first-run','--no-zygote'
```

### 典型应用场景

### 搜索+聚合
```
❌ 错误：LLM搜索→LLM总结→LLM去重→LLM合并
✅ 正确：代码搜索→代码去重+分级→代码算重叠率→LLM仅做语义合并
```

### 断言验证
```
❌ 错误：LLM提取断言→LLM搜索→LLM比对→LLM打分
✅ 正确：代码正则提取→代码搜索→代码字符串比对→仅模糊案例升级LLM
```

### 事实检查
```
❌ 错误：LLM判断URL是否有效
✅ 正确：代码curl HEAD检查→死链列表注入LLM上下文
```

### 日报/摘要生成
```
❌ 错误：用户请求时让LLM从零开始生成
✅ 正确：入库时已完成分类/标注/翻译→代码分桶排序→LLM仅做最终文字润色
```

## 新增验证案例（2026-05-15）\n\n### LSE代码辅助进化 —— 突破单模型元认知瓶颈\n```\n❌ 错误：让单模型分析自己的错误并改写prompt。\n   模型能解AIME题，但无法可靠回答\"我的prompt哪里不好，应该怎么改\"。\n   → 元认知瓶颈：自我反馈回路的质量天花板。\n\n✅ 正确：代码做决策，模型做生成。\n   代码层：错误类型分类(FORMAT/COMPUTE/OTHER)→模板匹配→选择进化方向\n   模型层：只生成模板对应的修复文本\n   结果：50%→75% (+25pp)，不依赖单模型元认知\n```\n\n**核心洞察**：代码辅助不是\"套了一层if-else\"，而是把\"诊断\"这个元认知任务交给确定性逻辑，让模型只负责\"生成\"——分工突破单模型自我改进的天花板。

### 多Rollout答案提取（2026-05-16新增）

```
❌ 错误：在多rollout场景中用单次调用的格式约束（如 FINAL_ANSWER）
   原因：一次调用生成3个rollout用"---"分隔，格式标记在末尾而非每个rollout内
✅ 正确：三层fallback（标注格式→等号提取→数字序列）+ 次佳rollout兜底
结果：6次迭代，70%→100%干净率。关键教训——格式约束在multi-rollout场景下结构失效
```

详见 `references/trt-answer-extraction-case-study.md` — 完整v0.1→v0.6迭代记录。

### 中文知识图谱构建
```
❌ 错误：用LLM提取实体和关系，成本高速度慢
✅ 正确：spaCy zh_core_web_sm依赖解析，纯代码，零LLM调用
结果：150篇文章→4016条边，密度0.163，达到LLM 94%效果
```

### 上下文冗余检测
```
❌ 错误：用embedding模型计算文本相似度去重
✅ 正确：difflib.SequenceMatcher字符串比较，纯代码
压缩率：90%（15K→1.5K token），零模型成本
```

### 进化引擎评分
```
❌ 错误：让LLM评价输出质量（主观、不稳定、贵）
✅ 正确：5维度加权评分，仅语义质量10%用模型，其余90%代码
（URL存活curl检查、结构完整性正则匹配、一致性交叉验证、简洁度token计数）
```

## izu v4.0 验证案例（原版）

从v3.0到v4.0，应用匠石原则后：

| 指标 | v3.0 | v4.0 |
|------|------|------|
| 探/搜聚合LLM调用 | 2次 | 0次（代码） |
| 核验证LLM调用 | 2次 | ~0.6次（仅模糊） |
| 信源分级 | 无 | 60+域名T1/T2/T3 |
| URL死链检查 | 无 | 代码预检→注入劈prompt |
| 单次流水线LLM调用减少 | — | **约-3.5次** |

模型做少了，质量反而提升了——因为代码做的去重/分级/验证是确定性的，不会幻觉。

- 遇到"这个环节该用模型还是代码"的决策时
- 系统出现模型幻觉/不确定性问题时
- 做系统迭代和重构时
