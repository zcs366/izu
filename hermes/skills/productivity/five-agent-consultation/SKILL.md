# 五人合议 · 多Agent分步审议协议

> "兼听则明，偏信则暗。" —— 《资治通鉴》
> 重大决策不经五人合议，等于用一只眼看路。

## 一、适用场景

**触发条件（满足任意一条即启动）：**

- 用户说"让子产/韩信/鲁班/萧何/子贡来看看"
- 用户说"五人合议"、"五子合议"、"全面审议"、"多方审议"、"分步决策"
- 涉及 izu 系统架构、功能增减、路线调整的重大决策
- 用户明确要求"不要一个人说了算"
- 一项功能涉及时：市场判断（该不该）+ 技术远景（长什么样）+ 工程可行性（能不能）+ 资源执行（怎么推）+ 力量调度（谁来干）
- 用户发送视频链接时标记「极大」

**「极大+视频」触发模式（2026-05-17 实战验证）：**
当用户发 YouTube/B站链接标记「极大」时，启动流程：
1. **第一步：并行启动** — 一条线程开始下载音频+whisper转录（后台 `background=True`），另一条线程搜索中文文章补充资料
2. **第二步：用文章资料启动合议** — 不等待STT结果，直接用找到的文章内容作为子Agent context
3. **第三步：合议产出先行** — 评估分析基于文章先行输出，STT完成后补充原始转录稿
4. **转录产出跟进** — 校对润色+存raw+存output，更新log
- 此模式已在同晚连续3次「极大」视频上验证通过

**「大+视频」处理区分（2026-05-19 验证）：**
当用户发B站/YouTube链接标记「大」时，**不需要视频下载和转录**：
- 直接用web_search + web_extract抓取文字文章作为评估素材
- 「大」级别的标准四段式评估（核心摘要→核实→定论→对张成市价值）完全可从文字文章完成
- 视频转录是「极大」级别的专属特权——「大」不需要

**不适用场景：**

- 简单问答（"今天天气"、"查个资料"）
- 已有明确结论的重复任务
- 用户说"直接做"且无歧义

## 二、协议流程

```
子产（该不该做？） → 韩信（最终长什么样？） → 鲁班（能不能做？架构简洁吗？要不要造新装备？）
    → 萧何（怎么推？资源够吗？分几步？） → 子贡（怎么调度？谁执行？怎么包装？怎么分发？）
    → 军师终裁（审核各Agent是否实做，解决冲突，一锤定音）
```

**顺序不可跳。跳步必乱。**

- 韩信定远景之前必须知道子产判断了需求
- 鲁班审架构之前必须知道韩信画了终局
- 萧何拆路径之前必须知道鲁班确认了可行性
- 子贡做调度之前必须知道萧何拆好了步骤

## 三、各角色职责与输出标准

### 3.1 子产 · 需求判断 + Interview 步骤

**回答：** 该不该做？为谁做？真实需求还是伪需求？

**前置步骤：Interview（参考 Jarrod Watts `/interview` 方式）**

在给出任何判断之前，子产必须先产出 **20-50 个澄清问题**，涵盖：
- 用户是谁、在什么场景下遇到问题
- 用户现在用什么土办法解决
- 这个需求的真实频率和痛感等级
- 有没有替代方案、竞品
- 不做会怎样、窄做行不行

这些问题不是走过场——子产自己必须逐条回答或标记"需用户确认"。回答完所有问题后才能进入正式判断阶段。

**输出要求：**
- 需求信号标注来源（真实文档/事件/用户抱怨，非猜测）
- 用户画像（具体的人，非统计数字）
- 替代方案即竞品（用户现在用什么土办法？）
- 一句话定位公式
- **前置问题清单**（20-50个已生成，关键问题已回答/标记待确认）
- 明确判断：该做/不该做/窄做/宽做

**禁止：** 泛泛说"用户需要"。必须有据。禁止跳过 Interview 步骤直接给判断。

### 3.2 韩信 · 技术远景

**回答：** 3-6个月后这东西长什么样？技术方向怎么走？

**输出要求：**
- 终局画像（用户第一次打开时的体验叙述）
- 技术阶梯（现在→2个月→6个月）
- 与AGI方向的贴合论证
- 三句话定调
- 优先级行动表（P0/P1/P2）

**禁止：** 从今天往后推。必须从终局往回倒。

### 3.3 鲁班 · 工程审计 + 装备制造

**回答：** 能不能做？是否叠床架屋？是否臃肿？对整体效果是否有提升？需要造什么新装备/工具？

**输出要求：**
- 逐项诊断（不是泛评，指向具体代码行/设计点）
- 做减法清单（砍什么、合并什么、保留什么）
- 匠石边界核查（代码/模型分割是否合理）
- 量化对比（砍前vs砍后：检查点数量/脚本行数/LLM调用次数）
- 装备制造判断（现有工具够不够？缺什么？怎么造？）

**核心铁律：** 能用代码就别用模型。每次想加东西，先问能不能砍东西。匠石发现缺口 → 鲁班造工具填缺口。

**禁止：** 说"整体还行"。必须指向具体冗余。

### 3.4 萧何 · 执行路径

**回答：** 怎么推？资源够吗？分几步？每步交付什么？

**输出要求：**
- 资源盘点（硬件/API/工时/成本，精确到￥）
- **成本必须三问**：每项花销必须同时回答「花在哪？」「为什么花？」「不花会怎样/省了损失什么？」。禁止只列数字不加解释——用户看不懂"$584 Demo"是什么意思。
- 阶段拆解（每步：输入/输出/工时/交付物）
- 关键路径（哪条任务链决定总工期）
- 风险矩阵（概率×影响×应对）
- 边际成本计算（新增功能对日常运行成本的增幅）
- **工时折算比**：张成市的可用时间需要主动确认，不可假设固定值。2026-05-19用户明确告知日均6h+，但此前被错误假设为1h数月。每次排期前必须用fact_store.search(query='张成市时间')核查最新信息（memory也可能保存但不可靠）。
- **🔴 横向工时验证**：鲁班的工时估算暗含"每天2-3小时全职coding"假设是常见错误。做法：将鲁班每项任务的报时与张成市当前实际可用工时对齐。

**禁止：** 排期不看用户的时间约束。张成市日均有效工时1小时。

### 3.5 子贡 · 力量调度

**回答：** 怎么调动全境力量执行？谁来做？各团队如何联动？对外怎么沟通？怎么包装？

**输出要求：**
- 调度指令（任务→执行团队/Agent→时限→预期输出，四要素齐全）
- 并行/串行分析（哪些可同时进行，哪些有先后依赖）
- 跨团队协同（实验室A与实验室B的接口/数据流）
- 包装方案（产出如何对外呈现？分几层受众？什么渠道？）
- 分发计划（什么产出推送到什么平台、什么频率）
- 变通预案（如果执行卡住，绕行方案A/B/C）

**禁止：** 只调度不跟踪。调度指令发出后必须有追踪机制。

### 3.6 军师 · 终裁

**回答：** 各Agent是否真的做了工作？结论间有无冲突？最终决策是什么？

**输出要求：**
- 逐Agent验证（是否实做？有据可查？还是泛泛而谈？）
- 冲突裁决（不同Agent的建议冲突时，裁决并给出理由）
- 子贡调度可行性复核（分配的团队/资源是否真实可用？）
- 最终决策（做什么/不做什么/什么时候做）
- **🔴 P0/P1/P2 可执行任务表** — 每项包含：任务描述、交付物路径、验收标准。**不是"建议做X"，而是"正在做X"**。用户说"开干"时立即执行，不需要再审批。
- 签核 → 子贡拿着签核结论执行调度。在"开干"模式中签核后直接执行P0。

**禁止：** 各Agent没说做就不做，明显冲突不解决就放行。子贡调度明显不合理不指出。

### 3.7 军师终裁 · 详细验证方法论

军师终裁的核心不是"读一遍输出然后表态"，而是**用filesystem和工具做实打实的证据核查**。以下是2026-05-16 izu可信AI四面体合议中验证的五步法：

#### 3.7.1 第一步：定位Agent实际产出文件

战术：
1. crontab -l 或 cronjob list → 看实际运行的cron的job_id
2. find /home/zcs -name "*dispatch*" 找调度文件
3. ls -la ~/.hermes/skills/ 下各Agent产出的references/
4. 对于"调度令"类产物：直接cat实际文件并wc -l验证行数

信号：
- Agent说"已写入zigong-dispatch-order.md" → 检查文件是否真实存在、行数多少
- Agent说"3个新文件" → 看是否有izu_*.py
- Agent说"cron已修改" → 看cron实际prompt内容

#### 3.7.2 第二步：用精确行号交叉验证

对每个Agent的"具体引用"，在终端里直接read_file指定offset行号：
  read_file(path=..., offset=420, limit=30)
  → 验证Agent说"L425-446"是否真的在那段范围

关键核查点：
- 鲁班说"L425-446, 175行系统prompt" → read offset=420 count=30 → 看prompt长度
- 鲁班说"L228-251 code_dedup_aggregate" → read offset=225 → 确认overlap_ratio存在
- 鲁班说"izu_align_checker.py 287行" → wc -l 确认

#### 3.7.3 第三步：冲突检测 —— 逐Agent交叉对比

读完全部五个Agent输出后，列出所有"不一致"点：

冲突类型A：范围冲突
  子产说"P2做" → 萧何说"推迟"
  → 找出谁错了、为什么错（可行性/时间/资源）

冲突类型B：方案冲突
  子贡推荐方案A(5分钟) vs 萧何留ABC三个候选
  → 看边际收益曲线：10倍投入是否带来10倍收益？

冲突类型C：否决冲突
  子产提议"优先级引擎" → 鲁班"红牌否决" → 萧何不列入
  → 三比一即为结论，军师只需确认否决理由是否成立

每个冲突的裁决必须给出：
  - 裁决结果（选A/合并/推迟/否决）
  - 核心理由（一条，不废话）
  - 否决方的原始引用（说明军师读过了）

#### 3.7.4 第四步：调度可行性复核

子贡的调度令必须校验：
  1. 任务分配的人/系统/Agent是否真实存在
     → izu_*.py 检查文件是否存在
     → 引用的cron job_id是否在cron.list()中
  2. 时间约束是否合理
     → 张成市日均1小时 → 每个任务不能超过45分钟
  3. 成本估算是否可验证
     → 每项有$数字 → 加总与原计划一致？

#### 3.7.5 第五步：签核格式

签署格式（仿《资治通鉴》臣光曰）：

```
🏮 军师终裁令 · {干支日期}

**臣光曰：** {一段简洁判断，点名做了什么、没做什么}

一、逐Agent验证
  ❌/✅ 子产 — {证据引用，精确到文件名/行数}
  ❌/✅ 韩信 — {同上}

二、冲突裁决
  冲突1：{冲突描述} → 裁决：{结论} — {理由一句话}

三、最终决策
  | 项目 | 决策 | 时间 | 负责人 |
  |------|------|------|--------|
  | P0反馈闭环 | 立刻做(A方案) | 今日 | 军师 |

四、签核
  军师·{姓名}  {干支日期} · {时辰}
  子贡——执行。
```

## 四、执行方式

### 降级模式：军师直断（子代理不可用时）

**触发条件：** delegate_task 子代理全部超时（陷阱八），或可用模型不支持 delegate_task。

**流程：** 跳过子代理调用，军师直接执行分析。覆盖五个角色视角：
- 子产视角：需求判断（该不该、窄还是宽）
- 韩信视角：终局画像（3-6个月后长什么样）
- 鲁班视角：架构审计（砍什么、造什么装备）
- 萧何视角：执行路径（分几步、成本多少）
- 子贡视角：调度方案（谁执行、怎么分发）
- 军师终裁：冲突裁决+最终决策

**输出标注：** 在结论开头标注"军师直断（子代理超时降级）"，以区分完整合议结果。

#### "开干"协议（2026-05-20 更新：PRD模板+Non-Goal机制）

#### 核心流程

```
用户讨论/合议/规划阶段 → 军师产出终裁(含P0/P1/P2任务表)
    → 军师自动出PRD（含Goal/Non-Goal/依赖顺序/验收标准）
    → 用户过目核准 → 用户发出"开干"指令
    → 【此刻才激活执行模式】
    → 直接进入编码/写作/实现，不再产出额外计划文档
```

**为什么需要PRD先行（来自百度PRD→Goal→After-Goal实践）：**
- 用户说"开干"后最容易出问题的不是做了什么，而是**没做什么**（即Non-Goal）
- 明确Non-Goal = 避免"做完了你说不是这个意思"的返工
- PRD强制先想清楚：用户故事/验收标准/依赖顺序/明确不做的事

#### 军师的守门职责

**核心规则（2026-05-19用户直接下达）：**
> "以后一定要严格按照军师裁定 + 我的开干批准才能执行。"

这意味着「开干」不再是自由触发词，而是一个两端授权的执行开关：

**授权流程：**
```
用户讨论/合议/规划阶段 → 军师产出终裁(含P0/P1/P2任务表)
    → 用户发出"开干"指令 → 【此刻才激活执行模式】
    → 直接进入编码/写作/实现，不再产出额外计划文档
```

**军师的守门职责：**
1. 非"开干"不执行。用户说"继续""接着说""然后呢"——这些不是"开干"，不触发执行
2. "开干"后自动授权：P0当日交付、P1次日优化、终端命令自动授权、文件创建/修改自动授权
3. 例外（三件事仍需明确批准）：对外公布/发表 / 花钱 / 不可逆破坏性操作
4. 任务范围声明：用户说"开干"时先确认执行边界（"好，先做X和Y，Z等下一步"），避免盲目开工
5. 🔴 **开干前先扫wiki**：P0执行开始之前，必须用 session_search + wiki搜索 检查该项目/主题的最新进展。用户可能在近期对话或wiki中投喂了最新知识、论文链接、方向调整。**先刷新认知再动手，防止在过期假设上施工。** 2026-05-19 ITA训练管线案例：用户说"开干"后军师直接写解码器，被纠正"先摸索，及时跟进最新发展，wiki里有ita相关内容"。反思：开干不等于盲干，先确认手头是不是最新地图。

**「开干」模式（2026-05-18实战验证）：** 军师直断产出后，用户说"开干"=自动触发执行模式。规则：
- 军师直断报告的P0/P1/P2任务表直接变为执行指令，**不需要逐项请示**（用户已授权一次性批准）
- P0 = 当日交付，P1 = 次日优化
- 军师直接进入编码/写作/实现状态，不产生产出计划/时间表/调度文档（用户说"我要看结果而不是干等着"）
- execution delegation 此时可以安全使用——用户已进入等待交付模式，不再有新消息打断

**注意：** 合议即执行（2026-05-16验证），子贡调度令产出后立即进入 P0 编码，军师终裁签核后不等待而直接开干。此模式适用于"决策边界清晰、执行路径明确"的场景。当合议目标为"选一个方案直接落地"时，军师终裁后可跳过等待期直接执行。

### 标准模式（五人合议，推荐）

五个独立Agent顺序执行（子产→韩信→鲁班→萧何→子贡），然后军师终裁。

```python
# 顺序执行——每一步依赖前一步输出
# Step 1: 子产
delegate_task(goal="判断该不该做...", context="...")
# Step 2: 韩信（接收子产输出）
delegate_task(goal="画终局画像...", context="子产判断：...")
# Step 3: 鲁班（接收韩信终局）
delegate_task(goal="审架构+装备判断...", context="韩信终局：...")

**五阶段协议（2026-05-16 ITA项目实战验证）：**

## 五、陷阱与修复

### 陷阱一：跳步——鲁班在韩信之前审计

**症状：** 没有终局画像就开始审架构。鲁班审的是"当前设计"，不是"未来设计"。

**修复：** 确保韩信先出终局画像，鲁班的审计对象是终局画像的实现方案。

### 陷阱二：子产说"该做"就说做——没有追问"窄做还是宽做"

**症状：** 子产一确认需求真实，就直接上全量方案。忽视"窄做比宽做容易保有"。

**修复：** 子产的判断必须包含范围建议（全做/只做核心/先做1个看效果）。军师在终裁时检查。

### 陷阱三：鲁班只审架构不审代码

**症状：** 鲁班说"架构合理"但没看具体实现。代码里有冗余、LLM prompt违规无人发现。

**修复：** 鲁班的输出必须包含对具体代码行/函数/prompt的引用。没有引用的审计视为未完成。

### 陷阱四：萧何排期忽略用户时间约束

**症状：** 排期按全职工程师节奏（1天8小时，1周40小时）。

**修复：** 张成市日均有效工时1小时。排期必须乘以0.2-0.3系数。

### 陷阱五：军师放行未实做的Agent

**症状：** Agent输出看起来很完整，但仔细看——需求信号无来源、架构诊断无行号、排期无工时估算、调度无任务ID。军师没有逐项验证就签核。

**修复：** 军师的审核必须包含逐Agent的实际工作验证，有具体引用才算通过。

### 陷阱六：子贡调度"空中楼阁"

**症状：** 子贡分配了不存在的Agent/团队，或调度指令没有追踪机制。

**修复：** 子贡的调度指令必须基于真实存在的Agent/实验室/工具。军师终裁时复核调度可行性。

### 陷阱七：五人变四人——忘了子贡

**症状：** 习惯了旧的四子合议流程，萧何之后直接跳到军师。

**修复：** 萧何之后的"怎么调度？谁执行？怎么包装？"是子贡的专属问题。跳步则执行悬空。

### 陷阱八：群体盲思——五人快速一致时无人质疑

**症状：** 五个Agent在首轮就全部达成一致，看起来高效，实际可能是跟风效应。

**发现：** 基线合议中共识比常达1.0（5/5一致），元角色诊断全部正确识别为"跟风"或"群体盲思"。

**修复：** 启用TRT-H元合议模式——在合议中植入元认知观察者，发现盲思时发出硬约束干预（如"必须提出反对主流观点的论点"），共识比可从1.0降至0.8。

### 陷阱九：delegate_task 子代理超时（免费/小模型限制）

**症状：** 调用 `delegate_task` 启动子代理后，子代理返回 `interrupted`（Parent agent interrupted — child did not finish in time），0 个 API 调用完成。**根因是模型能力不足，不是 delegate_task 机制本身的问题。** 免费模型（如 `google/gemma-4-31b-it:free`）因推理速度慢或上下文窗口小导致超时。

**已验证可靠的模型（2026-05-16 更新）：**

| 模型 | 子代理完成率 | 平均耗时 | 备注 |
|------|------------|---------|------|
| `deepseek-chat` (DeepSeek V3) | 10/10 (100%) | 55-200s | ✅ 首选，成本极低，已验证两次完整五人合议 |
| `deepseek-v4-flash` | 未实测子代理 | — | 理论上可靠，但 deepseek-chat 已完成全量验证 |
| `google/gemma-4-31b-it:free` | 0/3 (0%) | 53s超时 | ❌ 不可用于子代理 |

**2026-05-16 验证**：第二次五人合议（子产→韩信→鲁班→萧何→子贡）全部在 `deepseek-chat` 上成功，5/5 完成，耗时 55-203s 每 Agent。总用时约 11 分钟（含工具调用）。**结论锁定：`deepseek-chat` 是五人合议的首选子代理模型。**

**修复（按顺序尝试）：**

1. **首选：用 `deepseek-chat` 跑子代理**（已验证10/10完成率，两次完整五人合议。2026-05-16 确认比 `deepseek-v4-flash` 更可靠稳定）。
2. **降级为军师直接分析**（时效优先时）：当所有子代理超时且用户期望快速响应时，军师直接执行分析——覆盖五个角色视角。输出仍按合议格式，但标注"军师直断（子代理超时降级）"。
3. **缩小 context**：如果子代理超时，将每个子代理的 context 压缩到 500 字以内，只留核心判断要素。

**注意：** 2026-05-14 会话中三个子代理（子产/匠石/萧何）因 `gemma-4-31b-it:free` 全部超时。2026-05-15 同一天另一会话使用 `deepseek-chat` 跑完整五人合议（子产→韩信→鲁班→萧何→子贡），全部成功。**结论：子代理超时是模型选择问题，不是架构问题。**

### 陷阱十（修正）：合议过程中用户发新消息被打断

**发现时间**: 2026-05-17 批量摄入合议；2026-05-18 再次验证

**症状**: 合议进行到鲁班/萧何时，用户持续发新链接→子Agent在跑但在等待时被父Agent中断（`interrupted`状态）。五次合议中鲁班被打断三次，最终需降级为军师直断。

**根因**: delegate_task 子代理在快速连发场景中脆弱——父Agent收到新消息时，未完成的子代理被强制中断。2026-05-18会话中三次尝试 delegation（子贡/萧何/三子并行），三次全部被用户新消息打断。

**修复**:
1. **首选：立即切换到军师直断** — 当用户在快速连发模式（3+条连续消息带链接）时，**完全跳过 delegate_task**。不要尝试第一次失败后再试——子代理在连发模式中100%会被打断。直接走降级模式，军师一个人覆盖五个角色视角。
2. **次选：批量模式**（参考第10节）——评估先行，合议收束。在用户还在发链接时不要启动合议，等投喂结束后统一处理。
3. **避免**：不要在用户持续投喂内容时启动任何 delegate_task。连发模式中 delegate_task 的成功率为 0/3（2026-05-18已验证）。
4. **铁律**：检测到用户连发模式 → 停止一切 delegation → 立即转军师直断 → 用户说"开干"后再启动 execution delegation（此时不再有新消息打断，成功率高）

### 陷阱十一：触发词带URL但未先抓取内容

**症状：** 用户说"极大，https://mp.weixin.qq.com/s/xxx"，军师直接启动五人合议但没把文章内容给各Agent。子产拿不到需求信号来源、韩信看不到具体背景——输出空洞无据。

**修复：** 触发词与URL同时出现时，第一步必须**抓取并通读全文**，然后再启动合议。标准流程：`wechat-article-fetch`（或其他抓取方式）→ 通读全文 → 提取核心事实和关键引用 → 作为子产context的第一段传入。案例：2026-05-15 Cherny文章合议，先fetch到/tmp/wechat_text2.txt，通读确认关键事实（Sequoia访谈、/loops+Routines、真实案例），再逐一传给五Agent。

### 陷阱十二：时间线乐观偏差——韩信说6个月，萧何说9个月

**症状：** 韩信画的终局画像很性感（"6个月后双击代码出编码"），但按张成市日均1h折算后，萧何发现实际需要9-12个月。鲁班的工程估算暗含"每天2-3小时全职coding"假设，与用户实际可用工时不符。

**修复：** 
1. 鲁班报工时后，萧何必须做**假设验证**（见萧何技能2.10节）——基准是张成市日均1h，不是日均8h
2. 韩信的终局时间线需要乘以**2-3倍系数**（按日均1h对全职工程师的折算比）
3. 方案必须给出A/B/C三档：推荐方案（9个月成本~$900）、缩水方案（6个月砍需求）、极端方案（3个月只出原型）
4. 军师终裁时间线以萧何版本为基准，而非韩信版本

### 陷阱十三：叙事膨胀——立项书混入励志语言和外部技术叙事

**症状：** 军师终裁后产出的立项书混用两种语言：
- 对内励志：「AGI」「AI母语」「知识晶体」「得道」
- 对外严肃：「代码语义瓶颈的可恢复性证明」「稳定低维语义表示」
投资人/外部审阅者会被前者劝退，团队会被后者冷落。

**修复：**
1. 立项书输出分**两层叙事**：正文用收敛的技术语言（「探索比token更稳定的代码中间表示」），附录或备注保留愿景
2. 禁止在成本预算、技术路线、评估标准等章节使用愿景语言
3. 如果用户有意将立项书给外人看，在定稿前做「叙事收缩检查」——把「AI母语」改成「可逆的代码语义编码」，把「得道」改成「知识传递」，把「帝国」改成「试验」
4. 允许叙事有野心，但证据和承诺必须保守

### 陷阱十四：合议后无标准化产出文档

**症状：** 五人合议跑完一轮，产出散落在各个Agent的对话记录里，没有一份集中的、可直接存档/分发的文档。子贡需要手动拼凑各Agent输出。

**修复：** 五人合议 + 全团合议Phase 5完成后，军师终裁应立即输出「项目立项书」——一份集成所有Agent意见的结构化文档（格式见 `references/project-charter-template.md`）。子贡拿着立项书做调度，不再需要回翻对话记录。

立项书至少包含：
- 项目总览（一句话+核心数据表）
- 五人合议各Agent意见摘要
- 技术路线图（里程碑+交付物+验收标准）
- 成本预算（每项花在哪+为什么花+不花会怎样）
- 应用场景与使用方式
- 与izu的关系定位
- 发布计划与风险清单

参考案例：ITA项目立项书（`output/doc/ita-project-charter-v1.0.md`）

### 陷阱十五：极大视频触发的跨技能整合断裂

**症状：** 用户说"极大，<视频URL>"，军师触发五人合议后产出独立文档，但视频本身的评估分析（`media-transcribe-research` skill的职责）与合议结论割裂——视频的转录稿、技术分析在一个文件，合议的决策、调度令在另一个文件。军师终裁中已经有的改进建议没有回流到视频评估分析中。

**修复：**
1. 当合议由`media-transcribe-research` skill中的"极大"分流触发时，军师终裁必须在**同一会话**中完成
2. 军师终裁的"最终决策"表必须作为视频评估分析中`## C. 改进建议`的P0/P1/P2条目写入
3. 调度令（子贡产出）存入`wiki/exec-plan/`，评估分析（军师产出）存入`wiki/research/{slug}-eval.md`，两者通过`## 附：五人合议军师终裁`节在评估分析中互链
4. 签核格式中的"最终决策"表同时写两处：合议记录（做决策依据存档） + 评估分析（做行动指引存档）

**参考案例：** 2026-05-17 TML交互模型合议 — 评估分析位于`wiki/research/thinking-machines-lab-interaction-model-eval.md`，合议结论作为该文档的`## 附：五人合议军师终裁`节存档。

### 陷阱十六：子代理因上下文过大超时（即使deepseek-chat）

**症状：** 子产/韩信顺利完成，但鲁班（需要大量文件读写）反复被 `interrupted`。2026-05-17批量化合议中验证：鲁班因文件读写调用的上下文积累超过模型有效处理范围。此前10/10成功的deepseek-chat在大型上下文下也超时。

**根因：** 不是模型问题，是**上下文膨胀**——鲁班收到的前驱Agent输出+自身file I/O积累导致context过大。

**修复：**
1. **精简上下文传递**：传给鲁班的context只保留子产/韩信的核心结论（P0/P1/P2排序+终局画像），不要附带完整子Agent输出原文
2. **限制file工具scope**：传给鲁班的`search_files`加`path`+`limit`参数窄化范围
3. **降级军师直断**：当子产+韩信已完成、后续Agent反复超时时，军师基于前两Agent输出做工程判断+终裁
4. **提取中断中的产出**：子代理即使被`interrupted`，其summary和部分tool调用的输出通常仍有价值，军师应提取利用

### 陷阱十七：产出的不是执行而是计划

**发现时间**: 2026-05-18

**症状**: 用户说"我要看结果而不是干等着！为什么你不主动行动？"——军师终裁后输出了调度计划/时间表/分析报告，但用户想要的是**已经落地的东西**（代码、文件、实现的改动）。

**根因**: 军师把"分析完成"误认为"任务完成"。对于已经分析透彻的问题，用户期望的是**立即执行**而非**继续规划执行**。

**修复**:
1. 军师终裁的最终决策表(P0/P1/P2)必须包含**可直接执行的指令**，不是"建议做X"而是"正在做X"。不产出独占的"调度计划/排期表"文件——这些信息内嵌在执行产出中即可。
2. 当用户说"开干"后，**立即转入执行状态**。P0任务直接开始编码/写入，不产生产出计划文档。
3. 区分"需要进一步分析" vs "分析已完成可直接执行"——如果可行性和路径已经清晰（经子产/韩信/鲁班/萧何确认），军师终裁后直接执行，不要再输出调度文档让用户审批。
4. 子贡的调度令在"开干"模式中应最小化——只列出任务+负责人+时限，不需要详细的并行/串行分析（用户已经有这个直觉了）。
5. 关键区别：**规划文档让军师自己安心，执行产出让用户满意。选后者。**

### 陷阱十八：立项书一次产出后不再更新

**发现时间**: 2026-05-19

**症状**: 五人合议产出立项书后，项目推进了数周（M1已完成第一阶段：修复FSQ故障、实现编码器v0.1、编写42个测试、全部169通过），但立项书仍停留在v1.0初版，里程碑状态还是"未开始"。立项书成了历史文档，不再是行动指南。

**用户反馈（原文）**：*"立项书要随着进展调整，记得写清版本号"* — 这不是一次性的建议，是明确的格式约束。

**根因**: 立项书被视为"合议产物"而非"项目治理工具"。合议结束后就没再碰过。

**修复**:
1. **立项书头部必须包含版本号** — 格式 `vX.Y`（X=里程碑版本，Y=小修订），放在项目总览表第一行。初始版本 `v1.0`。
2. **每次实质性变化更新版本号** — 里程碑完成、成本变化、路线变更、新增交付物、测试结果更新。判断标准：这个变化如果下次打开立项书看不到，你会觉得文档是废纸。
3. **立项书末尾必须包含 changelog 表** — 每次更新追加一行（不要修改旧行），格式：`| 版本 | 日期 | 变动 | 原因 |`。「原因」列必须写清楚「做了什么+为什么」，禁止「更新」「修订」等无信息量的词。
4. **里程碑状态列实时更新** — 在技术路线图表格中增加「状态」列（✅已交付 / ⏳进行中 / 🔜未开始）。不要等到里程碑全部完成才改一次。
5. **成本跟踪** — 预算表增加「实际支出」列。每次产生支出后填入。预算偏差>20%时在 changelog 中说明。
6. **风险状态列** — 新增「状态」列（🟢未触发 / 🟡已监控 / 🔴已触发）。已发生风险移到底部保留但不删除。
7. **每次更新触发的时机**：用户说"开干"后执行完成 → 更新立项书；有新测试数据（如测试通过率变化）→ 更新验收标准状态；有新花销 → 更新预算表。
8. **禁止删除历史版本记录** — changelog 是审计线索，删行等于造假。

**参考**: 立项书模板 `references/project-charter-template.md` 已内嵌上述所有规则。使用该模板新建立项书即自动应用版本管理。

### 陷阱十九：项目框架套研究——掩盖科学问题

3. 研究模式中，韩信和子贡不是核心角色——ITA的远景已明确，不需要更多愿景分析
4. 铁律：**如果理论下界排除了99%精度的可能，目标需要修改，不是优化实现**

### 陷阱二十二：开干前没有Non-Goal——"做完了你说不是这个意思"

**发现时间：** 2026-05-20 百度PRD→Goal→After-Goal文章分析

**症状：** 用户说"开干"后，军师直接执行。但用户验收时发现产出物包含了用户不想要的内容，或遗漏了用户默认"不该做"的部分。返工率高。

**根因：** 军师对"开干"的理解 = 执行已确认的P0/P1/P2任务表。但任务表只写了"做什么"，没写"不做什么"。用户的脑子里有隐形的Negative Scope。

**修复：**

4. Non-Goal 可以是外延控制（"不涉及X模块"）也可以是深度控制（"不做Y方向"）

### 陷阱二十二：「极大」级流程/方法论文章不应走五人合议

**发现时间：** 2026-05-20 PRD→Goal→After-Goal文章处理验证

**症状：** 用户说"极大，https://..."启动五人合议，但文章内容是关于**工作流/方法论/实践总结**（如百度PRD→Goal→After-Goal流水线），不是研究问题或架构决策。五人合议产出与军师直断几乎一致，但耗时多3-5倍。

**根因：** "极大"的触发词绑定了五人合议，但合议是为**决策/研究**设计的，不是为**消化已知模式**设计的。对于一篇已经把方法论说清楚的文章，不需要子产判断该不该、韩信画远景——只需要评估价值并连接到已有知识体系。

**识别信号（区分流程文章 vs 研究问题）：**

| 流程/方法论文章 | 研究/决策问题 |
|----------------|--------------|
| 作者已有明确结论 | 结论未知，需要判断 |
| 阐述怎么做/为什么这么做 | 回答该不该做/能不能做 |
| 文章本身就是完整交付物 | 文章是输入，需要加工输出 |
| 举例：百度PRD→Goal实践 | 举例：Cherny数千Agent战略 |

**修复：**
1. `极大` + 流程/方法论文章 → **走军师直断**（五个角色视角快速覆盖）
2. `极大` + 研究/决策问题 → **走标准合议**（子产→韩信→鲁班→萧何→子贡）
3. 判断方法：通读全文后问自己"这篇文章有没有提供一个可以直接抄的招式？" 有→军师直断，没有→合议

**验证（2026-05-20）：** PRD→Goal→After-Goal走军师直断，2小时交付合议报告+概念页+对比页+合成综述，总耗时不到同级别合议的1/3。

| 角色 | 问什么 | 输出 | 典故 |
|------|--------|------|------|
| **子产** | 该不该？<br>研究方向对不对？ | 项目：需求判断<br>研究：关键问题定位+假设验证 | 子产不毁乡校 |
| **韩信** | 长什么样？ | 终局画像+技术路线 | 韩信将兵，多多益善 |
| **鲁班** | 能不能？缺不缺装备？ | 架构审计+装备方案 | 匠石运斤成风 + 鲁班造云梯 |
| **萧何** | 怎么推？资源够吗？ | 执行路径+成本表 | 镇国家，抚百姓，不绝粮道 |
| **子贡** | 怎么调度？怎么包装？ | 调度指令+分发方案 | 子贡一使，五国各有变 |
| **军师** | 都实做了吗？冲突？ | 终裁决断 | 兼听则明 |

## 七、与"子贡"的特殊关系

子贡是五人中最特殊的一个。他是军师的副手和参谋长，身兼双重角色：

1. **在五人合议中**：萧何之后最后发言，提供调度视角
2. **合议结束后**：从"参政"切换到"执行"，拿着军师签核的结论调动全境力量

这意味着：
- 五人合议的发起和后续执行，子贡是天然的衔接者
- 如果合议结论需要后续调度（调动实验室/agent群），子贡自动接手
- 军师终裁签核后，子贡必须在12小时内产出调度指令

### 子产+子贡合写模式（赞助/申请/外联场景）

**触发：** 当合议任务是面向**外部审核员**的文案类工作——申请API赞助、争取合作、对外正式沟通等。

**执行：** 五人合议仍走完整流程（子产断需求→韩信画终局→鲁班审工程→萧何拆路径→子贡做包装），但最终交付物由 **子产和子贡合写**：

- **子产**负责：挖审核员心理、反推评分标准、定位差异化优势、发现生态关系杠杆
- **子贡**负责：吸收子产洞察→转化为打动人的话术→写出完整表单/邮件/申请文案

**为什么：** 子产的深度搜索能力能挖出常规搜索挖不到的信息（如2026-05-15挖出Hermes Agent在小-miMo生态合作名单），子贡的包装能力能将洞察转化为审核员想读的文案。两者独立输出不如合写交付物。

**案例：** 2026-05-15小米MiMo申请——子产挖出生态合作关系+审核员五维度评分矩阵，子贡据此写出5字段完整申请表文案，韩信终局画像作为"标杆素材"注入文案。GitHub优化由鲁班审计+萧何排期+军师执行。

## 八、元合议发现：诊断与干预的两层元认知

2026-05-15，太阳神计划TRT-H实验验证：在五人合议中植入元角色（Meta-Council）审视讨论流程。

**核心发现**：元认知在合议中有两个层次——"诊断"和"干预"，难度不同。

```
诊断层（元角色擅长）：
  ✅ 正确识别"跟风"——多人附和首发言者
  ✅ 正确识别"群体盲思"——五人快速形成一致意见
  ✅ 正确识别"遗漏角度"——某个关键视角被忽略
  3题测试，诊断准确率100%

干预层（元角色不足）：
  ⚠️ "指定子产唱反调"→五人仍选共识
  ⚠️ "请反驳前任"→Agent表示"有道理，但我还是选A"
  指令太软，无法打破已形成的共识惯性
```

**启示**：元角色需要更强的干预机制——不只是"建议"，而是直接注入每个Agent的system prompt（"你必须在回答中包含至少一个反对观点"）。诊断是第一步，有效的干预是第二步。

## 十、批量化合议模式（快速连发场景）

**触发条件：** 用户在单会话内连续发送多个标记「极大」的链接/内容，导致3+条极大线积累。

**核心原则：评估先行，合议收束。**

**2026-05-17 实战：** 单会话内积累3条极大线（Evolver工程 + Prompt Caching + Anthropic平台），用户持续发新链接的节奏不允许每篇独立跑合议。

**执行：**
1. 每条极大线先独立完成评估（wiki+output+HTML+log），不等待合议
2. 积累满3条或用户说「合议」时统一触发
3. 子产（3条优先级）→韩信（合并画终局影响）→鲁班（合审工程）→萧何（合并算成本排序）→子贡（统一调度）→军师终裁
4. 输出单份「批量合议报告」至 wiki/exec-plan/

**与传统差异：** 传统=评估→合议→决策→执行（串行深）；批量=多条评估并行→统一合议→优先级排序→分步执行（并行先广后深）

**注意：** 合议目的是优先级裁决和资源分配——三件事先做哪件、资源怎么切。评估已在链路前半段完成。

**2026-05-18 增强验证：** 批量化合议 + 军师直断 + 开干执行 三阶段完整链路：
1. 用户连发6+条内容，每条独立评估入库
2. 积累到第4条时触发核战队审读，但因持续打断→军师直断
3. 军师直断报告直接产出P0/P1/P2可执行任务表
4. 用户说"开干"→立即进入编码执行状态
5. P0当日交付（回归测试框架），P1当日追加交付（耦合复杂度+压缩预算）
6. 47/47测试全过

**关键区别：** 之前批量化止于"优先级裁决+报告"，本次延长到"裁决→执行→交付"全链路。详见 `references/2026-05-18-hybrid-review-execution.md`

### 变异模式：军师直断合成（8+篇同主题极大级）
**触发条件：** 5+篇标记「极大」的文章属于同一认知主题，用户在快速连发模式中持续投喂。

**与「降级模式」的区别：** 降级模式（§4）是子代理超时的**备选方案**——走预想流程但Agent不可用。本模式是**有意的结构选择**——从一开始就走军师直断，因为不适合走5-agent流程：8篇文章×5代理=40次delegate_task，在火线场景中100%会被用户新消息打断，且8篇同主题会产生大量重复劳动。

**执行：**
1. 不用delegate_task——直接军师读取所有文章
2. 不写逐篇独立评估——写一篇框架合成文档
3. 输出结构：合成图景 + 维度展开（每维做对照表） + P0/P1行动计划
4. raw文章正常入库（wiki/raw/articles/*.md）
5. 跳过合议标记——合成本身就是「合议」（军师直断版本）
6. 产出：wiki/research/（合成版） + output/极大/（.md+.html） + output/极大/action-plan.md

**验证：** 2026-05-19 成功处理8篇极大级文章（Harness Engineering + AI Skills + Memory + 编排）。详见 `render-eval-report` skill 的 `references/2026-05-19-mass-synthesis-8-articles.md`。

**安全阀：** 如果识别后发现文章分属2-3个不同主题，退回标准批量化合议模式（§10主模式），按主题分组后每主题各走一轮。

## 十一、研究模式（Research Mode）

> **核心认知（Claude 2026-05-19）：** 五人合议是为"项目决策"设计的——它回答"该不该做"、"怎么做"、"多少钱"。但研究的本质不是决策，是假设-检验-修正循环。研究问题不是"该不该做"，而是**"真相是什么"**。
>
> 把研究问题塞进项目决策框架，产出的是一张好看的路线图，但会掩盖最根本的科学问题。ITA项目的"压缩率和语义保真度之间的率失真曲线在哪里"——这个问题的答案不在任何一个合议角色的职责表里。
>
> **根本区别：**
> ```
> 项目决策框架                         研究框架
> ━━━━━━━━━━━━━━━━━                  ━━━━━━━━━━━━━━━━━
> 该不该做？                           真相是什么？
> 怎么做？                             假设是什么？
> 多少钱？                             怎么检验？
> 谁执行？                             修正了什么？
> 路线图好看吗？                       我们学到了什么？
> ```

### 11.1 触发条件

研究模式取代标准合议模式，当以下条件满足时激活：
- 问题核心是**未知的科学真相**，不是已知范围内的执行决策
- 用户明确说这是「研究」而非「项目」
- 用户说「ITA研究」「理论验证」「实验设计」「假设检验」
- 问题涉及"如果X成立，Y会怎么样"而非"要不要做X"

### 11.2 角色池的扩展

研究模式在五人合议的基础上引入四个新角色、调整两个现有角色：

#### 新增研究角色（4人）

| 角色 | 身份 | 使命 | 在合议中的位置 |
|------|------|------|---------------|
| **惠施** | 概念辨析官 | 把每个核心概念翻译成可测量、可操作的定义。不解决定，只澄清含义。 | Round 0：必须最先发言 |
| **墨子** | 形式化验证官 | 把核心主张翻译成可证伪的数学命题，用率失真定理计算理论下界。 | Round 1：在概念澄清之后 |
| **商鞅** | 实验设计官 | 不关心愿景，只关心"用最少资源获得最大信息量"。设计最小可行实验。 | Round 2：在理论边界之内 |
| **张仪** | 最强攻击官 | 找到最可能导致项目失败的一个点 + 降级方案。替代子贡在研究模式中的位置。 | 最后一轮：终审攻击 |

#### 调整现有角色

| 角色 | 项目模式职责 | 研究模式职责 |
|------|------------|------------|
| **子产** | 需求判断——该不该做、为谁做 | **研究方向**——关键问题在哪、假设是什么、方向对不对 |
| **子贡** | 调度分发——谁执行、怎么包装 | **由张仪替代**——最强攻击，找单点失败 |
| **鲁班** | 工程可行——能不能做、造什么装备 | 工程可行——**但在理论约束内**（墨子的理论边界不可突破） |
| **韩信** | 技术远景——3-6月后长什么样 | 研究模式中**不是核心角色**——ITA的远景已明确（RTCE基准+语义编码），不需要更多愿景分析 |
| **萧何** | 执行路径——怎么推、资源够吗 | 执行路径不变——工时分配 + 成本估算 |

### 11.3 ITA研究合议序列（6轮）

研究模式是**顺序执行**的——每轮依赖前一轮的输出，不可并行：

```
Round 0: 惠施（概念澄清）
  → 输出：每个核心概念的操作性定义
  → 示例：「代码语义」是什么语义？「理解」的标准是什么？「Steering成功」怎么测量？

Round 1: 墨子（形式化验证）
  → 输入：惠施的操作性定义
  → 输出：率失真边界 + 信息论约束 + 理论上限
  → 铁律：如果理论下界排除了99%精度，目标需要修改，不是优化实现

Round 2: 商鞅（最小可行实验设计）
  → 输入：墨子的理论约束
  → 输出：20工时基线实验设计 + 成功/失败判断标准
  → 示例：先用CodeBERT跑500个函数的round-trip，看现有基线在哪

Round 3: 鲁班（工程可行性）
  → 输入：商鞅的实验设计 + 墨子的理论约束
  → 输出：在理论边界内的技术实现方案 + 工具选型
  → 约束：不能超出理论边界。如果不满足，必须指出。

Round 4: 萧何（资源路径）
  → 输入：鲁班的技术方案
  → 输出：资源盘点 + 工时分配 + 成本估算 + 关键路径

Round 5: 张仪（最强攻击）
  → 输入：完整的方案（Round 0-4全部输出）
  → 输出：最可能导致失败的一个点 + 降级方案
  → 只找1个，最致命的那1个
```

### 11.4 izu研究合议序列（5轮）

izu研究在五人合议基础上小改，适合已知框架内的研究方向评估：

```
Round 0: 子产（需求判断+研究方向——双身份）
  → 既是：该不该做？（项目）
  → 又是：关键问题在哪？假设是什么？（研究）
  → 输出：需求判断 + 研究方向定位

Round 1: 韩信（技术远景）
  → 这项研究对izu 3-6个月方向的影响

Round 2: 鲁班（工程可行性）
  → 能不能做？有没有重复造轮子？

Round 3: 萧何（执行路径）
  → 资源盘点。阶段拆解。关键路径。

Round 4: 张仪（最强攻击）
  → 最可能导致失败的一个点 + 降级方案
  → 替代子贡
```

### 11.5 核战队在双轨道中的角色

1. **不替代五人合议**——项目决策仍走标准合议流程。研究模式和项目模式是互补的，不是替代关系。
2. **不适合所有问题**——只适用于"科学真相未知"的问题。已知的技术实现方案不需要墨子/惠施。
3. **成本约束**——研究模式（6轮顺序）比项目模式（5人并行）耗时更长。每轮约1-3分钟，全流程约10-15分钟。
4. **1周试行**——2026-05-19起试行1周，到期评估效果。详见 `~/.hermes/scripts/research_orchestrator.py`（v4.0, 双轨道自动化）。
