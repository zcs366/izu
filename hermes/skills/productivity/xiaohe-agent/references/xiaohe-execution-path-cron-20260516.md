## 一、假设验证方法论

### 核心原则

鲁班（技术方）和萧何（执行方）对同一任务估算不同是正常的。萧何的职责不是推翻鲁班，而是：
1. **复现鲁班的计算逻辑**（他为什么说2分钟？）
2. **识别漏算项**（他忘了什么？）
3. **重新估算**（给出修正后的工时）
4. **提炼决策点**（哪里需要军师介入）

### 假设验证模板

```
鲁班预估：[X分钟/小时]
萧何复算：[X分钟/小时]
差异分析：
| 步骤 | 鲁班假设 | 实际 | 差异原因 |
|------|---------|------|---------|
| 步骤1 | [描述] | [描述] | [原因] |
| 步骤2 | [描述] | [描述] | [原因] |

结论：[总体判断]
```

### 这次的关键发现

鲁班说"P0只需2分钟"。萧何复算后发现：

| 步骤 | 鲁班假设 | 实际估算 | 差异 |
|------|---------|---------|------|
| 找到cron prompt | 已定位（0min） | 需从36个job中识别出哪个prompt（5-10min） | ❌ 漏算——没有统一prompt入口 |
| 加一句话 | 几秒 | 2分钟 | ✅ 基本正确 |
| 决策分歧 | 无需决策 | 需要选择方案A/B/C（10-15min） | ❌ 漏算——军师需要选择改哪个job |
| 验收测试 | 1分钟 | 5-10min | ❌ 漏算——改完要验证 |

**结论**：鲁班的2分钟是"执行时间"而非"决策+执行时间"。实际需30-50分钟含决策，但如果军师当场拍板方案A，从拍板到执行只需5-10分钟。

### 判断技巧

- **"改一行代码"和"决定改哪一行"是两回事。** 永远把决策时间单列。
- **不要假设定位成本为零。** 从收到指令到打开正确文件，中间可能隔着几十个cron job需要遍历。
- **验收不可省略。** 哪怕只是改prompt文本，也要跑一次确认格式/语气正确。

## 四、边际成本计算的经验补充

### 四种常见情况的成本判定

1. **纯prompt改文本**（不增加API调用）：**¥0**
2. **纯代码启发式规则**（正则、字符串匹配、文件读写、状态检查）：**¥0**
3. **新增LLM调用**：按调用频率 × 输入/输出token × 单价计算
4. **减少已有cron job**：**成本降低**（省掉被删除job的API调用）

### 这次的计算

| 改动 | 边际成本 |
|------|---------|
| P0：prompt末尾加一句话 | ¥0（不改API调用量） |
| P1：izu --resume参数 | ¥0（仅当显式调用才触发） |
| P1：假引文检测器（纯启发式） | ¥0（不调LLM） |
| P2：基地数字化1% | ~¥0.05-0.2/天（新增1个cron） |
| P3：cron修剪（砍12条） | ⬇️ 日均成本降79%（省最多） |

### 判断技巧

- 如果新功能不依赖LLM推理，成本=0
- 如果新功能减少cron job，成本降低
- 安全网/检查点可能节省成本（避免失败job无限循环浪费API）

## 六、关键原则（这次新增的）

1. **假设拆解是萧何的核心价值**。鲁班说"2分钟"，萧何要问："2分钟？从哪一步到哪一步？中间有哪些步骤被省略了？"
2. **工时估算必须区分"决策时间"和"执行时间"**。决策时间不可取消，只能压缩（给选项让军师选）。
3. **每个执行计划末尾必须有一个"待军师决策"区块**。不要让军师从报告中自己提炼决策点——萧何要替他提炼好。
4. **版本登记不是事后的**。从报告生成那一刻起就要给版本号。
5. **外部依赖需要作为独立风险项列出**（这次：P2的妻子配合度，P0的军师决策速度）。
