# 萧何执行路径拆解·真实案例

> 源会话：2026-05-15，军师祭酒问鲁班审计后，萧何拆Loop合约安全网+语法糖执行路径。
> 这是萧何技能框架在Hermes Agent cron系统中的一次实战运用，未来处理同类任务可以此为模板。

---

## 背景

鲁班对Hermes Agent的cron子系统做了架构审计，发现35个定时job缺乏安全网：
- 任何job失败无通知
- 失败job会反复重试直到死
- 没有现场保留（失败时的输出、上下文）
- 没有观察/诊断/重试的交互命令

军师让萧何做执行路径拆解。

---

## 一、资源盘点方法论

### 盘点清单

```
1. LLM API（模型/提供商/Key/成本）
2. 代码库（已存在的功能模块、新功能可复用的基础设施）
3. 调度器（什么结构、怎么tick、怎么deliver）
4. 已有数据（jobs.json schema、现有job配置）
5. 人力（张成市日均有效工时、是否自己写代码）
6. 现有运行成本（当前日均API调用量 × 单价）
```

### 这次盘点的关键发现

- **35个job，34个enabled**，分布在个人Telegram、群元宝、研究流水线
- **研究流水线（Stage2→6）是链式依赖**，每小时触发一次
- **现有成本极低**：日均37次API调用 × ~¥0.034/次 = **¥1.26/天**
- **现有基础设施极其完善**：scheduler已有run_job()/tick()/deliver/挂起/恢复，几乎不需要从头造
- **成本空间充裕**：新功能边际成本趋近于零

### 盘点技巧

- 不要只靠读README，要实际读源码（`cron/scheduler.py`、`cron/jobs.py`、`tools/cronjob_tools.py`）
- 不要只数job数量，要看每个job的deliver target、schedule、enabled/state状态
- 成本估算要精确到百万tokens单价 × 实际使用量，不是毛估估

## 二、阶段拆解方法论

### 拆解模板

```
## 阶段[N]：[阶段名称]（P[优先级]）

| 步骤 | 输入 | 输出 | 工时(h) | 交付物 |
|------|------|------|---------|--------|
| N.1 [步骤名] | [前置依赖] | [输出产物] | [小时] | [具体交付物] |

**阶段小计：X小时（X天）**
```

### 这次拆解的关键约束

- 张成市 **日均1小时有效工时**，不是写代码的（全部AI生成）
- 所以拆解必须按 **每天可完成的小块** 来分，而不是按专业角色分
- 每个步骤的工时估算必须 **<=1小时**，否则一天做不完
- 总工时=实际天数（日均1h × 天数 = 总工时）

### 拆解结果

```
阶段一（P0）：安全网核心 — 2.5h / 2.5天
  1.1 schema+字段注入（0.5h）
  1.2 调度器计数器（1.0h）← 关键路径
  1.3 暂停时Telegram通知（0.5h）
  1.4 测试+部署（0.5h）

阶段二（P0）：语法糖命令 — 3.5h / 3.5天
  2.1 /loops list（0.5h）
  2.2 /loops status（0.5h）
  2.3 /loops log（0.5h）
  2.4 /loops retry（0.5h）
  2.5 /loops resume（0.5h）
  2.6 路由集成（0.5h）
  2.7 测试（0.5h）

阶段三（P0）：stop_condition评估 — 1.5h / 1.5天
  3.1 循环摘要prompt模板（0.5h）
  3.2 失败诊断prompt（0.5h）
  3.3 集成到scheduler（0.5h）

阶段四：完善+文档 — 1.5h / 1.5天
  4.1 手动暂停/启用命令（0.5h）
  4.2 全局上限兜底（0.5h）
  4.3 用户文档（0.5h）
```

## 三、关键路径方法论

这次的关键路径：

```
安全网核心(2.5d) → 语法糖命令(3.5d) → 评估(1.5d) → 完善(1.5d)
```

**判断方法**：
1. 每阶段的输出是下一阶段的输入 → 必须串行
2. 没有可以跟关键路径并行的独立任务组（张成市一天只有1小时，不能并行做两件事）
3. 最危险的子路径：不是最长那个，而是 **依赖最多后续步骤的那个**（这里：1.2调度器计数器）

### 判断技巧

- 列出所有任务的 **前置依赖图**
- 所有依赖链中 **最长的那条** 就是关键路径
- 如果某个节点被多个后续节点依赖，它就是 **高风险点**
- 注意：张成市日均1小时的场景下，**所有任务天然串行**，关键路径就是总工期

## 四、风险矩阵方法论

### 模板

```
| 风险 | 概率 | 影响 | 风险值(=P×I) | 应对 |
|------|------|------|--------------|------|
| [描述] | 低/中/高 | 低/中/高 | [数字] | [具体措施] |
```

### 这次的风险矩阵

| 风险 | 概率 | 影响 | 风险值 | 应对 |
|------|------|------|--------|------|
| ① `mark_job_run`调用点选错，计数器不生效 | 中(40%) | 高 | 1.6 | 先写测试：创建一个repeat=1的job，确认执行后state=paused |
| ② Telegram消息格式化错 | 低(20%) | 中 | 0.6 | 安全网纯文本；复杂格式化在阶段二再做 |
| ③ AI生成代码有bug需多轮调试 | 高(60%) | 中 | 1.8 | 每步提交小增量，一步测通再下一步 |
| ④ 现有35个job与新增字段不兼容 | 低(15%) | 高 | 0.75 | 默认值设None（旧job不启用），新创建才有上限 |
| ⑤ gateway重启中断 | 中(30%) | 低 | 0.3 | systemd自动重启 |
| ⑥ 张成市连续中断4天+ | 中(30%) | 高 | 1.5 | 第一阶段2.5天如果中断，考虑周末补1-2h |
| ⑦ DeepSeek API高峰期出错 | 低(15%) | 低 | 0.15 | fallback自动走MiniMax-CN |

### 风险值解读

- **>=1.5** → 必须主动应对（减概率或减影响）
- **0.5-1.5** → 有应对即可
- **<0.5** → 接受

**最高风险组合**: ①+③+⑥ → 解法：**第一天先做最小可行测试**

## 五、边际成本计算模板

### 公式

```
边际成本 = 新增API调用量 × 每百万tokens单价 × 日/周/月频率
```

### 这次的计算

```
当前日均成本:
  37次调用 × (15K输入 + 500K输出) × (¥2/M输入 + ¥8/M输出) = ¥1.26/天

新功能边际成本:
  安全网: ¥0（纯逻辑，零API）
  语法糖: ¥0（读取jobs.json + 格式化输出）
  诊断: 每天多1-2次 × 0.5K输出 × ¥8/M = ¥0.004-0.008/天

结论: 边际成本趋近于零（¥0-10/年），完全不用考虑成本限制
```

### 判断技巧

- 如果新功能依赖LLM推理，要算 **输入+输出token总量**
- 如果新功能只依赖读取本地JSON/json.sqlite + 格式化输出，**成本=0**
- 已有基础设施（gateway/scheduler/delivery）的使用**不增加成本**
- 安全网实际上可能**省钱**（避免失败job无限循环浪费API）

## 六、执行建议模板

```
1. Day 0（今天就做）：[最简可行工作，半小时内能完成的]
2. Day 1：[核心风险降维]
3. Day 2-N：[依次推]
提交频率建议：每天结束时提交一个可工作的增量
```

## 关键原则总结

1. **先盘点再拆解。** 不知道有什么资源，拆的任务可能不现实
2. **任务可今天开始。** 拆出来的任务，打开终端就能写第一行代码才算拆到位
3. **成本先算。** 每个技术决策附一个边际成本估算
4. **卡点先清。** 不绕过障碍，直接标出来、给解法
5. **最少步骤发布。** 从代码写完到用户能用，中间不超过3步
6. **薅羊毛是美德。** 免费>低成本>付费。API能省则省
