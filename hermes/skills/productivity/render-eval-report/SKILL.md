# render-eval-report：全流程评估管线

## 一、核心工作流

### Step 1: 内容抓取
- 公众号 → `web_extract`
- 论文/博客 → `web_extract`
- YouTube / B站视频 → 分两种路径：

#### 路径A：转录评估（信号词「存入wiki」「转录」「转存」）
按 `video-to-wiki` 技能全流程：查字幕 → 下载字幕/Whisper转录 → wiki入库

#### 路径B：元数据评估（信号词「评估分析」「评估」「极大」）
跳过全量转录，直接从元数据评估：
1. 获取视频元数据（B站API: `x/web-interface/view?bvid=BV号`）
2. 检查字幕可用性（`data.subtitle.list` 是否非空）
3. **有字幕** → 考虑下载字幕做文本评估
4. **无字幕** → 仅用description + 额外检索补充信息（如播客系列可能有补充文章/评论区讨论）
5. 产出格式：星级评定 + 论点摘要 + 对齐度分析表 + 批判性评估 + 行动清单
6. 标记 `status: raw` 及 `transcription: none` 在 frontmatter 中
7. 存入 wiki/raw/ — 不留入 output/ 除非明确要求 HTML 渲染

#### 路径B+：三角验证评估（当评估对象涉及可交叉验证的源码时）

当视频/文章中的论点可以通过**已知工程实现**（如泄露源码、开源代码库）来验证时，走此增强路径：

1. 完成路径B标准步骤 1-4
2. **交叉验证**：搜索对应的工程实现（源码 API、开源库、泄露代码分析、官方文档）
   - 优先搜索：GitHub 开源仓库、泄露源码分析文章、官方 API 文档
   - 搜索信号词：产品名 + "leaked source" / "source code" / "源码" / "architecture"
   - 不要因为视频/文章没说就认为不存在——产品文档和源码常常比播客更真实
3. **三角对照表**：视频观点 ↔ 工程实现真相 ↔ 自身系统能力
4. 修正视频中的误判（如「概念阶段」→实际已工程化，或「只有A能做到」→B其实也能）
5. 产出格式增加「三角对照」章节

**触发信号**：视频涉及的具体产品/工具有可获取的源代码或详细的工程分析。**宁可多做一步搜索，不要默认视频观点为真。**

**⚠️ 关键教训（2026-05-20）**：
- 评估「硅谷温差 Ep2: Agent记忆系统=AGI ?」时，视频称Dreaming是「仅停留在概念阶段」
- 用户指出 Claude Code 泄露源码中已有完整实现
- 调出源码分析后，发现 Dreaming 已是完整工程化功能（三重门+锁文件+后台subagent，200+行 TypeScript）
- **教训**：不要假设播客追不上工程进展。对于涉及热门开源/泄露源码的产品，评估前先快速搜索源码分析文章
- **三角验证是对评估者最好的纠偏机制**——它迫使你找到第三方的工程事实，不依赖单一信息来源

> **何时走路径B**：用户说「评估分析」「看看这个视频」「极大」「评价」等，或视频仅5分钟以下且信息量明显可通过描述概括。路径B产出的是**评估**，不是转录稿。

### Step 2: 等级判定
| 级别 | 动作 | 存储 |
|------|------|------|
| **极大** | 评估+入库+output/极大/ + trigger_consultation | wiki/research/ + output/大或极大/ + 合议标记 |
| **大** | 评估+入库+output/大/ | wiki/research/ + output/大或极大/ |
| **中/小** | 快速评估+log记录 | log.md（不创建独立文件） |

### Step 3: 评估撰写
写入 `wiki/research/`，YAML frontmatter必须完整：
- `title`, `source`, `date`, `eval_level`, `tags`

结构为：概述 → 论点 → 启示 → 检查清单 → 军师判断

### Step 4: 输出交付
写入 `output/大或极大/`，精简版Markdown，去frontmatter。

### Step 5: 渲染HTML
```bash
python3 /mnt/i/hermes/tools/render_report.py <wiki版路径> -o <output版路径>.html
```
优先用wiki版（有frontmatter才能正确渲染标题和级别徽章）。

### Step 6: 追加日志
追加到 `wiki/log.md`。

## 二、特殊模式

### 快速连发模式（单会话多链接）
用户连续发链接时，根据链接数量和主题关系分两种路径：

#### 路径A：异主题/少量链接（≤4篇）
每篇独立处理但可并行：
- `delegate_task` 分派子线程处理两篇极大级文章
- 中/小级可直接快速评估回复不入库或单笔记
- 批次结束后统一追加 log.md
- 极大级触发合议标记但不等待合议——评估先行，合议在批次结束后单独触发

#### 路径B：同主题火线合成（5+篇极大级，同一主题）
跳过逐篇独立评估，直接做框架合成：
- **前提**：所有文章必须属于同一认知主题（人工判断→看标题+核心论点是否指向同一领域）
- **步骤**：
  1. 批量抓取所有文章内容
  2. 并行保存全部 raw 到 wiki/raw/（直接 write_file，不需要 delegate_task）
  3. 识别连接主题——用一张合成图景（ASCII图表）把文章之间的关系画出来
  4. 写一篇框架合成文档：分维度（哲学层/资产层/执行层/管理层/记忆层/工程层）展开
  5. 每个维度做**对照表**：每篇文章的核心主张 ↔ 我们体系的现有能力 ↔ 差距
  6. 产出 P0/P1 行动计划（带难度⭐和价值💎评级）
- **输出**：wiki/research/（单篇框架合成） + output/极大/（.md + .html） + output/极大/action-plan.md
- **不做什么**：不写逐篇独立评估，不触发5-agent合议
- **验证**：2026-05-19 成功处理8篇极大级Harness Engineering/AI Skills主题文章

### 知识框架合成（批处理后）
批量处理完关联文章后，最后一步必须做框架合成——**异主题模式**中这是后处理步骤，**同主题火线合成模式**中它就是主输出：
1. 回顾所有文章的内在联系
2. 将它们映射为一个统一的认知框架
3. 在一篇总结性评估中呈现（如年度综述评估）
4. **这个合成不是可选项**——它把碎片转化为体系，是评估的最高价值产出

### P0/P1 行动计划的输出格式
在"开干"模式或"同主题火线合成"模式中，评估产出必须包含可执行任务表。推荐格式：

| 优先级 | 任务 | 难度 | 价值 | 说明 |
|--------|------|------|------|------|
| P0 | 具体动作 | ⭐~⭐⭐⭐ | 💎~💎💎💎 | 简要理由 |

要求：
- P0 = 当日/次工作日可交付，P1 = 本周优化
- 难度和价值分开标注（这样用户可以根据自己的时间和精力做选择）
- 每个任务必须有具体的产出物（"做审计"→"产出audit-report.md"）
- 最后加 **不做清单**——明确哪些事本周不碰并给出理由

### 开干模式
用户说「开干」时，将所有待执行建议结构化为 **P0（当日交付）** 和 **P1（次日推进）**，设todo并立即执行第一项。

## 四、输出特性

### 4a. 标准输出组件
- YAML frontmatter解析到元数据头
- 自动目录导航（sticky侧栏）
- h3自动折叠（details/summary）
- Pygments代码高亮
- 斑马纹表格和评估级别徽章 ✅
- 滚动时目录项高亮 ✅
- 定论徽章（✅/⚠️/❌带彩色class）✅
- 可折叠详情段（details/summary）✅
- 行级胜出标记表（col-win/lose/equal）✅
- 军师按专属引用框（sigil-quote）✅
- 进度条（P0(红)/P1(橙)/P2(黄)）✅
- 批次处理后的框架合成
- 开干模式：建议 → P0/P1 → todo → 执行

### 4b. 用户偏好：「全部列表」输出格式

当用户说「全部列表」「列表」「拉单子」「拉清单」时，输出格式切换为**纯列表模式**，规则如下：

1. **自然分组**：按领域/类别分成若干组，每组用 emoji 标题（如 📺 播客系列 / 🛠️ 工程落地 / 🧠 架构思考）
2. **优先级标签**：每项前置 `P0`、`P1`、`P2` 标签（即使不在行动清单场景，也按轻重缓急标记）
3. **可用性标记**：已完成项用 `[x]` / `✅`，待办用 `[ ]` / `☐`
4. **观感原则**：宁愿多换行，不要挤一段。每项一行，不要用逗号串起多项
5. **补充分类**：如果列表涉及视频/文章集合，用格式化表格（编号/标题/时长/播放量/日期/链接）呈现
6. **结尾留钩子**：清单末尾留一句 "你想先从哪个入手？" 或给出推荐优先级

> **触发词**：「全部列表」「列表」「拉单子」「拉清单」「要得，全部列表」

## 五、HTML 输出：Phase 1 → Phase 2

**2026-05-19 升级：从 markdown→HTML 转换升级为手写 HTML 原生信息密度。**

### Phase 1（旧，不推荐）
```python
# markdown 库直接转换 → 纯排版，无信息层级
html_body = markdown.markdown(md_content, extensions=['tables', 'fenced_code'])
full_html = f"<!DOCTYPE html>...{base_css}...{html_body}..."
```
问题：所有内容平等展开，需全文阅读才能定位结论，无视觉引导。

### Phase 2（推荐，当前标准）
**手写 HTML 结构**，利用 HTML 作为信息密度的原生表达载体。核心组件：

| 组件 | CSS Class | 用途 |
|------|-----------|------|
| 定论徽章 | `.badge-pass/green/yellow/red` | 一眼定位结论级别 |
| 折叠详情 | `<details><summary>` | 需要时展开，不需要收起 |
| 高亮对照表 | `.col-win/.col-lose/.col-equal` | 行颜色标记胜出列 |
| 信息卡片 | `.card .card-title` | 分组信息区块 |
| 军师按引用框 | `.sigil-quote` | 军师按专属样式 |
| 进度条 | `.progress-fill .progress-p0/1/2` | 实施优先级可视化 |

**可复用模板**：`templates/izu-report-phase2.html`（开箱即用，复制修改即可）

> **核心原则**：HTML 不是 Markdown 的转译目标，而是信息密度的原生表达载体。用 HTML 写报告 = 用 CSS 做信息分层 + 用结构做阅读节奏 + 用交互做注意力引导。

## 七、陷阱（Pitfalls）

1. ❌ **不推荐 markdown→HTML 转换**（Phase 1）——所有内容平等展开，无信息密度。应直接手写 HTML（Phase 2）
2. 优先渲染wiki版（有frontmatter），output版无frontmatter会缺失级别徽章
3. wiki+output+HTML+log四条线须同一turn完成不能遗漏
4. 多个链接分别处理不合并在一个报告中
5. npm安装时注意包名冲突：wx-cli（2016年旧包）≠ @jackwener/wx-cli（2026年新版），装完后验证命令名（可能不是包名）
6. HTML 模板的 badge/col-win 等 class 必须与 CSS 定义一致——复制粘贴时注意完整拷贝 `<style>` 块
7. 行级胜出标记表（col-win/lose/equal）仅对比表使用，核实表不需要（核实表只需要普通斑马纹）
8. 军师按引用框（sigil-quote）的伪元素 `::before` 依赖 `position: relative`——如果父容器定位改了需检查
9. Progress bar 颜色语义：P0=红(紧急)、P1=橙(本周)、P2=黄(跟踪)——不要混淆
10. **B站视频无字幕是常态**：很多B站视频（尤其是播客类）不提供字幕。路径B（元数据评估）时不要试图强行转录——时长35分钟+的播客Whisper转录耗时过长且不值当。用description + 额外检索就够了
11. **用户说「全部列表」后不要继续追问**：直接拉完整的清单给出去，末尾可以留一句推荐优先级，不需要问"要不要详细版"
