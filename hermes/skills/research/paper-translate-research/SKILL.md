# 论文文章翻译研究 — Paper Translate & Research

> **🔑 触发词**：`论文skill` + 链接
>
> 示例：`论文skill https://arxiv.org/abs/2301.xxxxx`
> 示例：`论文skill 研究这篇博客 https://xxx`
>
> 适用：arXiv论文、技术博客、X平台深度推文串、行业报告、技术文档

## 核心理念

与 wiki-project-study（做手册）不同，此 skill 的定位是 **自我训练工具**——你不是在读一篇文，你是在借一篇文逼自己学会这个领域。

## 输入

| 类型 | 示例 | 提取方式 |
|------|------|---------|
| arXiv 论文 | `arxiv.org/abs/2301.xxxxx` | arxiv API → PDF全文/摘要 |
| 技术博客 | 各大平台博客链接 | web_extract / curl 全文抓取 |
| X 推文串 | `x.com/user/status/xxx` | xurl skill / web_extract |
| 行业报告 | PDF 链接 | 下载 → marker-pdf 提取文本 |

## 流程（五步）

### 第一步：全文提取

1. **检测来源** → 选对提取工具
2. **全文抓取** → 不截断、不漏图说明（图片alt text保留）
3. **预处理** → 去除广告/导航，保留正文+参考文献

### 第二步：全文翻译

**铁律：全文翻译，不是摘要。**

- 原文一段 → 译文一段（交替排列）
- 术语首次出现：**括号加注原文+一句话精确定义**
- 保留原文所有引用标记 [1][2]
- 图表：保留原文描述，标注 `[图N]` 占位
- 输出为：`wiki/translations/{source-slug}-full.md`

**术语注规范**：

```
> 模型采用了 Mixture of Experts（MoE，混合专家模型——将大模型拆分为多个"专家"子网络，
> 每次只激活其中一部分，从而在不增加推理成本的前提下扩大模型容量）架构……
```

### 第三步：核心观点识别

从译文中提炼 3-5 个核心主张：
- 每个主张用一句话概括（≤50字）
- 标注原文依据（哪段/哪章）
- 判断：增量贡献 / 争议点 / 已知结论

### 第四步：izu 关联研究

对每个核心观点，展开 **三个关联主题** 的研究：

| 维度 | 做法 | 输出 |
|------|------|------|
| **纵向深挖** | 这个观点的技术源头是什么？谁先提出的？经历了什么演变？ | 技术谱系梳理 |
| **横向对比** | 同时期还有哪些团队/方案在解决同一问题？差异在哪？ | 对比分析 |
| **前沿展望** | 这个观点指向什么未来？哪些条件具备后会爆发？ | 原创前瞻判断 |

三个关联主题的研究各自产出 300-500 字解读，统一输出到 `wiki/research/{topic-slug}-izu.md`。

### 第五步：术语表 + 学习路径

- **术语表**：文中出现的所有专业术语 → 中英对照 + 精确定义 + 使用场景
- **延展阅读**：3-5 篇关联论文/文章（优先选有冲突观点的）
- **自测问题**：3 个问题检验是否真正理解（不是记忆型，是推演型）

## 输出结构

```
wiki/
├── translations/{slug}-full.md          # 全文原文+译文
├── research/{slug}-izu.md               # izu研究解读
└── glossary/{slug}-terms.md             # 术语表（可选，术语多时单独出）
```

## 触发词

**唯一触发词**：`论文skill` 

只要用户消息中出现 `论文skill` + 任意链接（arXiv / 博客 / X / PDF），即启动此 skill。

## 注意事项

1. **全文翻译不可省略**——用户强调"必须是全文"，不是摘要不是要点
2. **术语首次即注，不重复**——后文同一术语不再加注
3. **izu研究要"展望"**——用户厌恶总结旧信息，要指向未来
4. **给出方法论不给答案**——让用户自己推演，skill 只搭脚手架
5. **来源可追溯**——每个判断标注依据（✅原文 / ⚠️推断 / ❓待核实）

## 陷阱

### delegate_task 超时（长论文的常见失败模式）

将论文翻译+研究委托给子Agent时，10页以上的论文（arXiv全文1500+行）几乎必然触发600s超时。子Agent花费大量API调用提取和阅读全文，耗尽迭代预算后在中途失败。

**恢复模式**（已验证）：
1. 检查子Agent是否存了临时文件（`find /tmp -name '*arxiv*'`）
2. 如果有提取的文本，自己读取内容（`read_file`）
3. 直接用 `write_file` 撰写翻译稿——你已有全文内容，不需要再委托
4. 翻译稿和izu研究分开写入，先翻译后研究

**不要做的事**：
- 不要重试delegate_task——同样的长论文会再次超时
- 不要让子Agent同时做翻译+研究——分离任务，逐个击破

### 并行处理两篇论文

同时delegate两篇论文的任务时，两个子Agent都会超时。改为：
1. 并行抓取两篇论文的全文（各自用 `delegate_task` 提取+保存临时文件）
2. 自己依次撰写翻译稿和izu研究
3. 第一篇完成后再开始第二篇的翻译
