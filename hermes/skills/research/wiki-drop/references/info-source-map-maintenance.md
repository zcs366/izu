# 信息源地图维护指南

> 用户张成市在长期信息摄入中，维护了一份结构化信息源地图（`wiki/concepts/my-info-sources.md`）。
> 每当他发来新公众号文章，识别账号并补入源地图是与入库同等重要的操作。
> 注意：本指南中的源数量和分类会持续增长，**每次使用前先读取源地图文件确认最新状态**。

## 何时触发

用户发送微信公众号文章链接时，**同时做两件事**：
1. 入库文章（raw + 评估/概念）
2. **识别账号并更新源地图**

用户明确标注"极大"的文章 → 走完整评估管线（见下方"极大文章评估"）

## 更新已过期的参考文件

本参考文件（info-source-map-maintenance.md）中的源数量和分类会随源地图增长而过期。
**每次更新源地图后，应同步检查本文件中记录的源数量和分类是否需要更新。**
如果不同步更新，后续加载此技能时会使用过时信息，导致判断失误。

## 添加新源的流程

当用户说"这个公众号我也喜欢"、"怎么没加进XX"或连续发送同一账号的多篇文章时：

1. **从文章内容识别账号名**——微信文章末尾通常有公众号名称，或从 `source:` 元数据字段获取
2. **判断属于哪条线**——科技/人文/艺术/文学？注意同公众号可能跨线（如北岛的今天文学=文学线，但也是艺术诗歌平台）
3. **检查是否已存在**——源地图中搜索公众号名，防止重复添加
4. **在源地图末尾追加**——用 `patch` 或直接 `write_file` 追加
5. **区分相似账号**——"古籍"和"善本古籍"是两个不同账号，不可混为一谈

## 盲区字段的填写规则

每个源的 `盲区` 字段**必须填写**，这是用户明确要求的。常见盲区类型：
- 观点偏乐观/悲观（如"情绪偏乐观"）
- 信息来源不可验证（如"Claude Mythos只有10人用过——无法考证"）
- 内容层次单一（如"不涉及当代科技和时事"）
- 需交叉验证的断言（如"夸张化严重，需交叉验证"）
- 纯文学不涉及科技（如"纯文学，无科技/时事内容"）

## 更新已有源

当用户再次分享同一账号的文章时：
1. 不新增条目（已有）
2. **更新 `代表文章` 字段**——将新文章添加到列表头部
3. 如果对源的理解加深（发现新的盲区/特点），更新相应字段
4. 如果发现该源有系列文章（如昀启AI+的"两条原则→Harness 12模块→交付路径"属于同一体系），一并列出

## 用户"再多再来"模式（高频率投喂）

用户可能在一轮对话中连续发送10+个链接，不等逐个分析完成就发下一个。
处理策略：
1. **快速fetch，不深度分析**——优先获取文章内容，没时间就只存URL
2. **批处理入库**——攒够一批后统一更新源地图
3. **不做单篇深度评估**——除非用户明确说"极大"或"评估分析"
4. **关键词判断公众号**——从URL或内容快速判断账号归属

## "极大"文章评估管线

当用户说"极大，评估分析，入库"时，走完整管线：

1. **fetch** — web_extract获取全文
2. **深度评估** — 撰写评估报告，包含：一句话判断、核心贡献、与用户实践的映射、盲区推敲、综合评分
3. **双版本输出** — 输出到 `output/极大/{slug}.md` + `output/极大/{slug}.html`
4. **标注源身份** — 如果是新源，添加到源地图；如果是已有源，更新代表文章
5. **创建wiki概念页** — 对文章提出的原创概念（如"初稿准确率""上下文工程""Agentic Harness"）创建 `wiki/concepts/` 页面
6. **HTML渲染要求** — .html文件需带基本CSS样式（表格、引用块、评分标签），参考已有极大文件

"极大"的判断标准：文章提出体系化理论框架/原创概念/对用户当前工作有直接理论指导意义。

## 批量历史文章入库（"全部消化"模式）

当用户说"全部消化"或"分批分计划把它们之前的公众号好文章都入库"时：

1. **优先级**：科技源 > 人文源 > 文学源 > 艺术源
2. **搜索方法**：
   - Bing搜索：`"公众号名" 文章` 或 `site:mp.weixin.qq.com "公众号名"`
   - 36氪/虎嗅/投资界等转载平台可找到公众号作者的文章列表
   - GitHub安全类profile（如 `tanjiti/sec_profile`）收录了安全类公众号的文章索引
3. **筛选标准**：每源找3-5篇代表作，优先选有数据/有框架/有原创观点的
4. **更新源地图**：将找到的文章填入所源的 `代表文章` 字段
5. **不贪多**：一次会话处理5-8个源即可，不追求一次性完成全部

## 用户关于源的明确偏好（从对话中提取）

- 对账号区分敏感："古籍"和"善本古籍"是两个不同账号
- 同一类源放在一起对比：如"善本古籍（东瀛访书史）跟你喜欢的程门问学、文汇学人是同一脉学术深度"
- 科技源偏好多层结构：叙事型（老范/智能情报所）→ 数据型（世界模型工场）→ 资讯型（新智元）
- "41个源，够用了"之后用户仍在继续投喂，说明没有真的"够用"的概念——是持续增长的过程
- 用户对源地图的结构化展示（按线/按数量）接受度好，喜欢用"══"框起来的汇总列表
