# Wiki 入库决策树

在抓取一篇文章后，需要判断将内容存入 wiki 的哪些页面。以下是基于实际经验总结的决策框架。

## 核心原则

- **实体（Entity）** = 谁写了它 / 谁做的 / 谁被提及（人、组织、产品）
- **概念（Concept）** = 它讲了什么（理论、框架、协议、模式）
- **对比（Comparison）** = 两样东西的横向比较（产品对比、技术选型）
- **raw 是原始材料**，永远不改；**wiki 页面是编译产物**，增量更新

## 文章深度筛选（优先执行）

**不是每篇文章都值得建 wiki 页。** 处理之前先判断内容深度：

| 深度等级 | 特征 | 处理方式 |
|---------|------|---------|
| **深度**（值得建页） | 新工具/协议/框架的完整介绍、有独特视角的对比分析、有实操价值的指南 | 按常规流程建概念/实体/对比页 |
| **中等**（值得引用） | 对现有概念有补充价值，提供了新数据或新案例 | 更新现有实体/概念页即可，sources 中引用 |
| **浅度**（仅存 raw） | 基础科普、入门教程、无新信息的热点速评 | **只存 raw，不建任何 wiki 页**。在 log.md 标注 `Note: 基础科普文，仅存 raw，未建概念/实体页` |

**判断标准**：这篇文章我下次查这个主题时会主动想看它吗？ 
- 是 → 值得建页
- 不是，但里面有可以引用的数据 → 更新现有页
- 不是，只是填充信息 → 仅存 raw

## 决策流程

```
文章抓取完成
    │
    ├── 判断深度（见上方"文章深度筛选"）
    │   └── 浅度 → 仅存 raw，跳过决策流程
    │
    ├── 作者是否已存在于 wiki？
    │   ├── 否 → 创建 entities/{author-slug}.md
    │   └── 是 → 检查是否需更新（新系列/新角度）
    │
    ├── 文章核心主题是否已有概念页？
    │   ├── 否 → 创建 concepts/{topic-slug}.md（见下方"何时创建概念页"）
    │   └── 是 → 更新已有概念页（新增章节/补充数据/提升置信度）
    │
    ├── 文章是否为横向对比/选型分析？
    │   └── 是 → 优先放入 comparisons/（而非 concepts/）
    │
    ├── 文章是否提供了已知实体的新数据？
    │   └── 是 → 更新实体的 sources 列表 + 正文补充
    │
    └── 所有操作完成后：
        ├── 更新 index.md（新增条目 + 总页数）
        └── 追加 log.md（记录 ingest）
```

## 何时创建概念页 vs 更新已有概念页

| 场景 | 操作 | 例子 |
|------|------|------|
| 全新协议/框架，wiki 中无任何记录 | **创建 concept** | AG-UI 协议、GenericAgent、CDP Bridge MCP |
| 已有概念页 + 文章提供了实践指南 | **更新 concept**（新增章节） | hermes-profile-system ← 新增实战章节 |
| 已有概念页 + 文章补充了新视角 | **更新 concept**（新增段落） | agent-skills-system ← 新增 GEPA Loop |
| 文章是已有概念的"另一种表述"/重复信息 | **仅更新 sources**，概念页可略 | 一般性综述文章 |
| **横向对比/选型分析** | **创建 comparison** | hermes-vs-openclaw（放入 comparisons/ 而非 concepts/） |

## Comparison 页管理

- 对比页放在 `comparisons/` 目录下
- 命名格式：`{a}-vs-{b}.md`（如 `hermes-vs-openclaw.md`）
- 对比页应该是**判断辅助工具**而非百科条目——聚焦于选型差异和各自最佳场景
- 对比项不应在概念页重复展开，而是用 `[[wikilinks]]` 指回概念页
- 在 index.md 的 `## Comparisons` 章节下登记

## Entity Slug 命名规则

- 中文昵称 → 拼音或英文翻译（`gaoguan-dazhuang`, `wuguo-ai`, `yugong-ai`）
- 英文名 → 保持原样（`tech-sensor` — 意译）
- 特殊符号 → 用连字符（`i-longxia` for "i龙虾"）
- 避免歧义 → 如果昵称太通用，加 disambiguation（`guoguo-ai-note` for "蝈蝈的AI笔记"）

## Raw Slug 命名规则

基于**主题**而非文章 ID：

```
hermes-agent-per-provider-proxy.md    ✓ 好 — 一看就知道内容
s-abc123.md                           ✗ 差 — 微信ID无意义
```

## 交叉引用规范

每个新建/更新的页面必须：
1. 至少有 2 个 `[[wikilinks]]` 指向其他 wiki 页面
2. sources 列表中包含对应的 raw 文件路径
3. 如果文章是系列的一部分，在 entity 页标注系列关系

## 批次处理效率建议

处理多篇文章时：
1. **先全部抓取并保存 raw**（一次性完成所有 fetch）
2. **再逐一分析并更新 wiki 页面**（避免每次切换上下文）
3. 最后**一次性更新 index.md 和 log.md**（合并所有变更）

但更好用的模式（如已验证）：**每篇单独处理**，因为每篇的入库决策（创建 vs 更新 vs 仅存 raw）各不相同，串行处理更不容易漏改。
