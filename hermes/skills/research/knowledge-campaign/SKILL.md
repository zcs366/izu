# Knowledge Campaign — 长编研究法

> **触发指令**：`用 knowledge-campaign 研究 XXX 领域`
>
> 示例：`用 knowledge-campaign 研究 AGI`
> 示例：`用 knowledge-campaign 研究 具身智能`
> 示例：`用 knowledge-campaign 研究 AI安全对齐`

## When to Use

Use this skill when the user wants to deeply understand **a broad domain or knowledge area** (not a specific product/tool).

| 场景 | wiki-project-study 适用 | knowledge-campaign 适用 |
|------|------------------------|------------------------|
| "学怎么用Claude Code" | ✅ | ❌ |
| "研究AGI到底是什么" | ❌ | ✅ |
| "写一个ComfyUI操作手册" | ✅ | ❌ |
| "搞懂AI安全对齐全貌" | ❌ | ✅ |
| "学Markdown语法" | ✅ | ❌ |
| "理解具身智能的所有路线" | ❌ | ✅ |

**判断标准**：
- 有明确的产品/工具名，产出中文操作手册 → **用 wiki-project-study**
- 是一个学术领域/产业方向/知识体系，需要先画地图 → **用 knowledge-campaign**
- 不确定时，问用户一句："这是想学一个工具（走wiki-project-study），还是想搞懂一个领域（走knowledge-campaign）？"

## Philosophy

这个方法论如今在「祝」产品中得到了工程化实现（参见 `references/祝白皮书精要.md`）。其认识论根基是**明学纲要**（Ming Doctrine），特别是：

- **第二则·得道**：知道先于掌握。系统的第一责任不是帮人"看见不知道"，是帮人"获得知道"——哪怕薄薄一层，也足以改变后面所有的选择和判断。长编是"得道"的工具，不是目的。
- **第三则·明从兼听**：长编收集阶段必须兼收各方观点。没有哪篇论文、哪个人握有全部真理。当所有人都说"这个答案是对的"，反问"谁定义的对？"
- **第四则·以幻破幻**：学习不是灌输真理，是不断制造幻觉又推翻幻觉。长编阶段允许广泛涉猎（包括有争议的、未证实的观点），定本阶段再辨伪求真。展望面允许大胆想象——"没有幻觉就没有未来的真"。
- **第五则·省**：每个面收集完后，反思"这个面收齐了吗？漏了什么？"，更新后再进下一个面。整个长编完成后，做三编通读（省/齐/得/乐），逐面精炼。
- **第六则·以乐为终**：这个项目的真正生命不是"知道AGI"，是"在学习的过程中感到快乐"。每一次"通了"的瞬间，就是这个系统唯一该给的奖励。
- **第七则·时中**：知识无涯人生有涯，不在宽度上贪多，在深度上扎根。定本不追求面面俱到，追求"该深的地方扎下去了"。

### 核心认识论：长编是索引，不是池子

**长编不是资料池，是资料池的索引。** 这是本方法论最重要的一条认识。

世界是无限的，一个领域的知识永远收不"全"。真正有价值的工作不是把所有内容塞进长编，而是建立**层层展开的索引结构**：

| 层 | 内容 | 用途 |
|----|------|------|
| **层1** | 长编九面地图 | 概览和导航，让使用者知道有哪些方向可走 |
| **层2** | 专题深挖 | 每个面引出的深层专题（5000-10000字），覆盖层1的入口 |
| **层3** | 原始文献和一手资料 | 论文、报告、采访、数据源——层2指向的原始材料 |
| **层4** | 使用者自己的实践笔记 | 个人经验、实验数据、一手观察——别人无法复制的部分 |

索引的目标不是"覆盖世界"，是**直到使用者得道快乐**——在某个面里找到他需要的钥匙，打开他自己的门。

核心概念参考 `references/ming-doctrine.md`（v0.3）。

## Methodology: 三段式

### 第一阶段：画地图（Domain Mapping）

**目标**：把整个领域拆成若干"面"（facets）。这不是最终的定本结构，是收集阶段的行动地图。

**做法**：
1. 和用户一起画第一版地图（面数通常在5-12之间）
2. 每个面给一个名字、一句定义、一个"齐的标志"
3. 用户确认"齐了"再进入第二阶段

**版本管理铁律**：每次修改文件必须更新版本号并加变更说明。旧版本不删。建版本日志。用户明确说过：改了要加版本号，要看到变迁的痕迹。

**"齐"的含义**（这是本方法的核心概念）：
- 不是"全部"（不可能全部）
- 是"结构完备、各归其位"——没有明显盲区，每个子问题都有对应的面
- 面之间有清晰的逻辑关系（不是散乱的列表）
- 每个面有明确的"收齐标准"

**格式参考**：

```
## 面X：[名称]

**目标**：[一句话说明这个面要搞清楚什么]

**收集清单**：
- [ ] [子问题1]
- [ ] [子问题2]
- [ ] [子问题3]

**齐的标志**：[能说清什么就算齐了]
```

### 第二阶段：收长编（Collection Until 齐）

**目标**：每个面独立收集材料，收到"齐"的标志达成。

**做法**：
1. **地图批准后，面可自由推进**——用户批准地图后，即可逐面收集，**无需等每个面单独批准**。实验证明用户讨厌逐个请示的流程，会明确说"不要等我批准了，开干！"
2. 如果用户中间说"等等，我先想想"——停，给他空间
3. 每个面用并行搜索（多路 ddgs + Wikipedia API + curl）+ 关键论文/文章提取
4. 收集完成输出到 `output/doc/{domain}长编_面{number}_{name}.md`（使用编号+中文名的命名约定，如 `AGI长编_面1_定义面.md`）
5. 若用户中途想查看某个面，随时给；若用户不查，继续推进到全部完成
- **并行搜索**：同时搜索多个子方向（用多路terminal + python ddgs并行），而非串行一个搜完再搜下一个
- **工具失效时的分级降级策略**：
  1. 首选 web_search（Firecrawl）— 搜索+提取一体，最方便
  2. 如果 Firecrawl 返回 Payment Required（额度耗尽）→ 降级到 ddgs（DuckDuckGo Python包）：`python3 -c "from ddgs import DDGS; results = list(DDGS().text('query', max_results=10))"`
  3. 如果 delegate_task 返回 401（API key未配置）→ 不要重试，直接手动搜索
  4. 如果 delegate_task 返回 5xx（服务端错误）→ 不要重试同一模型，直接手动搜索
  5. 如果需要获取结构化内容 → 用 Wikipedia API：`curl -sL 'https://en.wikipedia.org/w/api.php?action=query&prop=extracts&exintro&explaintext&titles=TITLE&format=json'`
  6. 如果需要获取网页内容 → 用 `curl -sL URL | python3 -c "import re,sys,html; text=re.sub(r'<[^>]+>',' ',sys.stdin.read()); print(html.unescape(text)[:3000])"`
- **关键词调优**：如果搜索结果跑偏（如搜AGI搜到税务的Adjusted Gross Income），加"-adjusted -gross"排除词，或用更具体的关键词

**"齐"的检查**：
- 这个面的关键人物/观点/事件都覆盖了吗？
- 有没有只看到一方观点？
- 最新进展（最近6个月）有没有遗漏？
- 有没有明显的"我还不知道我不知道的"感觉？

如果感觉盲区仍在，继续收集，直到用户说"齐了"。

### 阶段间流程：通读三编（Three-Pass Review）

**触发条件**：长编九面（或全部面）收齐后，进入定本前。

**目标**：不嫌多，只怕挂一漏万。每个面做三遍"省/齐/得/乐"检查，逐面精炼。

**做法**（第一编由执行者自己做，第二第三编可结合用户一起）：

每遍对每个面过一遍，四个问题：
1. **省** — 这个面最新的信息有没有遗漏？有没有需要更新的判断？（参考第五则·省——反思即更新）
2. **齐** — 结构完备了吗？各归其位了吗？有没有明显的盲区？有"我还不知道我不知道的"感觉吗？
3. **得** — 这个面读下来，获得了什么新知？它能改变我的认知或行动吗？
4. **乐** — 读起来有收获感吗？有没有"啊原来如此"的时刻？

| 遍数 | 侧重点 | 谁来做 |
|------|--------|--------|
| **第一编** | 结构和内容——检查遗漏和错误，补充材料 | 执行者（军师）独立完成 |
| **第二编** | 逻辑和判断——检查推理是否自洽、观点是否平衡 | 用户/执行者协作 |
| **第三编** | 体验和表达——检查是否可读、有没有真洞察 | 用户主导 |

**版本管理**：每次修改后，更新面文件的版本号，加补注：
```diff
**版本**：v1.0 · 2026-05-10
**版本**：v1.1 · 2026-05-10（第一编补完：加了XXX、XXX）
```
旧的版本文件不要删。对比着看变化是用户的重要需求——他说过："又直接改了，要做版本号变更啊，我要看到变迁的痕迹。"

建一个 `版本日志.md` 跟踪所有项目的版本演变。

**核心原则**：不嫌多，只怕挂一漏万。宁可多补几条啰嗦了，也不要漏掉一个关键视角。补完了，用户说"齐了"，才能进定本。

---

### 第四阶段：出认知地图——不是定本，是引导

**重要修正**：定本不是由执行者写的。定本是使用者/学习者在资料池中自己游出来、自己写出来的。执行者做的事情不是"写定本"，而是：

1. **建池子**（长编）——把资料收齐
2. **画地图**（认知地图）——引导使用者在池子里找到自己的路径

**认知地图**是独立于长编的交付物，7-10页，手机可读。它的设计原则：

- **不是显式的导航图**——不要做成"去面X看第Y节"的指引。地图要**藏在文字里**：用引子勾住读者，用节奏带他走，用好的写作质量本身引导他自己想去深挖。"写得漂亮，让人拍案叫绝，还想读"——这就是地图。
- **不是知识卡片**——不应该是干巴巴的"三个事实+一个行动"。每一页要有叙事弧线：开头抓人，中间有画面，结尾留下悬念。
- **每一页都有"钩子"**——读完这页，读者会想知道"那然后呢？"。这个"然后"的答案在长编的某个面里——但不显式标注，读者自己会去找。找的过程就是学习。
- **地图要有见解**：不是"这里有什么"，而是"我对这里的判断是什么"。普通地图只有地名，认知地图要有**简介和见解**（介出来）
- **最后一页是挂轴地图**：展示各面之间的逻辑关系（不是散列表），加上索引层级说明。这一页特别需要写出判断和通路——"面X和面Y的咬合点是Z"

**认知地图和长编的关系**：

```
长编（层1索引） → 认知地图（导航） → 使用者在池中游 → 自己写出自己的"定本"
```

输出位置：`output/doc/{domain}认知地图_7页_v{version}.md`

## 轻量级路径：祝聚焦文章（Focused 祝 Article）

**不打开新窗口，直接在会话中完成。**

适用场景：用户说"启动任务：祝 XXXX"——一个具体问题，不是宽领域研究。

| 对比 | 完整长编研究 | 聚焦祝文章 |
|------|-------------|-----------|
| 话题 | 宽领域（AGI、AI安全） | 具体问题（听话教育后遗症） |
| 面数 | 5-12面 | 1个主题，4-8个自然段落 |
| 画地图 | 需要（和用户一起拆面） | 跳过（结构由军师判断） |
| 输出 | 长编每面6000-10000字 + 认知地图 | 一篇4000-8000字文章 |
| 时间 | 数天到数周 | 30分钟到2小时 |
| 用户参与 | 逐面确认"齐"后再推进 | 意图澄清 → 开干 → 第二编审阅 |

### 聚焦祝文章工作流

```
用户说"启动任务：祝 XXX"
  → 第0步：意图澄清（输出3条方向观察，让用户确认或纠正）
  → 收到"直接走""开干" → 自由执行
  → 第1步：并行搜索（ddgs多路，Firecrawl降级）
  → 第2步：撰写初稿（开门画面 + 逐层展开 + 文化/历史纵深 + 实践出路 + 祝号）
  → 第3步：第一编自劈（军师独立审读，找漏洞、缺角度、模糊处）
  → 第4步：打补丁（补内容、修数据、加视角、清理标记）
  → 第5步：交付 + 邀第二编（用户审阅+修正）
  → 第6步：第三编精化（表达+节奏+祝号打磨）
```

### 关键注意事项

**1. 意图澄清是第0步，不是选择题**
输出观察而非问题。格式例：
> "这个题我不用问你太多——你的身份我已经摸清了。
> 方向我猜三条：①[方向A] ②[方向B] ③[方向C]
> 猜对了直接走，猜错了告诉我。"
注意：用户说"直接走"或"开干"才是开始信号。在此之前保持讨论。

**2. 第一编自劈必须在交付前完成**
永远不要直接把初稿扔给用户。先自己劈自己一遍。找：
- 缺了什么关键视角？（阶层？历史？地域？）
- 引用的东西有没有模糊的？（没给研究出处？年份？机构？）
- 结构有没有偏？（用户真正关心实操，你却只在谈理论？）
- 有没有写得太"专家腔"忘了用户要看的懂？
劈出洞，补上，再交付。"第一编劈审记录"写在文件末尾，让用户看到你的思考过程。

**3. 聚焦文章的结构参考**
开门一幅画面 → 定义/本质判断 → 逐层展开（4-6层深度）→ 文化/历史背景（让文章有重量）→ 实践出路（落到用户身上）→ 祝号（观察式收尾，真诚犀利有温度）

**4. 搜索优先度**
- 用 ddgs 并行搜，一次5-6个查询
- 搜到好文章后尝试 curl 抓正文（--max-time 15秒，超时跳过）
- Firecrawl 作为首选但随时准备降级
- 不追求"引用完美"，追求"结构完整、判断有据"

**5. §NEW§ 标记的使用**
打补丁时可以用 §NEW§ 标记新增内容，方便用户定位。但交付前必须全部清理干净（grep -c '§NEW§' 确认=0），否则显得粗糙。
更好的做法是：直接 patch 修改原文，不留标记。版本日志记录变更即可。

## 元规则：时时跟进

**这不是一次性工程。**

知识领域每周都有新东西。地图里的每个面都需要持续更新。

**做法**：
1. 第一轮出定本后，保持 `长编_面X.md` 文件
2. 定期间隔（建议每月一次）检查每个面是否有新进展
3. 有新发现时，更新对应的长编文件，再决定是否出定本新版本
4. 版本号递增（v1.0 → v1.1 → v2.0）

一句话：**定本写完不是结束，是下一次更新的起点。**

## 进阶：izu流水线（七智能体八步研究引擎 v2.0）

**适用场景**：当常规收集方式效率不够时，或需要进行大规模多轮精炼时。这是本技能的生产引擎。

### 引擎：`scripts/izu-pipeline.py` v2.0

**八步七角色**（探→搜→织→对齐→写→劈→修→核）：

| 步骤 | 角色 | 职责 |
|------|------|------|
| 1 | **探** | DuckDuckGo搜索+curl抓取3个网页全文，画出知识地图草稿 |
| 2 | **搜** | 三层搜索分析（广度扫→深度钻→交叉验证），标注信息缺口 |
| 3 | **织** | 编织关联网络→信息分层（✅⚠️❓）→给"写"的材料包 |
| 2.5 | **对齐** | 检查是否对准用户原始关切，偏了给修正指令 |
| 4 | **写** | 厚重化写作。支持`--format html`输出交互式HTML |
| 5 | **劈** | 逐段审读批评。像张成市那样劈 |
| 6 | **修** | 逐条修改定稿。铁律：不得虚构URL |
| 7 | **核** | 反向搜索验证，标注✅已验证/⚠️待核实/❌可能虚构，给可信度评分 |

完整文档见 `izu-pipeline` skill。

### 调用方式

```bash
# 完整流水线
cd /mnt/i/hermes/scripts && python3 izu-pipeline.py "研究主题"

# HTML输出
python3 izu-pipeline.py "研究主题" --format html
```

## 进阶二：选题漏斗法（Topic Funnel）

**适用场景**：用户给了一个宽泛的信号("深入研究文章X，找出项目机会")，需要从发散到收敛，最终锁定一个方向。

### 六步漏斗流程（本会话验证）

```
文章深度分析
    → 生成10个选题（发散，覆盖多维度）
        → 从3个视角精选3个（收敛，技术/商业/范式各一）
            → 3篇并行ai祝研究（平行）
                → 跨成果汇总与遴选 → 选定1个项目
                    → 对该项目做深度可行性研究
```

### 第一步：深度分析

快速提取文章的核心洞察，分层拆解：

| 层 | 关注什么 |
|----|----------|
| 表层 | 文章在说什么 |
| 中层 | 反转原则——文章揭示了什么根本转变 |
| 深层 | 工具链/价值链/范式层面有什么新格局 |
| 最深层 | 哪些隐性机会线可以转化为研究方向 |

**技巧**：识别5条左右的"隐性机会线"——文章没有明说但可以从逻辑推导出的商业/产品/技术机会。

### 第二步：生成10个选题

基于隐性机会线，生成10个方向。每个选题需包含：
- 编号+一句话标题
- 一句话说明（是什么）
- 一句话机会判断（为什么值得研究）

### 第三步：三视角筛选 → 3个选题

从三个不同视角各选一个，覆盖完整光谱：

| 视角 | 关注 | 代表性选题偏向 |
|------|------|--------------|
| 🏗️ **产品视角** | 能做什么产品/工具？最直接的商业化路径 | 工具类、SaaS类 |
| 🧠 **范式视角** | 这个变化意味着什么？对认知/工作方式的影响 | 方法论类、趋势类 |
| 💰 **商业视角** | 市场在哪？能赚什么钱？哪个机会最大 | 平台类、生态类 |

**筛选原则**：
- 三个选题要能连成一条逻辑链：从近到远，从实到虚
- 每个选题都要有"可落地的项目机会"元素
- 覆盖用户的当前实践（近）到未来平台化（远）

### 第四步：并行研究

对3个选中选题启动并行ai祝研究（见"并行研究与跨成果合成"节）。

### 第五步：跨成果汇总与遴选

从三个研究结果中提各案的核心发现（3个方向×各自推荐项目），建立对比矩阵：

| 维度 | 选题A | 选题B | 选题C |
|------|-------|-------|-------|
| 一句话 | 核心价值 | 核心价值 | 核心价值 |
| 最佳项目 | 项目名+可行性评分 | ... | ... |
| 市场 | 估算 | ... | ... |
| 技术门槛 | 低/中/高 | ... | ... |
| 用户现有基础 | ❌空/⚠️部分/✅已有 | ... | ... |
| 个人可行性 | ⭐评级 | ... | ... |
| 商业想象力 | ⭐评级 | ... | ... |

**综合判断**：选择"你现在就能做"的那个——用户现有基础设施最匹配、技术门槛最低、个人可行性最高。

### 第六步：深度可行性研究

对选定项目启动深度聚焦ai祝研究，要求：
- 具体的技术架构（精确到库名、API、工作流）
- 分阶段MVP路线图（以周/天为单位）
- 风险评估与对策（技术、时间、动力）
- 商业模式探索

## 进阶三：并行研究与跨成果合成（Parallel Research & Cross-Synthesis）

**适用场景**：多个研究方向需要同时深入，然后汇总对比，避免串行耗时和视角偏倚。

### 并行研究的两种模式

#### 模式A：delegate_task 并行（推荐用于3-5个独立选题）

```python
# 每个子任务是一个完整的聚焦ai祝研究
# 任务内自包含：搜索 → 写作 → 自劈 → 输出文件
delegate_task(
    description="同时研究N个选题",
    tasks=[
        {"goal": "研究选题A，写聚焦祝文章", "toolsets": ["web","terminal","file"]},
        {"goal": "研究选题B，写聚焦祝文章", "toolsets": ["web","terminal","file"]},
        ...
    ]
)
```

每个子任务的context需包含：
1. **背景文章核心洞察** — 从源文章提取的3-5条核心论点（统一上下文）
2. **选题说明** — 当前选题的具体要求、研究痛点
3. **写作要求** — 风格、面向人群、字数、输出格式

#### 模式B：串行-轻量级（用于2-3个方向，时间充裕时）

逐个研究，每完成一篇立即交付，根据反馈微调下一方向。

### 跨成果合成方法

并行研究全部完成后执行：

1. **独立提取**：对每篇研究报告，独立提取核心发现
   - 提出的产品/项目机会（每个的可行性、市场、技术门槛）
   - 关键词句和核心论点
   - 最推荐的项目方向
2. **建立对比矩阵**：横轴=三个选题，纵轴=评估维度（见"选题漏斗法·第五步"）
3. **综合判断**：结合用户现状、可行性、商业想象力做最终选择
4. **输出汇总文件**：`ai祝_汇总对比与项目遴选.md`

### 「用大心」原则（用户明确强调）

在ai祝研究的**展望面**，遵循以下规则：
- 大胆想象3-5年后的形态，不要怕夸张
- 跨领域连接：把A领域的发现和B领域的进展连起来
- 允许"幻觉"——没有想象出来的未来就没有走过去的可能（对应明学第四则·以幻破幻）
- 展望面是唯一不需要严谨引用的章节，但它需要有逻辑链
- **不要在这个面缩回去**——用户用"用大心"三个字强调过

具体做法：
- 每个产品方向给出3-5年的演进路径
- 描述"当X变成Y时，世界会怎样"的具体场景
- 用画面感描述未来，不讲抽象概念

## 角色分工

```
[你：军师/Plan] ── plan、调度、合成最终输出
    ┌────┼────┐
    │    │    │
  [搜]  [写]  [劈]
  搜集   写   审读开劈
  智能体 智能体 智能体
```

| 角色 | 职责 | 工具 |
|------|------|------|
| **搜** | 收集资料。结构化输出，关键数据注明来源 | terminal + DDGS + Wikipedia API + curl |
| **写** | 根据搜集到的资料写出可读的文稿。面向非专业读者，用类比和对比表格 | `subagent.py`脚本调用DeepSeek/其他API |
| **劈** | 毫不留情的审读人。找漏洞、数据缺失、逻辑断裂、模糊说法。不说好话 | `subagent.py`脚本，系统提示设为"劈"模式 |

### 工作流（v2.0 八步版）

```
query → 探(DuckDuckGo+curl抓取)→搜(三层搜索)→织(关联网络)→对齐(对准检查)
    → 写(厚重写作)→劈(逐段批评)→修(修改定稿)→核(反向验证+可信度评分)
```

详见 `izu-pipeline` skill。旧版三角色(搜/写/劈)+subagent.py 已完全淘汰。

### 流水线工具：`祝` CLI Agent（v0.4）

**`祝` 是本技能的生产工具。** 它封装了完整的v0.4流程，用户直接在终端敲：

```bash
祝 "研究主题"                # 默认3编，约30分钟（含交互式意图澄清）
祝 "主题" --quick            # 快速模式1编，约10分钟出草稿
祝 "主题" --deep             # 深度模式5编
祝 "主题" --wild             # 发散模式（高温度0.9，5编起）
祝 "主题" --focused          # 精炼模式（低温度0.2，3编内）
祝 "主题" --t 0.8            # 自定义温度
祝 "主体" --silent           # 批量模式（跳过意图询问）
祝 --version                 # 版本信息
```

**装在哪**：`~/.local/bin/祝`（系统PATH）
**脚本源**：`/mnt/i/hermes/scripts/祝.py`
**旧名兼容**：`~/.local/bin/研` 仍保留（指向同一脚本）
**产出**：`{主题}_长编_{时间戳}.md` + `{主题}_认知地图_{时间戳}.md`，存于 `output/doc/`
**画像存档**：`output/doc/_profiles/default.json`

**写作标准（v0.4）**：
1. **厚重句** — 在人类经典文献中留下一笔的独特风景。十年后有人翻到还会停下来读一遍。
2. **画面** — 不讲概念，讲「咬着铅笔头，在草稿纸上画了第七遍」。
3. **节奏** — 短句一拳打过来，长句一口深呼吸。
4. **展望与连接** — 关注不同领域之间的联系和未来趋势，而非仅总结已知资料。
5. **祝号** — 输出尾巴是观察，不是问句。真诚、犀利、有温度。

**当你需要时**：让用户直接在终端敲命令，不需要经过你中转。这是本技能从「军师手动执行」到「用户自助使用」的跃迁。

### 底层代理：`subagent.py`

位置：`scripts/subagent.py`。直接调用 DeepSeek API，绕过 delegate_task 的模型配置缓存问题。

**什么时候不用流水线**：
- 小规模快速搜索（3-5次搜索能搞定）→ 直接手动搜更快
- 用户需求不明确，还在探索阶段 → 先对话，不要启动自动化流程
- delegate_task 正常工作且速度够快 → 优先用 delegate_task

**什么时候用**：
- 大规模长编收集（面数多、内容广）
- 需要反复精炼（三编循环）
- delegate_task 不可靠（429限流、5xx错误）

## User Preferences（embed these）

1. 用户有自己的七则认识论（明学纲要），不要轻易挑战他已经想透的东西。如果他劈你（纠正你），那是他在帮你把地基打牢。——参见第四则「以幻破幻」
2. 用户反感「催进度」式的推进。他需要的不是快，是「齐」。催促只会让他怀疑根基不牢。必须先建立哲学根基，他说「开干」才是真开干。在此之前保持讨论状态，让他自己走到那个点。
3. 用户享受被深刻的问题激发。你问的问题越深，他的回答越有价值。不要停留在表面。
4. 用户对虚荣的引用（自己没真懂的典故/数据）极度敏感。引用必须先真懂，不懂宁可不引。
5. 用户思考方式是「从第一性原理出发」——先问「本质是什么」，再问「怎么干」。
6. **用户重视「展望」超过「总结」**。所有可搜资料都已过时，真正价值在于把A领域的发现和B领域的进展连起来，指向未来趋势。
7. **写作标准极高**：要求「在人类经典文献中留下一笔的独特风景」——厚重到十年后有人翻到还会停下来读一遍。
8. **用户厌恶营销式写作**。祝号必须是观察，不是问句。真诚、犀利、有温度，而非"贴心小助手"式的low钩子。姜太公钓鱼愿者上钩。
9. **参数必须开放**。道不变（得道、快乐、触类旁通），术全可变（温度、种子、策略、长度）。「做死」是懒惰的设计思维。
10. 写给你服务的「可能不太懂或根本不懂」的人。用户亲口说的：时时记得让你做事的人可能也是并不太懂或者根本不懂。这意味着：
    - 所有术语第一次出现时用括号简要解释
    - 使用对比表格（「以前是X，AGI时代变成Y」）
    - 关键概念用一句话+一个类比说清
    - 输出结构：先给「一句话说清」，再展开细节
    - 不要假设读者有技术背景
    - 如果搜到的是英文资料，输出时翻译+转述成中文，不要贴原文
11. 输出文件用中文命名，带编号。格式：{domain}长编_面{number}_{name}.md（如 AGI长编_面1_定义面.md）。方便按序阅读。定本用 {domain}_定本_v{version}.md。
12. 永远保留版本历史。每次改文件都要更新版本号，加变更说明。旧版本不删。建版本日志。
13. 认知地图的写作标准很高。不是干巴巴的知识点，要有引子、有画面、有节奏、有情绪。「写得漂亮，让人拍案叫绝，还想读」本身就是引导——好的文字会让读者自己想去深挖。

## Pitfalls

1. **不要跳过阶段一直接收材料。** 地图没画好就动手，一定漏东西。画地图的时间不能省。
2. **不要在定义面上偷懒。** 定义是所有面的基础——如果连"这个领域到底指什么"都没搞清，后面的收集一定跑偏。
3. **不要回避争议。** 一个好的长编，恰恰要把争议收齐全——各方的主张、论据、代表人物。只收一方的材料等于没收到位。
4. **不要在展望面束手束脚。** 用户明确说了"展望允许幻觉"。这是唯一一个可以大胆想象的章节。如果你在这里反而缩回去了，说明你没理解"以幻破幻"的真正含义——没有想象出来的未来，就没有走过去的可能。
5. **不要一次收所有面。** 一个面一个面来。用户精力有限，他过目需要时间。
6. **定本不要追求"绝对客观"。** 没有绝对的客观。关键是"我的判断有依据、有逻辑、说清楚了为什么这么看"。
7. **当用户说"等等，我先想想"时，等。** 不要追问，不要催，给他空间。（第五则·省）
8. **地图批准后不要每面请示。** 用户说了"开干"就是自由执行信号。唯一需要请示的是：地图批准（第一阶段结束）和对"是否现在就进入定本阶段"做确认。
9. **不要问用户"你选哪条路"——如果你已经知道方向。** 如果用户明确说了"先干X"，不要问他"你确定吗"、不要问他"还有没有别的想法"。直接执行。用户说"我对做项目没有任何经验"时，你替他做决定。
10. **先哲学，后行动。** 用户必须在行动前先把根基想透。如果你催他推进，他会说"不是你这样做得，你操之过急"。保持讨论状态直到他说"开干"。
11. **不要输出页码、编号、章节号。** 认知地图不要「第X页」，段落自然流淌。用户说"这些第一页第二页全都去掉"。
12. **写长编时注意力块（attention block）管理：** 每个面的输出控制在6000-10000字。太短说明没收齐，太长用户读不完。关键信息前置：每个面开头给一个"一句话说清"表格或速览卡片，帮用户快速抓住重点。
15. **「用大心」原则**：用户强调在展望面要"用大心"——大胆想象、跨领域连接、允许幻觉。敢想比正确重要。具体做法：每个产品方向给出3-5年演进路径，描述场景而非概念，用画面而非抽象推理。此条已内化为"进阶三"的章节。

## ⚠️ Critical: 祝 CLI 后台运行问题（v0.4.1）

**1. 输出缓冲被吞**
- 背景进程 stdout 默认 pipe 缓冲，log() 的内容不出现
- **修复**：`log()` 中加 `sys.stdout.flush()`
- **临时方案**：重定向到文件 `> /tmp/zhu_stdout.log 2>&1`，用 `tail -f` 追踪

**2. --focused/--wild 不自动跳过意图澄清**
- `clarify_intent()` 在后台无 stdin 时卡死在 `input()` 调用
- **必须显式加 --silent**：`祝 "主题" --focused --silent`
- 计划修复：focused/wild 模式自动设 silent=True

**3. foreground 超时不足**
- 3编流程约12-15分钟，terminal timeout 默认180s
- 前台运行设 `timeout=600` 以上，或改用后台+文件重定向
