# 并行研究实战记录（2026-05-12）

> 从一篇文章到项目可行性研究的完整五步流程。
> 源文章：《大模型首选格式Markdown，被30年前的工具取代了？》

## 核心流程

```
文章深度分析 → 10选题 → 三视角选3 → 3篇并行ai祝 → 跨成果汇总遴选 → 选定WikiMeld → 深度可行性研究 → 网站/GitHub固定成果
```

## 各步骤实战数据

| 步 | 耗时 | 产出 | 关键决策 |
|----|------|------|---------|
| 深度分析+10选题 | ~5分钟 | 文章4层洞察 + 5条隐性机会线 + 10选题 | 分层拆解法（表→中→深→最深） |
| 三视角筛选 | ~2分钟 | 3个选题：产品/范/商业各一 | 逻辑链：近→远，实→虚 |
| 3篇并行ai祝 | ~3.5分钟 × 3 | 3篇聚焦祝文章（每篇6000-8000字） | 用delegate_task并行 |
| 汇总遴选 | ~25秒×3篇提取+汇总 | 对比矩阵 + 选定WikiMeld | 用户现有基础设施=决胜因素 |
| 深度可行性研究 | ~3.5分钟 | WikiMeld可行性研究（600行） | 技术方案精确到库名和API |
| 网站/GitHub | ~10分钟 | 官网单页 + README + 4个研究案例 | 单页HTML，水墨文人风 |

## delegate_task 配置要点

每个子任务的context结构：

```json
{
  "context": "## 背景文章核心洞察\n\n[从源文章提取的3-5条核心论点]\n\n## 选题说明\n\n### 当前痛点\n[具体问题描述]\n\n### 研究要求\n1. ...\n2. ...\n3. ...\n\n### 写作要求\n- 面向人群\n- 风格要求\n- 禁用项\n- 输出文件路径\n\n### 输出文件\n保存到 /mnt/i/hermes/output/doc/xxx.md",
  "goal": "深度研究选题X：标题。写一篇完整的聚焦祝文章（4000-8000字）。",
  "toolsets": ["web","terminal","file"]
}
```

## 跨成果提取方法

对每篇研究报告，用独立的delegate_task读取并提取：

```json
{
  "context": "文件在 /mnt/i/hermes/output/doc/xxx.md",
  "goal": "读取并提取核心发现：①产品机会（可行性评分/市场/技术门槛）②关键词句③最推荐项目方向",
  "toolsets": ["file"]
}
```

输出结构化提取结果，然后手工汇总对比矩阵。

## 网站/GitHub产出模式

研究完成后，将成果转化为持久化形式：

1. **官网**：单页HTML（静态，GitHub Pages部署），包含方法论+研究案例+关于
2. **GitHub仓库**：README + cases/目录（研究案例副本）
3. **命名规范**：中文名「爱祝」，英文名「izu」，混名「ai祝」

## 关键教训

- 并行研究的核心优势不是快，是**保持各方向之间的独立性**，避免先入为主
- 跨成果遴选时，**用户现有基础设施**往往比商业想象力更重要——能现在就做的事 > 未来可能做但需要团队的事
- 「用大心」原则在展望面特别有效——三篇研究中读者反馈最好的都是"大开脑洞的展望部分"
- 网站和GitHub是研究的"固化层"——在研究完成后立即做，趁热打铁，不然容易烂尾
