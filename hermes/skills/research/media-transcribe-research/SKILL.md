# 音视频转录研究 — Media Transcribe & Research

> **🔑 触发词**：`转录skill` + 链接（或 `转录这个视频` + 链接）
>
> 示例：`转录skill https://www.bilibili.com/video/BV1xxx`
> 示例：`转录这个视频 https://youtube.com/watch?v=xxx`
>
> 适用：YouTube、B站、播客、在线课程、技术演讲、科技时评

## 核心理念

你看文字比听/看快。此 skill 把音视频的内容变成你能扫读的文字，再按内容类型分流处理——技术教程做成手册，观点讨论做成 izu 研究，最后强制输出**评估分析**（启示+改进建议），把别人的经验变成你的行动。

## 输入

| 平台 | 字幕获取 | 无字幕降级（推荐顺序） |
|------|---------|---------------------|
| **YouTube** | `fetch_transcript.py`（youtube-content skill） | Groq STT API（压缩 mp3 ≤25MB）→ 本地 faster-whisper |
| **B站** | API 字幕接口（`api.bilibili.com/x/player/v2`） | Groq STT API → 本地 faster-whisper（medium CPU ~10min/20min音频，已缓存时可靠）|
| **播客/其他** | RSS/网页抓取 | Groq STT API → 本地 faster-whisper |

## 流程

### 第一步：获取语音文本

1. **先查字幕** → 有字幕直接用（最快）
2. **无字幕 → STT，推荐优先级**：
   - **优先 Groq STT API**（whisper-large-v3-turbo，免费额度，通常 <30s 完成 17min 视频）
   - **🔴 前置检查**：`GROQ_API_KEY=***` 是**占位符**，非有效 Key。见下方 `<references/key-validation.md>`。如果无效，直接降级到本地 faster-whisper
   - 备选：本地 faster-whisper medium（CPU ~10min/20min 音频，已缓存时可靠）
3. **Groq 快速路径**：
   - 音频压缩（必须 ≤25MB）：`ffmpeg -i input.wav -b:a 64k output.mp3 -y`
   - API key 位置：`~/.hermes/.env` → `GROQ_API_KEY`（不在 config.yaml 的 stt 段里）
   - 调用参考：`curl` 带 Bearer 认证 + `whisper-large-v3-turbo` 模型 + `verbose_json` 格式
4. **保存原始转录** → `wiki/transcripts/{slug}-raw.json`（含时间戳）

### 第一步半（优化步骤）：并行搜索中文补充资料（无字幕加速 + 评估先行）

> **适用场景**：无字幕需降级到STT（等待8-12分钟），或用户标记了「大」「极大」
> **核心价值**：不被STT阻塞分析流程。通过中文文章可先行完成评估分析，STT只保留原始稿

#### 快速通道（核心优化）

当用户标记「大」或「极大」时，成功找到高质量中文文章后，**评估分析可以不等STT结果先行输出**：

1. **搜索中文资料与音频下载并行启动**：
   ```
   搜索词 = "{视频标题关键词} {作者/品牌名}" (中文)
   ```
2. **优先检索平台顺序**：
   - 51CTO / CSDN → 深度技术解读
   - 知乎专栏 / 微信公众号 → 分析框架+引述
   - 新浪财经/华尔街见闻 → AI产业新闻转述
   - 英文源：TechCrunch / VentureBeat / The Decoder（当中文资料不足时）
3. **找到高质量文章后的工作流**：
   - 提取结构化内容 → 直接写评估分析（C.改进建议可基于文章生成）
   - 在 `## 前置说明` 中列出所有信源，标注「主信源：视频原文声+中文文章交叉验证」
   - STT仍在后台跑 → 转录稿只作为原始存档保留，评估已基于更丰富的文章信息完成
4. **极重要规则**：
   - 中文文章是**补充信源，不是替代**。转录完成后仍需做校对润色并保存原始稿
   - 若搜索结果不匹配（标题党/营销号），丢弃，等STT结果
   - 同一频道连续3+条内容时，在 `## 前置说明` 标注来源同质化风险

### 第二步：校对润色（🔴 硬性步骤，绝对不可跳过）

**Whisper 转录三大通病：**

| 问题 | 示例 | 修正 |
|------|------|------|
| **同音错别字** | "让 Cloud Code 给我声称 HTML" | → "让 Claude Code 给我**生成** HTML" |
| **语句割裂** | "这篇文章的标题很简单 / 叫HTML的不合理有效性" | → 合并为一句，补标点 |
| **标点缺失** | 纯空格拼接，无句号逗号 | → 按语义补全标点，自然断句 |

**校对规则：**
1. **逐段比对**：将原始分段合并为自然段落（通常 3-5 个原始段 → 1 个自然段）
2. **专有名词修正**：Claude Code（非 Cloud Code）、GPT（非 G P T）、API（非 A P I）
3. **同音字排查**：重点排查——生成/声称、在/再、的/地/得、它/他/她
4. **补标点不断意**：以逗号、句号自然断句，但绝不改动原意
5. **模糊处标注**：实在听不清的标 `[音]`，语义不通的标 `[疑]`
6. **输出校对版**：覆盖 `{slug}-raw.json` 或另存 `{slug}-corrected.json`

**✂️ 禁止：** 改原意、删口语、脑补内容。

### 第三步：格式化全文

**铁律：全文转录，不是摘要。**
- 原文一段 → 译文一段（交替排列）
- 非中文内容全部翻译成中文
- 术语首次出现：**括号加注原文+一句话精确定义**
- 时间戳保留（`[MM:SS]` 格式）
- 输出：`wiki/transcripts/{slug}-full.md`

### 第四步：内容分流判断

| 内容类型 | 判断信号 | 走哪个分支 |
|---------|---------|-----------|
| **技术教程/操作指南** | 大段操作步骤、参数讲解、界面演示 | → 分支A：做手册 |
| **科技评论/观点讨论** | 多观点碰撞、行业分析、趋势判断 | → 分支B：izu研究 |
| **二者兼有** | 既有操作又有观点 | → 先B后A（先抓观点再补手册） |
| 🔴 极大级别 | 用户标记"极大"或内容直接对标核心项目（izu/Hermes架构/Agent协作） | → 分支B + 走极大级评估路径（see references/maximum-level-evaluation.md）。合议是否触发由用户信号表决定。 |

### 分支A：做手册

参照 `wiki-project-study` 模式B（用户操作指南），从转录中提取操作步骤并结构化。

### 分支B：izu 研究

1. **提炼核心观点**（3-5个，每个≤50字，标注视频时间戳依据）
2. **三个关联主题**：纵向深挖 / 横向对比 / 前沿展望
3. **可证伪性检验**：哪些断言可验证？哪些是信仰？
4. 输出：`wiki/research/{slug}-izu.md`

### 第五步半（新增）：原始出处核实（🔴 铁律，不可跳过）

> **用户铁律**: "不能坚信二手资料，必须吃透第一手资料！切记切记！查信息的原始出处，特别是有论文的必须下载论文研究，核实！"

**所有视频/文章解读都是二手资料。必须在入库前核实原始出处。**

#### 核实流程

1. **识别原始出处** — 视频描述/文章中提到论文名称/作者 → 搜索 arXiv、OpenReview、Semantic Scholar
   ```python
   搜索词 = f"\"{论文标题}\" arXiv"
   ```
   常见论文平台：arXiv.org / OpenReview.net / paperswithcode.com / transformer-circuits.pub / proceedings.mlr.press

2. **提取论文摘要+作者+日期** — 从原始论文页面获取，而非从视频描述中引用
   - 记录：论文标题、作者列表、机构、发布日期、会议/期刊、代码仓库
   - 存储：`wiki/raw/papers/{slug}.md` （用论文原始标题，非视频标题）

3. **对比视频解读 vs 论文事实** — 逐项对比，特别关注：

   | 对比维度 | 视频常见夸大模式 | 检查方法 |
   |---------|----------------|---------|
   | 核心主张 | "彻底颠覆""革命性突破" | 去论文摘要看原文措辞 |
   | 实验数据 | 模糊描述"大幅提升" | 找具体数字（+X% / Y pp） |
   | 适用场景 | 暗示通用/全能 | 看论文实验设置和限制条件 |
   | 作者归属 | "清华发布"/"斯坦福开源" | 核实作者机构和官方背书 |
   | 时间线 | 暗示"刚刚突破" | 看论文提交日期+历次版本 |

4. **记录差距** — 在评估分析的 `## 前置说明` 中添加「核实对照」段落
   - ✅ 准确：视频说法与论文一致
   - 🟡 模糊/简化：视频概括了但方向正确
   - 🔴 夸大/失真：视频严重偏离论文事实
   - 示例格式见 `references/primary-source-verification.md`

5. **更新wiki条目前先纠正** — 不要直接使用视频的描述存入wiki
   - 用论文原始摘要改写条目（论文原文表述）
   - 在条目末尾注明「纠正：本文存疑」或「视频说法与论文不符处」
   - 保存两个版本：raw（视频版，标注「未经核实」）+ papers（论文版，标注「已核实」）

#### 核实优先级

| 来源 | 可信度 | 核实需求 |
|------|--------|---------|
| arXiv论文原文 | ✅ 高 | 直接采信 |
| 官方博客（Anthropic/OpenAI/Google） | ✅ 高 | 直接采信 |
| 最佳拍档TV/中文解读类视频 | 🟡 中 | **必须核实**，通常准确但可能省略限制条件 |
| wow频道/营销号类视频 | 🔴 低 | **必须核实**，常见大幅夸大和标题党 |
| 知乎想法/短内容 | 🟡 中 | 部分准确，需交叉验证 |
| 评论区精华 | ⚠️ 参考 | 不能作为主要信源，只能作为补充视角 |

#### 核实不通过的处理

如果论文原文无法获取（付费墙/会员专属）：
1. 在评估分析中标明「⚠️ 论文原文未获取，以下基于视频解读」
2. 降级处理：从「极大」降为「大」，从「大」降为「中小」，标注「可信度待验证」
    - 记录待获取队列：`wiki/queue/unverified-papers.md`

### 第六步：评估分析与行动启示（强制步骤）

> **不论走分支A还是B，此步骤必须执行。**

从**自身项目视角**做三层评估：
- **A. 核心论点评估**：主张 + 论据充分度 + 可证伪性 + 盲点
- **B. 对我们的启示**：关联点 + 借鉴思路 + 警示 + 一致性对比
- **C. 改进建议**：按 P0（本周）/ P1（两周）/ P2（一个月+）分级，每个建议必须有具体行动、视频依据、预期效果

输出：`wiki/research/{slug}-eval.md`。模板见 `references/evaluation-analysis-template.md`。

### 第七步：生成 HTML

全文转录 → 深色主题 HTML（tooltip 术语注 + 可点击时间戳），输出到 `wiki/transcripts/{slug}-full.html`。

## 用户信号与处理级别

用户发送链接时通过标记表达处理深度要求，判定后再启动流程：

| 用户说 | 级别 | 处理方式 | 输出位置 |
|--------|------|---------|---------|
| `极大 <URL>` | 🔴 极高 | 全量分析。**优先路径**：快速通道（跳过转录）→ 识别原始论文 → arXiv核实 → 写极大级评估报告（see `references/maximum-level-evaluation.md`）→ HTML双版 → wiki概念页 → log。**若用户同时要求合议**，则触发 `five-agent-consultation` 后再写报告。用户只说"评估分析，入库/极大"时走单Agent报告路径，不说"开干"不触发合议。 | wiki + `output/极大/` |
| `大 <URL>` | 🔴 高 | 标准评估分析（三层评估+改进建议）+ 隐式"存入wiki" | wiki + `output/大/` |
| 仅 `<URL>` | 🟡 中/默认 | 标准评估 → 入wiki（若用户前文已示意批量摄入则隐式） | wiki |
| `评估可行性 <URL>` | 🟢 低 | 评估但不入wiki | 仅当前对话 |
| `存入wiki <URL>` | 🟢 默认 | 抓取原文 → 入库raw → 评估 → 不入output | wiki |

## 输出结构

### 核心规则

1. **原文必须保留**：用户习惯看转录原文（时间戳+全文），评估分析中也要附带原文信息
2. **双路径输出**：wiki存放永久存档，`/mnt/i/hermes/output/大/` 和 `/mnt/i/hermes/output/极大/` 供用户随时浏览
3. **分级目录**：输出按级别分文件夹，不混放。**成对产出**（转录原文+评估分析），缺一不可

### 路径映射

```
wiki/
├── transcripts/{slug}-raw.json        # 原始whisper输出
├── raw/{slug}-transcript.md           # 校对后的时间戳全文（用户观看用）
├── research/{slug}-eval.md            # 评估分析（强制产出）
└── research/{slug}-izu.md             # izu研究（仅分支B）

/mnt/i/hermes/output/（即 I:\hermes\output\）
├── 大/
│   ├── {slug}-transcript.md           # 转录原文（带时间戳）
│   └── {slug}-eval.md                 # 评估分析
└── 极大/
    ├── {slug}-transcript.md           # 转录原文（带时间戳）
    └── {slug}-eval.md                 # 评估分析（含合议结论）
```

### 产出铁律

- 🔴 原文（raw transcript）和评估分析（eval）必须成对出现，缺一不可。用户习惯看原文，需要「慢慢消化」
- 🔴 评估分析的 `## 前置说明` 必须列出所有信源（视频/文章/补充资料）
- 🔴 「极大」级别：评估分析的 `C.改进建议` 栏必须包含五人合议的军师终裁

## 注意事项

### 🔴 致命陷阱

1. **Groq Key 可能是占位符**：`~/.hermes/.env` 中的 `GROQ_API_KEY=***`（三个星号）是占位符，**不是有效 Key**。调用前必须检测：
   ```bash
   if grep -q 'GROQ_API_KEY=\*\*\*' ~/.hermes/.env; then
     echo "⚠️ 降级到本地 faster-whisper"
   fi
   ```
   `***` 是字面值——发现后直接降级，不要重试。

2. **永远不用 `/tmp/` 做工作目录**：WSL 的 `/tmp/` 在网关重启后会被系统清理。用稳定的用户工作区路径，如 `/mnt/i/hermes/tmp/bilibili_audio/`。

3. **本地 faster-whisper 时间成本**：medium 模型处理 20min 音频约需 8-12 分钟（CPU 4核全开）。这是可靠但慢的后备路径——跑上就等，不要中断。

4. **Groq API key 在 `.env` 不在 `config.yaml`**：`config.yaml` 的 stt 段只有 `provider: groq`，key 在 `~/.hermes/.env`。

5. **Groq 文件大小限制 25MB**：WAV 文件 17min=180MB，必须 `ffmpeg -b:a 64k` 压缩到 ~8-9MB MP3。

### 常规注意事项

6. 四步顺序不可打乱：转录→校对→分流→评估
7. 校对完后以"听众"视角通读一遍
8. 评估分析必须有可执行项（P0/P1/P2），不是空话
9. 视频比论文更重"时效性判断"
10. **信息同源偏差**：连续处理同一频道/来源的视频（如"最佳拍档"频道的多期内容），报道风格和编辑判断会趋同。评估分析时要额外标注"来源同质化程度"，并主动寻找反方/不同视角的资料。同一频道连续3+条内容时，必须在`## 前置说明`中标注来源同质化风险。

## 补充工作流

### 纯文章评估（非音视频）

当用户发送**微信公众号文章/网页链接**而非视频时，跳过转录步骤：

```
纯文章URL → 抓取全文（web_extract优先） → 校对（如有HTML噪音） → 内容分流 → 评估分析 → 入库
```

- 不需要下载音频/STT。直接抓取文字内容
- 「极大」级别的文章同样触发五人合议
- 用户信号表不变

### YouTube 页面内容快速通道（跳过转录）

当 YouTube 视频的**页面元数据（标题、描述、评论区精华）**经 `web_extract` 已提供足够分析内容时（如前天刚发布的新视频，评论区已有深度讨论，描述有详细摘要），**可跳过完整的音频转录流程**：

```
YouTube URL → web_extract（获取页面可见内容） → 元数据+评论区信息足够？→ 直接进入内容分流+评估分析
```

**触发条件**（满足任一即可）：
- 视频描述包含详细摘要/文章链接（如 "基于a16z万字文章"）
- 评论区已有深度技术讨论，且讨论质量高
- 视频为中文解读类（讲解已有文章/论文——原文内容独立可得）
- 用户标记「大」「极大」且 10+ 条高质量评论可用

**⬇ 降级条件**（以下情况应走标准转录流程）：
- 页面内容过少（≤200字可读内容）
- 视频含大量 demo/演示画面，文字无法覆盖
- 技术演讲需要逐字逐句分析

**处理方式**：对页面内容做结构化提取（标题→摘要→评论区精华→相关资源），评估分析中标注「信息源：视频页面元数据+评论区，未转录完整音频」，并指出评论区观点可能来源单边（评论区自我筛选偏差）。

### 相关条目配对处理（同一频道/同主题连击）

当用户在同一会话中连续发送同频道、同主题的链接（如"最佳拍档TV"前后两天的问题篇+解答篇），应做**配对处理**而非独立入库：

**检测信号**（满足≥2条）：
- 同一频道/UP主，相邻发布日期的视频
- 内容明显为"问题→答案"/"病→药"/"A面→B面"关系
- 用户无刻意分隔（连续发送，无中断）

**配对处理流程**：
1. **分别入库** — 每个视频单独走 raw + concept/entity 评估流程
2. **创建对比页** — 在 `comparisons/` 下创建配对对比页，关键维度：
   - 各自核心主张
   - 共同结论（两方都同意什么）
   - 分歧/互补点（各自覆盖了什么盲区）
   - 叠加视图（两张图叠起来看到了什么新东西）
3. **提供综合合成** — 向用户输出"连起来看"分析，不止罗列各自要点，而是给出**叠加后的新认知**。结构：
   - 各自定位（一个讲什么，一个讲什么）
   - 交叉验证点（哪里互相印证、哪里互相补充）
   - 对自身项目的**综合启示**（两张图一起看，才发现此前没看到的全局路径）
4. **标注关联** — 在两个 concept 页面互相添加 `[[wikilink]]`，comparison 页同时链接两个 concept

> ⚠️ 配对不意味着合并——两个内容保持各自独立的 wiki 入口。配对是额外层，不覆盖原有结构。

### 英文内容翻译要求

当用户明确说「翻译」或评估对象为纯英文内容时（如官方英文PDF/博客）：

1. **先获取原文全文**（PDF需用web_extract转换）
2. **产出翻译稿**：在`output/`中与评估分析并列存放，文件名标记`-zh.md`
3. **评估分析基于翻译版写**，但C栏引用应保留英文关键词以便溯源
4. **原文稿同时保留**：输出目录中必须同时存在原文和译稿，不覆盖

### 任务优先级与请求中断

用户可能在新请求中覆盖旧请求。处理规则：

1. 后台任务（STT转录/cron）继续运行，不受新请求影响
2. 前台任务（当前正在输出的内容）按新请求优先级切换
3. **用户明确要求的完整流程（评估分析翻译+入库+输出）应当在后台完成后补完**，不能因为新请求而永久丢弃
4. 如果发现旧请求的交付物未完成，在合适时机主动询问是否需要补完
