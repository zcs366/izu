## 减法清单（W1可开工）

### 1. 合并对齐角色（P0，1人日）
- **当前**：izu-pipeline.py L425-446，175行系统提示词 + 一次完整LLM调用，只为了做"织的关联地图是否对准用户原始关切"
- **问题**：对齐检查本质是keyword交集计算 + 余弦相似度比较，完全可以用纯代码做
- **方案**：替代代码约30行
  ```python
  # 1. 从用户原始prompt提取n个关键词（regenerate + stopwords过滤）
  # 2. 从织的关联地图提取m个关键词
  # 3. 计算关键词交集率
  # 4. 如果交集率<阈值（如0.4），才调LLM做深层判断
  ```
- **收益**：减少1次LLM调用/次运行。按izu每天3-5次运行，每月节省60-100次API调用
- **文件**：izu-pipeline.py，修改call_deepseek(prompt, "对齐")调用链

### 2. 降级劈×3为劈×1（P0，0.5人日）
- **当前**：izu-pipeline.py L20说"劈×3聚合：三视角批评+合并"，L491-499是单一劈角色提示词
- **问题**：三视角（逻辑/技术/事实/来源/表达/风格）从未验证过带来了额外的收益。code_fact_check_urls（L348-363）已经做了死链检查。三视角相当于3倍的推理成本
- **方案**：维持单一劈角色，但将code_fact_check_urls的结果直接注入劈的prompt（当前已经是这样做的，见izu skill文档）
- **收益**：减少2次LLM调用/次运行（三聚合实际是1次生成? 需确认代码走3次独立LLM还是1次三段输出）

### 3. 探×2→探×1（P0，0.5人日）
- **当前**：双探并行A角搜"前沿进展"B角搜"争议批评"，然后code_dedup_aggregate做URL集运算
- **问题**：code_dedup_aggregate（L228-251）的overlap_ratio通常>60%——说明60%的搜索覆盖是冗余的
- **方案**：改为单探+再搜索策略。首轮搜索后，如果T1信源覆盖率<阈值，再搜第二轮
- **收益**：减少1-2次LLM调用/次运行

- **不能做的**：不建完整Graph DB，不引入图数据库
