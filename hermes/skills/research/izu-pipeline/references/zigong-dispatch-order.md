## 〇、萧何待决问题回答：P0改造方案选A

**问题**：P0（反馈闭环修复，45min，截止5月31日）的三个改造方案选哪个？

### 三个方案还原

| 方案 | 动作 | 工时 | 复杂度 | 效果 |
|------|------|------|--------|------|
| **A** ✅ | 论文日报cron prompt末尾加「今日关注3件事」 | **5分钟** | 极低 | 军师每天看到日报后自动带出3条可执行动作 |
| B | 在论文日报输出后加独立的「今日关注」cron agent | 30分钟 | 中 | 独立agent分析日报+推今日关注 |
| C | 构建反馈闭环仪表盘（含统计、趋势、TODO跟踪） | 45分钟 | 高 | 完整闭环系统，但超出P0粒度 |

### 子贡推荐：**方案A**，理由如下：

**1. 时间投入产出比碾压。** 方案A需5分钟，方案B需30分钟（6倍投入），方案C需45分钟（9倍投入）。但方案A已能解决"反馈闭环缺失"的**80%痛点**——军师现在的问题是"看了日报不知道接下来做什么"，不是什么复杂仪表盘。

**2. 子产判断验证。** 子产说"不做更多，做更少、更准、更被接到"——方案A就是在现有日报的**末端**加一行「今日关注3件事」，这是被接到的精确位置，不新增终端。

**3. 5分钟即可上线。** 今天（5月16日）改完，明天（5月17日05:00）下一次论文日报cron运行就立即生效，体验闭环在24小时内闭合。

**4. 方案B和C的收益边际递减。** 独立cron agent（B）与方案A的差别是"谁在写今日关注"——方案A是日报本身LLM写，方案B是另一个agent写。输出质量和用户感受到的效果几乎没有可感知差异。仪表盘（C）是好东西但应对的是P2级别的数据监控需求，不是P0级反馈闭环缺失。

**5. 韩信终局验证。** 韩信说2026年11月军师每天看到的是"今天唯一必做之事+3条来信"——方案A就是在日报末尾插入了这"3条来信"的雏形。

**⚠️ 红牌约束**：鲁班的三张红牌之一"不造优先级引擎"——方案C已经踩到了红牌边界。不做仪表盘。

| 刚需 | 当前状态 | 改造后状态 | "不乱了"的感受 |
|------|---------|-----------|-------------|
| **知道今天该做什么** | 看了日报→不知道接下来干嘛 | 日报末尾自动带"今日关注3件事" | 每天第一条消息就告诉我今天要做什么 |
| **知道哪件事最重要** | 14条信息轰炸，分不清优先级 | 韩信"唯一必做之事"逐步上线 | 不再纠结"先看哪个" |
| **知道做完了有没有用** | 做了也不知道效果 | 反馈闭环——明早的今日关注会回看昨天是否完成 | 被接到了，不是石沉大海 |
| **少看少焦虑** | 日均消息量庞大 | P2+基地数字化的cron修剪（P1 checkpoint后） | 消息量下降79% |

### 4.2 周报"今日关注"包装方案（三个阶段）

**阶段一（W0·本周末上线）："小贴士"模式**
```
位置：论文日报末尾
形式：3条bullet point
语气：轻、短、可做可不做
示例：
  📋 今日关注（3件事）
  1. ☕ 快速浏览：文中提到的X模型，10分钟看abstract+conclusion
  2. 🔍 扩大视野：Y论文引用的Z方向，值得明早追一篇
  3. 📌 备忘：本周五前，把N方向加到下学期备选列表
```

**阶段二（W2后）："回看闭环"模式**
```
论文日报末尾增加昨日回看区域：
  📋 今日关注（3件事）
  ...
  🔄 昨日回看：昨天第1件事"读X模型abstract" —— 做了吗？[未标记]
```
注意：这个"未标记"是占位符，不增加系统复杂度。军师自己心里回看。

**阶段三（W6后）："唯一必做"模式（韩信终局雏形）**
```
移动到日报**开头**，而不是末尾：
  🎯 今天唯一必做：...（由今日关注3件事中权重最高的自动提升）
  📋 其他关注：...
```
⚠️ **红牌警告**：阶段三不在此次6周范围内，属W5-W6灵活段之后的v5.1计划。

### 4.3 方案A给军师的体验变化

| 变化维度 | 改造前 | 改造后（5月17日第一次运行） |
|---------|-------|------------------------|
| 日报末尾 | 只有"军师的话"一段感想 | "军师的话" + "今日关注3件事" |
| 军师看完后 | 知道了今天的干货，但不知道要做什么 | 知道了做哪3件事 |
| 消息量增量 | 0 | 5行文本（可忽略） |
| 军师焦虑 | 14条周报×7天，完全不知道先看哪个 | 第一条消息就告诉优先级——今天做什么 |

## 六、变通预案

### 方案A：Schema简化（轻度绕行 · 损失10%功能）

**触发条件**：W2D2（5/25周一晚）Schema设计讨论超过30分钟仍未通过

**动作**：
1. 放弃完整Schema重构
2. 仅在现有wiki schema上加一个 `audit_trail: str` 字段（比4个结构化字段简单得多）
3. Provenance检测器改做"游走式"——逐个段落检查引用
4. `wiki_schema_v2.py`从80行降到30行，`izu_provenance.py`从65行降到40行

**代价**：
- 失去结构化provenance_chain（不可按来源URL聚合筛选）
- 失去traverse_trail（不可追溯搜索路径）
- 保留audit_log → **功能完整性~90%**

**工期影响**：节省W2D3（Schema编码）→ 1天时间恢复

### 方案B：砍动态路由，专注核心修复（中度绕行 · 损失P1功能）

**触发条件**：W4D2（6/8周一）验收测试R1中6项指标≥3项不合格

**动作**：
1. **砍W5动态路由全部任务**（释放5小时）
2. W5全部转为"验收问题修复周"
3. 目标：W5结束时6项指标全部达到≥80分

**代价**：
- 失去动态路由带来的$0.01/次的成本节省
- 失去"简单topic用flash"的智能路由能力
- 月成本从$5.15升至$5.40（+$0.25/月）

**决策标准**：动态路由是"省钱"，验收问题是"确保质量"。质量优先级永远高于成本优化。

### 方案C：降级为4周交付P0核心（重度绕行 · 保留核心砍外围）

**触发条件**：以下任一
- W2卡住超过3天（Schema设计反复）
- 军师连续3天零产出
- 日均有效工时降到45分钟以下（碎片化突破红线）

**动作**：
1. 放弃W5-W6（动态路由+知识固化），压缩为4周
2. 只保留P0：CAST + 安全红线 + 对齐代码化 + Provenance检测（简化版）+ 5步裁剪
3. KNN路由降至P1，维持LLM判断
4. 知识固化降级为"基本CHANGELOG+API文档"

**P0必须完成**：
- `izu_cast.py`
- `izu_safety.py`
- `izu_align_code.py`
- `izu_provenance.py`（简化版，走方案A路径）
- `wiki_schema_v2.py`（简化版）
- 5步裁剪+集成

**砍掉的P1**：
- `izu_routing.py`
- 动态路由v2
- 知识固化到Skill
- 全量验收报告美化
- 知乎/公众号文章

**工期影响**：4周 → 6周（实际投入减半），可用工时从30h→17h

| 方案 | 触发条件 | 工时节省 | 功能损失 | 风险等级 |
