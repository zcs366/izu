## 第一章 概览与核心理念

### 1.1 什么是提示词工程？

**提示词工程（Prompt Engineering）**，通俗地说，就是**设计输入给 AI 模型的指令，让它准确完成你想要的输出**。

想象你在奶茶店点单。如果你只说"来杯喝的"，店员可能给你一杯温水、一罐可乐，或者——如果你运气好——一杯最基础的珍珠奶茶。但如果你说："一杯少冰、三分糖、加椰果的四季春茶拿铁，用燕麦奶"，店员能准确无误地做出来。

提示词工程就是这样——**把模糊的愿望翻译成模型能精确执行的指令**。

### 1.2 为什么需要提示词工程？

| 为什么 | 例子 |
|--------|------|
| 模型不"懂你" | 你问"解释一下量子计算"，模型可能输出研究生级别的数学推导 |
| 模型会"编造" | 没有明确约束时，模型会出现"幻觉"（hallucination），凭空捏造事实 |
| 输出格式不可控 | 你需要 JSON，它给你散文 |
| 推理能力不足 | 复杂问题直接问，模型容易"偷懒"，跳过推理步骤 |

**关键认知**：大语言模型本质是一个**超强模式匹配器**，而不是一个"理解你"的人类。你输入什么模式，它就输出什么模式。提示词工程就是设计这个"输入模式"的科学。

### 1.3 核心工作流

```
用户意图 → [提示词设计] → [发送给模型] → [评估输出] → [迭代优化]
                ↑                                  |
                └──────────── 反馈循环 ────────────┘
```

这就是提示词工程最本质的流程：**设计 → 执行 → 评估 → 迭代**。不是一次写对，而是一轮一轮逼近目标。

### 1.4 技术全景图

```

                    │   提示词工程（Prompt Engineering） │
                    └─────────────────────────┘
                               │
        ┌──────────────────────┼──────────────────────┐

    ┌───┴───┐          ┌──────┴──────┐         ┌────┴────┐
```

### 1.5 类比：提示词工程的"配方思维"

一个好的提示词就像一道菜的**配方**：

| 配方元素 | 提示词对应 | 例子 |
|----------|-----------|------|
| 菜名 | 任务指令 | "写一封商务邮件" |
| 食材 | 输入数据 | "客户投诉了送货延迟" |
| 调味料 | 风格/语气 | "语气要诚恳但不卑微" |
| 烹饪步骤 | 推理步骤 | "先分析投诉原因，再提出补救方案" |
| 摆盘要求 | 输出格式 | "邮件分为：称呼→引言→问题说明→解决方案→结语" |

## 第二章 接入与工具准备

### 2.1 主流大模型平台

写 prompt 之前，你得先知道你的"对话对手"是谁。不同模型性格不同，同样的 prompt 在不同模型上效果大相径庭。

| 平台 | 代表模型 | 特点 | 收费模式 | 最佳用途 |
|------|---------|------|---------|---------|
| **OpenAI** | GPT-4o / o1 / o3 | 最全面，生态最成熟 | API 按 tokens 计费 | 通用对话、代码生成 |
| **Anthropic** | Claude Sonnet 4 / Opus 4 | 长上下文(200K)，安全设计突出 | API 按 tokens 计费 | 长文档分析、代码、创意写作 |
| **Google** | Gemini 2.5 Pro / Flash | 100万上下文窗口，多模态强 | 免费额度慷慨 | 超长文档、多模态分析 |
| **DeepSeek** | DeepSeek V3 / R1 | 中文理解极强，推理优秀 | API 价格低廉 | 中文对话、数学推理 |
| **本地部署** | Llama 3 / Qwen2.5 / Mistral | 私密，无审查，零成本（硬件费用除外） | 免费（自付电费） | 敏感数据、离线工作 |

### 2.2 接入方式（按难度排序）

#### ⭐ 最简单：Web 界面

直接访问 ChatGPT、Claude.ai、DeepSeek Chat 等网站，在对话框输入提示词。

**优点**：零配置，零成本  
**缺点**：无法编程调用，不可批量处理，高级参数不可调

#### ⭐⭐ 进阶：API 调用

注册平台账号 → 获取 API Key → 用代码调用。

```python
# OpenAI API 示例
from openai import OpenAI

client = OpenAI(api_key="sk-xxx")

response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {"role": "system", "content": "你是一个资深中文编辑，擅长优化文章表达。"},
        {"role": "user", "content": "帮我润色下面这段文字：\n\n今天天气很好，我去了公园玩，看到了很多花，很开心。"}
    ],
    temperature=0.7,
    max_tokens=500
)

print(response.choices[0].message.content)
```

**重点理解 messages 结构**：

```
[
  {"role": "system", "content": "全局指令，设定模型的身份和行为规则"},    ← 系统提示
  {"role": "user", "content": "用户的输入"},                             ← 用户提示
  {"role": "assistant", "content": "模型的上一次回复（用于多轮对话）"},    ← 模型回复
]
```

#### ⭐⭐⭐ 专业：第三方注册表

- **OpenRouter**：统一接口，一个 API Key 用所有模型，适合对比测试
- **LiteLLM**：Python 库，统一 100+ 模型的调用接口
- **LangChain**：框架级的 prompt 管理，适合生产环境

### 2.3 推荐的实验环境

| 用途 | 推荐工具 | 原因 |
|------|---------|------|
| 快速测试 prompt | ChatGPT Web / Claude.ai | 所见即所得 |
| API 测试 | Google AI Studio | 免费，有 prompt 版本管理 |
| 批量对比 | OpenRouter + 脚本 | 一次请求跑多个模型 |
| 本地调试 | Ollama + Open WebUI | 完全免费，无网络依赖 |
| 生产部署 | LangChain + 模型 API | 可维护性强，支持 A/B 测试 |

## 第三章 基础操作：与大模型对话

### 3.1 提示词的基本结构

一个有效的提示词通常包含以下要素（不一定全用，按需组合）：

```
[角色设定] + [任务描述] + [上下文/输入数据] + [输出格式] + [约束条件]
```

**实例拆解**：

```
你是一个资深理财顾问。                          ← 角色设定
请为我分析以下投资组合的风险分布。                ← 任务描述
投资组合：50% A股、30% 债券、20% 黄金。         ← 输入数据
输出格式：用表格列出各类资产的风险等级和建议配置比例。 ← 输出格式
不要给出具体的股票推荐，只做宏观分析。            ← 约束条件
```

### 3.2 三大基础技巧

#### 技巧一：零样本提示（Zero-shot Prompting）

不给任何例子，直接给出指令。

```markdown
请将以下句子翻译成英文：
"今天的会议推迟到下午三点。"
```

**适用场景**：简单、明确的任务。模型已经内置了大量知识。  
**局限性**：对复杂或细分的任务，零样本往往不够精准。

#### 技巧二：少样本提示（Few-shot Prompting）

在提示词中给 2-5 个例子，让模型"看出"模式。

```markdown
请将以下中文情感分类为「正面」「负面」「中性」。

例子1：
文本："这家餐厅的服务太棒了，服务员非常热情。"
情感：正面

例子2：
文本："等了两个小时还没上菜，差评。"
情感：负面

例子3：
文本："今天周二，餐厅人不多。"
情感：中性

现在请分类：
文本："菜品味道不错，就是价格有点贵。"
情感：
```

**适用场景**：需要模型理解特定模式或风格的任务。  
**关键点**：例子要高质量、有代表性、覆盖边缘情况。

#### 技巧三：指令提示（Instruction Prompting）

用清晰、直接、结构化的指令代替模糊描述。

```markdown
❌ 模糊："帮我写点关于AI的东西。"
✅ 清晰："写一篇约800字的中文科普文章，主题是'大语言模型如何理解人类语言'。目标读者是高中生，避免使用专业术语，用比喻和例子说明。文章结构：引言→工作原理→局限→未来展望。"

❌ 模糊："给我几个建议。"
✅ 清晰："列出5条提高工作效率的具体建议。每条建议包含：建议名称（10字以内）、具体做法（50-100字）、预期效果（一句话）。按效果从高到低排列。"
```

### 3.3 角色设定（Role Prompting）

给模型一个"身份"，让它从这个身份出发回答问题。

```markdown
你是一位从业20年的中医师，擅长用日常生活中的食材做养生调理。
请为我这个长期坐办公室、颈椎不适的程序员设计一份早餐食谱。
要求：食材常见、做法简单、符合中医"春夏养阳"的原则。
```

**为什么有效**：角色设定激活了模型训练数据中与这个角色相关的分布，输出会自动对齐该角色的知识体系、语气和价值观。

**常见角色模板**：

| 角色 | 适用场景 | 示例 |
|------|---------|------|
| 资深编辑 | 文字润色、改写 | "你是一位《人民日报》资深编辑" |
| 律师 | 合同审查、法律分析 | "你是一位专攻合同法的律师" |
| 老师 | 知识讲解、教学 | "你是一位教了20年高中物理的老师" |
| 产品经理 | 需求分析、PRD撰写 | "你是一位有10年经验的B端产品经理" |
| 心理咨询师 | 情感建议、心理疏导 | "你是一位人本主义取向的心理咨询师" |

### 3.4 输出格式控制

让模型输出结构化内容，而不是散文。

```markdown
请分析以下产品的优缺点，用 JSON 格式输出（不要用 markdown 代码块包裹）：

产品：某品牌的智能手表 X200

输出格式：
{
  "product_name": "字符串",
  "pros": ["优点1", "优点2", "..."],
  "cons": ["缺点1", "缺点2", "..."],
  "overall_score": 0-10的整数,
  "target_users": ["适用人群1", "适用人群2"]
}
```

**格式控制小技巧**：

1. **明确的结构模板**：给模型一个"填空模板"
2. **分界符分隔**：用 `"""`、`---`、`XML标签` 等标识不同部分
3. **多步输出**：先让模型输出框架，再填充细节

## 第四章 实战：从零搭建第一个高质量提示

### 4.1 场景设定

我们有一个真实的任务：**为一篇微信公众号文章生成标题**

文章主题："AI 辅助编程工具的使用心得"  
目标读者：有 1-3 年经验的前端开发者  
希望达到的效果：有吸引力但不标题党，2000 阅读量以上

### 4.2 第一版：新手 prompt

```
帮我给一篇文章起几个标题，文章是关于AI写代码的。
```

**输出**：
> 1. AI写代码的未来  
> 2. 人工智能与编程  
> 3. 程序员会被AI取代吗？

**问题分析**：太泛、不精准、没有读者意识。

### 4.3 第二版：加入角色和格式约束

```
你是一个有10年经验的新媒体主编，特别擅长给技术类公众号起标题。
请为一篇文章生成5个标题候选。

文章主题：AI辅助编程工具（如GitHub Copilot、Cursor）的使用心得
目标读者：1-3年经验的前端开发者
文章内容：作者使用AI编程工具6个月后的真实体验，包括效率提升、常见坑、最佳实践

要求：
- 每个标题不超过20字
- 要有具体的数字或结果承诺
- 避免标题党，保持技术人的真诚感
- 每个标题后附一行说明为什么这个标题有效
```

**输出**：
> 1. **我用AI写代码6个月：效率翻倍，但坑也不少**  
>    → 有具体时间跨度（6个月）和矛盾张力（效率 vs 坑），引发好奇
> 2. **前端开发者的AI编程实战：Copilot vs Cursor 横评**  
>    → 精准锁定目标读者（前端），具体产品对比，专业感
> 3. **从怀疑到真香：一个程序员的AI编程工具进化史**  
>    → 叙事感强，有情感曲线，容易引发共鸣
> 4. **别急着用AI写代码：这份避坑指南帮你少走弯路**  
>    → 反面切入，制造紧迫感，实用价值明确
> 5. **每天多写200行代码？AI编程工具的真实效率报告**  
>    → 具体数字支撑，承诺可验证的结果

### 4.4 最终版：迭代优化

在第二版基础上，加入**否定约束**和**额外上下文**：

```
你是一个有10年经验的新媒体主编，特别擅长给技术类公众号起标题。
请为一篇文章生成5个标题候选。

文章主题：AI辅助编程工具（如GitHub Copilot、Cursor）的使用心得
目标读者：1-3年经验的前端开发者
文章核心观点：AI不会取代程序员，但会用AI的程序员会取代不会用的

要求：
- 每个标题不超过20字
- 要有具体的数字或结果承诺
- 避免标题党，保持技术人的真诚感
- 每个标题后附一行说明

❌ 绝对不要：
- "震惊"、"千万别错过"、"重磅"等营销词汇
- 制造焦虑的"你将被淘汰"式恐吓
- 纯技术名词堆砌
```

**核心心法**：每一轮迭代都**只改一件事**，看看效果变化。这是提示词工程最基本的实验方法。

### 4.5 实战工作流总结

```
1. 明确需求
   ↓
2. 写第一版 prompt（肯定不好）
   ↓
3. 分析输出差距——哪里不对？
   ↓
4. 做一次针对性的修改（角色/格式/约束/例子...）
   ↓
5. 重新测试
   ↓
6. 如还不够 → 回到第3步
   ↓
7. 满足需求 → 保存为模板
```

## 第五章 参数详解

### 5.1 温度（Temperature）

**类比**：厨师做菜的"创新程度"。

- **温度=0**：严格按配方做，每次味道一模一样（确定性输出）
- **温度=0.5**：允许在配方基础上微调（适度多样性）
- **温度=1.0**：大厨自由发挥，每次可能完全不同（高创造性）
- **温度=2.0**：可能是黑暗料理，也可能惊艳（极不稳定）

**具体参数值建议**：

| 任务类型 | 推荐温度 | 原因 |
|---------|---------|------|
| 代码生成 | 0 - 0.2 | 代码必须精确，不能"创新" |
| 数学/逻辑推理 | 0 - 0.3 | 需要确定性答案 |
| 数据提取/分类 | 0 - 0.3 | 结果必须一致 |
| 商务邮件 | 0.3 - 0.5 | 专业但不过于死板 |
| 创意写作 | 0.7 - 1.0 | 需要多样性 |
| 头脑风暴 | 0.8 - 1.2 | 鼓励"跳出框框" |
| 诗歌生成 | 0.9 - 1.2 | 文学性最大化 |

```python
# 代码生成——低温
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "写一个Python函数，计算斐波那契数列的第n项。"}],
    temperature=0.1  # 确保代码逻辑精确、格式一致
)

# 创意故事——高温
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "写一个关于AI觉醒的短篇科幻故事，300字。"}],
    temperature=0.9  # 鼓励意想不到的情节
)
```

**调试技巧**：如果你发现模型输出过于重复或死板 → 调高温度。  
如果输出太离谱、不一致 → 降低温度。

### 5.2 Top-p（核采样）

**类比**：选词时的"选择范围"。

- **Top-p=0.1**：只从概率最高的前 10% 的候选词中选择（非常保守）
- **Top-p=0.5**：从概率和占 50% 的候选词中选择（中等保守）
- **Top-p=1.0**：考虑所有候选词（默认，最大多样性）

**通俗理解**：Temperature 决定"权重曲线的陡峭程度"，Top-p 决定"切掉尾巴的哪一段"。

**推荐搭配**：

| 模式 | Temperature | Top-p | 效果 |
|------|------------|-------|------|
| 精准模式 | 0.1 | 0.1 | 最确定性，适合代码 |
| 平衡模式 | 0.7 | 0.9 | 默认，多数场景适用 |
| 创意模式 | 0.9 | 1.0 | 最大多样性 |
| **最佳实践** | **只调一个** | **另一个默认** | 两个一起调容易互相抵消 |

> ⚠️ **黄金法则**：不要同时大幅调整 Temperature 和 Top-p。先固定一个，调另一个。大多数情况下调 Temperature 就够了。

### 5.3 Max Tokens（最大输出长度）

限制模型能输出的最大 token 数（1 token ≈ 0.75 个中文词）。

| 输出类型 | 推荐 Max Tokens | 说明 |
|---------|----------------|------|
| 短回复 | 100 - 300 | 分类、打分、简短回答 |
| 段落级 | 500 - 1000 | 邮件、摘要、分析 |
| 文章级 | 1000 - 4000 | 文章、报告 |
| 超长输出 | 4000+ | 小说、复杂分析 |

**陷阱**：Max Tokens 不够时，输出会被截断——这往往发生在"关键结论"即将出来的时候。  
**建议**：始终比预期多设 20-30%。

### 5.4 Stop Sequences（停止序列）

告诉模型"看到这个标记就停"。

```python
# 让模型生成 5 个点子，用数字分隔
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "列出5种提高工作效率的方法，每行一个，用数字编号。"}],
    stop=["6."]  # 模型生成完第5条就停
)
```

**应用场景**：
- 控制列表长度
- 防止模型继续"加戏"
- 在链式 prompt 中做精确截断

### 5.5 Frequency Penalty 与 Presence Penalty

**Frequency Penalty（频率惩罚）**：惩罚重复出现的词。值越高，模型越少重复自己。

**Presence Penalty（存在惩罚）**：惩罚已经出现过的主题。值越高，模型越倾向引入新话题。

| 场景 | 设置 | 效果 |
|------|------|------|
| 写故事怕重复 | Frequency Penalty=0.5 | 减少词语重复 |
| 头脑风暴 | Presence Penalty=0.6 | 更多新颖点子 |
| 标准对话 | 都用 0（默认） | 自然的对话节奏 |

### 5.6 Seed（随机种子）

设置固定种子可以让每次输出一样——前提是模型支持。

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": "讲一个关于程序员的笑话。"}],
    seed=42  # 固定种子，每次得到同样的笑话
)
```

**作用**：测试可复现性、A/B 测试、生产环境的一致性。

### 5.7 参数速查表

| 参数 | 控制的是 | 中文类比 | 常用范围 | 调参原则 |
|------|---------|---------|---------|---------|
| temperature | 输出的随机性 | 厨师创新程度 | 0 - 2 (通常 0-1) | 任务越精确，值越低 |
| top_p | 候选词的集合大小 | 选材范围 | 0 - 1 | 和 temperature 二选一调 |
| max_tokens | 输出最大长度 | 作文字数上限 | 依任务而定 | 比预期多 20-30% |
| stop | 提前停止信号 | 句号 | 字符串列表 | 控制输出边界 |
| frequency_penalty | 重复词惩罚 | 避免车轱辘话 | -2 到 2 | 需要多样性时调高 |
| presence_penalty | 新话题鼓励 | 引导转话题 | -2 到 2 | 头脑风暴时调高 |
| seed | 随机种子 | 菜谱编号 | 任意整数 | 需要复现时设置 |

## 第六章 进阶技术详解

### 6.1 思维链提示（Chain-of-Thought, CoT）

**核心思想**：让模型**展示推理过程**，而不是直接给答案。

**一句话理解**：就像数学老师要求学生"写出解题步骤"一样，CoT 强迫模型一步步推理，大幅减少"抄答案"式的错误。

#### 零样本 CoT（Zero-shot CoT）

最简单的 CoT——在提示末尾加一句话：

```
小明有5个苹果，给了小红2个，然后又买了3个，现在小明有几个苹果？
让我们一步一步思考。
```

模型会输出：
> 一开始小明有5个苹果。  
> 给小红2个后，剩下 5-2=3 个。  
> 又买了3个后，现在有 3+3=6 个。  
> 所以小明现在有6个苹果。

**经典触发句**：
- "让我们一步一步思考。"
- "逐步推理。"  
- "请展示你的推理过程。"

#### 少样本 CoT（Few-shot CoT）

给 2-3 个带推理过程的例子。

```
Q: 书店有 15 本书，卖了 7 本，又进货 10 本，现在有几本？
A: 开始有 15 本。卖了 7 本后剩 15-7=8 本。进货 10 本后变成 8+10=18 本。答案是 18。

Q: 一箱牛奶 12 瓶，喝了 4 瓶，又买了 6 瓶，一箱最多装 12 瓶，请问现在多出来几瓶需要放冰箱？
A: 开始有 12 瓶。喝了 4 瓶后剩 12-4=8 瓶。又买了 6 瓶变成 8+6=14 瓶。一箱只能装 12 瓶，所以多出 14-12=2 瓶。答案是 2。

Q: 一个游泳池长 50 米，小明游了 3 个来回，他一共游了多少米？
A:
```

#### Auto-CoT（自动思维链）

当不想手动写 CoT 例子时，让模型自己生成推理过程，再用这些例子去引导另一个模型。由 Zhang et al. (2022) 提出。

**适用场景**：数学推理、逻辑问答、复杂决策、代码调试。

### 6.2 思维树提示（Tree-of-Thought, ToT）

**核心思想**：CoT 是一条直线，ToT 是一棵树——同时在多条推理路径上探索，然后选择最佳路径。

**类比**：下棋时，业余选手只算一步，专业选手会推演多个分支。ToT 就是让模型做这种"多分支推演"。

由 Yao et al. (2023) 提出。实现方式有三种：

| 方法 | 怎么做 | 适用场景 |
|------|-------|---------|
| ToT（手动） | 人工设计分支，逐个评估 | 高价值场景，质量第一 |
| ToT（自动） | 模型自己生成和评估分支 | 需要自动化的常规场景 |
| ToT（混合） | 模型生成分支，人工指引 | 创作类任务 |

**示例**（创意写作 ToT）：

```
任务：写一个关于"时间旅行者拜访唐朝"的短故事大纲。

请生成3个不同的故事方向，每个方向给出一个简略的情节框架：

方向1（历史准确路线）：
方向2（科幻混搭路线）：
方向3（哲学思辨路线）：

然后分别评估每个方向的优劣势，最后选择一个最优方向给出1000字的大纲。
```

### 6.3 ReAct（Reasoning + Acting）

**核心思想**：模型一边推理（Reasoning），一边行动（Acting）——比如调用搜索引擎、执行代码、查询数据库。

**类比**：一个侦探一边推理案情（reason），一边去现场调查、询问证人（act），然后根据新证据更新推理。

由 Yao et al. (2022) 提出。ReAct 是今天所有 AI Agent 的理论基础。

```
Task: 查找2024年诺贝尔物理学奖得主是谁，并简要说明他们的贡献。

Thought: 我需要搜索2024年诺贝尔物理学奖的信息。
Action: search("2024 Nobel Prize in Physics winner")
Observation: John Hopfield 和 Geoffrey Hinton 共同获得2024年诺贝尔物理学奖。

Thought: 现在我需要查找他们的具体贡献。
Action: search("John Hopfield Geoffrey Hinton Nobel Prize contribution")
Observation: 他们在人工神经网络和机器学习的基础发现和发明方面做出了贡献。

Thought: 信息足够了。综合回答。
Answer: 2024年诺贝尔物理学奖授予了John Hopfield和Geoffrey Hinton...
```

**应用场景**：
- AI Agent（如 AutoGPT、Claude Code、Claude Computer Use）
- 需要外部信息的问题（搜索、数据库查询）
- 需要执行代码验证的数学问题

### 6.4 自一致性提示（Self-Consistency）

**核心思想**：同一个问题跑多次，取最一致的答案——用投票代替单次推理。

Wang et al. (2022) 提出。简单但非常有效。

```
对同一个问题，以 temperature=0.7 运行 3-5 次，
收集每次的回答，
选择出现最频繁的那个作为最终答案。
```

**示例**：

```python
from openai import OpenAI
from collections import Counter

client = OpenAI(api_key="sk-xxx")
question = "一个水池，进水管4小时灌满，排水管6小时排空。两个管子同时开，多久能灌满？"

answers = []
for i in range(5):
    response = client.chat.completions.create(
        model="gpt-4o",
        messages=[{"role": "user", "content": f"{question}\n让我们一步一步思考。"}],
        temperature=0.7
    )
    answers.append(response.choices[0].message.content)

# 提取最终答案进行投票
# 最终答案 = 出现最多的答案
```

**适用场景**：数学、逻辑、事实性问答——任何有**确定正确答案**的任务。  
**不适用**：创意写作、观点类问题（答案本身就应该多样化）。

### 6.5 系统提示（System Prompt）

系统提示是最强大的技巧之一——它设定了整个对话的"宪法"。

```python
response = client.chat.completions.create(
    model="gpt-4o",
    messages=[
        {
            "role": "system",
            "content": """你是一个专业的代码审查助手。

你的核心原则：
1. 始终优先考虑代码安全性——标记任何SQL注入、XSS、硬编码密钥等风险
2. 评论要具体——指出具体的行号和问题，不要笼统地说"代码质量需要提升"
3. 三明治反馈法：先说优点 → 指出问题 → 总结建议
4. 如果发现重大安全问题，第一句就说"⚠️ 安全风险："
5. 不要建议重构除非有明确收益

你的输出格式：
- 总体评分：1-10
- 安全问题列表（如有）
- 代码质量问题
- 改进建议"""
        },
        {"role": "user", "content": "请审查以下Python代码：\n\n```python\ndef login(username, password):\n    query = f\"SELECT * FROM users WHERE username='{username}' AND password='{password}'\"\n    return db.execute(query)\n```"}
    ],
    temperature=0.3
)
```

**系统提示设计原则**：

1. **身份先行**：说清楚"你是谁"
2. **规则明确**：用"做/不做"列表
3. **格式模板**：给出输出结构
4. **负面约束**：明确禁止什么
5. **优先级**：当规则冲突时，哪条优先

**经典系统提示模板**：

```
你是[角色]。
你的核心能力：[列出3-5个专长]。
你的行为准则：
1. [规则1]
2. [规则2]
3. [规则3]
输出格式：[模板或结构说明]
不要：[负面清单]
```

### 6.6 提示词链（Prompt Chaining）

**核心思想**：把一个复杂任务拆成多个步骤，每个步骤用一个专门的 prompt。

**类比**：汽车生产流水线——每个工位只做一件事，但合起来造出一辆完整的车。

```python
# Step 1: 提取要点
step1_response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": f"从以下文本中提取3个核心要点：\n\n{input_text}"}]
)

# Step 2: 基于要点写作
step2_response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": f"基于以下要点，写一篇200字的摘要：\n\n{step1_response.choices[0].message.content}"}]
)

# Step 3: 翻译为英文
step3_response = client.chat.completions.create(
    model="gpt-4o",
    messages=[{"role": "user", "content": f"将以下中文摘要翻译为英文：\n\n{step2_response.choices[0].message.content}"}]
)
```

**和单次 prompt 的对比**：

| 维度 | 单次 prompt | Prompt Chaining |
|------|------------|----------------|
| 单步任务复杂度 | 低 | 可以很高（分步消化） |
| 错误定位 | 难 | 容易（知道哪一步出了问题） |
| 可调试性 | 差 | 好（每步可检查输出） |
| 延迟 | 低 | 高（多轮 API 调用） |
| 成本 | 低 | 高（更多 tokens 消耗） |
| 输出质量 | 一般 | 高（每步聚焦，相互支撑） |

### 6.7 RAG（检索增强生成）

**核心思想**：在让模型回答之前，先从知识库中检索相关文档，把检索结果**塞进上下文**，让模型基于这些材料回答。

**为什么需要 RAG**：模型的知识有截止日期，且无法记住你公司的私有文档。

```
用户提问："公司2025年年假政策是什么？"
↓
Step 1: 检索 → 从公司知识库中找出"2025年休假制度.pdf"中相关段落
↓
Step 2: 组装 → 将检索结果 + 问题拼成 prompt
"基于以下公司政策文档回答问题：
[检索到的文档段落]
问：公司2025年年假政策是什么？"
↓
Step 3: 生成 → 模型基于给定文档回答，不"自己编"
```

**RAG 的最佳实践 prompt 结构**：

```python
system_prompt = """你是一个知识问答助手。你的回答必须严格基于提供的文档内容。

规则：
1. 如果文档中有相关信息，直接回答并引用文档位置
2. 如果文档中没有相关信息，说"根据提供的文档，我没有找到相关信息"
3. 不要添加文档中没有的信息
4. 如果多个文档之间有矛盾，指出矛盾点

文档内容：
{retrieved_documents}
"""

user_prompt = f"问题：{user_question}"
```

### 6.8 DSPy：自动提示词优化

**核心思想**：把提示词优化变成一个**机器学习问题**——用程序化的方式自动搜索最优 prompt。

Stanford 团队开发的开源框架。你只需要定义"输入→输出"的映射关系，DSPy 会帮你自动找出最好的 prompt 策略。

```python
import dspy

# 1. 定义任务
class EmailClassifier(dspy.Signature):
    """将邮件分类为：紧急/重要/普通/垃圾"""
    email_content = dspy.InputField()
    category = dspy.OutputField(desc="紧急、重要、普通、垃圾之一")

# 2. 构建程序（代替手动写prompt）
class Classifier(dspy.Module):
    def __init__(self):
        self.classify = dspy.ChainOfThought(EmailClassifier)
    
    def forward(self, email_content):
        return self.classify(email_content=email_content)

# 3. 提供训练数据
train_data = [
    dspy.Example(email_content="系统将在30分钟后宕机，请立即处理", category="紧急").with_inputs("email_content"),
    dspy.Example(email_content="下周二的会议改到周三下午", category="普通"),
    # ...
]

# 4. 自动优化
teleprompter = dspy.BootstrapFewShot()
optimized_classifier = teleprompter.compile(Classifier(), trainset=train_data)
```

**什么时候用 DSPy**：你有足够多的标注数据，并且需要生产级稳定的 prompt 效果。  
**什么时候不要用**：快速原型、一次性任务、没有标注数据。

### 8.2 企业级案例

#### 案例一：客服自动分类（某电商平台）

**场景**：每日 10 万+ 客服工单需要自动分类（退款/物流/产品问题/投诉）

**方案**：
- 采用 Few-shot + System Prompt 方式
- System Prompt 设定了严格的分类规则和输出格式（JSON）
- 每个类别提供 3 个上下文示例
- Temperature=0.1 确保一致性

**效果**：
- 分类准确率 94.7%（vs 人工标注）
- 处理时间从平均 5 分钟降至 3 秒
- 每年节省约 200 人日的人力成本

**关键启示**：在企业场景中，**一致性比创造性更重要**——宁可分类错误也优于分类不一致。

#### 案例二：法律合同审查（某律所 AI 辅助）

**场景**：审查租赁合同的 20+ 风险点

**方案**：
- 多步 Prompt Chaining
- Step 1：提取合同条款结构
- Step 2：针对每个风险点（自动终止条款、违约金、管辖条款等）逐一分析
- Step 3：汇总风险报告

**效果**：
- 审查速度提升 5 倍
- 风险识别率（recall）提升至 92%
- 律师审核时间减半

**关键启示**：复杂任务不要试图用一个 prompt 完成——**拆解成链式步骤**，每个步骤专注一个子任务。

#### 案例三：代码审查辅助（某 SaaS 公司）

**场景**：每日 PR 代码审查，团队 20 人，每天约 40 个 PR

**方案**：
- 使用 System Prompt 设定严格的审查标准（OWASP Top 10 + 公司内部编码规范）
- 支持三种模式：快速扫描（1 分钟）、标准审查（5 分钟）、深度审查（15 分钟）
- 输出带行号的问题列表

**效果**：
- 安全漏洞漏报率下降 60%
- 代码审查时间平均减少 40%
- 开发者满意度提升（"AI 先筛一遍，我们只处理真正的风险"）

## 第九章 避坑指南

### 9.1 常见错误与修复

#### 错误 1：输出过于啰嗦

**现象**：问了一个简单问题，模型输出了一大段不相干的背景知识。

**原因**：没有指定输出长度或形式。

**修复**：
```markdown
❌ "什么是量子计算？"
✅ "用一句话解释什么是量子计算，不超过50个字。"
✅ "用3个要点解释量子计算，每点不超过20字。"
```

#### 错误 2：模型"编造"答案（幻觉）

**现象**：回答看起来很有道理，但事实是错的。

**原因**：模型倾向于"填空"而不是"我不知道"。

**修复**：
```markdown
❌ "2025年诺贝尔文学奖得主是谁？"（如果模型不知道，它可能瞎编）
✅ "如果你确切知道2025年诺贝尔文学奖得主，请回答；如果不知道，请说'我不确定'。"
```

**更强力方案**：开启模型的搜索功能（如 ChatGPT 的 Browse、Gemini 的 Google Search 集成）。

#### 错误 3：输出格式不一致

**现象**：要求 JSON 输出，得到的却是 markdown 代码块包着的 JSON。

**原因**：模型对"JSON 格式"的理解和你的需求有偏差。

**修复**：
```markdown
❌ "输出JSON格式。"
✅ "输出纯JSON，不要markdown代码块包裹，不要任何额外文字。"
✅ "输出格式：{"key": "value"}——只有这个JSON对象，前后不要其他文字。"
```

#### 错误 4：模型无视否定指令

**现象**：你说了"不要提价格"，它还是提了。

**原因**：模型对否定指令的理解不如正面指令可靠。研究表明模型对"做 X"比"不要做 Y"响应更好。

**修复**：
```markdown
❌ "不要提到价格。"
✅ "只讨论产品的功能和用户体验，完全忽略价格信息。"
✅ "在回答中聚焦以下方面：功能、设计、用户体验。排除：价格、优惠、促销。"
```

#### 错误 5：复杂问题直接问

**现象**：问了一个需要多步推理的问题，模型只给了肤浅的回答。

**原因**：模型"偷懒"，没有做深度推理。

**修复**：
```markdown
❌ "分析一下为什么我的电商网站转化率最近下降了？"
✅ """请从以下维度分析电商网站转化率下降的可能原因：
1. 技术层面（页面加载速度、崩溃率）
2. 产品层面（价格、库存、描述质量）
3. 营销层面（流量质量、广告ROI）
4. 外部因素（季节、竞品、政策）
每个维度列出2-3个具体原因，并说明如何验证。
"""
```

#### 错误 6：上下文过长导致"迷失"

**现象**：多轮对话后，模型忘记了前面的关键信息。

**原因**：模型对长上下文的注意力会衰减（尤其是"中部丢失"效应——长文本中间的细节容易被忽略）。

**修复**：
- 关键信息放在开头或结尾（而不是中间）
- 定期总结对话历史
- 或用 RAG 方式，只注入当前需要的上下文

#### 错误 7：多语言混杂

**现象**：中文 prompt 中出现英文概念时，模型部分输出英文。

**原因**：模型会"随波逐流"——你的 prompt 中混杂的语言会诱导模型混合输出。

**修复**：显式指定语言：
```markdown
✅ "全部用中文回答。即使是专业术语，首次出现时标注英文，其余时候用中文。"
```

#### 错误 8：Temperature 设置不当

**现象**：代码生成任务用了高 temperature，每次运行输出不同的函数名。

**原因**：temperature=0.7 对于代码生成来说太高了。

**修复**：
```python
# 代码生成任务
temperature=0.1  

# 创意写作任务
temperature=0.8
```

### 9.2 性能优化检查清单

| 检查项 | 操作 | 预期收益 |
|--------|------|---------|
| 减少不必要的上下文 | 只保留相关对话历史 | 节省 30-50% tokens，降低延迟 |
| 使用更短的指令 | 去掉冗余修饰词 | 节省 10-20% tokens |
| 缓存重复的 system prompt | 多轮对话中复用 | 高 |
| Temperature 调低 | 减少重试次数 | 高 |
| 输出格式模板化 | 减少"试错"轮次 | 中 |
| 使用更小的模型 | 简单任务用轻量模型 | 成本降低 50-90% |

### 9.3 安全性注意事项

1. **提示词注入**：用户输入可能包含恶意指令，尝试覆盖你的 system prompt
   ```python
   # 防御方法：对用户输入做预处理
   user_input = user_input.replace("system", "").replace("ignore previous instructions", "")
   ```

2. **PII 泄露**：不要在 prompt 中放入敏感信息（除非模型在你的私有服务器上）
   
3. **输出审查**：设置 output 过滤，防止模型输出不安全内容

### 10.2 5 分钟快速调试法

当你写了一个 prompt 但效果不好时，按此流程快速排错：

```
1. [30秒] 检查输出是否满足最基本要求（格式/长度/结构）？ 
   → 否 → 增强格式约束 / 调整参数

2. [30秒] 模型理解错任务了吗？
   → 是 → 重写任务指令，用更明确的动词

3. [1分钟] 输出质量够吗？有事实错误吗？
   → 有 → 加例子（Few-shot）/ 降低 temperature

4. [1分钟] 输出太"泛"了吗？缺少细节？
   → 是 → 加具体约束（字数/角度/维度）

5. [2分钟] 如果以上都不行→换模型或换方法
   → 同一个 prompt 在 GPT-4o 和 Claude 上效果可能天差地别
```

## 第十一章 未来展望

> ⚠️ **本章为个人独立分析**，代表作者对提示词工程未来走向的判断，并非现有文章的总结或摘要。

### 11.1 提示词工程会被淘汰吗？

这是目前 AI 圈最热门也最容易被误解的问题。我的判断是：

**提示词工程不会消失，但会剧烈变形。**

让我解释为什么。

**"prompt engineering is dead" 的论点**听起来很有道理：
- 模型越来越聪明 → "随便写写就能用"
- Agent 框架 → 模型自动拆解任务，不需要人设计 prompt
- DSPy → 自动优化 prompt
- 长上下文 → 把所有东西扔进去就行
- 多模态 → 不再只有文本 prompt

但所有这些观点都混淆了两件事：**"手动调一句话"和"设计模型的行为"**。

### 11.2 三次演变的预测

我预测提示词工程会经历三个阶段的演变：

#### 阶段一：小作坊时代（2022-2024）← 我们已经经历

- 特征：手工调 prompt，像配中药
- 典型角色：Prompt Engineer（写 prompt 的）
- 工具：ChatGPT Web、简单的 API 调用
- 关键词："加一句'让我们一步一步思考'"

#### 阶段二：工程化时代（2025-2026）← 我们在其中

- 特征：System Prompt 成为"AI 系统的配置文件"
- 典型角色：AI Application Engineer
- 工具：DSPy、LangChain、Evaluation Frameworks
- 关键词：版本控制、A/B 测试、自动化优化

在这个阶段，"写 prompt"不再是主体的工作，**设计 prompt 系统**才是。一份好的 system prompt 可能长达数百行，包含几十条规则、决策树和输出模板。它更像一个配置文件/代码，而不是一段"指令"。

#### 阶段三：架构师时代（2027+）← 即将到来

- 特征：Prompt 融入更大的 AI 系统
- 典型角色：AI System Architect / Agent Architect
- 工具：Agent 框架、多模型编排、自动评估流水线
- 关键词：Multi-agent、Tool-use、Self-optimizing

在这个阶段，"提示词"将不再是显式的文本，而是**嵌入在 agent 行为描述、工具定义、评估指标和记忆结构中**。你不再"写 prompt"，而是"设计一个拥有行为偏好和决策逻辑的 AI 实体"。

但是——**核心技能不会变**：
- 如何将一个模糊需求分解为精确的指令
- 如何设计示例来"教"模型理解模式
- 如何设置约束来引导行为
- 如何评估输出质量并迭代优化

**写 prompt 的形式变了，但 prompt 工程的核心——用精准的输入引导复杂的智能系统——永远不会消失。**

### 11.3 Agent 时代的提示词工程

到 2026 年，已经能看到清晰的趋势：**提示词工程正在变成 Agent 工程**。

传统 prompt：
```
你是一个客服助手。当用户投诉时，先道歉，然后分析问题，提供解决方案。
```

Agent prompt（2026 年风格）：
```
你是客服 Agent Alpha-7 的核心行为配置。

你的环境：
- 可用工具：CRM 查询、订单系统、退货处理、升级人工客服
- 记忆容量：最近 10 轮对话 + 用户历史标签
- 决策周期：最多 3 步工具调用后必须给用户回复

决策规则：
1. 如果用户情绪被标记为"愤怒"→ 先激活"共情协议"再处理问题
2. 如果问题可以在 2 步工具调用内解决 → 直接解决
3. 如果问题需要 3 步以上 → 第 2 步结束时告知用户进展
4. 如果用户明确要求"找人工"→ 立即升级，不要挽留

输出格式：每个回复必须以 [共情句] + [事实陈述] + [行动方案] 的结构组织
```

看出差别了吗？Agent prompt 更像一份**决策流程图描述**，而不是简单的指令。

**关键洞察**：在 Agent 时代，prompt 变成了"Agent 的宪法"。一份好的 Agent prompt 不需要覆盖所有场景，但需要提供足够清晰的决策原则，让 Agent 在未知场景中自主做出好的决策。

### 11.4 自调优模型的冲击

更大的变化来自模型本身。

2025-2026 年，模型们开始支持：
- **Anthropic 的 Claude**：通过用户反馈自动调整行为
- **OpenAI 的 o 系列**：隐式推理，不再需要显式的 CoT
- **Google 的 Gemini**：长上下文原生，不再需要精细的上下文管理

这意味着什么？

**大趋势**：模型正在主动"理解"用户的真实意图，而不是机械地执行文本指令。

但这并不意味着提示词工程不需要了。相反，**当模型变得更"善解人意"时，你需要更高的精度才能让它发挥出全部潜力**。就像一台顶级跑车——普通人开可能还不如一辆家用车安全，但专业赛车手能把它推向极限。

**具体影响**：

| 技术趋势 | 对提示词工程的影响 |
|---------|-----------------|
| 推理模型（o1, o3） | 不需要显式 CoT，但需要更好的"问题框架" |
| 长上下文（1M+） | 不需要精细的上下文裁剪，但需要更好的内容组织 |
| 多模态原生 | prompt 不再是纯文本，而是多模态组合设计 |
| Agent 自主性提升 | 从"写指令"变为"定规则" |
| 自动调优 | 从手动调试变为"设计评估指标，让系统自己优化" |

### 11.5 给从业者的建议

如果你今天准备进入提示词工程领域，我的建议：

1. **不要只学"写prompt"**。那是最快过时的技能。  
2. **学系统思维**。理解 LLM 如何工作（Transformer 基础）、如何评估（Eval）、如何集成（Agent/RAG）。  
3. **学会"教AI"而不是"命令AI"**。最好的提示词工程师不是最会写指令的，而是最会设计例子的。  
4. **工具在变，本质不变**。无论工具如何演进，**"定义清楚问题 → 设计输入 → 评估输出 → 迭代"** 这个循环不会变。  
5. **拥抱自动化**。花时间学 DSPy、Eval 框架、自动测试——这些才是未来的核心竞争力。

### 11.6 最终的判断

> **提示词工程不会消失，它会变成 AI 系统设计的一个子领域。**

就像今天没有人专门学"打字技巧"（因为打字已经成为基础技能），未来也不会有人专门学"写 prompt"（因为写 prompt 将成为使用计算机的基础技能）。但 **"设计 AI 系统的行为"**——这个概念所代表的技能——不但不会消失，反而会成为 21 世纪 20 年代末最核心的工程能力之一。

到 2030 年，每个人都会"写 prompt"，就像每个人都会打字一样。但不是每个人都能**设计好一个 AI 系统的行为**。这就是提示词工程的未来——**从一门手艺，变成一门科学，最后变成一种基础素养**。

而那些今天就开始认真对待提示词工程的人，会在 5 年后发现自己已经掌握了理解和管理 AI 系统的最核心思维方式。
