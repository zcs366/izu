从龙虾切到 Hermes 也有一段时间了，但一直在将它作为一个升级版的龙虾在用，直到看到这篇文章《15 Hermes Agent features you’ve never touched》，才发现我对他的使用太浅了。整理了一下，希望对使用 Hermes 的你有帮助。

Hermes 真正有价值的地方，不在于“回答得更聪明”，而在于它围绕长期记忆、会话状态、文件回滚、多模型路由、多平台触达、定时任务、Webhook、Skills 工作流，搭了一套完整的 Agent Harness。

原文提到 15 个很多人没碰过的 Hermes 能力，这里从 Agent 工程视角重新解释：这些功能到底解决了什么问题，以及每个功能在实际工作里应该怎么用。
一、最容易被跳过的基础设置：让 Agent 先“成为一个人”
1. /personality + SOUL.md：别再每次都写“你是一个资深专家”
很多人每次开启新对话，第一句都是：

“你是一个资深架构师……”

但在 Hermes 里，这类长期设定应该沉淀到 SOUL.md。

SOUL.md 是 Hermes 启动时读取的核心人格文件。你可以在里面定义 Agent 的说话风格、边界、目标用户、默认判断方式，以及它应该如何拒绝不合理请求。

/personality 则允许你在不同人格之间切换。

这背后的价值是：不是让 Agent “本轮更听话”，而是让 Agent 拥有稳定的工作身份。

对于真正长期使用 Agent 的人来说，人格不是 Prompt，而是系统配置。

实际怎么用：

如果你主要把 Hermes 用来做公众号、技术研究和工程复盘，可以先把 SOUL.md 写成这样：

# SOUL.md你是一个偏工程化视角的 Agent 研究助手。你的目标不是简单回答问题，而是帮助我把碎片信息整理成可复用的观点、文章、SOP 和工作流。你默认会：- 先提炼核心观点；- 再结合实际场景解释；- 最后给出可执行步骤；- 避免空话、套话和营销腔。

以后再写文章、整理会议纪要、拆 Agent 架构时，就不用每次都重新告诉它“你要像一个懂工程的人一样回答”。

如果你有多个使用场景，比如“技术顾问”“公众号编辑”“代码审查助手”，可以分别定义不同 personality，然后用 /personality 切换。
2. MEMORY.md + USER.md：别再反复介绍你是谁、项目是什么
Hermes 还有两个长期记忆文件：

MEMORY.md：记录项目事实，比如当前系统架构、业务背景、长期决策、历史约束。

USER.md：记录用户偏好，比如你的角色、表达风格、取舍倾向、工作上下文。

原文提到，Hermes 会用 FTS5 和 LLM 摘要机制帮助检索历史记忆。也就是说，几周前的项目背景，今天仍然可以被带回当前会话。

这解决的是 Agent 使用中一个非常常见的问题：每次开新会话，都像重新入职一次。

真正的 Agent 不应该只记住当前窗口，而应该知道“你是谁”“你正在做什么”“你之前为什么这么选”。

实际怎么用：

先把 USER.md 写清楚，记录你这个人的长期偏好：

# USER.md我是某 ToB AI 公司的工程/产品负责人，主要关注 Agent 工程化、视觉 AI、零售数字化、云边协同、交付验收和团队效率。我的输出偏好：- 喜欢结构化表达，先讲结论，再讲逻辑；- 写公众号文章时，希望有观点、有案例、有工程落地；- 不喜欢空泛概念，所有观点最好能落到真实工作流；- 默认使用中文输出。

再把 MEMORY.md 写成项目事实库：

# MEMORY.md当前重点项目：1. Agent 工程化文章系列：围绕 Harness、Skill、可观测性、评估、长期记忆展开；2. 企业内部 AI 工作流改造：希望把周报、会议纪要、日志排障、代码分析、知识库整理逐步 Agent 化；3. 公众号内容方向：AI Agent、工程实践、ToB AI 落地、大小模型融合。长期判断：- Agent 不是聊天机器人，而是可持续运行的工作流系统；- Skill 是 Agent 工程化的基本单元；- 可观测、回滚、权限、成本控制，是 Agent 从 Demo 走向生产的关键。

每周复盘结束后，还可以让 Hermes 帮你筛选哪些内容值得写回 MEMORY.md：

请从本周复盘中筛选值得写入 MEMORY.md 的长期事实，只保留项目方向、关键决策、长期约束和稳定偏好，不要记录临时任务。

这样每周总结就不会只是一次性输出，而会逐渐沉淀成 Agent 的长期上下文。
3. /insights [days]：让你知道 Agent 时间都花在哪了
/insights 30 可以查看最近 30 天的使用分析：哪些项目消耗 token 最多，哪些模型成本最高，Agent 经常卡在哪些任务上，你反复在问什么问题。

这看起来像统计报表，但本质上是 Agent 可观测性。

很多人只关注单次对话是否成功，却很少回头看：

我到底把 Agent 用在了哪些工作上？

哪些任务值得沉淀成 Skill？

哪些工作一直在重复消耗 token？

如果说日志是系统的可观测性，那么 /insights 就是个人 Agent 使用行为的可观测性。

实际怎么用：

建议把 /insights 7 变成每周一的固定动作：

/insights 7

跑完后，不要只看数据，可以继续追问：

基于过去 7 天的 /insights，帮我总结：1. 我本周最常使用 Hermes 处理的 3 类任务；2. 哪些任务值得沉淀成 slash command；3. 哪些任务成本较高，可以考虑换便宜模型或拆成辅助模型；4. 给我一个本周 Agent 使用优化建议。

这一步的价值是，把“我感觉最近一直在忙”变成可分析的数据。

如果你发现自己一周内反复让 Hermes 做会议纪要、代码分析、公众号草稿，那就说明这些不是一次性任务，而是应该沉淀成 Skill 的高频工作流。
4. /snapshot：给 Agent 配置做快照，而不是改崩了再后悔
/snapshot 可以保存当前 Hermes 的配置和状态。后续如果你改坏了配置，比如重构 SOUL.md、调整模型、改了一堆行为策略，还可以通过 /snapshot restore <id> 回到之前的稳定状态。

这件事非常工程化。

我们写代码知道要 commit，要 rollback，但很多人配置 Agent 时却是裸奔：今天改一点人格，明天改一点记忆，后天调一下模型，最后自己也不知道为什么 Agent 变蠢了。

Hermes 的快照能力，本质上是把 Agent 自身也纳入版本管理。

实际怎么用：

凡是要动长期配置前，先做一次快照：

/snapshot

尤其是这几类操作之前：
大改 SOUL.md；重构 MEMORY.md；批量调整模型配置；尝试新的 Skill 或自动化流程；准备开启比较激进的 /yolo 模式。
如果改完发现 Agent 输出风格变奇怪、记忆变乱、命令表现不稳定，就恢复到之前状态：

/snapshot restore <id>

你可以把它理解成：每次给 Agent “换脑子”之前，先打一个系统还原点。
二、会话过程中的控制能力：不要一错就重开5. /branch / /fork：像 Git 一样分叉一条对话路径
当你已经在一个复杂任务里积累了大量上下文，突然想尝试另一种方案，最笨的办法是新开一个会话。

问题是，新会话会丢掉前面辛苦构建的上下文。

/branch 或 /fork 的意义是：保留当前主线，然后分叉出一条支线去探索。

这很像 Git 分支。你可以在支线上尝试风险更高的方案，如果结果不好，再回到主线。

对于复杂研发任务、方案设计、文章打磨，这个能力非常关键。

实际怎么用：

比如同一份周复盘，你可能想生成两个版本：

一个是内部周报，强调进展、风险、下周动作；

另一个是公众号素材，强调观点、案例、方法论。

这时候不要在一条对话里来回拉扯，可以先保留主线，然后分叉：

/branch

在新分支里输入：

基于刚才的周复盘，不要写内部管理视角，改成一篇公众号选题草案，主题是“为什么 Agent 不是聊天机器人，而是工作流系统”。

这样一个分支做严肃周报，一个分支做内容创作。试错空间更大，也不会污染主线。
6. /rollback：Agent 改坏代码时，不一定非要靠 Git 救命
Hermes 会记录它动过的文件检查点。当 Agent 进行了破坏性修改，你可以用 /rollback 恢复。

这不是替代 Git，而是补了一层 Agent 操作级别的安全网。

Git 更像项目级版本管理；/rollback 更像 Agent 每次动手前后的局部保护。

如果你让 Agent 长时间改代码、重构目录、批量改配置，这个能力非常重要。

实际怎么用：

适合在这类任务里使用：

请帮我重构这个模块，把重复逻辑抽到 service 层，并更新相关测试。

或者：

请批量调整这个项目的配置文件，把旧的环境变量命名统一替换成新的规范。

这种任务一旦 Agent 改错，影响范围可能很大。执行前最好确认当前目录干净，执行后如果发现明显问题，先不要手动乱改，直接：

/rollback

然后再让 Agent 分析：

刚才的修改为什么会失败？请只给我修改计划，不要动文件。

这样可以把“Agent 改坏代码”从灾难，变成一次可回放、可复盘的操作。
7. /btw：临时问一句，但不要污染主线
/btw 是一个很有意思的命令：它可以使用当前上下文回答一个临时问题，但不会调用工具，也不会持久化到主会话。

适合这类场景：

“顺便帮我判断一下这个方案有没有坑。”

“这段代码是不是有明显问题？”

“这个命名是不是太怪？”

它解决的是主线污染问题。

复杂任务中，很多临时问题只是脑子里闪过的一句，不值得写进长期上下文，更不应该影响 Agent 后续判断。

实际怎么用：

比如你正在让 Hermes 写一篇 Agent 可观测性的文章，中途想到一个问题：

/btw 这里把 insights 类比成 Agent 可观测性，会不会有点牵强？

或者你正在做代码排障，中途想确认一个命名：

/btw 这个方法叫 buildSessionTrace 合适吗？有没有更好的命名？

这类问题只需要一个快速判断，不需要进入主线，也不需要写进记忆。用 /btw 会比新开会话更自然。
8. /steer 和 /queue：长任务跑到一半，也可以中途转向
Agent 一旦进入多轮工具调用，经常会出现一种情况：它已经跑起来了，但你突然发现它方向不对。

比如它正在用生产环境 API，而你希望它用测试环境。

普通做法是中断、重来。但 Hermes 可以用 /steer 给下一步工具调用注入修正指令，而不中断当前任务。

/queue 则可以把下一轮要做的事排队。

这类能力非常接近真正 Agent Harness 需要的“中途干预机制”。

不是所有 Agent 任务都应该一键到底。更理想的方式是：人可以在任务执行中轻量介入，但不破坏上下文和缓存。

实际怎么用：

比如 Hermes 正在整理一份周报，你发现它开始写成流水账了，可以直接：

/steer 本次周报请重点关注 Agent 可观测性和 Hermes 工作流，不要把会议纪要写成流水账。

如果你已经知道下一步要做什么，可以提前排队：

/queue 周报整理完后，继续帮我提炼 3 个适合公众号展开的选题，并给出标题和开头。

再比如它正在查日志，你发现环境不对：

/steer 后续查询都使用 staging 环境，不要访问 prod。

这种方式比“停掉重来”更适合长任务，因为它保留了上下文，也不会浪费已经建立好的 prompt cache。
9. /yolo、/fast、/reasoning：控制风险、速度和思考深度
Hermes 提供了一些运行模式开关：

/yolo：跳过危险命令审批，适合非常信任环境时使用，但要谨慎。

/fast：切换到更低延迟的处理模式。

/reasoning：调整推理模型的 reasoning effort。

这说明一个问题：Agent 不应该只有一种运行姿态。

有些任务要稳，有些任务要快，有些任务要深度推理，有些任务只是批量体力活。

成熟的 Agent 系统，应该允许用户在任务级别调整成本、速度和风险。

实际怎么用：

可以按任务类型选择模式：

写文章、做架构设计、分析复杂 Bug 时，用更高 reasoning：

/reasoning high

只是改格式、整理清单、批量生成标题时，用快一点的模式：

/fast
/yolo 只建议在低风险环境里用，比如临时 demo 项目、沙箱目录、已经有 Git 保护的本地仓库：

/yolo

我的建议是：生产环境、客户项目、重要代码库，不要轻易 yolo。Agent 提效的前提，是你知道它什么时候可以放手，什么时候必须拴绳。
三、多模型和多供应商：别被单一模型锁死10. /model [--provider] [--global]：Agent 状态不变，底层模型可切换
Hermes 设计上是 provider-agnostic 的。你可以在不中断 Agent 状态的情况下切换模型和供应商。

原文提到的供应商包括 Anthropic、OpenAI、OpenRouter、NVIDIA NIM、Kimi、Gemini、AWS Bedrock、Vercel AI Gateway 等。

这背后的关键不是“支持很多模型”这么简单，而是：Agent 的状态、工具、记忆、技能，应该和模型解耦。

模型是可替换的执行引擎，Agent Harness 才是长期资产。

实际怎么用：

建议按任务分层切模型：

复杂设计、核心文章、难 Bug，用最强模型；

批量整理、格式转换、轻量总结，用便宜模型；

临时 brainstorming，可以用速度更快的模型。

例如：

/model anthropic:claude-opus-4-7

用于复杂架构或深度文章。

/model openrouter:kimi-k2.6

用于相对便宜的资料整理和体力活。

关键点是：切模型时，Agent 的状态和上下文仍然保留。你不是在换一个聊天机器人，而是在给同一个 Agent 换发动机。
11. Auxiliary models：不要所有任务都用最贵模型
Agent 并不只是回答问题。

它还要做上下文压缩、会话总结、标题生成、视觉处理、摘要归档等辅助工作。

Hermes 支持给这些辅助任务单独配置模型。

比如主模型用强模型处理复杂推理，压缩和标题生成用便宜小模型。

这对成本控制非常关键。

很多 Agent 系统贵，不是因为核心推理贵，而是因为所有边角料任务都在用最贵模型。

一个成熟的 Agent 系统，应该有主模型，也应该有辅助模型分工。

实际怎么用：

终端直接运行：

hermes model

然后选择：

Configure auxiliary models

进去后会看到类似这些任务：

visionweb_extractsession_searchtitle_generationcompressionapprovalskills_hubmcpflush_memories

选择某个任务后，再选 provider 和 model。

可以这样理解：主模型负责“脑力活”，辅助模型负责“杂活”。

例如：
主模型：写方案、做推理、拆复杂问题；压缩模型：负责长上下文压缩；标题模型：负责生成会话标题；总结模型：负责会话摘要、周报初稿、归档摘要。
如果你发现 /insights 里 token 成本很高，可以优先检查这些辅助任务是不是都在用强模型。

实际落地时，可以先做一个简单原则：凡是“不需要深度推理，只需要整理和压缩”的任务，都不要用最贵模型。
四、触达和自动化：Agent 不应该只待在一个聊天窗口里12. 17 个平台网关：让 Agent 去团队真正工作的地方
Hermes 支持 Telegram、Discord、Slack、WhatsApp、Signal、Email、SMS、Matrix、Mattermost、飞书、企业微信、钉钉等多个平台。

这说明 Hermes 的目标不是做一个单点聊天窗口，而是成为跨平台 Agent Gateway。

对企业来说，这点尤其重要。

因为真正的工作流并不发生在一个 App 里：研发在 GitHub，沟通在飞书/钉钉，告警在 Slack，任务在 Linear/Jira，文档在 Notion。

Agent 如果只能待在一个窗口里，就很难进入真实工作链路。

实际怎么用：

一开始不要贪多，先接一个你每天都打开的平台。

如果你个人使用 Telegram，就先接 Telegram；如果团队工作主要在飞书/钉钉，就优先接团队 IM；如果研发流程在 Slack，就先接 Slack。

然后给不同平台定义不同用途：
私聊：个人研究、临时想法、文章草稿；团队群：周报、告警摘要、任务提醒；邮件：较正式的外部沟通；CLI：代码、日志、文件操作。
不要一开始就追求“17 个平台全接上”。真正重要的是，让 Agent 进入你已经存在的工作流，而不是额外制造一个入口。
13. /voice：语音不是噱头，而是降低输入摩擦
Hermes 支持 CLI、Telegram DM、Discord 频道、Discord 语音频道里的实时语音。

这类能力看似不是核心，但在很多场景里很实用：走路时、开车时、临时记录想法时，语音比打字更自然。

对于 Agent 来说，输入摩擦越低，它越容易变成日常工作流的一部分。

实际怎么用：

适合这几类场景：

/voice

然后直接说：

帮我记录一个文章想法：Agent 可观测性不是监控模型，而是监控任务链路，包括输入、工具调用、状态变化、失败原因和成本。

或者：

帮我把刚才这个想法整理成 3 个公众号标题，明天我再展开。

语音最适合用来捕捉“还不成形的想法”。不要一开始就要求它生成完整文章，而是先让它帮你把灵感变成结构化素材。
14. Cron + /webhook-subscriptions：一个负责定时拉，一个负责被动收
Hermes 内置 Cron 调度。你可以用自然语言描述计划任务，比如：

每周五 5 点，总结本周 GitHub commits，并发到 Slack 的 standup 频道。

/webhook-subscriptions 则是反方向：外部系统把事件推给 Hermes，比如 GitHub、Vercel、Stripe、可用性监控等。

一个是定时主动执行，一个是被动接收事件。

这两个能力组合起来，Hermes 就不只是“你问我答”，而是可以进入事件驱动和定时执行的自动化系统。

从这个角度看，很多人用 Zapier 做的事，Agent Harness 其实也可以承担一部分。

实际怎么用：

最适合先落地的是每周固定任务。

比如每周五下午 5 点，自动生成一份周报草稿：
