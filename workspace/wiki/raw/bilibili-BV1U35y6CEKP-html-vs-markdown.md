### 一、开篇：一篇引爆开发者社区的文章

**[00:00]**

大家好，我是AI启示录。

最近科技圈有一个讨论特别火——火到什么程度呢？一篇来自 Anthropic 内部工程师的文章，在 X 平台上线不到48小时，就获得了超过780万的阅读量，12000多次转发，2万多人收藏。

这篇文章的标题很简单，叫《HTML的不合理有效性》[^1]。但它真正引爆讨论的，是文章里的一句话：**"HTML是新的Markdown。"**

说这句话的人叫塔里克·西帕尔（Tariq Sepah）[^2]。他不是什么普通的开发者，而是 Claude Code[^3] 团队的核心工程师。

更有意思的是，不只是他一个人这么做——Claude Code 团队里越来越多的人，都已经放弃了 Markdown，全面转向了 HTML。

这个消息一出来，整个开发者社区直接炸锅了。要知道，Markdown 已经统治了技术文档领域整整十年。从 GitHub 的 README 到技术博客，从会议记录到 API 文档，几乎所有技术相关的文字内容，都是用 Markdown 写的。它简单、轻量、跨平台，几乎是所有开发者的通用语言。

现在，创造了目前最强编程 AI 之一的团队，自己先把 Markdown 给抛弃了。这到底是怎么回事？是 Markdown 真的不行了，还是 AI 时代的工作流发生了我们还没意识到的根本性变化？

今天这期视频，我们就来把这件事彻底讲清楚。

### 二、塔里克其人

**[01:22]**

先给大家介绍一下塔里克这个人——他的履历非常有意思。

MIT 媒体实验室硕士毕业，是 YC W20 批次的创业者[^4]，创办过一家游戏公司，融了1700万美元。后来他卖掉了自己的 SaaS 产品，在一年多前加入了 Anthropic。

用他自己的话说，他加入 Anthropic 的原因是"AI精神病发作"——觉得 Claude Code 就是软件开发的未来，于是放下一切，All in 了进来。

他在 Claude Code 团队里，同时负责工程、内容和用户反馈三条线。我们现在用 Claude Code 时非常熟悉的一个功能——当 AI 信息不够时，会主动向你提问，而不是瞎猜——就是他设计的。

今年3月份，他写过一篇关于 Claude Code 内部如何使用 Skills 的长文，当时也在行业里引发了不小的震动。那篇文章里透露，Anthropic 内部有几百个活跃的 Skills 在运行，远比外界想象的要多得多。

而这次，他不仅写了文章，还把自己和团队日常使用的20个 HTML 文件，全部开源在了 GitHub Pages 上，按用途分成了九大类。每一个都是单独的 HTML 文件——不需要安装任何东西，浏览器打开就能直接用。

这些案例看完，你大概就能明白，为什么他们会放弃 Markdown 了。我挑几个最有代表性的，给大家讲一讲。

### 三、三个核心场景

#### 场景一：代码审查（Code Review）

**[02:34]**

第一个，也是开发者反映最强烈的场景——**代码审查**。

我们平时在 GitHub 上看 PR 的 Diff，就是一行行的代码：左边是旧版本，右边是新版本，用加号和减号标记改动。如果改动比较大、文件比较多，看起来会非常累，而且很难一眼看出哪些改动是关键，哪些是无关紧要的。

塔里克的做法是：让 Claude Code 审查一个 PR，直接生成一个 HTML 页面。这个页面里有完整的 Diff 渲染，但和 GitHub 不一样的是，每一段改动旁边都有**内联注释**，而且每条注释都按严重程度做了颜色编码：

- **红色**：必须修改的 Blocking 级问题
- **黄色**：值得一看的建议
- **绿色**：写得不错的地方

最绝的是，页面顶部有一张**风险地图**——6个被修改的文件，用不同颜色标注了风险等级。你扫一眼就能立刻知道，应该重点审查哪个文件。页面底部还自动生成了修复建议清单。

塔里克说，他现在每次 PR 都会附带一个这样的 HTML 代码审查页，体验比 GitHub 默认的 Diff 视图好得多。

原因很简单：**代码的 Diff 本质上是空间信息，Markdown 把它压平成了一维的文字，而 HTML 能把它还原回二维的空间结构。**

#### 场景二：交互式技术教程

**[03:46]**

第二个例子——**交互式技术教程**。

如果让 Claude 用 Markdown 解释"一致性哈希"（Consistent Hashing）这个概念，它大概会给你写两页干巴巴的文字，再加上一张用 ASCII 字符画的圆圈。你得一边读文字，一边在脑子里想象那个哈希环的结构，以及节点增减时 key 是怎么重新分配的。

但换成 HTML 之后，情况就完全不一样了。塔里克展示的这个一致性哈希教程，页面上直接画了一个**可交互的环**。四个节点，32个 key 分布在环上，每个节点用不同颜色标注它管辖的弧段。你可以点击"加一个节点"或者"删一个节点"的按钮，实时看到 key 的重新分配过程。

旁边还有一张对比表，清晰地展示了传统取模哈希方法和一致性哈希在节点变化时的数据迁移量差异。页面底部是一个悬停高亮的术语表——鼠标移到哪个术语上，就会显示对应的解释。

同样的内容，一个是让你读文字然后脑补，一个是让你直接操作和观察。哪个学习效率更高？不言而喻。

#### 场景三：用完即弃的编辑器

**[04:43]**

第三个，也是我觉得最有启发性的一个概念——**用完即弃的编辑器**。

比如，你有24个工单需要重新排序。如果用传统的方式，你可能会在聊天框里一条条告诉 AI："这个放第一位，那个往后挪两位，这几个先不做。"或者你会打开一个 Markdown 文件，手动调整列表的顺序。

但塔里克的做法是，让 Claude Code 直接生成一个 HTML 文件——每个工单是一张**可拖拽的卡片**，页面上有"现在""下一步""稍后""砍掉"四列。Claude 会先用自己的判断做一轮预排序，你只需要做少量的拖拽微调。调完了，点一下底部的"复制为 Markdown"按钮，就能导出最终顺序。

再比如微调系统提示词（Prompt）。Claude 会生成一个左右对照的编辑器：左边是可编辑的提示词，变量槽位会被高亮显示；右边实时渲染三个样例输入的效果；底部还有字符和 Token 计数器。

这些工具不是什么复杂的产品，也不是可复用的组件——它们就是为当前这一个特定任务量身定制的、用完就扔的单 HTML 文件。任务完成了，这个文件也就没用了。

更关键的是，这里面引入了一个非常重要的概念——**双向交互**。HTML 文档不再是只读的了。你可以在页面里进行操作——AI 生成的滑块、旋钮、拖拽区域都是活的。你调完参数之后，点一下"导出"按钮，就能把结果转换成文本，再粘回 Claude Code，Claude 继续干活。这样就形成了一个完整的闭环：

> 人给 AI 指令 → AI 生成 HTML 工具 → 人在工具里操作调整 → 把结果导回给 AI → AI 再继续执行

在这个闭环里，**AI 生成的不再是文档，而是工具。**

### 四、更多用法

**[06:21]**

除了这三个核心场景，塔里克的案例库里还有很多有意思的用法。

比如**周报**——不再是干巴巴的文字列表，而是配上小图表和彩色时间线，经理周一早上扫一眼就够了。

比如**实施计划**——把时间线、里程碑、数据流图、内联圆形图、风险表，全部塞在一个页面里。Markdown 写的计划是说明书，HTML 写的计划是仪表盘。

还有**设计系统可视化**——Claude 可以直接读取代码库，把颜色变量渲染成色板，把组件的所有尺寸、状态、变体铺在一张表上。

还有**动画原型**——你可以拖动滑块，调整缓动曲线和动画时长。调完参数，一键复制回代码。

甚至还有用单个 HTML 文件做的**幻灯片**——不用打开 Keynote，不用导出 PDF，浏览器打开就能演示。

### 五、Markdown 到底怎么了？

**[07:10]**

看到这里，很多人可能会问：Markdown 到底怎么了？它不是挺好的吗？为什么突然就不行了？

塔里克的判断，建立在两个非常关键的变化上。

**第一个变化：AI Agent 的输出越来越复杂。**

一份超过100行的 Markdown 文件，塔里克坦言自己读不下去，也别想让团队里的其他人读下去。这其实是一个非常普遍的痛点——现在我们用 AI 写东西，很容易就会得到一份几百行甚至上千行的文档。一份技术方案，AI 可以把背景、目标、设计、实现、测试、风险全部给你写得清清楚楚，看起来非常完整。

但问题是：你真的会从头到尾读完吗？大多数时候，我们都是打开扫一眼，觉得大概没问题，然后就让 AI 继续执行了。不是因为内容不好，而是因为它太长、太平、太像一堵文字墙了。

Markdown 的表达方式是线性的——标题下面是段落，段落下面是列表，列表下面是代码块。短的时候很清楚，一长就非常考验人的耐心。

**第二个变化：人们越来越少亲自编辑这些文件了。**

规范文档、参考资料、头脑风暴的输出，大多数时候都是让 Claude 来写。真要改的时候，也不是自己打开文件一点点改，而是继续对 Claude 说"这里改一下，那里重写一下"。很多文件从头到尾，你可能一个字符都没有亲手敲过。

这就意味着，Markdown 最大的优势——**易于编辑**——被彻底架空了。Markdown 统治开发者工具链十几年，靠的是一个核心假设：**人要亲手编辑文件**。所以它的所有语法设计——标题用井号，加粗用星号，列表用横杠——都是为了让人类用手指打字的时候更方便。所有符号都在键盘上触手可及。

但当写文件的人从人变成了 AI，这个假设就不成立了。

对于 AI 来说，写 HTML 和写 Markdown 没有本质区别，甚至 HTML 能表达的东西更多。而对于看文件的人来说，有颜色、有布局、有交互的 HTML 阅读体验，显然比纯文本的 Markdown 好得多。

还有一个容易被忽略的好处是：分享 Markdown 文件，大多数浏览器原生渲染效果都不好，你通常只能把它当附件塞进邮件，或者贴到飞书、Notion 这样的在线文档里。而 HTML 只要传到 S3 上就有链接，同时在哪里都能打开。

塔里克说：**"如果你的方案是 HTML 格式的，别人真的会去读它的概率，比 Markdown 高得多。"**

当然，HTML 也不是没有缺点。塔里克自己也承认，生成 HTML 的时间比 Markdown 慢2到4倍，版本控制的 Diff 乱得没法看，而且确实更臃肿难看。

但他提出了一个非常有力的反问：**你真的会去读 HTML 生成的东西，而 Markdown 的长文档，大概率你划两下就关了。读了和没读——这个差距可比那点 Token 效率大多了。**

换句话说：**当瓶颈从 Token 数量变成了人的注意力，格式的选择逻辑就彻底翻转了。**

### 六、Markdown 派 vs HTML 派：一场没有必要的争论

**[09:55]**

这件事在网上引发了非常激烈的争论，迅速分成了针锋相对的两派。

一派是坚定的 Markdown 党，觉得 Markdown 才是 AI 时代的源代码。另一派是 HTML 党，觉得塔里克发现了一个了不起的真相。

但在我看来，这场争论其实非常没有必要——因为两边说的根本就不是一回事。

有一位开发者说得特别好：**"MD 党回答的是'我们用什么写'，HTML 党回答的是'我们给人什么看'。这两个根本不是同一个问题，怎么会有谁取代谁呢？"**

我们来看看 Markdown 党的论据。

去年8月，OpenAI 发布了 AGENTS.md——就一个 Markdown 文件，放在项目根目录，告诉 AI Agent 怎么干活。一年时间被6万多个开源项目采用。Cursor、Devin、Claude Code、GitHub Copilot 全部支持。

去年12月，Linux 基金会直接成立了 Agentic AI 基金会，把 AGENTS.md 捐出去做开放标准。白金成员包括 AWS、Anthropic、Google、Microsoft——基本是 AI 行业的半壁江山，一起给 Markdown 站台。

今年4月，安德烈·卡帕西（Andrej Karpathy）开源了 LLM Wiki，核心架构就是三层 Markdown：raw 目录放原始资料，wiki 目录放 AI 写的概念页和索引，Claude 定义 Schema 和规则。仅仅那个 CLAUDE.md 文件，单日就涨了7900个 Star，现在已经快5万了——一个 Markdown 文件，5万 Star，这在 GitHub 历史上都是非常罕见的。

Cloudflare 的实测数据显示：同一篇博客，HTML 需要16180个 Token，转成 Markdown 只要3150个，压缩了80%。这意味着同样的 LLM 预算，可以处理7到17倍的请求。

GitHub 官方博客今年也说了一句非常经典的话：**"文档不再是描述代码——文档就是代码。自然语言被编译成下层语言，恰好长得像 Python 或者 JavaScript。"**

这些证据都非常硬，完全可以得出"Markdown 才是这个时代的源代码"的结论。

但 HTML 党的论据同样硬。塔里克说的空间信息、动态体验、结构化阅读、双向交互——每一条都是真实存在的痛点。Anthropic 今年4月推出的 Live Artifacts，已经把 HTML 从静态产物升级成了持久化、可交互、能拉实时数据的仪表盘。

塔里克有一句话我印象特别深：**"我用 HTML 的真正原因，是我感觉自己和 Claude 之间的关系更紧密了。HTML 让他重新感觉自己在 AI 协作中在场，而不是一个只会说'好的、继续'的旁观者。"**

所以你看，两边都赢了——因为他们摸到的是同一头大象的不同部位。真正的答案其实非常简单：**Markdown 和 HTML 不是替代关系，而是分工关系。**

### 七、AI 时代的解耦：生产和消费各自登顶

**[12:35]**

以前 Markdown 和 HTML 也有过论战。那时候 HTML 是默认——博客、文档、官网都是 HTML。后来 Markdown 兴起，因为它写起来快、看起来干净。那个论战的隐含前提是：**生产者和消费者是同一个人**。你写一份文档，自己看或者写给同事看，写的人和读的人都是人，所以选格式要折中——既要好写，又要好看。Markdown 胜出，因为它的折中点最舒服。

但 AI 出现后，第一次出现了一个新情况：**生产成本可以被 AI 吸收**。你不再需要亲手编辑产物——HTML 因为太重而被嫌弃的那部分代价，由 AI 承担了。你只需要承担消费的部分。

这意味着，原来要折中的需求，被解耦成了两端的极端优化：

- **最优生产端要的是什么？** 轻快、可迭代、Token 效率高 → **那就是 Markdown。**
- **消费端要的是什么？** 丰富、可视化、可交互、好分享 → **那就是 HTML。**

两端各自登顶，中间那个折中位置没人需要了。

最干净的证据，其实就是塔里克自己——同一个工程师，3月份发了篇 Skills 使用指南，里面强调 Skills 不只是 Markdown 文件，但核心还是 Markdown。他在**生产端力推 Markdown**。5月份发了这篇《HTML的不合理有效性》，他在**消费端力推 HTML**。同一个人在两端各自做出了最优选择，互不打架。他自己就是这个分工的活样本。

第二个例子是卡帕西和莱克斯·弗里德曼（Lex Fridman）那对组合。卡帕西的 LLM Wiki 内核是 Markdown——所有原始资料、概念页、索引都是 Markdown。莱克斯·弗里德曼用了同款架构，但在外面加了一层，让 AI 生成动态 HTML 加 JavaScript——可以排序、过滤、调参、做交互、可视化。**内核是 Markdown，外层是 HTML。**不是莱克斯替换了卡帕西，是他在卡帕西的基础上加了一层消费层。两层各做各的事，不冲突，反而互相加强。

所以塔里克没错，Markdown 也没错——他们都对了一半。但只要还困在"Markdown vs HTML"这个二元对立的框子里，就永远只能拿到一半的真相。

**以前的工作流是：人写 Markdown，人看 Markdown。
现在的工作流是：人写 Markdown，AI 改 Markdown，AI 生成 HTML，人看 HTML。**

这才是 AI 时代真正的工作流。

当然，这并不是说 Markdown 就会消失——就像命令行不会消失一样，Markdown 也会一直存在。它依然是轻量文本、简单说明、长期维护文档的最佳选择。但它的统治地位可能真的到头了，至少在 AI 生成内容的消费端，HTML 会越来越成为默认的选择。

### 八、更深层的问题：如何保持参与感

**[15:16]**

这件事真正值得我们思考的，其实不是哪个格式更好，而是一个更深层的问题：**在 AI 能力越来越强的今天，我们如何保持自己的参与感，不被 AI 甩出去？**

塔里克在文章结尾说的那句话，我觉得是整件事最核心的价值。他说：

> "之前我开始担心，因为我不再深入阅读那些方案了，我只能放手让 Claude 自己做决策。但用了 HTML 之后，我感觉自己比以前任何时候都更在 Loop 里了。"

这才是问题的关键。

AI 现在太能写了。它可以给你生成一份看起来完美无缺的几百行方案。如果你用 Markdown，你大概率扫一眼就过了，然后让 AI 继续执行。表面上看，这是效率的提升。但实际上，你正在逐渐失去对整个过程的判断和控制。

而 HTML 带来的变化，是把人重新拉回到这个循环里。它让计划更容易读，让方案更容易比较，让代码变化更容易审查，让参数更容易调整，让结果更容易回传给 AI。**它没有让 AI 变得更独立，而是让人更容易介入。**

当 AI 的能力越来越强，人和 AI 之间的**信息带宽**就成了最大的瓶颈。对人的信息输入而言，如果说 Markdown 是一根水管，那 HTML 可以看作是一条马路。而我们未来要探索的，是如何把这条马路变成高速公路。

也许未来某一天，AI 给我们的交付物不再是静态的页面，而是可交互的视频——AI 不只是生成一个东西让你自己看，而是带着语音，像一个同事一样给你讲方案、走读代码、解释思路。你可以随时打断和提问。

但不管技术怎么发展，有一点是不会变的：**工具永远是为人服务的。最好的 AI 工具，不是把人排除在外的全自动工具，而是能让人更好地参与进来、发挥人的判断力和创造力的工具。**

Markdown 和 HTML 之争，本质上不是格式之争，而是 AI 时代人和机器如何更好协作的探索。塔里克和他的团队走在了前面。他们用自己的实践告诉我们：**当写的人变成了 AI，看的人还是人——那一切，就都应该围绕人的体验来重新设计。**

| 术语 | 原文 | 解释 |
|------|------|------|
| **HTML** | HyperText Markup Language | 超文本标记语言，网页的骨架语言。相比 Markdown，HTML 可以直接控制样式、布局和交互行为，无需经过中间转换 |
| **Markdown** | — | 轻量标记语言，用简单符号（`#` `*` `[]`）排版。优势是源码可读性强、编辑门槛低，但最终需转换成 HTML 才能渲染 |
| **Claude Code** | — | Anthropic 的 AI 编程助手，类似 Cursor / Copilot，可在终端中直接生成和修改代码 |
| **Anthropic** | — | 美国 AI 安全公司，Claude 模型的开发者，由前 OpenAI 员工创立。核心理念是"宪法式 AI"（Constitutional AI） |
| **Token** | 词元 | 大语言模型处理文本的最小单位。中文约 1-2 字/Token，英文约 0.75 词/Token。Token 数直接决定 API 调用成本 |
| **Diff** | — | 代码差异对比视图，用 `+`（新增）和 `-`（删除）标记改动行。GitHub PR 页面的核心组件 |
| **PR** | Pull Request | 代码合并请求。开发者完成修改后发起 PR，由同事审查（Code Review）后方可合入主分支 |
| **Blocking 级问题** | — | 代码审查中最高严重级别——必须修改后才能合并的问题，如安全漏洞、逻辑错误 |
| **一致性哈希** | Consistent Hashing | 分布式系统中分配数据的算法。相比简单取模，它在节点增减时只需迁移少量数据（通常是 1/N），是分布式缓存的核心技术 |
| **Agentic Workflow** | 智能体工作流 | AI 不止回答问题，而是自主规划步骤、调用工具、检查结果、迭代修正的完整工作链条 |

| **Live Artifacts** | — | Anthropic 2026年4月推出的功能：Claude 生成的 HTML 页面可以保持在线、实时更新数据，从一次性的静态产物升级为持久化仪表盘 |

| **S3** | Amazon S3 | 亚马逊的云存储服务。把 HTML 文件上传到 S3 即可获得一个公网可访问的 URL，相当于"一键部署网页" |
| **Schema** | 模式/结构定义 | 在 AI 语境中，指告诉 Claude 如何组织知识库的规则文件，定义了 raw → wiki → index 的三层结构 |
| **YC** | Y Combinator | 硅谷最知名的创业孵化器。W20 指 2020 年冬季批次。曾孵化 Airbnb、Dropbox、Stripe 等公司 |
| **缓动曲线** | Easing Curve | 动画中控制速度变化的曲线（如先快后慢），在 CSS/SVG 动画中广泛使用 |
| **信息带宽** | Information Bandwidth | 单位时间内人能从 AI 输出中吸收的有效信息量。HTML 通过颜色、布局、图表等视觉通道，比纯文本的带宽高得多 |
