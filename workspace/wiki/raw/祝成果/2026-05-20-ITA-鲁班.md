# 鲁班

## 理论约束回顾（墨子的判决）

1. ❌ 整个函数→单个FSQ向量：率失真不可行（容量 15-50 bits vs 需要 300-600 bits）
2. ✅ FSQ token 序列化：理论可行（等价于新 tokenizer）
3. ✅ 执行轨迹/行为签名的 FSQ 压缩：理论可行（熵小得多）

**本评估在约束 #2 和 #3 的范围内给出工程方案。**

---

## 工程方案 A：FSQ-Code Tokenizer（推荐优先）

### 架构
```
code → CodeBERT Encoder → 768d embedding → PCA 降维 (5-10d)
      → FSQ Quantize → FSQ tokens → Decoder/Projector → 恢复
```

### 工具选型

| 组件 | 选择 | 理由 |
|------|------|------|
| 编码器 | CodeBERT-base（125M params） | 免费、轻量、代码语义预训练 |
| 降维 | sklearn PCA | 确定性的，不需要训练 |
| 量化 | numpy FSQ（~50行自实现） | FSQ 本质上就是 round() + clamp() |
| 解码 | PCA 逆变换 | 确定性的 |
| 语义度量 | CodeBERTScore（F1 + cos sim） | 开源，与编码器一致 |
| 功能测试 | RTC（round-trip correctness） | DeepMind 开源，ICML 2024 |

### 工程复杂度
- 总代码量：约 300 行 Python
- 不需要 GPU 训练（仅推理）
- 运行时间：60 个样本 × 9 种配置 ≈ 30 分钟（CPU 即可）

### 是否重复造轮子？
否。FSQ 在 CV 领域验证过，但**代码域无人尝试**。CodeBERT→FSQ→RTC 这条链路是新鲜的。
RTC 论文本身做的是 code→NL→code，不是 code→compressed→code。

## 工程方案 B：Behavior-Signature FSQ（备选）

### 思路
不压缩代码本身，而是压缩代码在特定输入下的执行轨迹：
```
code + test_input → 执行轨迹（trace） → embedding → FSQ → 行为签名
```

### 优势
- 熵小得多（一条执行路径远小于整个函数）
- 对代码理解要求低（不需要理解代码语义，只需捕获执行行为）
- 可用于代码聚类、异常检测

### 劣势
- 丢失函数的通用性（换了输入就不行）
- 需要运行时执行，成本高
- 未压缩代码本身

### 工具选型
- 轨迹嵌入：可使用执行日志的 LLM embedding（如 text-embedding-3-small）
- 量化：同样 FSQ
- 验证：用原始代码在随机输入下执行比较

### 复杂度
- 需要实际运行代码（有沙箱风险）
- 不适合大规模部署

---

## 工程优先级建议

1. **P0（本周）**：方案 A——CodeBERT→PCA→FSQ→CodeBERTScore 基线
   - 20 工时，回答核心问题
2. **P1（下周）**：如果基线通过，集成到完整的 FSQ tokenizer
   - 训练一个轻量 decoder 从 FSQ tokens 恢复代码
3. **P2（长期）**：方案 B 作为补充，用于行为级代码理解

## 工程风险

1. PCA 降维到 5-10d 可能损失太多语义信息（但 FSQ 论文在图像域验证了 4-6d 即可）
2. CodeBERT 嵌入是否对代码的**功能语义**敏感，而非仅仅是表面结构？——需要商鞅的实验来验证
3. 如果 CodeBERTScore 对函数等价性不敏感（即两个等价代码的 CodeBERTScore 可能不高），需要换编码器（如 CodeLlama embedding）
