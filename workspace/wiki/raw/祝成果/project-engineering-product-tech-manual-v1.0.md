# 📐 项目·工程·产品 · 深度技术手册 v1.0

> **科技组织的三重基石：如何管理时间（项目）、质量（工程）、方向（产品）。**
>
> 写给：技术管理者、架构师、创业者——需要同时理解这三套逻辑的人。

---

## 第一章 概览与核心理念

### 1.1 三根支柱，三种逻辑

任何科技组织最终交付的价值，都来自**三个正交维度的合力**：

| 维度 | 定义 | 核心矛盾 | 代表角色 |
|------|------|---------|---------|
| **项目** (Project) | 临时性工作，有明确的起止时间和交付物 | 范围 vs 时间 vs 成本（铁三角） | 项目经理 (PM/TL) |
| **工程** (Engineering) | 系统的内在质量——正确性、可靠性、可维护性 | 速度 vs 质量（"先上线再说" vs "重构三个月"） | 工程师/架构师 |
| **产品** (Product) | 对外交付的用户价值——有用、可用、想用 | 用户需求 vs 技术可行性 vs 商业可持续 | 产品经理 (PM) |

**为什么三者容易混淆？** 因为在日常语言里，"做一个项目"、"做一个产品"、"做一个工程"听起来像同一件事。但实际上：

- 一个**产品**可以包含多个**项目**（微信是一个产品，它的支付功能上线是一个项目）
- 一个**项目**需要**工程**能力来执行（"重构数据库"这个项目需要工程能力）
- **工程**实践可以在**产品**生命周期中持续积累（技术债、代码规范、基础设施）

### 1.2 历史溯源：三者何时开始分化

| 年代 | 事件 | 影响 |
|------|------|------|
| 1950s | 系统工程的诞生（贝尔实验室、RAND） | 大型军工项目催生了系统化的工程管理思维 |
| 1970s | 软件工程概念正式提出（NATO 1968 会议） | "软件危机"让人们意识到编码不等于工程 |
| 1980s | PMI 成立，PMBOK 编纂 | 项目管理从通用管理学科中独立 |
| 1990s | 互联网兴起，"产品经理"概念从宝洁传入科技 | 快速迭代打破了瀑布模式，产品管理成为独立职能 |
| 2001 | 敏捷宣言发布 | 项目、工程、产品的边界开始融合——"可工作的软件"高于一切 |
| 2010s | DevOps + 持续交付 | 工程实践和项目节奏进一步融合——部署频率从天变成秒 |
| 2020s | AI/ML 工程化（MLOps） | 概率性系统打破了确定性工程假设，三者关系再次重构 |

### 1.3 核心洞见：这不是三种角色，是三种不可消除的张力

很多人幻想"只要找到一个好流程，三者就能和谐统一"。但事实上：

- **项目要确定性**（什么时候做完），**产品要灵活性**（根据反馈调整）——这是永恒张力
- **工程要完美**（没有技术债），**项目要交付**（技术债可以先欠着）——这是永恒张力
- **产品要最大限度满足用户**，**工程要保持系统简洁**——这是永恒张力

**好的管理不是消除张力，而是在张力中做清醒的权衡。** 某个阶段偏向哪一端、欠了什么债、什么时候还——这些才是真正需要的能力。

## 第二章 项目管理：从甘特图到 AI 时代

### 2.1 经典三约束（铁三角）

```
           范围 (Scope)
            /\
           /  \
          /    \
         /      \
        /________\
   成本(Cost)   时间(Time)
```

传统项目管理的核心公式：三者中任何一个变了，另外两个必须跟着变。**对铁三角撒谎是项目失败的第一大原因**——假装范围扩大了但时间和成本不变。

### 2.2 瀑布 vs 敏捷：不是"哪种更好"

| 维度 | 瀑布 (Waterfall) | 敏捷 (Agile/Scrum) |
|------|-----------------|-------------------|
| 适用场景 | 需求明确且不会变 | 需求不确定，需要探索 |
| 交付节奏 | 一次性大交付 | 每 1-4 周小交付 |
| 文档 | 前置，详细 | 刚好够用 |
| 变更成本 | 高（改需求 = 重做前面的阶段） | 低（下个 Sprint 调整即可） |
| 典型案例 | 基建、航天、政府合同 | 互联网产品、创业公司 |
| 核心风险 | 交出来发现不是用户想要的 | 没有整体架构，"拼凑"感 |

**敏捷不是"不做计划"，而是"做够近期用的计划，剩下的保持弹性"。**

### 2.3 Scrum 三件套

```
Sprint 回顾 ──→ Sprint 计划 ──→ 每日站会 ──→ Sprint 评审 ──→ 重复
  (我们怎么改进)  (这次做什么)  (今天卡在哪)  (做出来了什么)
```

| 仪式 | 频率 | 时长 | 核心问题 |
|------|------|------|---------|
| Sprint 计划 | 每 Sprint 一次 | 2-4 小时 | 这个 Sprint 做什么？怎么定义做完？ |
| 每日站会 | 每天 | 15 分钟 | 昨天做了什么？今天要做什么？有什么阻塞？ |
| Sprint 评审 | 每 Sprint 一次 | 1 小时 | 向干系人展示成果，收集反馈 |
| Sprint 回顾 | 每 Sprint 一次 | 1-2 小时 | 团队流程哪方面可以改进？ |

**Scrum 最常见的失败模式**：站会变成汇报会（每个人对着项目经理汇报，而不是互相通气）。站会的基本原则是**开发团队内部的同步会**，不是向上汇报。

### 2.4 看板 (Kanban)——另一种哲学

Scrum 是时间盒（固定长度 Sprint），看板是流控制（限制在制品数量）。

```
待办       进行中(≤3)    审查中(≤2)    完成
[Task A]    [Task C]      [Task E]      [Task H]
[Task B]    [Task D]                   [Task I]
[Task F]    ← WIP限制：最多3个
[Task G]
```

**看板 vs Scrum 选择指南**：

| 选 Scrum 当... | 选看板当... |
|--------------|-----------|
| 工作可以按固定周期规划 | 工作连续到达（如运维、客服支持） |
| 需要迭代节奏来建立团队默契 | 团队已经很默契，Sprint 的仪式感多余 |
| 干系人期望定期演示 | 干系人随时可以看板 |

### 2.5 AI/ML 项目的特殊性

ML 项目的 WBS（工作分解结构）和传统软件不同：

```
传统软件 WBS：
  需求分析 → 架构设计 → 编码 → 测试 → 部署

ML 项目 WBS：
  问题定义 → 数据收集 → 数据清洗 → 特征工程
    → 模型训练(可能需要多轮)
    → 模型评估 → 如果不行，回到数据收集/特征工程
    → 模型部署 → 在线监控 → 模型更新/回滚
```

**关键区别**：ML 项目有**数据依赖**和**概率性输出**两个传统项目管理框架无法直接处理的维度。数据质量不可控、模型效果不可预知——这使得传统的"固定范围+固定时间"的承诺在 ML 项目中几乎必然被打破。

**推荐实践**：
- 用**里程碑**代替精确的截止日期（"3月15日完成第一轮评估"而不是"3月15日模型上线"）
- 用**实验跟踪**代替任务清单（每个实验 = 一次假设+一次验证）
- 预留**探索缓冲**——Sprint 中 30% 的时间给实验性工作

## 第三章 工程：系统的内在质量

### 3.1 工程的核心指标

| 指标 | 含义 | 测量方式 |
|------|------|---------|
| **正确性** | 系统按预期行为 | 测试覆盖率 + 生产事故率 |
| **可靠性** | 系统持续正常运行 | 可用性 (99.9%/99.99%)、MTBF、MTTR |
| **可维护性** | 修改一个功能的成本不随时间指数增长 | 代码圈复杂度、耦合度、技术债评估 |
| **可扩展性** | 应对增长的能力 | 吞吐量/延迟曲线、水平扩展能力 |
| **安全性** | 抵御恶意行为的能力 | 渗透测试、漏洞扫描、安全审计 |

### 3.2 技术债——工程维度最重要的概念

Ward Cunningham 在 1992 年创造了这个比喻：**技术债 = 为了短期交付速度而牺牲的长期代码质量，它会像金融债一样产生"利息"。**

```
技术债类型：
├── 故意的 (Deliberate) —— "我们知道这写得不好，先上线再说"
│   代价：可控，但要记在账上，计划还债时间
├── 不小心的 (Inadvertent) —— "写完才发现设计有问题"
│   代价：通过 code review 减少这类债务
└── 战略性的 (Strategic) —— 老系统已经不适应新需求
    代价：不是还旧债，而是建新系统（重写/迁移）
```

**技术债的管理框架**：

```
1. 可视化：代码里用 TODO/FIXME/HACK 标记，或专门的债登记表
2. 量化：估算每笔债的"利息"（每周多花多少时间绕开它）
3. 优先还：利息最高的先还，而不是"最旧的"或"最好改的"
4. 纳入节奏：每个 Sprint 固定 15-20% 时间清理技术债
```

### 3.3 架构决策——工程的顶层设计

架构不是在白板上画方块和箭头。架构是对**不可逆决策**的管理。

```
每做一个技术决策，问自己：
  这个决策以后需要改的代价有多大？
  
  低代价（可逆）→ 快速决定，错了再改
  高代价（不可逆）→ 推迟决定，收集更多信息
```

**架构决策记录 (ADR)**：一个被低估的工程实践。每次做重大架构决策时，写一份半页纸的文档，记录：

```
# ADR-001：选用 PostgreSQL 作为主数据库

状态：已接受
日期：2026-01-15
决策：使用 PostgreSQL，不使用 MySQL

背景：新系统需要强一致性、JSON 查询和地理空间支持
选项：
  - PostgreSQL：JSON 支持好，GIS 拓展成熟，生态丰富
  - MySQL：团队更熟悉，但在 JSON 查询上较弱
后果：
  - 正面：更丰富的数据类型和查询能力
  - 负面：团队学习成本、部分 ORM 特性需要适配
```

**ADR 的价值不在于记录本身，在于它强迫你做决策时思考后果。**

### 3.4 CI/CD——工程的自动化骨干

```
CI (持续集成)          CD (持续交付/部署)
   │                      │
   ▼                      ▼
提交代码 → 自动构建 → 自动测试 → 自动部署(到staging) → (可选)自动部署到生产
```

| 实践 | 成熟度阶梯 |
|------|----------|
| 有版本控制 | Lv 0（不用 Git 的不叫工程） |
| 有自动构建 | Lv 1（能一键编译/打包） |
| 有自动测试 | Lv 2（每次提交跑测试套件） |
| 有持续集成 | Lv 3（每次提交合入主干前自动验证） |
| 有持续交付 | Lv 4（随时可部署，但手动触发） |
| 有持续部署 | Lv 5（通过测试的提交自动上生产） |

**2024 年数据**：根据 Google DORA 报告，顶级团队每天可部署多次，变更失败率低于 5%，故障恢复时间小于 1 小时。而低绩效团队可能需要数月才能部署一次。

### 3.5 ML 工程（MLOps）——新的工程维度

ML 系统引入了一系列传统软件工程没有的问题：

| 传统软件工程问题 | ML 特有的对应问题 |
|----------------|-----------------|
| 代码版本控制 | 代码+数据+模型+超参数都要版本控制 |
| 单元测试 | 模型验证（分布漂移检测比单元测试复杂得多） |
| 生产监控（CPU/内存/延迟） | 模型质量监控（预测分布、准确率漂移、特征缺失率） |
| 部署（推送新版本） | 模型部署（可能需要 A/B 测试、影子模式、金丝雀发布） |
| 回滚 | 模型回滚（回到上一个版本的模型+特征工程管道） |

**MLOps 成熟度模型**：

| 级别 | 特征 |
|------|------|
| Lv0 | 手动训练，手动部署，没有实验跟踪 |
| Lv1 | 训练管道自动化，实验跟踪，模型版本管理 |
| Lv2 | CI/CD 管道包含模型验证，自动部署 + 自动回滚 |
| Lv3 | 全自动再训练（漂移检测触发），A/B 实验框架 |

## 第四章 产品：交付用户价值

### 4.1 产品管理的核心框架

**双钻石模型 (Double Diamond)**——产品发现的标准流程：

```
        发现阶段                  交付阶段
    ┌─────────────┐         ┌─────────────┐
    │ 发散  │ 收敛 │         │ 发散  │ 收敛 │
    │      ▼      │         │      ▼      │
    │ 理解问题     │         │ 探索方案     │
    │  (调研、     │         │  (原型、     │
    │   访谈、     │         │   测试、     │
    │   数据)      │         │   迭代)      │
    └─────────────┘         └─────────────┘
```

**核心原则**：不要在理解问题之前跳到解决方案。大多数失败产品的根因是工程师一上来就开始写代码，产品经理一上来就开始画界面——但没人真正搞清楚"用户到底有什么问题"。

### 4.2 需求优先级框架

| 框架 | 核心逻辑 | 适用场景 |
|------|---------|---------|
| **RICE** | Reach × Impact × Confidence ÷ Effort | 量化决策，适合有数据的成熟产品 |
| **MoSCoW** | Must/Should/Could/Won't | 快速分类，适合早期产品 |
| **Kano 模型** | 基本型/期望型/兴奋型 | 理解用户对不同类型功能的感受 |
| **机会成本排序** | "不做这个，我们能做的最有价值的事是什么？" | 资源极度受限的团队 |
| **用户故事地图** | 按用户旅程排列，找 MVP 切割线 | 从零开始的产品 |

**Kano 模型详述**——最有解释力的产品框架之一：

```
用户满意度
  ▲
  │        ╱ 兴奋型（有了会惊喜，没有无所谓）
  │       ╱
  │      ╱
  │  ───╱──── 期望型（越多越好）
  │   ╱
  │  ╱
  │ ╱
  │╱──────── 基本型（没有就愤怒，有了是应该的）
  └──────────────────→ 功能实现程度
```

**Kano 的深刻之处**：兴奋型功能会随着时间退化——今天的"哇"是明天的"应该"。AI 助手在 2023 年还是兴奋型，2025 年已经是基本型。

### 4.3 产品指标——北极星与反指标

**北极星指标**：一个最能代表产品为用户创造的核心价值的数字。

| 产品 | 北极星指标 |
|------|----------|
| Spotify | 听歌总时长 |
| Airbnb | 预订过夜数 |
| Slack | 发送的消息数 |
| Notion | 活跃工作区数 |

**反指标**：容易误导的虚荣指标。

| 虚荣指标（别只看这个） | 更有意义的指标 |
|---------------------|-------------|
| 注册用户数 | 周活跃用户数 (WAU) |
| 下载量 | 次日留存率 |
| 页面浏览量 (PV) | 核心任务完成率 |
| 功能上线数 | 功能使用率 |

### 4.4 AI 产品的特殊性

| 传统产品假设 | AI 产品的现实 |
|------------|-------------|
| "用户体验是确定的" | 用户体验是概率性的——同一个输入可能有不同输出 |
| "功能好坏是可测试的" | 模型质量可能有长尾问题（99% 好但 1% 灾难） |
| "迭代周期以周为单位" | 训练一个模型可能就要几天，迭代天生就慢 |
| "数据是辅助决策的" | 数据是产品本身——模型的质量由数据决定 |

**AI 产品经理需要额外掌握的**：
- 理解模型的能力边界（不是"AI 什么都能做"）
- 理解数据飞轮（用户使用 → 产生数据 → 模型变好 → 更多用户）
- 理解失败模式（幻觉、偏见、安全风险）——这些是产品问题，不只是技术问题

## 第五章 三者的交叉地带

### 5.1 工程-产品交叉：技术可行性塑造产品可能性

Steve Jobs 的名言广为人知，但少有人理解其工程含义：

> "People who are really serious about software should make their own hardware."
> —— 实际上是 Alan Kay 说的

翻译成工程-产品语言：**如果一个技术限制影响了你产品的核心差异化，你就应该自己掌握那层技术。**

Netflix 做 CDN、Google 做服务器、Apple 做芯片——这不是"什么都要自己做"的傲慢，而是**核心差异化不能外包**。

### 5.2 项目-工程交叉：技术债的本质是"时间 vs 质量"在时间轴上的映射

```
Week 1: 快速上线，欠下技术债
Week 4: 技术债利息 → 新功能变慢
Week 8: 技术债利息 → 新功能非常慢
Week 12: 技术债利息 > 新功能开发速度 → 系统进入"死亡螺旋"
```

**死亡螺旋的信号**：
- 每个 Sprint 花在"修 bug"上的时间超过 50%
- 新人入职需要超过 3 个月才能有效贡献
- "这个只有老张能改"成为口头禅
- 部署频繁回滚

### 5.3 产品-项目交叉：路线图不是承诺书

产品路线图最大的陷阱：**把它当成项目计划的变体。**

```
路线图应该是：
  未来6个月，我们打算探索这些方向
  基于当前的信息，我们认为这些最重要

路线图不应该是：
  3月15日上线XX功能
  4月1日上线YY功能
  （这是项目计划，不是路线图）
```

**好的路线图**：按"现在 → 下一步 → 未来"组织，只有"现在"的列有明确日期，"下一步"是模糊目标，"未来"是方向性意图。

## 第六章 AI 时代的范式转移

### 6.1 AI 对项目管理的冲击

| 冲击 | 具体表现 |
|------|---------|
| **估时失效** | 传统软件开发可以按"用户故事"估点，ML 任务中"训练一个模型"可能需要 1 天也可能 1 个月（取决于数据质量和问题难度） |
| **依赖链不确定** | 数据标注质量 → 模型效果 → 产品体验，任何一个环节出问题都需要回溯 |
| **"完成"的定义变了** | 模型上线只是开始，持续监控和再训练是"完成"的一部分 |

**推荐的 AI 项目管理实践**：

```
Sprint 中区分两种任务：

确定性任务（传统开发）：
  □ 搭建模型服务 API          估 3 点
  □ 完成数据管道 ETL           估 5 点
  □ 部署监控仪表板             估 2 点

探索性任务（ML 实验）：
  □ 实验：尝试 Transformer + 新损失函数    时间盒 3 天
  □ 实验：对比 3 种特征工程方案            时间盒 2 天
  □ 实验：分析模型在长尾数据上的表现        时间盒 2 天
```

探索性任务用**时间盒**代替**估算**——"花 X 天在这个方向上，到时间根据结果决定下一步"，而不是"完成这个任务"。

### 6.2 AI 对工程的冲击

**代码生成工具（Copilot, Cursor, Claude）正在改变工程的含义。**

```
传统工程时间分配：
  写代码 40% | 读懂代码 25% | 调试 15% | 设计 10% | 沟通 10%

AI 辅助后的时间分配：
  写代码 10% | 读懂代码 30% | 调试 20% | 设计 15% | 审查AI产出 15% | 沟通 10%
```

**工程的角色从"写代码的人"变成"代码的设计者和审查者"**。这意味着：
- 代码审查能力比编码速度更重要
- 系统设计能力比框架熟悉度更重要
- 测试策略比实现细节更重要

**"氛围编程" (Vibe Coding)** 是 2025 年的现象：用自然语言描述需求，AI 生成全部代码，开发者只做审查和微调。这进一步把工程的核心从"写"变成了"判断"。

### 6.3 AI 对产品的冲击

| 冲击 | 表现 |
|------|------|
| **产品形态从"工具"变成"代理"** | 用户不再操作界面完成任务，而是告诉 AI 目标，AI 自主执行 |
| **"功能"的边界模糊** | 传统产品：每个功能需要设计和开发。AI 产品：一个通用能力可以覆盖多个使用场景——但每个场景的行为不完全可控 |
| **竞争壁垒从功能转向数据和网络效应** | 基础模型越来越同质化，差异化靠专有数据和用户基础 |

**AI 产品的核心悖论**：越强大（通用能力越强）就越不可控（输出越难预测），越不可控就越难做成产品（用户要的是可靠的工具，不是聪明的但不可靠的助手）。

## 第八章 业内评价与案例

### 8.1 亚马逊的"两个披萨团队"——产品-工程-项目一体化

Jeff Bezos 的规则：每个团队小到两个披萨就能喂饱。这种团队天然做到了：
- **产品**：团队直接面向用户需求，不需要跨部门协调
- **工程**：团队拥有自己的服务的全栈，包括运维
- **项目**：小团队节奏快，天然 Sprint

**代价**：可能导致重复造轮子（多个团队做类似的中间件），需要强有力的平台团队来平衡。

### 8.2 Google 的 OKR 实践

Google 从 Intel 借鉴了 OKR（目标与关键成果），并将其融入从产品到工程的全流程：

```
O (目标)：让 Gmail 成为世界上最快的邮件服务
  KR1：页面加载时间 < 100ms (P99)    ← 工程指标
  KR2：日活用户增长 20%               ← 产品指标
  KR3：在 Q2 结束前完成新版上线        ← 项目指标
```

**OKR 的精髓**：一个目标可以同时包含产品、工程、项目的关键成果——它迫使你思考三者的平衡。

> 来源：John Doerr《Measure What Matters》(2018)

### 8.3 Spotify 的 Squad 模型——一个被过度传播也过度批评的案例

Spotify 在 2012 年公开了其工程文化模型——Squad、Tribe、Chapter、Guild。它解决了：
- Squad（小队）= 产品-工程-项目的最小自治单元
- Tribe（部落）= 相关 Squad 的集群
- Chapter（分会）= 跨 Squad 的专业社区（前端工程师 Chapter）
- Guild（行会）= 兴趣驱动的跨组织社区

**批评**：Spotify 自己后来也修改了这个模型。Henrik Kniberg（原始作者）多次强调"这不是一个框架，不要复制，要学会其中的原则再适配"。但太多公司只是复制了组织结构图而没学到核心——**自治小队需要成熟的工程基础设施支撑**。

### 8.4 AI 公司的组织实验

| 公司 | 做法 | 信号 |
|------|------|------|
| **OpenAI** | 研究员驱动产品方向，工程服务于研究 | 研究优先的组织模式 |
| **Anthropic** | "对齐"团队和产品团队并行 | 安全/伦理作为一个独立的产品维度（不仅是工程维度） |
| **Midjourney** | 极小的团队（~10人），无产品经理 | 创始人直接做产品决策 |
| **Cursor/Anysphere** | 开发者工具，工程师即用户 | 用户和制造者是同一群人时，产品-工程边界几乎消失 |

**共同信号**：AI 公司普遍比传统软件公司更"研究驱动"，产品经理的角色从"定义需求"变成"将研究发现转化为用户价值"。这要求产品经理有比过去更强的技术理解力。

## 第九章 避坑指南

### 9.1 项目管理常见陷阱

| 陷阱 | 症状 | 修正 |
|------|------|------|
| **估算即承诺** | 工程师说"大概 3 天"，被当成"3 天必须做完" | 估算用范围（2-5 天），承诺用具体日期（3 月 15 日），二者分开 |
| **站会变成微型汇报** | 每个人对着项目经理说话，不是互相说话 | 站会只回答三个问题且彼此对话，项目经理旁听 |
| **只追进度不看阻塞** | 站会上每个人都说"正常"，但没人说被什么卡住 | 明确鼓励"我需要帮助"的文化，阻塞项单独可视化 |
| **Sprint 太长或太短** | 四周 Sprint = 失去紧迫感；一周 Sprint = 永远在开会 | 两周是大多数团队的甜点 |
| **回顾会变成吐槽会** | 列了一堆问题，但没有行动项 | 每次回顾会最多产出 1-3 个可执行的改进行动 |

### 9.2 工程管理常见陷阱

| 陷阱 | 症状 | 修正 |
|------|------|------|
| **过度设计** | 为一个 100 个用户的系统设计了百万用户的架构 | YAGNI (You Ain't Gonna Need It) 原则——先解决当前问题，再扩展 |
| **测试写了但没价值** | 测试覆盖率 90%，但测的都是 getter/setter，核心逻辑没测 | 测试策略优先核心路径和边界条件 |
| **技术债从不偿还** | 每次 Sprint 都说"下个 Sprint 清理"，但永远有"更紧急的事" | 固定 20% 时间给技术债，不可协商 |
| **微观管理** | 技术负责人审查每一行代码 | 用 lint/自动化测试替代人工检查，人工审查只看架构风险 |
| **过早优化** | 花一周优化了一个占总耗时 1% 的函数 | 先用 profiling 找到真正的瓶颈 |

### 9.3 产品管理常见陷阱

| 陷阱 | 症状 | 修正 |
|------|------|------|
| **解决方案跳跃** | "我们应该做一个 XX"——直接跳到方案，没有定义问题 | 强制先回答"谁在什么场景下有什么问题" |
| **功能膨胀** | 产品越来越复杂，但核心体验没有提升 | 每季度问"我们可以删掉什么"。删功能比加功能更需要勇气 |
| **以竞品代替用户** | 因为竞争者在做，所以我们也做 | 竞品分析是输入，不是决策。最终判断标准是用户是否需要 |
| **数据驱动变成数据奴役** | 只看能测量的，忽略不能测量的 | 定性研究（用户访谈）和定量分析（数据）必须并行 |
| **忽视"不做什么"** | 路线图只有"增加"，没有"砍掉"和"不做" | 路线图的背面——明确列出不做的事情——和正面同等重要 |

### 9.4 AI 特有陷阱

| 陷阱 | 症状 | 修正 |
|------|------|------|
| **模型中心主义** | "加一个更好的模型就能解决所有问题" | 先检查数据质量、产品设计、用户体验，最后才是模型 |
| **离线指标和在线指标脱节** | 测试集上准确率 95%，上线用户满意度很低 | 定义在线评估指标（用户留存率、任务完成率），和离线指标对齐 |
| **数据管道是二等公民** | 花 80% 时间在模型上，20% 在数据管道上 | 实际应该反过来——Google 的研究者说他们花 80% 时间在数据上 (Sculley et al., 2015, NIPS) |
| **忽视模型退化** | 部署后不再监控，三个月后发现模型完全不准了 | 部署第一天就建立漂移监控 |

## 第十章 进阶技巧与最佳实践

### 10.1 切换思维模式的训练

三种思维模式需要在一天内多次切换。以下是一个练习：

```
上午 9:00 - 9:30  产品模式：看用户反馈、数据分析
上午 9:30 - 11:00 工程模式：写代码/做架构/Code Review
上午 11:00 - 11:15 项目模式：更新看板、检查阻塞项
下午 2:00 - 3:00  工程模式
下午 3:00 - 3:15  项目模式：站会
下午 3:15 - 5:00  根据当天优先级灵活分配
```

**关键**：不要在同一时间段内混合模式。上下文切换是认知上的最大成本——从"这个函数怎么优化"跳到"这个需求优先级对不对"需要时间。

### 10.2 从零搭建科技组织的推荐路径

```
阶段 1：单兵作战（1人）
  产品思维主导 → 找到方向
  工程思维服务 → 快速验证
  项目思维最弱 → 允许（这时不需要项目管理）

阶段 2：二人组（2-5人）
  保留产品方向感 + 引入轻量工程规范
  项目：一个共享待办清单就够了

阶段 3：小队（5-15人）
  必须引入明确的项目节奏（Scrum/看板）
  工程规范制度化（CI/CD、code review、测试要求）
  产品角色可以仍然由创始人兼任

阶段 4：多团队（15-50人）
  产品-工程-项目必须由不同人负责
  需要平台/基础设施团队支持工程效率
  需要跨团队的项目协调机制

阶段 5：规模化（50+人）
  需要专门的工程效率团队、产品运营团队、项目办公室
  核心挑战从"做出来"变成"做一致"——多个团队产出的产品体验一致吗？
```

### 10.3 技术人员向管理转型的路线

```
你是一个工程师，你想往管理走——

错误路径：放弃写代码，专门开会
  → 失去技术敏锐度 → 团队不再尊重你的技术判断
  → 管理价值无法量化 → 自己也不知道自己在干什么

正确路径：保持技术参与，渐进增加管理比重
  第1步：带1-2个新人（师徒制，非正式管理）
  第2步：负责一个模块的技术决策（Tech Lead）
  第3步：负责一个小项目的协调（增加项目思维）
  第4步：负责一个小团队的全面管理（项目+工程+人员）
  第5步：负责多个团队或一个产品线

每一步的过渡周期约6-12个月
```

**最重要的转型素质**：从"我自己做"变成"我让别人做得比我好"。这需要克服所有优秀工程师最深的恐惧——"如果我不自己写，质量会下降"。

## 第十一章 未来展望

### 11.1 AI 编码对工程角色的重构

未来 3-5 年，"软件工程师"这个职业的含义将发生根本性变化。不是消失——是重构。

```
今天的工程师：写代码、调试、review、部署
明天的工程师：定义需求、设计架构、审查AI产出、验证质量

类比：从"纺织工人"变成"纺织机械师"
——不是不需要人了，是需要更高阶的判断力和系统思维
```

**哪些工程能力会升值**：
- 系统设计和架构判断——AI 擅长实现，不擅长权衡
- 代码审查——当 90% 的代码由 AI 生成时，审查能力成为瓶颈
- 测试策略——保证 AI 产出的正确性
- 安全审计——AI 生成的代码可能包含隐蔽的漏洞

**哪些工程能力会贬值**：
- 框架记忆（"React 的某个 API 怎么写"）——AI 秒答
- 样板代码编写——AI 秒写
- 简单的 bug 修复——AI 秒诊断

### 11.2 产品管理的演化：从"Feature Factory"到"AI 编排者"

传统产品经理定义功能、排优先级、写 PRD。在 AI 时代：

- **从"定义功能"变成"定义行为边界"**——AI 系统的行为是弹性的，产品经理需要定义的不是"按钮应该长什么样"而是"AI 在这个场景下可以提供哪些帮助，不能做什么"
- **从"需求文档"变成"评估标准"**——传统 PRD 将变成评估模型行为的标准和测试用例
- **从"用户研究"变成"使用行为分析 + AI 交互模式发现"**——用户如何使用 AI 系统会出现传统工具没有的行为模式

**最被低估的 AI 产品能力**：理解模型的失败模式，并将其转化为产品决策。比如，"模型的幻觉率是 3%，这意味着在医疗场景下不能独立给出诊断建议"——这是产品判断，不是技术判断。

### 11.3 项目管理的终极悖论

AI 让个体生产力飙升——一个人 + AI 可以完成过去一个团队的工作。这意味着：

- **更小的团队可以做更大的事** → 传统的项目协调需求降低
- **但协调仍然是瓶颈** → 当 5 个超高效个体需要协作时，协调成本占总体成本的比例反而更高

**我的判断**：AI 不会消灭项目管理，但会改变它的形态。未来的项目管理更像是**"编排"而不是"跟踪"**——项目经理不催进度，而是确保 AI 和人类之间的信息流畅通、每个人（和每个 AI Agent）知道自己在协作网络中的"下一跳"是谁。

这和路由协议的演进逻辑一脉相承。

### 11.4 三者的最终融合形态

我看到的终局不是"三个角色各司其职"，而是**每一位技术人员都需要内化三种思维**：

```
传统组织：                      未来个体：
  ┌──┐ ┌──┐ ┌──┐              ┌──────────────┐
  │项│ │工│ │产│              │ 一个人，     │
  │目│ │程│ │品│              │ 三种思维模式  │
  └──┘ └──┘ └──┘              │ 随时切换     │
  各管各的                      └──────────────┘
```

这不是说不需要分工和协作。而是说**当 AI 消除了大量执行层面的工作后，剩下的纯人类的劳动就是判断、权衡和方向选择**——而这恰恰需要同一个人同时拥有产品感、工程判断力和项目节奏感。

**未来的超级个体，不是一个什么都会写的全栈工程师，而是一个能在三种思维模式间无缝切换的决策者。**
