## 壹 · 任务背景

### 现有系统梳理

| 系统 | 角色 | 当前状态 |
|------|------|----------|
| **Daily Briefing** | cron job驱动的每日固定简报 | 已有日程机器人+报告模板，输出固定关注点+灵活快讯 |
| **记忆胶囊** | 决策快照封装单元 | Phase 1已完成信息架构设计（692行规格文档） |
| **temporal_decay.py** | 时序衰减引擎 | 已就绪，支持断言存储+衰减查询 |
| **decision_graph.py** | 决策链路有向图构建 | 已就绪，有`format_briefing_decision_summary()`函数 |

### 设计约束

1. Daily Briefing是**文本为主**的推送（Telegram/微信），不是HTML UI
2. 长编（izu-pipeline产出）是**markdown文件**，不是渲染网页
3. 用户终端为手机端阅读，空间珍贵，每行字都需竞争注意力

## 贰 · 今日决策回溯区块设计

### 2.1 区块位置：Briefing 第四区块（非第三）

> **否决回溯**：原设计文档写的是"第三区块"，但实际briefing模板结构为：
> 1. 📊 五个固定关注点
> 2. 🔄 灵活快讯（5-10条）
> 3. 💡 点睛
> 4. 📎 信息源
>
> **修正方案**：决策回溯插入在💡点睛之后、📎信息源之前，作为第四区块。
> 
> 为什么不是第三？因为"灵活快讯"之后用户注意力已耗散，"点睛"是情绪落点，在此之后用"决策回溯"把情绪转化为行动锚点，再以"信息源"收尾——这才是认知心理学上的合理节奏。

```
┌─ Daily Briefing ─────────────────────────────────────┐
│                                                        │
│  📊 五个固定关注点（必须填满，每条60-150字）          │
│                                                        │
│  🔄 灵活快讯（5-10条，每条一句话）                    │
│                                                        │
│  💡 点睛（可选，一句升华/行动号召）                   │
│                                                        │
│  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  ← 视觉分隔线
│                                                        │
│  ⚖️ 今日决策回溯   ← 第四区块                          │
│    ● 新鲜 · AI Agent框架选型                          │
│    ○ 银窗 · 论文日报选稿逻辑                          │
│                                                        │
│  ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─  ← 视觉分隔线
│                                                        │
│  📎 信息源                                             │
└────────────────────────────────────────────────────────┘
```

### 2.2 区块样式规格

```
区块标题: "⚖️ 今日决策回溯"
          字号与briefing正文一致，emoji前缀做视觉锚点
          与内容间距: 1个空行

标题下的副标题行（仅在"有新决策"状态显示）:
  "你昨天在{N}个方向上做了判断，其中{M}个前提可能已变化"

每条胶囊项:
  格式: [时效标记] [标题（≤14字）]
        摘要一行（≤30字）
        状态标签 + 时间标签 + 年龄标签

视觉分隔:
  区块上下各一条分隔线（---）
  确保与"点睛"和"信息源"在视觉上区分开
```

### 2.3 胶囊项格式详解

```
状态A——有新的决策（24h内）:
─────────────────────────────────────────────────────────
  ● AI Agent框架选型
    建议LangGraph MVP，✅前提未变 · 7天前
    └─ [查看链路]  [复验 →]
─────────────────────────────────────────────────────────

状态B——只有旧决策（24h以上）:
─────────────────────────────────────────────────────────
  ○ 论文日报选稿逻辑
    宁缺毋滥原则，⚠️ 建议复验 · 5天前
    └─ [查看链路]  [复验 →]
─────────────────────────────────────────────────────────

状态C——没有可回溯的:
─────────────────────────────────────────────────────────
  📭 今日无待回溯决策
─────────────────────────────────────────────────────────
```

### 2.4 胶囊渲染字段映射（从decision_graph.py数据结构）

```
decision_graph.py 的 list_sessions() 返回:
{
  "slug": "2026年AI_Agent最新进展",
  "topic": "2026年AI Agent最新进展",
  "last_step": "核",
  "timestamp": "2026-05-16T14:00:00",
  "node_count": 8,
  "steps_completed": ["探","搜","织","对齐","写","劈","修","核"]
}

渲染映射:
  → 标题: topic（截断至14字）
  → 时间标签: 从timestamp计算"几天前"
  → 新鲜度: 基于temporal_decay引擎查询freshness
  → 前提状态: 通过attach_assertions_to_graph()检查decayed_weight

额外需要的字段（当前decision_graph.py未直接输出）:
  → freshness_level: "fresh" | "warm" | "grey" | "cold"
  → premise_status: "valid" | "changed" | "unknown"
  → summary_short: 胶囊摘要（30字以内）
  → source_count: 依赖来源数
```

### 3.2 关键设计决策：预聚合 vs 实时生成

| 方案 | 做法 | 优缺点 |
|------|------|--------|
| **方案A：预聚合（推荐）** | cron session启动前，由shell脚本/Wrapper调用 decision_graph.py 生成Markdown块，作为固定尾段注入prompt | ✅ 数据准确，不依赖LLM的判断力<br>✅ 聚合逻辑可控，测试方便<br>❌ 需要额外python脚本 |
| **方案B：实时生成** | 在briefing prompt中写"请调用decision_graph获取今日决策回溯" | ❌ cron session无工具调用权限<br>❌ LLM可能格式走样、幻觉决策内容<br>❌ 无法保证数据准确性 |

**结论：采用方案A。** 增加一个wrapper脚本（或修改现有daily-research-orchestra.py），在构建briefing prompt前先调用聚合脚本。

### 3.3 聚合脚本规格

```python

# 输入：无（自动扫描所有活跃会话）
# 输出：Markdown文本块（可直接粘贴到briefing prompt中）

def build_decision_review_block():
    """构建⚖️今日决策回溯的完整Markdown块"""
    from izu_shared.decision_graph import list_sessions, build_graph
    from izu_shared.temporal_decay import TemporalDecay
    
    td = TemporalDecay()
    sessions = list_sessions()
    
    # 1. 筛选：只在fresh/warm范围内的会话
    eligible = []
    for s in sessions:
        freshness, age_hours = get_freshness(td, s["slug"])
        if freshness in ("fresh", "warm"):
            eligible.append({
                "session": s,
                "freshness": freshness,
                "age_hours": age_hours,
            })
    
    # 2. 排序：新鲜优先，同一层级按时间倒序
    # 3. 生成Markdown（见下文渲染规格）
    # 4. 返回文本块
```

## 肆 · 触发条件与位置策略

### 4.1 推送时机

| 场景 | 推送策略 | 理由 |
|------|---------|------|
| **有新鲜决策（<72h）** | 在Daily Briefing内固定展示（第四区块） | 用户每天看briefing时自然触达，不额外推送 |
| **只有银窗决策（72-168h）** | 在Daily Briefing内以精简版展示 | 低优先级，不占主要注意力 |
| **灰区/冷存储决策** | 不在Briefing显示，留待"长编关联触发"或"追问" | 太旧了不天天提醒 |

### 4.2 是否独立推送

**不。** 决策回溯永不独立推送。

- 只在Daily Briefing中出现
- 例外：当**前提变化检测**触发时（temporal_decay检测到某决策的前提断言权重骤降），才通过"祝号"独立推一条消息
- 这个例外场景已经在记忆胶囊设计中定义了（场景C·自动推送）

### 4.3 什么时候跳过

满足以下任一条件则完全不显示该区块：

1. 没有活跃的fresh/warm会话
2. 所有活跃会话的 freshness 均为 grey/cold 且无前提变化
3. 用户昨天没有进行任何决策（降级文案："📭 今日无待回溯决策"）

### 4.4 降级文案

```
场景1：没有可回溯的决策
  "📭 今日无待回溯决策"
  副标题: "昨日未产生新判断。决策回溯将随新决策自动出现。"

场景2：只有过旧决策（>168h，但用户关注度匹配）
  "📭 近7日无新决策。你有{N}个旧决策可查看（需主动问）"

场景3：系统未完成聚合（兜底）
  "⚖️ 决策回溯暂不可用（系统聚合中，稍后刷新可见）"
```

## 伍 · 三种状态渲染

### 5.1 状态A：有新的决策回溯 → 完整区块

**条件**：至少1个 fresh（<72h）胶囊存在

```
---
⚖️ 今日决策回溯
你昨天在2个方向上做了判断，其中1个前提可能已变化。

● AI Agent框架选型 → 建议LangGraph MVP
   ✅ 前提未变 · 7天前 · 依赖 12 来源
   └ [查看链路]  [复验 →]

○ 论文日报选稿逻辑 → 确定宁缺毋滥原则
   ⚠️ 建议复验 · 5天前 · 依赖 5 来源
   └ [查看链路]  [复验 →]
---
```

**长度控制**：不超过5条。超过则按新鲜度排序取前5条，末尾加"还有{N}个决策..."

### 5.2 状态B：只有旧决策（24h以上）→ 精简版

**条件**：无 fresh 胶囊，但有 warm（72-168h）胶囊

```
---
⚖️ 今日决策回溯

○ 论文日报选稿逻辑 → 宁缺毋滥原则
   ⚠️ 建议复验 · 5天前
   └ [查看链路]

⚠️ 你的{M}个决策已超过24小时未复查。
---
```

**区别**：
- 无"你昨天做了..."副标题
- 每条胶囊不再显示来源数
- 不加"你昨天做了N个方向"——因为不是昨天做的
- 末尾附加一条提醒

### 5.3 状态C：没有可回溯的 → 极简占位

**条件**：fresh + warm 均无，或昨晚零决策

```
---
📭 今日无待回溯决策
---
```

**设计思路**：
- 仅占两行，不占用用户注意力
- 但保留存在感——让用户知道系统在持续追踪
- 类似于"信箱为空"的视觉锚定

## 陆 · 设计之魂的否决检查

### 否决检查A：用户第一反应是"有用"还是"烦"？

| 风险维度 | 检查 | 缓解措施 |
|---------|------|---------|
| 信息密度 | Briefing本身已经很长，再加一快"新东西" | 区块不超过5行（含标题），每条胶囊信息压缩到极致 |
| 认知负担 | 用户每天要看一堆"过去做了啥" | 只有fresh/warm才显示。旧决策自动过滤不打扰 |
| 行动负担 | "看完就忘了" | 每条胶囊附带明确的行动路径：`[复验 →]` 是一个可点击的行动召唤 |
| 重复感 | "每天都显示一样的" | 按新鲜度驱动，旧的下沉，新的上升。如果所有决策都>7天，自动降级为精简版 |

### 否决检查B：这条信息的价值是什么？

回溯不是"让你再看一遍"——是"提醒你哪些判断可能已经过期了"。

价值量化：
- 每10条显示在briefing中的决策回溯，至少应该有1条触发用户"哦对，这个已经变了"的认知
- 如果连续3天都没有触发过复验，说明显示阈值偏宽——应收紧

### 否决检查C：与现有Briefing结构的冲突

| 冲突点 | 解决方案 |
|--------|---------|
| Briefing现在有"五个固定关注点""灵活快讯""点睛" | 决策回溯作为第四区块，有明确的分隔线 |
| 信息源在末尾，决策回溯在它前面 | 合理——看完回溯想看来源就自然往下翻 |
| 决策回溯可能会和其他区块信息重复 | 不会——固定关注点是外部信息，决策回溯是内部判断，信息域正交 |

## 柒 · 长编时效颜色标记渲染方案

### 7.1 问题定义

长编（izu-pipeline产出）是**纯Markdown文件**，不是HTML。纯文本中"颜色"不可直接渲染。

用户阅读长编的场景：
- 在Markdown阅读器/VS Code/GitHub中查看 `.md` 文件
- 在终端用 `cat` / `less` 阅读
- 被LLM引用到对话中

不存在"CSS颜色"的渲染环境。

### 7.2 方案评估

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **方案A：emoji前缀** | 🟢 新鲜 / 🟤 银窗 / 🔴 过时 | 一目了然，与设计规范色值视觉对应 | emoji在不同平台上渲染效果不同（苹果/微信/终端） |
| **方案B：文字标签** | `[新鲜]` `[银窗]` `[过时预警]` | 平台无关，清晰明确 | 字多占空间，"又多了一堆字" |
| **方案C：无渲染** | 不标颜色，只在"核"步骤产出中标注时效 | 干净，不改动长编正文 | 用户看不到时效信息，回溯链路断裂 |
| **方案D：混合方案（推荐）** | **标题行用emoji前缀** + **引用段落用文字标签** | 取A+B之长 | 需要制定统一规范 |

### 7.3 推荐方案：方案D（混合策略）

#### 分层渲染规则

```
在长编中的不同位置，采用不同标记策略：

┌──────┬────────────────────┬────────────────────────────┐
│ 位置  │ 标记方式            │ 理由                        │
├──────┼────────────────────┼────────────────────────────┤
│ 标题  │ 🟢 🟤 🔴 emoji    │ 标题行信息密度低，一个emoji  │
```

### 9.1 新增/修改组件清单

| 组件 | 类型 | 说明 |
|------|------|------|
| `decision_review_builder.py` | **新增** | 聚合脚本，调用decision_graph.py + temporal_decay.py 生成Markdown块 |
| `daily-briefing-system` prompt | **修改** | 在prompt中增加决策回溯区块的固定尾段占位符 |
| `daily-research-orchestra.py` | **修改** | 在构建briefing prompt前调用聚合脚本 |
| `核`步骤 prompt | **修改** | 增加"时效标注"输出要求 |
| `temporal_decay.py` | **无修改** | 当前API已足够查询freshness |
| `decision_graph.py` | **轻微修改** | `format_briefing_decision_summary()`需重写以匹配新格式（当前是表格形式，需改为精简版） |

### 9.2 实现优先级

```
P0（MVP必须）:
  □ decision_review_builder.py 聚合脚本
  □ briefing prompt 集成（固定尾段注入）
  □ 三种状态渲染的逻辑判定
  □ 长编中文字标签 [新鲜] [银窗] [过时预警]

P1（下一轮迭代）:
  □ "核"步骤的时效标注输出
  □ emoji标题前缀（需确认用户平台渲染效果）
  □ [查看链路] 的可点击交互（需Telegram/WeChat支持）

P2（远期）:
  □ 前提变化自动推送（场景C）
  □ 冷存储压缩后胶囊展示
```

### 9.3 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 聚合脚本运行耗时 > 用户等待阈值 | 低 | 中 | 聚合逻辑是纯本地文件扫描+数据库查询，<1s |
| Briefing prompt过长超过模型上下文 | 低 | 高 | 决策回溯块限制在5条以内，总字数<500字 |
| emoji在不同平台显示不一致 | 中 | 低 | 核心时效信息用文字标签兜底，emoji是辅助视觉锚点 |
| 用户连续N天看到"空状态" | 中 | 中 | 引入静默阈值：连续3天空状态则不显示该区块 |

## 拾 · 否决检查清单

### 设计之魂的三问

```
❓ 问一：用户看到这个区块的第一反应是什么？
✅ 答："哦对，我昨天做了这个判断，该看看变了没有。"

❓ 问二：如果这个区块今天不出现，用户会察觉吗？
✅ 答：大部分时间不会。这正是对的——不打扰是最高优先级。
       空状态≤2行，不留虚假的存在感。

❓ 问三：这个区块有让用户做出更好决策的可能性吗？
✅ 答：有的。前提变化提醒直接帮助用户避免"拿着旧地图走新路"。
```
