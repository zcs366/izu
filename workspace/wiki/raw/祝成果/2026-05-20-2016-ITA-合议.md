# 研究编排流水线 v4.0 — Phase 1A：ITA 6轮合议

> 题目：LLM形式化验证与自愈软件
> 精选来源：Tihanyi et al. 2025（Cited by 134）, Hao et al. 2025 NAACL（Cited by 41）

---

## Round 0 — 惠施（概念澄清）

**核心概念辨析：**

1. **"形式化验证"在这里指什么？**
   - 狭义：用SMT/SAT求解器验证逻辑公式的可满足性（Hao et al. 路线）
   - 广义：任何可证明正确性的数学方法，包括定理证明、模型检测、抽象解释
   - 我们的焦点：**在LLM的生成-验证闭环中使用SMT求解器**——即LLM产出的候选方案→形式化规约→求解器验证→反馈迭代

2. **"自愈软件"的边界？**
   - 主动型：LLM检测到安全违规后自动生成修复补丁（需验证修复正确性）
   - 被动型：运行时监控+回滚/隔离（不修复，只止损）
   - 该方向承诺的是主动型，但应警惕"修复可能引入新漏洞"的元问题

3. **关键概念区分**
   - **验证（Verification）** vs **测试（Testing）**：验证证明正确性（对所有输入），测试只检查有限样本
   - **正确性（Correctness）** vs **安全性（Safety）**：正确性≈满足规约，安全性≈不造成危害——前者是后者的必要不充分条件
   - **规约（Specification）** vs **实现（Implementation）**：规约错误是元错误，最难检测

**待检验的前提：**
- (P1) LLM能生成足够精确的规约以使形式化验证可行
- (P2) 验证反例能有效指导LLM修正
- (P3) "自愈"循环的收敛速度足够快以用于在线系统

## Round 1 — 墨子（形式化验证）

**形式化框架评估：**

### 采用者-检验者架构（Oracle-Checker Pattern）
```
LLM（生成候选规划/代码）→ 编译器/约束提取器 → SMT Solver（Z3/CVC5） → 反馈回路
```

**每条路径的形式化验证难点：**

1. **代码路径（Tihanyi et al. 路线）**
   - 可用工具：Z3、CVC5、Dafny、Lean
   - 难点：LLM生成代码 + 自动提取规格（Hoare triple生成）+ 验证
   - 成熟度：已有若干原型（Copilot+形式化验证集成），但生成规约的质量不可控

2. **规划路径（Hao et al. 路线）**
   - 可用工具：PDDL→SMT编码
   - 当前验证通过率：论文报告在规划任务上约78%
   - 关键约束：规约必须是完全状态化的（fully observable）

3. **在线行为路径（我们的兴趣点）**
   - 需要将Agent行为空间映射到形式化模型，这在开放环境下几乎不可能
   - 可行的折中：**只验证安全关键约束**（安全护城河），而非全行为正确性

### 形式化验证的四个可证伪命题：
1. F1: 在受限领域（如代码生成、确定性规划），LLM+SMT显著优于纯LLM（即：验证闭环带来>10%的准确率提升）
2. F2: SMT求解器返回的反例中，LLM能正确理解并修正的比例>60%
3. F3: 验证闭环的延迟在可接受范围内（<5秒/轮，3轮内收敛）
4. F4: 规约的质量（完整性）可以通过"验证规约的规约"来保证（元验证）

## Round 2 — 商鞅（实验设计）

**关键实验方案：**

### 实验A：验证闭环有效性基线测试
- **目标**：检验F1（LLM+SMT > 纯LLM）
- **设置**：选取HumanEval、MBPP、规划领域基准（Blocksworld、Logistics）
- **对比组**：纯LLM（直接生成） vs LLM+SMT验证闭环
- **指标**：首次正确率、最终正确率、平均迭代轮次
- **预期**：验证闭环在规划任务上应有>20%的提升，在代码任务上10-15%

### 实验B：反例利用效率测试
- **目标**：检验F2（反例→修正的转化率）
- **设置**：人为构造典型反例（安全违规、类型错误、逻辑矛盾），测试LLM能否正确修正
- **变量**：反例类型（counterexample格式）、LLM版本、是否提供额外上下文
- **关键发现期望**：不是所有反例都同等有用——unsat核心（unsat core）比完整反例更有效

### 实验C：在线部署可行性测试
- **目标**：检验F3（延迟约束）
- **设置**：在不同复杂度任务上测量验证闭环的端到端延迟
- **vs基线**：无验证（即时响应） 有验证但缓存 完全在线验证
- **接受标准**：95%的任务在5秒内完成验证

### 实验D（激进）：规约完整性挑战
- **目标**：检验"规约的规约"能否提升规约质量
- **设置**：让LLM生成规约，然后用另一个LLM检查规约的完整性，循环迭代
- **指标**：规约-实现的匹配率

## Round 3 — 鲁班（工程可行性与约束分析）

**在理论约束内的工程可行性：**

### 架构方案选型

**方案A：编译器插件模式**
- 实现：VS Code/IDE插件 → 用户写代码 → LLM补全 → 自动验证 → 实时反馈
- 技术栈：LSP协议 + Z3 Python API + LLM API
- 成熟度：高（Copilot已有类似架构，加上验证层即可）
- 风险：LLM生成的规约质量不可控，规约本身可能出错

**方案B：Agent运行时护栏模式**
- 实现：Agent行动前 → 行动规划提取 → 安全约束验证 → 通过/拒绝/修正
- 技术栈：Agent框架 + 领域特定约束编码器 + SMT solver
- 成熟度：中（需要针对不同Agent框架定制约束提取器）
- 风险：开放世界的约束规约不完备，假阴性（漏过违规）无法消除

**方案C：混合范式**
- 实现：关键路径用形式化验证，非关键路径用启发式检查
- 成熟度：高（最务实的选择）
- 推荐采用此方案

### 工程约束清单
1. **模型调用延迟**：每次验证循环需要1-3次LLM调用，累计延迟需优化
2. **规约自动提取精度**：当前最好水平约70-80%规约覆盖
3. **求解器可扩展性**：SMT求解对大状态空间呈指数增长，需领域剪枝
4. **多模态/开放环境**：图像、音频等非文本输入的规约提取尚未解决
5. **规约漂移**：系统目标演化时，规约需要同步更新——缺乏自动化机制

## Round 4 — 萧何（资源路径与执行计划）

### 分阶段实施路线图

**Phase 1（1-2个月）：原型验证 — Python代码的形式化验证闭环**
- 资源：1-2名工程师 + Z3 + LLM API credits
- 产出：HumanEval/MBPP上的验证闭环原型，可复现的基线结果
- 关键里程碑：实验A的完整结果

**Phase 2（2-4个月）：扩展到规划任务 + Agent护栏**
- 资源：2-3名工程师 + PDDL工具链 + 安全约束专家
- 产出：Agent运行时护栏原型，在受限Domain（如代码沙箱）上运行
- 关键里程碑：实验B、C结果

**Phase 3（4-6个月）：生产级系统 + 规约管理**
- 资源：全栈工程师 + DevOps + 安全审计
- 产出：可部署的形式化验证护栏系统，含规约版本管理与漂移检测
- 关键里程碑：实验D + 生产环境部署验证

### 资源瓶颈识别
1. **人才稀缺**：同时懂LLM和形式化验证的人极少（全球可能<200人）
2. **算力成本**：LLM+Solver双重算力消耗，每验证循环约$0.05-0.20
3. **规约库建设**：领域特定的安全约束规约需要与Domain Expert共创

## Round 5 — 张仪（最强攻击 / 致命论证）

### 对本方向的五层破坏性攻击

**攻击1：规约问题（Specification Problem）—— 最致命**
- "形式化验证只能验证你写进规约的东西。真正的安全风险往往是你从未想到要写进规约的东西。
- 自动驾驶的'不撞人'规约写得再好，但当它为了'不撞人'而急刹导致追尾时——哪个规约更优先？'
- 规约不完备性是不可消除的，这是Gödel不完备定理在工程中的影子。

**攻击2：LLM的规约生成能力——猫锁门**
- "让LLM生成规约，然后用SMT验证，再用LLM按反例修正——这等于让狐狸设计鸡笼的锁。
- 如果LLM本身不安全，它生成的规约就是不安全的。
- Hao et al. 78%的通过率意味着22%的任务是验证失败的——你如何确保那22%不会造成伤害？"

**攻击3：验证的验证（元验证深渊）**
- "你说要用形式化验证来验证AI——那谁来验证你的验证器？
- 验证器本身可能有bug（Z3也出过bug）。
- 验证器的验证需要更高阶的验证——这是无穷回归。"

**攻击4：经济性——验证比犯错更贵**
- "在1万亿参数的模型上，每次推理时做SMT求解的成本远高于大模型本身。
- 如果90%的情况下AI的决定是安全的，只为了那10%的安全风险而100%验证——成本不划算。
- '自适应验证'（只验证高风险决策）是唯一出路，但这又回到了'判断什么决策需要验证'这个元问题。"

**攻击5：开放世界中的完备性不可能**
- "形式化验证在封闭系统（代码、数学）中有效，在开放世界（网络、人机交互、物理世界）中无法达到完备性。
- Agent面对的是开放世界——你不知道它明天会遇到什么新场景。
- 封闭世界验证 + 开放世界部署 = 虚假的安全感。"

### 防御性回应
1. 对攻击1（规约问题）：承认，采用"分治"——不是验证所有安全属性，而是验证那些可用形式化语言表述的关键安全约束。把"无法规约的剩余风险"作为已知的开放问题。
2. 对攻击2（LLM生成规约）：采取"规约验证的规约"——用独立的、非LLM的机制（如模板、专家手写、形式化推导）生成规约。LLM只在严格受限的角色中参与。
3. 对攻击3（元验证）：只验证验证器中最关键的部分（SMT求解器本身已有独立的验证），不追求完整的元验证链。接受"经过独立验证的求解器"作为信任根。
4. 对攻击4（经济性）：只对安全关键决策做验证（自适应验证），判断逻辑由专家手写规则而非LLM。
5. 对攻击5（开放世界）：目标和范围限定——Agent只在受限环境中运行（代码沙箱、仿真环境、经过安全过滤的工具调用集合），完全开放世界部署不在此方案承诺范围内。

**最终判断：该方向有价值，但必须承认其根本限制——形式化验证不能解决"规约以外"的安全问题。它是一个"必要条件"而非"充分条件"。**
