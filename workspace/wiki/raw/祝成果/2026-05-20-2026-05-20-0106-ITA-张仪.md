# 张仪 — 最强攻击官

## 单点失败分析 + 降级方案

### 最致命的失败点: SAC 锚点选择在代码领域不成立

**为什么这是最致命的？**
SAC 的核心假设是「可以从上下文中选出锚点 token 来汇聚语义信息」。在自然语言中，锚点可能是"因此"、"综上所述"等关键连接词。但在代码中：
1. **代码语义分布均匀** — 一个 Python 函数的每行都可能包含关键语义信息（变量赋值、条件分支、返回值），不像自然语言有关键句。
2. **锚点选择的盲目性** — 如果锚点选在 docstring 而非核心逻辑行，压缩后语义损失不可控。
3. **函数签名是自然锚点？** — 函数签名确实承载关键信息，但仅有函数签名不足以重建函数体语义。如果锚点集中签名，非锚点 token 的信息丢失会严重损害执行等价性。

**影响范围**: 整个 4x 压缩方案都依赖 SAC 的锚点机制。如果锚点假设在代码上不成立，整个方案 A 坍塌。

### 降级方案: 结构化锚点（Structural Anchors）

放弃「自适应锚点选择」，改用 **代码结构强制锚点 (Structural Anchor Forcing)**：

1. **锚点集合由代码语法树决定**，而非注意力学习：
   - 每个函数体：函数签名（强制锚点）+ 每个代码块的第一个语句（锚点）
   - 每个类：类定义 + __init__ + 每个方法的签名
   - 每个条件分支：if/elif/else 行
   - 循环：for/while 行

2. **修改 SAC 架构**：
   - 使用 tree-sitter 解析代码 → 提取 AST → 从 AST 节点中选择锚点
   - 锚点 embedding 绑定 AST 节点类型（函数签名锚点 ≠ 条件分支锚点）
   - 非锚点 token 根据与锚点的 AST 距离分配注意力权重

3. **代价**：结构锚点增加了额外 4 工时（tree-sitter 集成），但提高了方案的可信度。

### 第二致命点: 语义保留度量缺乏执行等价性验证

- **问题**: 如果只用 BLEU/CodeBLEU 度量语义保留，可能高估（BLEU 高分但代码不执行）。
- **降级**: 强制在实验 P0 中加入执行等价性测试。对于 Python 函数，用 unittest 框架验证输入/输出对（3-5 个测试用例/函数）。

### 结论
SAC 锚点假设在代码上的有效性是整个 ITA 方案的最大单点风险。**建议在 P0 中增加 2 工时验证 SAC 锚点选择策略在代码上的效果**，再做是否切换到结构化锚点的决策。
