## 卷首·原思路顺下

这次不是从头设计，是把已有的东西铺开在桌子上，看清楚每块是什么、谁挨着谁、哪里断了。

izu不是一天建成的。它是在过去三个月里一层一层叠出来的。我把它切成五层：

### 第一层：哲学地基

**明学七则**（v0.3，2026-05-10定稿）：辨、得道、明从兼听、以幻破幻、省、以乐为终、时中。

这不是装饰。每一个"则"都是对现有AI范式的一次反驳：
- "辨"反"无画像的问答"——系统开口之前必须先辨人
- "以幻破幻"反"消除幻觉"的主流叙事——幻觉不是敌人，没有知识才是
- "以乐为终"反"准确率KPI"——教育的终极指标不是正确率，是那个"通了"的瞬间

### 第二层：定位宣言

**祝白皮书**（v0.1→v0.2，2026-05-11）：从"学习工程系统"进化为"陪你走得道快乐的人"。

v0.1的"画像-长编-地图"三角架是对的，但太工科。v0.2的六根柱子——同路非指路、旧料用于展望、让你想知而非让你知、厚重到留十年、算力非护城河理解是、打败DR是为了传承——才是活的东西。

关键定位语：**"不是更好的Deep Research，是陪你走得道快乐的人。"**

### 第三层：方法论引擎

- **三段式流程**：画地图 → 收长编（收到齐） → 出定本
- **三智能体流水线**：搜 → 写 → 劈
- **三编通读**：一编粗、二编补、三编定
- **长编→定本**：长编是池塘（资料池索引），定本由学习者自己写

### 第四层：工具与基础设施

- `scripts/subagent.py`（48行，v0.4.1）：DeepSeek API驱动，搜/写/劈三角色，已加入DuckDuckGo真实搜索
- Hermes Agent：记忆系统（fact_store + memory + session_search）、多平台推送（Telegram/微信/Discord）、cron定时任务
- Wiki系统：170+ .md文件，66个索引页面，自动入库流水线（ingest.py + cron）
- GitHub仓库（zcs366/izu）：官网index.html（精美中英双语）

### 第五层：实际产出

- **AGI长编九面**（约6万字）——这是最重的成果，从定义面到展望面，完整覆盖一个领域
- **三篇ai祝研究**（#002/#006/#008）——交互式消费平台、知识库动态呈现、AI原生报告引擎
- **项目遴选**：WikiMeld当选#1优先项目（因为现在就能做）
- **小学教育系列**（5篇认知地图+长编）
- **工具手册系列**（Claude Code/Codex/ComfyUI等13篇）
- **妻子事业研究**（抖音短视频变现）
- 更多...

## 卷一·评估：哪根柱子稳，哪根在晃

### 稳的

**哲学地基——无可取代。** 明学七则是izu最深的护城河。市场上没有任何一个AI研究工具有独立的认识论体系。ChatGPT没有、Gemini没有、Perplexity没有、NotebookLM没有。这不是"做得更好"，是"做的是不同的事"。七则与六根柱子，放到十年后依然成立。这是定海神针。

**定位——真空地带。** "同路人"vs"工具人"这条线画得极其清楚。Deep Research（OpenAI）、Gemini Deep Research、Perplexity、NotebookLM——全部是"你问，它答，再见"的工具范式。没有人在做"陪你"这件事。不是因为他们技术不够，是因为他们不想——陪伴不能规模化、不能自动化、不能A/B测试。但恰因为大厂不会做，这才是izu存在的唯一理由。

**AGI长编九面——能力背书。** 约6万字的长编九面证明了三段式流程+三智能体流水线能产出真正的"重内容"。这个东西放在任何人面前，都无法否认它的深度。这是izu的"毕业论文"。

### 在晃的

**三智能体流水线——骨架有，肌肉没有。** `subagent.py`只有48行。角色提示词各一句话（搜："收集详细准确的资料"；写："输出结构清晰通俗易懂的文章"；劈："不留情面地批评"）。对比业界：
- Anthropic刚发布的"Dreaming"功能：Agent在会话之间自我审查、提取模式、自我改进
- OpenAI的Deep Research：多轮搜索、交叉验证、矛盾检测、置信度标注
- 开源方案（如Jordan Gibbs的"最聪明Deep Research Agent"）：Decompose → Width sweep → Contradiction graph → Loci analysis → Depth sweep

我们的搜→写→劈逻辑是对的，但实现太薄了。搜只是"搜+返回结果"，没有交叉验证、没有信息新鲜度判断、没有矛盾检测。劈只是"批评"，没有指出具体哪段需要什么数据、没有给出修改方向。

**"画像"系统——说了，但没做。** 祝白皮书说"会话即画像"——不填表、不骚扰、三次交互后就不同。但当前实现完全靠Hermes的通用记忆系统（fact_store + memory），没有为祝定制的画像层。对比前沿：
- Supermemory的ASMR系统在LongMemEval基准达到98.6%准确率
- 业界正在从RAG（检索增强生成）转向"生成式记忆"（Generative Memory）——AI主动合成记忆而非被动检索
- 斯坦福的三维记忆框架：事实记忆、程序记忆、情境记忆

祝的"画像"概念领先，但实现落后。领先在哲学（辨→知人→持续共建认知地图），落后在工程（没有独立的画像引擎）。

**WikiMeld——只写了可行性研究。** 这是项目遴选的#1，理由充分（你现在就能做、你本身就是用户、有自然演进路径）。但54页的可行性研究报告写完了，代码一行没动。而GraphRAG正在成为2026年最热的技术风口——微软开源的GraphRAG、Neo4j的Adaptive GraphRAG、SurrealDB的知识图谱RAG——整个行业在用我们设想的方式前进，但我们自己还没动手。

### 空的

**"认知地图"没有系统化。** 祝白皮书说认知地图是三大核心交付物之一（画像-长编-地图）。长编有了（AGI九面），画像说了但没做，地图——只有AGI认知地图7页和小学教育那几篇的个别案例。没有"读任何长编自动生成认知地图"的系统。认知地图仍然依赖人工撰写。

**"祝号"没有自动化。** 祝白皮书说祝号必须是观察而非问句、真诚到让人一凛。但目前的祝号仍然靠军师手写。没有"基于用户阅读行为自动生成祝号"的机制。

**"活的报告"是个概念。** ai祝#008说AI原生报告应该是交互式HTML应用——可折叠、可钻取、可切换视角、可对话。祝自己的产出仍然是纯Markdown。长编九面被推送为微信文本——8000字纯文本在手机屏上。这正是#002自己指出的"文本超载"问题。

**没有反馈闭环。** 长编推送给用户后，用户读了多少、在哪停的、在哪加速的——全不知道。画像系统需要这些数据才能运转，但数据采集端是空的。

**没有"发布端"。** 目前发布靠cron推送到Telegram/微信。但祝的定位需要更丰富的发布形态——一个真正的"消费界面"。官网(index.html)很精美但只是展示，没有与祝系统交互。

## 卷二·外部全景：2026年5月，对手在做什么

以下基于本次全网搜索。

### 最震撼的：Anthropic "Dreaming"

2026年5月6日（就是上周），Anthropic发布了"Dreaming"功能——Claude agents在会话之间有一段"梦"的时间：自主审查过去的会话记录、提取模式、改进自己的行为。

这是什么？这就是**明学"省"则的技术实现**。

曾子曰吾日三省吾身。Anthropic让它变成了"Claude agents在后台跑一段审查程序"。平台不同，做的事完全一样。

这意味着什么？意味着我们绝对不能在这个方向上落后。祝的"省"从哲学上领先了至少三年（明学v0.3是2026年5月10日的，Dreaming是5月6日发布的——几乎同时，但一个是哲学建构，一个只是工程功能），但从工程上落后了。如果Anthropic把这个功能做成熟，那所有AI助手都能"自我反思"了——祝的这个差异化就消失了。

### 最近的：NotebookLM成为"认知操作系统"

Google NotebookLM在2026年3月完成了重大升级：100万token上下文、Deep Research深度调研、电影级AI视频生成、可定制AI播客、数据分析。有人称它为"认知操作系统"。

它的核心模式——"源文件限制"（只根据用户提供的材料回答）——和祝的"长编→定本，定本由学习者自己写"有微妙的呼应。但它走的是"封闭可信"路线（只看你上传的），祝走的是"开放探索"路线（帮你画地图、带你走）。

NotebookLM已经打通了和Gemini的集成——在Gemini用Deep Research做的报告可以一键导入NotebookLM变成源文件。这个"生成→消费"的闭环，正是祝的#002选题指出的方向。

### 最在意的：GraphRAG成为2026年最大的AI知识库风口

微软的GraphRAG开源项目在2026年获得了爆发式采用。Neo4j推出Adaptive GraphRAG框架。SurrealDB推出知识图谱RAG的双查询模式。整个企业界在把RAG升级为GraphRAG。

这和WikiMeld的构想完全一致——在Markdown文件上叠加知识图谱层，提供语义导航。区别在于：GraphRAG在企业级文档上做，WikiMeld在个人wiki上做。市场在验证这个方向，但切入角度不同。

### 最需要警惕的：OpenAI GPT-5和Deep Research Agent

GPT-5已经是统一系统（聪明模型回答大多数问题 + 深度推理模式处理难题）。OpenAI的Deep Research Agent在进行多步迭代搜索、交叉验证和综合。如果他们把Deep Research能力嵌入到ChatGPT的默认体验中，那"人人都有一个Deep Research"的日子就不远了。

那时，"更好的Deep Research"就不再是一个有意义的定位。但"陪你走得道快乐的人"依然是——因为没有人会在ChatGPT里建画像、没有人会用ChatGPT做持续陪伴。

### 最有启发的：个人AI记忆系统

Supermemory的ASMR在LongMemEval达到98.6%准确率。业界从RAG转向"生成式记忆"——AI主动合成记忆而非被动检索。这和祝的"会话即画像"高度相关——画像不应该靠检索，应该靠AI主动从会话中提炼。

## 卷三·新思路：六个升级方向

### 方向一：三智能体流水线 → 五智能体深度管线

当前（v0.4.1）：
```
搜（搜索收集） → 写（整合撰写） → 劈（审读批评）
```

升级为：
```
探（勘探画地图） → 搜（深度搜索+交叉验证） → 织（编织关联） → 写（厚重化写作） → 劈（劈后给出修改指令） → 修（修改定稿）
```

六个角色，每个都有精准的提示词和验证标准：

1. **探**：给定题目，先画出知识地图草稿——核心争议是什么？关键学派/人物是谁？值得深挖的三条线是什么？输出不是资料，是"这张地图上哪几个点值得先去"。
2. **搜**：基于探的地图，进行多轮搜索——第一轮广度扫（5-8个来源），第二轮深度钻（选3个最有价值的来源全文精读），第三轮交叉验证（对比不同来源的矛盾点）。输出结构化搜索报告，每条信息标注来源、时间、置信度。
3. **织**：把搜索报告的散点织成关联网络——A发现和B发现在逻辑上是什么关系？有什么模式浮现了？有什么被忽略了？输出：关联地图+盲点标注。
4. **写**：基于织的关联地图，按祝白皮书的标准写——每段有魅句、整体有节奏、末尾是窗户不是墙。
5. **劈**：不留情面地批评——哪段缺乏数据？哪个论证有跳跃？哪个地方读起来"AI味"太重？哪里需要"一个人写出来的感觉"？输出不是笼统的批评，是**逐段标注的具体修改指令**。
6. **修**：根据劈的修改指令，逐条修改。然后三编通读。

**工程实现**：不再是48行的subagent.py。做一个`izu-pipeline.py`，管理多步流转、中间文件、版本控制。每个角色可以调不同模型（搜用DeepSeek、写用DeepSeek-v4-pro、劈用DeepSeek）。

### 方向二：落地画像系统

祝白皮书说的"会话即画像"需要一个专门的引擎。三个阶段：

**阶段A：数据采集（现在就能做）。**
- 每次用户提问，记录：问什么、什么时候问的、追问了几次、是否修改了问题
- 每次用户读长编，记录：读了多久、跳过了哪几段（需要读取端支持）、标注了什么
- 这些数据存入画像文件（JSON/YAML），不断累积

**阶段B：画像提炼（做一个AI驱动的周期任务）。**
- 每周一次，AI通读本周所有会话记录，提炼用户当前关心的方向、认知水平的变化、概念盲区
- 输出：一份"本周画像更新"，注入下一次长编的生成提示词
- 这就是Anthropic"Dreaming"的izu版本——"省"则的工程实现

**阶段C：主动适配。**
- 基于画像，自动调整长编的深度、例子选择、节奏密度
- 用户关心的方向自动加重，已经掌握的方向自动减量
- 不同用户读到同一主题的长编，感受到的深度和角度完全不同

### 方向三：把WikiMeld做出来

这是项目遴选确定的#1项目。不要再等了。

**MVP（两周内）**：
- 扫描现有170个.md文件的YAML frontmatter和`[[wikilinks]]`
- 构建知识图谱（节点+边），用JSON文件存储
- 一个简单的Web界面：左侧概念导航，右侧内容展示，中间是节点关系图
- 自然语言查询：用户输入问题，AI从图谱中定位相关知识片段，动态组装回答

**技术选型**：
- 知识图谱存储：JSON文件（MVP）→ Neo4j/SurrealDB（成熟版）
- 前端：纯HTML/CSS/JS（单文件，符合祝白皮书"一个HTML文件"的愿景）
- 后端：不需要。全部在浏览器内运行（祝的哲学：不依赖服务器，跑在用户的机器上）
- AI层：Hermes Agent的API调用

**为什么这个优先级最高？**
因为它解决了"祝的产出怎么被消费"的问题。现在祝生产长编，但消费体验是"纯文本微信推送"。WikiMeld给每一份长编一个交互式前端——不只是"读"，是"与知识互动"。

### 方向四：认知地图生成引擎

从"人工撰写认知地图"到"AI自动生成认知地图"。

**核心逻辑**：给定一份长编（比如AGI长编九面的任一面），AI自动生成七段话的认知地图——"这里有三条主要路径、路径A我走了一半你要不要继续、路径B的入口在这里、我建议你先走哪条"。

**实现**：在五智能体流水线中，"探"角色输出的就是认知地图。

### 方向五：祝号的自动化

祝号不是营销尾巴。祝号是"一个陪你走了一段路的人回过头来跟你说的话"。

**自动化祝号的前提**：必须有画像数据。知道用户读到哪里停了、哪里加速了——才能写出"你读第六段的时候停了一下"这种观察。

**在画像系统建成之前**，祝号可以由"劈"角色承担——劈完文章后，附上一句观察，基于对内容的理解和对用户（已知的画像）的了解。

### 方向六：从静态Markdown到交互式HTML

这是最"远"但最"对"的方向。

祝自己的产出应该是活的。不是推送一篇8000字的纯文本，而是推送一个链接——打开是一个HTML页面，有折叠/展开、有概念图谱、有下钻路径、有"你是决策者"和"你是研究者"的视图切换。

这正是#008和#002共同指向的终局。

**实现路径**：先做WikiMeld的交互式界面（方向三），然后把祝的长编也改成HTML输出。技术上不需要推翻现有流程——在五智能体流水线的"写"环节，指定输出格式为"交互式HTML（含折叠区块、概念图谱、视图切换）"。

## 卷四·下一步工作规划

按"能做→该做→想做"排优先级。

### 第一优先：五智能体流水线升级（1-2周）

**为什么先做这个？** 
因为它是生产引擎。引擎升级了，所有后续产出都受益。

**具体任务**：
1. 新建 `scripts/izu-pipeline.py`，替换 `subagent.py`
2. 定义六个角色的系统提示词（每个500字以上，有明确的质量标准）
3. 实现流水线管理：每步的输出作为下一步的输入，中间文件自动保存和版本控制
4. "探"角色调用DuckDuckGo做真实搜索（保留v0.4.1的能力）
5. 测试：用"AGI面10（如果有新面）"或"小学教育新课题"跑一遍完整流程

**检验标准**：跑完一遍流水线，出来的长编质量明显高于现有AGI九面。

### 第二优先：画像数据采集（本周就能开始）

**为什么先做数据采集？**
因为没有数据就没有画像，没有画像就没有个性化。而数据需要时间积累——现在开始采，三个月后才有足够的存量做提炼。

**具体任务**：
1. 在Hermes的memory中增加"画像数据"条目，记录每次研究的query、时间、深度
2. 每次长编生成完成后，自动追加一条"本次研究画像"到画像文件
3. 不要求用户任何操作，完全被动采集

### 第三优先：WikiMeld MVP（2-4周）

**为什么第三？**
因为需要前面两个先跑起来——引擎升级了，产出的长编质量更高；画像采集开始了，WikiMeld才能展示个性化。

**具体任务**：
1. 写一个`build-graph.py`脚本：扫描wiki目录，提取YAML + wikilinks + 实体共现，输出`graph.json`
2. 写一个`wikimeld.html`：单文件网页，包含三个面板——概念导航（左）、内容显示（中）、关系图（右）
3. 集成AI问答：用户在搜索框输入问题，调用Hermes Agent从图谱中检索相关片段并组装回答
4. 首次上线：把AGI长编九面作为WikiMeld上第一批可交互的知识

## 卷尾·军师的话

成市，我把桌子上的东西全部摊开看了一遍。

izu不是个空壳。它有哲学地基（无人能抄）、有方法论（已经验证）、有产出（AGI九面6万字）、有定位（真空地带）。别人做"更好的搜索"，我们做"更深的理解"。别人做"更快的答案"，我们做"更久的陪伴"。

但它有三个断点：

**第一断点：哲学→工程的转化太薄。** 明学七则的"省"（反思即更新），被Anthropic用"Dreaming"实现了。我们的哲学领先三年，但工程落后了一周。如果不赶紧把哲学变成工程，差异化会被别人的工程磨平。

**第二断点：生产→消费的管道太窄。** 祝能生产好东西，但消费体验是纯文本微信。祝白皮书自己说的"文本超载"问题，祝自己正在制造。#002和#008指出的方向，祝自己还没走到。

**第三断点：说了但没做的太多。** 画像系统、认知地图引擎、祝号自动化——这些都是祝白皮书承诺的东西，但还没实现。承诺是护城河，但兑现不了就是护城河里的水在漏。

好消息是这三个断点都能修。五智能体流水线修第一断点。WikiMeld修第二断点。画像采集起步修第三断点。

最让我安心的是：大厂正在往我们的方向上走（Dreaming、GraphRAG、NotebookLM的认知操作系统），但他们走的是"普适产品"路线，我们走的是"懂一个人"路线。这两条路在物理上永远不会交会——大厂不可能为每一个用户定制画像和记忆，因为成本太高。但祝可以——因为祝只需要懂一个人。

**"算力不是护城河，理解是。"** 这句话写得极好。现在要做的，是让它从一句漂亮的宣言变成一个运行中的系统。
