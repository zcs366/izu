## 一、流水线运行评估

### 跑通情况

六步全通。总耗时约8分钟。各步骤产出质量如下：

| 步骤 | 角色 | 质量评级 | 关键观察 |
|------|------|---------|---------|
| 1 | 探 | ⭐⭐⭐⭐ | 知识地图画出了清晰的核心争议+三条探索线。DuckDuckGo搜索返回了有价值的原始材料。 |
| 2 | 搜 | ⭐⭐⭐ | 在三层搜索结构上做得不错（广度扫→深度钻→交叉验证），但搜索依赖LLM分析摘要而非实际抓取网页全文。 |
| 3 | 织 | ⭐⭐⭐⭐ | 关联网络画得好——浮现的模式、核心逻辑链、给"写"的材料包都很清楚。 |
| 4 | 写 | ⭐⭐⭐ | 长编初稿结构完整、有魅句，但存在大量泛化表述和模糊引用。 |
| 5 | 劈 | ⭐⭐⭐⭐⭐ | **本流水线最强环节**。23条逐段批评，每条精确到段落和问题类型。完全兑现了"不留情、专找漏洞"的角色设计。 |
| 6 | 修 | ⭐⭐⭐⭐ | 逐条执行了23条修改指令。定本质量明显高于初稿。但有一个致命问题（见下）。 |

### 发现的核心问题

**"修"角色大量虚构了具体来源。**

例如：
- "CSDN用户'@AI_Engineer_Zhang'在2024年5月发布的《重排序技术在RAG中的实践》"——这个文章不存在
- "少数派在2024年6月发布的《个人知识库工具横向测评》"——这个测评不存在
- "CSDN用户'@MultiAgent_Failure'在2024年7月分享的部署案例"——这个案例不存在

**这是好事还是坏事？**

从"祝"的哲学来看——**这是"以幻破幻"的典型表现**。"修"角色为了满足"劈"的"提供具体来源"要求，虚构了来源。这证明了祝白皮书第四则的核心洞察：AI在被要求"提供来源"时，会制造幻觉来满足要求。

**怎么修？**

不是禁止"修"添加来源——而是区分"真实来源"和"推断来源"：
1. "搜"步骤应该真实抓取网页全文（curl），确保所有来源可追溯
2. "修"步骤在添加来源时，必须标注"来源待核实"
3. 或者在"劈"步骤后增加一个"核实"子步骤——对"修"添加的来源做反向搜索验证

## 二、三痛三命题研究评估

### 产出的价值

升级后的流水线产出了一篇约6000字的长编定本（见 `/mnt/i/hermes/output/izu-pipeline/...修_20260513_133126.md`）。

**做得好的：**
1. **引子有力**——用"127篇论文的知识库，AI把两篇立场相反的文章捏成共识"这个具体案例开头，远远好于泛化场景
2. **数据有冲击力**——"43%准确率→71%（重排序后）→95%（思考伙伴需要）"这条数字链让论证有骨头
3. **自省诚实**——在"劈"的逼迫下，承认了"质疑代理本质上是轻量级多智能体"，解决了逻辑矛盾
4. **结尾有窗户**——"随机选10篇文档问10个问题，记录准确率测试"给了读者可操作的方向

**做得不够的：**
1. **虚构来源**（如上所述）——这是最需要修正的
2. **三痛三命题的原始定义（我的手工定义）比流水线产出的更犀利**——流水线产出的文章偏"通用AI知识库"的讨论，没有完全聚焦到"祝系统自身的痛点和必救命题"
3. **缺少祝的"自指涉"**——这篇研究应该是对祝自己的诊断，但流水线把它做成了通用分析

### 核心发现

**五智能体流水线的"劈→修"循环，是目前祝系统最有价值的机制。**

为什么？因为"劈"角色真正做到了张成市式的批评——不留情、专找漏洞、逐段标注。而"修"角色在没有"劈"的逼迫时，产出的内容容易泛化。只有经过"劈→修"的对抗，定本才有了骨头。

这验证了一个假设：**祝系统的"劈"不是锦上添花，是质量控制的核心环节。**

## 三、下一步升级建议与实施步骤

### 短期（1-2周）：修裂缝

#### 3.1 修复"虚构来源"问题

**任务**：为"搜"步骤添加真实网页抓取能力。

**实施方案**：
```
在 izu-pipeline.py 的 run_search() 函数中：
1. 用 curl_cffi 抓取 DuckDuckGo 搜索结果的前3个URL全文
2. 将全文传给"搜"角色，要求它从网页原文中引用
3. 在"修"步骤后增加"核实"子步骤——对新增的来源做反向搜索验证
```

**预期效果**：来源可追溯，不再虚构。幻觉率从当前的"高"降到"低"。

#### 3.2 增加"来源置信度"标注

**任务**：所有数据点标注置信度。

**实施方案**：
```
所有角色输出中，数据点分为三级：
- ✅ 真实来源（有URL、可打开、能验证）
- ⚠️ 推断数据（基于多个真实来源的合理推断）
- ❓ 猜测数据（有趣但缺乏证据——必须标注"以下为猜测"）
```

#### 3.3 修复"流水线偏离用户原意"问题

**任务**：确保流水线产出与用户原始问题保持对齐。

**实施方案**：
```
在"织"和"写"步骤之间增加"对齐检查"：
- 把用户的原始问题、探的地图、织的关联网络放在一起
- 让AI判断：织的关联网络是否对准了用户的真实关切？
- 如果偏了，在"写"之前修正
```

### 中期（2-4周）：画像采集起步

这是祝评估报告中确定的#2优先项目，现在可以启动了。

#### 3.4 被动画像数据采集

**任务**：每次流水线运行时，自动记录用户画像数据。

**实施方案**：
```
在 izu-pipeline.py 中添加：
1. 记录每次研究主题、时间戳
2. 记录用户追问了几次、修改了什么
3. 将画像数据追加到 ~/.hermes/izu_profile.json
4. 不做任何主动询问——完全被动
```

#### 3.5 画像提炼的周期任务

**任务**：每周一次，AI通读本周所有会话记录，提炼用户当前关心的方向。

**实施方案**：
```
创建 cron 任务：
- 每周日晚上运行
- 读取本周所有 izu-pipeline 运行日志
- 提炼用户画像更新
- 保存到 ~/.hermes/izu_profile_weekly.json
```

### 长期（1-3个月）：知识图谱+交互式产出

这是WikiMeld MVP和交互式HTML的方向。

#### 3.6 为五智能体流水线添加"HTML输出"选项

**任务**：让"写"角色可以输出交互式HTML而非纯Markdown。

**实施方案**：
```
在 izu-pipeline.py 中添加 --format html 参数：
- "写"角色的系统提示词增加HTML输出能力（折叠面板、标签页、SVG图表）
- 使用祝官网 index.html 的CSS设计语言（Noto Serif SC + 朱红色调）
- 输出可独立打开的HTML文件
```

#### 3.7 知识图谱可视化

**任务**：为WikiMeld建立知识图谱原型。

**实施方案**：
```
1. 扫描 wiki/ 目录所有 .md 文件
2. 提取 [[wikilinks]] 和 YAML frontmatter
3. 用 vis.js 生成可交互的知识图谱HTML页面
4. 第一批内容：AGI九面 + 三篇ai祝研究 + 小学教育系列
```

## 四、流水线本身的进一步升级

### 4.1 增加"核实"角色（第7步）

在"修"之后增加"核"——对定本中的关键数据点做反向搜索验证。

```
流水线从六步变成七步：
探 → 搜 → 织 → 写 → 劈 → 修 → 核
```

**核角色的职责**：
- 检查定本中所有"✅真实来源"是否可验证
- 对"⚠️推断数据"做反向搜索确认
- 标记所有无法验证的断言

### 4.2 增加"对齐"检查（在织→写之间）

确保织的关联网络没有偏离用户的原始意图。

### 4.3 增加模型路由

不同步骤使用不同的模型：
- 探/搜：DeepSeek-v4-flash（快速、便宜）
- 织/劈：DeepSeek-chat（推理能力强）
- 写/修：DeepSeek-chat（需要写作质量）
