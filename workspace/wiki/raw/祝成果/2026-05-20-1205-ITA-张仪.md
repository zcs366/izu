# 张仪 — 最强攻击官

## 单点失败分析

**最可能导致 ITA 轨道失败的一个点：代码库的「语义冗余」根本不存在。**

### 攻击论证

Semantic RD Theory 的核心假设是知识库包含"冗余状态"——即从 irredundant core 可以重新推导出的内容。这一假设在公理系统（数学定理、Datalog 事实集）中成立，但在**人类编写的代码中可能完全不成立**。

**理由**：
1. 人类程序员在写代码时已经做了**语义压缩**——变量名是精心选择的、控制流是逻辑最优的、表达式已经是最简形式。代码在写出来之前就已经经过了一次"语义最小化"
2. 墨子的估算假设 Python 函数有 ~50 tokens 但 core 只有 ~15，但这假设 core 不需要包含变量名、字面量、具体表达式——而这正是代码语义的本质内容
3. 如果 core 是「类型签名 + 控制流骨架」，那么 core→完整代码的恢复本质上就是**以类型签名和 if/else 结构为提示的代码生成**——这是 LLM 已经在做的事，不是「压缩」

**致命场景**：
- 商鞅的 Step 2 恢复率 < 30%
- 杠杆因子 Λ < 1.2（代码几乎没有冗余）
- 结论：Semantic RD Theory 对代码不适用，因为代码已经是最小化的

### 降级方案

#### 降级到「语义压缩」退化为「结构压缩」

**新定位**：不要追求「闭包等价」的语义保真度，改为追求「下游任务等价」——即在代码搜索/补全/修复任务上，压缩前后的性能不变。

- **技术路线**：用 SAE（稀疏自编码器）对代码隐空间做稀疏化压缩
- **理论支撑**：Anthropic 的 NLA 方法——即使 bottleneck 是自然语言文本（比代码更冗余），也能保持功能性
- **评估标准**：压缩前后在 HumanEval 上的 pass@k 不变
- **工程路径**：直接借 SAE 工具 (OpenAI's SAE visualizer / TransformerLens)

**成本**：
- 比原方案多 20 工时（训练 SAE 或从开放权重模型提取）
- 预训练 SAE 可能能用（Llama 3.2 / CodeLlama 已有公开 SAE）
- 预算增量：$30-50（GPU 时间）

#### 降级到「放弃 ITA 轨道」

如果核心验证（core 提取）严重失败，直接砍掉 ITA 轨道，资源全部转给 izu。
这是最务实的选项——$15 花完得到否定性结论，止损。
