# 研究编排流水线 v4.0 — Phase 2：核战队终审

> 审阅双轨道产出：ITA（形式化验证+LLM安全闭环）、izu（测试时计算扩展）

---

## 包拯（程序审计视角）

### 两个方向的逻辑链条完整性审查

**ITA轨道逻辑链：**
```
安全需求 → 规约提取 → 形式化验证 → 反例反馈 → 修正循环
```
- **断点A**: 规约提取环节依赖LLM自身能力。如果LLM连正确的规约都提取不出来，整个链条在第一环断裂。
- **断点B**: 修正循环的收敛条件未定义——如何判断"已经足够安全"？缺乏终止条件。
- **断点C**: "安全关键路径"的选择标准是谁定的？如果选择标准本身隐含安全漏洞，整个方案失去意义。
- **审计结论**: 逻辑链存在循环依赖（LLM既做生成又做规约提取），需要外部信任锚。

**izu轨道逻辑链：**
```
推理任务 → 计算预算 → 策略选择 → 验证评分 → 结果输出
```
- **断点A**: 验证(PRM)和生成(LLM)的依赖关系没有解耦。PRM过拟合到LLM的分布=无效验证。
- **断点B**: 自适应TTC的"元特征提取器"是谁训练的？如果它也是LLM，同源偏差问题同样出现。
- **断点C**: 在Agent场景中，每个中间步骤都需要验证——但Agent产生的步骤数量本身是不确定的。
- **审计结论**: 核心问题都是"验证器的独立性"——两个方向面临同一个结构性问题。

### 结构性问题：验证器独立性危机
- ITA的验证器是SMT Solver（独立于LLM的数学工具）→ 理论上更强，但规约提取依赖LLM
- izu的验证器是PRM/ORM（也是神经网络）→ 与LLM同源，独立性存疑
- **关键建议**: ITA路线在"验证器的独立性"上天然优于izu路线

## 奥威尔（安全/控制视角）

### 安全边界与权力不平等分析

**ITA方向的安全画像：**
- **控制力**: 高（形式化验证提供数学确定性，但仅限规约范围内的安全）
- **剩余风险**: "规约外风险"——未想到的场景、未定义的约束
- **攻击面**: 
  1. LLM生成的规约可能被对抗性Prompt污染
  2. 求解器本身的漏洞（罕见但真实存在）
  3. 验证逻辑被绕过（如果Agent发现验证路径的确定性漏洞）
- **安全等级评估**: 在封闭系统中可达到高安全性，在开放系统中迅速退化

**izu方向的安全画像：**
- **控制力**: 中（TTC不直接提供安全保证，只是经济性优化）
- **剩余风险**: TTC可能掩盖而非解决安全问题——"花更多计算思考"不一定带来更安全的决策
- **攻击面**:
  1. PRM可能被训练数据毒化
  2. 自适应TTC策略可能被攻击者预测和利用（知道系统在什么情况下会减少思考）
  3. 验证回路本身消耗计算资源，可被DoS攻击
- **安全等级评估**: 比ITA方向低一个数量级——TTC不解决安全问题，只优化计算分配

### 权力不平等警示
- ITA方向赋予"验证者"极大的权力——谁控制规约，谁就控制整个系统的行为边界。规约制定者拥有事实上的绝对权力。
- izu方向赋予"策略控制器"极大的权力——谁决定TTC策略，谁就决定计算资源的分配。在高价值任务的推理上尤为关键。
- 两个方向都需要对"控制者"的问责机制，否则存在权力滥用的系统性风险。

## 鲁班（工程实现视角）

### 工程可行性对比

| 维度 | ITA方向 | izu方向 |
|------|---------|---------|
| 技术成熟度 | 中低（原型阶段） | 中（已有self-consistency等工具） |
| 工程复杂度 | 高（LLM+Solver+规约管理） | 中（vLLM+PRM管线） |
| 部署难度 | 高（需要形式化验证专家） | 中（现有推理框架可扩展） |
| 可扩展性 | 差（SMT求解对大规模状态空间脆弱） | 好（自适应策略可以工程化） |
| 成本收益 | 高风险高回报（安全护城河） | 中等风险递增回报 |
| 人才可获得性 | 极难（双重专长） | 较难（RL+推理系统） |

### 联合建议
1. **近期（0-3个月）**: 主攻izu方向（Phase 1——self-consistency基线），建立TTC基础管线
2. **中期（3-6个月）**: ITA方向从代码验证切入（Phase 1——HumanEval验证闭环），与izu方向并行
3. **远期（6-12个月）**: 两个方向融合——izus的TTC策略由ITA的验证信号指导。验证信号（SMT求解器）提供"硬约束"，TTC策略在硬约束内优化"软目标"

### 具体的融合架构示意
```
Agent行动规划 → ITA验证器（SMT求解器）→ 通过（回到Agent）→ 拒绝（返回反例）
                                     ↓
                              izu TTC策略评估
                              （这个反例需要多少额外推理？）
                                     ↓
                              Agent再推理（动态TTC）→ 再验证
```

**核心洞见**: ITA提供"正确性"，izu提供"效率"。没有正确性的效率是危险，没有效率的正确性是昂贵。两者必须共存。
