# 张仪 — 最强攻击

## 单点失败分析

### 🎯 最可能导致项目失败的一个点：
**「Skill 生态兼容 ≠ 真正用起来。izu 会兼容 MCP + SKILL.md 格式，但永远停留在兼容层，用户感觉不到变化，项目变成『为了兼容而兼容』的僵尸功能。」**

### 为什么会死

```
核心问题：izu 的内在 Agent 架构与 MCP/Skill 范式存在根本不匹配
↓
izu 的 tool 调用是线性编排（顺序执行）
MCP 协议期望的是实时双向通信（tool → agent → tool 异步推送）
↓
兼容层做成了薄薄的接口适配——能用，但不自然
↓
用户：好像能加载外部 skill 了，但还不如自己写 prompt
↓
工程师花 6 周做兼容，0 周做核心能力
↓
izu 变成了「一个能跑 MCP 但不会自进化的 Agent」= 和所有其他 Agent 一样
↓
死于平庸
```

### 根本原因
这不是技术问题，是**优先级陷阱**。兼容生态（Skill/MCP）给了工程师「在做有价值的事」的错觉，但它本身不是用户价值。用户价值是**自进化**——而自进化需要全新的记忆和 skill 获取架构，和兼容层是两个不同的方向。

## 降级方案

### 降级 A（推荐）：兼容层轻量化、核心功能优先
- MCP 兼容只做 1 周（最基本的 adapter），不做全兼容
- Skill 标准按需兼容，不预先适配所有字段
- 把节约的 5 周时间投入 Auto-Skill 和 Memory 系统
- **结果**：izu 在自进化能力上领先，兼容性逐步完善

### 降级 B：拆阶段验证
- 先只做 Skill Retrieval（第1-2周就出可见效果）
- 如果用户感知到「izu 变聪明了」，再继续记忆系统
- 如果用户没感觉，立即止损，重新评估路线

### 降级 C：不做生态兼容，专注核心
- 不接 MCP，不接 SKILL.md
- 全力做自进化 Agent 核心
- 等自进化做稳定了再考虑兼容
- **风险**：6个月后 izu 变成孤岛

## 推荐
**选降级 A。** 兼容层只花 1 周做完基本的，剩下时间全部投入自进化核心能力。用户不会因为「支持 MCP」而用 izu，但会因为它「越来越聪明」而留下来。
