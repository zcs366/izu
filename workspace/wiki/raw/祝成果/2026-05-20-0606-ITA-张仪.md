# 张仪 — 最强攻击

## 单点失败分析

### 🎯 最可能导致项目失败的一个点：
**「代码行为语义在隐空间中不是线性可分的」**

### 为何这是最致命的

整个 ITA 路线的前提假设是：代码行为（功能等价类、算法类别、框架用法）在隐空间中存在线性方向，就像语言身份那样（Goncharov 已验证）。但这是一个高风险的假设迁移：

1. **语言身份 vs. 代码行为是两种不同性质的语义**。语言是表面特征（词汇、语法模式），在隐空间的分布可能天然各向异性。代码行为是深层功能特征——排序算法的多种实现可能隐空间距离很大。
2. **Goncharov 的结果不能直接泛化**。他们验证的是「英语 vs 西班牙语」的语言方向——这是有明确分布差异的二元分类。代码行为的类别边界可能模糊得多（快速排序和归并排序的实现非常不同，但行为等价）。
3. **如果线性探针 < 60%，所有后续实验失去理论基础**。PCA steering、FSQ 都是有损的，但如果基础表示已经无法线性区分，steering 不可能有效。

### 怎么死

```
实验1 代码行为线性探针 → 准确率 53%
↓
实验2 PCA steering → 无法找到可靠的代码行为方向
↓
实验3 FSQ round-trip → 量化信息损失进一步模糊类别边界
↓
结论：代码行为在隐空间是高度非线性的
↓
ITA 路线的核心假设崩塌
↓
需要非线性 steering（需额外研究，时间×3）
```

## 降级方案

### 降级 A（最小代价）：缩小 scope
- 不追求控制「代码行为」，只控制「代码语言/框架」——这是 Goncharov 已验证的可控维度
- 实际价值：控制多语言生成的语种准确率（对 izu 的跨语言代码理解有用）
- 工作量减少 60%，风险降低 80%

### 降级 B（中等代价）：换非线性方法
- 用 MLP 替代线性 steering，或使用 Ablation-based activation editing
- 代价：从推理时 O(1) 变为需要 2-pass 推理或微调
- 需要额外 2-4 周研究时间

### 降级 C（方向转换）：不做 steering，做 code representation quality
- 如果 steering 不可行，改做「代码嵌入质量评估」
- 用 FSQ 量化后的嵌入做代码搜索/聚类，评估代码域压缩的可用性
- 有价值但不 sexy，适合快速产出

## 推荐
**先做实验1（线性探针），这是最大风险点的直接检验。** 如果通过（>85%），继续；如果不通过，立即执行降级 A。
