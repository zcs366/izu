## 1. 问题定义：痛在哪里

### 1.1 现状画像

你有一个已经跑起来的 wiki（170 个 .md 文件，66 个索引页面），结构清晰：

| 目录 | 数量 | 功能 |
|------|------|------|
| `entities/` | 40 | 人、组织、工具 |
| `concepts/` | 24 | 抽象概念和方法论 |
| `comparisons/` | 1 | 对比分析 |
| `raw/` | 96 | 原始文章、论文、转录 |
| `projects/` | 4 | 项目文档 |

每天的 cron 自动抓取微信公众号/B 站/知乎内容，`ingest.py` 解析入库，更新 index、log。这是一个已经自动运转的「信息处理工厂」——原料进来，文章出去。

### 1.2 三个真实痛点

#### 痛点 A：信息检索是「翻箱倒柜」

wiki 现在是扁平文件堆。你要查「OpenClaw 和 Hermes 谁更适合做自动化」，得：

1. 先知道 `comparisons/hermes-vs-openclaw.md` 存在
2. 在终端/编辑器里 grep 或找文件
3. 打开看——发现它只记了对比，没记「我的具体场景该怎么选」
4. 再去翻 `entities/openclaw.md`、`entities/hermes-agent.md`、`concepts/agent-three-evolution-stages.md`
5. 自己脑内拼图

80% 的时间花在「找」和「拼」上，不是「用」。

> **数据点**：170 个文件，85 个文件包含 `[[wikilinks]]`。关系已经写在文件里了，但没人把它们画出来。

#### 痛点 B：知识是「死」的，不是「活」的

今天 ingest 了一篇关于「HTML 取代 Markdown」的文章。这篇信息和 wiki 里已有的 `ai-output-format-html-vs-markdown.md` 概念冲突吗？补充吗？推翻吗？

**目前：你完全不知道。** 除非你手动去对比。

wiki 在「积累」，没有在「演化」。每天都往里倒新料，但旧知识的更新、矛盾检测、关联发现——全靠你的大脑。170 个文件，人的工作记忆容量是 7±2 个单位。你不可能记住所有页面写了什么。

#### 痛点 C：知识消费门槛高

wiki 是写给自己看的 Markdown。你想分享给朋友/同事：

- 「这是我整理的 Agent 生态对比」
- 对方看到的是纯文本 `.md` 文件
- 没有图、没有交互、没有导航
- 除非对方也熟悉这套 wiki 结构，否则无法消费

**你的知识被困在文件格式里。**

### 1.3 一句话概括

> 你现在有一个可靠的「知识仓库」，但缺一个「知识服务层」——能搜、能问、能画、能主动通知你「有新东西需要你知道」。

## 2. 产品构想：WikiMeld 是什么

### 2.1 核心定义

**WikiMeld 是架设在现有 Markdown wiki 之上的「动态知识服务层」。**

它不改动你任何现有文件。不加新数据库。不重构 wiki 结构。它是一个纯「壳」——读取 .md 文件，构建知识图谱，提供 AI 问答，渲染交互页面。

### 2.2 四大功能模块

#### 模块 A：知识图谱层

**做什么：** 从 170 个 .md 文件中自动提取实体、概念、关系，构建有向图。

**输入：**
- YAML frontmatter（type, tags, sources, confidence）
- `[[wikilinks]]` 跨页面引用
- 文章内实体共现分析（同一 source 被多个页面引用）
- raw/ 与 entities/concepts 的从属关系

**输出：**
- 节点：entity（40）/ concept（24）/ comparison（1）/ raw article（96）/ project（4）
- 边：`提及`、`对比`、`引用`、`属于同源`、`前置知识`、`冲突`（人工标注后）
- 图数据库可查（Cypher 查询或向量检索）

**关键设计决策：**
- 不需要用户写任何新标记。`[[wikilinks]]` 和 frontmatter 已经足够
- 可选增强：用 LLM 做一次全库扫描，自动发现隐含关系（如「X 文章批评了 Y 文章的观点」）

**工作量估值：**

| 子任务 | 工具/方法 | 工作量 |
|--------|-----------|--------|
| YAML/链接解析器 | Python `yaml` + `re` 解析 frontmatter 和 wikilinks | 4 小时 |
| 关系图构建（内存） | NetworkX 建立图模型 | 3 小时 |
| 向量化语义搜索层 | `sentence-transformers` 将每个页面转为 embedding，`faiss` 本地索引 | 6 小时 |
| LLM 关系增强可选 | 用 DeepSeek API 扫描页面对，发现隐含关系 | 8 小时 |

#### 模块 B：智能问答与导航

**做什么：** 在知识图谱上叠加 AI 问答。用户不用「搜」关键字，而是「问」问题。

**交互方式：**
- 自然语言查询：「OpenClaw 和 Hermes 各自最适合什么场景？」
- 模糊查询：「那个讲记忆系统的胖小天是谁来着？」
- 探索式查询：「我 wiki 里关于 AI 安全有哪几篇文章？它们之间什么关系？」
- 溯源查询：「conflict.md 里说的那个矛盾，原始来源是什么？」

**技术方案：**

有两种策略，按阶段实施：

**策略 B1（Phase 1 即可做）：RAG + 图谱上下文**
1. 用户问题 → DeepSeek API 理解意图
2. 解析出目标实体/概念/标签
3. 在图谱中找到关联节点集合
4. 将节点的 Markdown 内容拼成上下文窗口
5. DeepSeek 生成回答，每条引用标注来源页面

**策略 B2（Phase 2+）：Agent 式多跳推理**
1. Hermes Agent 接收问题
2. 调用 wiki-graph skill（搜索图谱节点）
3. 根据返回的信息决定下一步（继续深入某个节点，还是对比两个节点）
4. 多轮工具调用后合成答案
5. 核心能力：Hermes 本身就擅长工具编排，这里只需要写一个 skill

**工作量估值：**

| 子任务 | 工具/方法 | 工作量 |
|--------|-----------|--------|
| B1 RAG 查询管道 | Python `httpx` 调 DeepSeek API + 图谱上下文拼接 | 6 小时 |
| B2 Hermes Skill 开发 | 写一个 wiki-query skill，注册 qdrant/knowledge 工具 | 10 小时 |
| 查询结果前端展示 | 回答 + 引用链接 + 相关节点推荐 | 4 小时 |

#### 模块 C：动态渲染引擎

**做什么：** 把 .md 文件渲染成交互式 HTML 页面，不是静态的——是「在浏览器里可以操作」的。

**页面类型：**

| 视图类型 | 用途 | 交互能力 |
|----------|------|----------|
| **文章视图** | 标准 Markdown 渲染，保持原有排版 | 到其他页面的可点击链接 |
| **图谱视图** | 力导向图，节点 = wiki 页面，边 = 关系 | 拖拽、缩放、点击节点打开文章 |
| **时间线视图** | 按 created/updated 排列，展示知识演化 | 时间轴滚动、筛选日期范围 |
| **卡片视图** | 类似 Notion gallery，展示页面摘要 | 按标签/类型/置信度筛选 |
| **对比视图** | 专门渲染 comparison 类型，左右/表格对比 | 可折叠/展开维度 |

**技术选型：**

**方案一：轻量级（推荐 Phase 1）**

| 组件 | 选型 | 理由 |
|------|------|------|
| 构建工具 | **Next.js**（或更轻的 Vite + React） | 你熟悉 React 生态 |
| Markdown 渲染 | **react-markdown** + **rehype-raw** | 支持自定义组件注入 |
| 图谱可视化 | **vis-network** 或 **d3-force** | 轻量，不需要 GraphQL 后端 |
| 时间线 | 手写 CSS + React 组件 | 需求简单，不必引入库 |
| 部署 | **静态导出**（next export）或 **单 HTML 文件** | 无需服务器，可直接放到 /mnt 共享 |

**方案二：全面交互（Phase 2+）**

| 组件 | 选型 | 理由 |
|------|------|------|
| 图谱 | **Cytoscape.js** | 比 vis-network 更强，支持布局算法切换 |
| 全文本搜索 | **Lunr.js**（前端）或 **MeiliSearch**（后端） | 前端索引适合静态部署 |
| 状态管理 | **Zustand** | 比 Redux 轻 10 倍 |
| 图表 | **Recharts** | 基于 D3 的 React 图表库 |

**为什么不用 Obsidian/Notion？**
- Obsidian 是编辑器，不是展示层——你不想把 "壳" 做成另一个编辑器
- Obsidian Publish 付费且不支持你自定义 AI 问答
- 你要的是「展示 + 查询」层，不是「编辑」层

**工作量估值：**

| 子任务 | 工作量 |
|--------|--------|
| 核心 Markdown 渲染器 + wikilink 解析跳转 | 8 小时 |
| 图谱视图（vis-network） | 10 小时 |
| 卡片/时间线视图 | 6 小时 |
| 搜索功能（Lunr.js 前端索引） | 4 小时 |
| 对比视图专用渲染 | 4 小时 |

#### 模块 D：更新推送与矛盾检测

**做什么：** 让 wiki 从「被动查阅」变成「主动通知」。

**两个核心能力：**

**D1：矛盾检测**
- 每天 cron 触发 ingest 后，自动运行矛盾检测
- 新入库的文章与已有 entities/concepts 对比
- DeepSeek API 判断：冲突？补充？推翻？无关？
- 检测到冲突 → 在目标页面标注 `contradiction` → 推送通知到微信

> 例如：今天 ingest 了一篇说「Markdown 必被 HTML 取代」的文章，而 wiki 里 `ai-output-format-html-vs-markdown.md` 只是中立记录了两方观点。系统检测到「新文章立场强烈倾向于 HTML 取代论」→ 推送：「注意：新文章对 Markdown 的未来做出激进预测，与当前中立记录形成张力，建议更新概念页面。」

**D2：个性化更新推送**
- 追踪用户关心的实体/概念（可配置关注列表）
- 当这些页面有更新时，主动推送到微信
- 推送格式：一句话摘要 + 变化类型 + 链接

**技术方案：**

```
[ingest.py 完成] → [触发 WikiMeld 检测脚本]
    │
    ├── D1: 取新 raw 的 embedding → 与已有节点 embedding 对比
    │   ├── 相似度 > 0.85 → LLM 分析关系（补充/冲突/无关）
    │   └── 冲突 → 更新 frontmatter + 记录到 log
    │
    └── D2: 检查关注列表 → 有更新 → 微信推送
```

**工作量估值：**

| 子任务 | 工作量 |
|--------|--------|
| 矛盾检测管道（embedding + LLM 分类） | 8 小时 |
| 微信推送集成（利用已有 Hermes 微信渠道） | 4 小时 |
| 关注列表管理（前端配置页面） | 4 小时 |

## 3. 技术架构：具体怎么搭

### 3.1 整体架构图

```
┌─────────────────────────────────────────────────────────┐
│                    用户浏览器（前端）                       │
│  React SPA: 文章视图 / 图谱视图 / 问答界面 / 时间线        │
└────────────────────────┬────────────────────────────────┘
                         │ HTTP / WebSocket
                         ▼
┌──────────────────────────────────────────────────────────┐
│               WikiMeld 服务层（轻量后端）                    │
│                                                          │
│  ┌──────────┐  ┌──────────┐  ┌──────────────────────┐   │
│  │ 文件解析器  │  │ 图谱引擎  │  │ AI 查询引擎          │   │
│  │ (Python)  │  │(NetworkX)│  │ (DeepSeek API 调用)  │   │
│  └──────────┘  └──────────┘  └──────────────────────┘   │
│                                                          │
│  ┌────────────────────────────────────────────┐          │
│  │ 更新检测器 (cron hook → embed → compare → notify) │   │
│  └────────────────────────────────────────────┘          │
└────────────────────────┬──────────────────────────────────┘
                         │ 读 .md 文件（只读，永不修改）
                         ▼
┌──────────────────────────────────────────────────────────┐
│               /mnt/i/hermes/wiki/（现有文件系统）            │
│  entities/  concepts/  comparisons/  raw/  projects/     │
│  完全不动。不加新文件。不加新目录。                           │
└──────────────────────────────────────────────────────────┘
```

### 3.2 技术选型明细

#### 前端

| 选项 | 方案 A（推荐 Phase 1） | 方案 B（Phase 2） |
|------|------------------------|-------------------|
| 框架 | Vite + React (TS) | Next.js |
| 部署方式 | 静态 HTML（放 /mnt 共享） | Node 服务 |
| 图谱 | vis-network (CDN 加载) | Cytoscape.js |
| 搜索 | Lunr.js (前端索引) | MeiliSearch (后端) |
| 构建产物 | 单文件或几个文件 | 完整 SPA |
| 学习成本 | 低，你已熟悉 React | 中，需要学 SSR |
| **工作量大** | **6-8 小时上手** | **16-20 小时** |

**推荐策略：Phase 1 用方案 A，Phase 2 迁移到方案 B。** 前端架构允许渐进增强。

#### 知识图谱存储

这是最关键的决策点。你不需要 Neo4j。

| 方案 | 存储方式 | 查询能力 | 适合阶段 | 工作量 |
|------|----------|----------|----------|--------|
| **A: 内存图 + JSON 持久化** | NetworkX 建图，定期 dump 为 JSON | Python 内存查询，够快 | Phase 1 | 3 小时 |
| **B: SQLite + 关系表** | node 表 + edge 表 + embedding 表 | SQL 查询，支持持久化 | Phase 1-2 | 6 小时 |
| **C: Qdrant (向量数据库)** | Docker 运行，存 embedding | 语义搜索，但关系查询弱 | Phase 2 补充 | 4 小时 |
| **舍弃: Neo4j** | 需要 Docker/服务器 | 过强了，大炮打蚊子 | 不做 | 0 |

**推荐：Phase 1 用方案 A（内存图 + JSON 快照），Phase 2 升级到 B（SQLite）。** 你的 wiki 才 170 个文件，内存图完全够用。Neo4j 是为百万级节点设计的，不要引入不必要的运维负担。

#### AI 层

你已有 DeepSeek API 和 Hermes Agent。接入方式：

**方式 1：直接 API 调用（Phase 1 推荐）**

```python
import httpx

async def ask_wiki(question: str, context: str) -> str:
    response = await httpx.AsyncClient().post(
        "https://api.deepseek.com/v1/chat/completions",
        headers={"Authorization": f"Bearer {DEEPSEEK_KEY}"},
        json={
            "model": "deepseek-chat",
            "messages": [
                {"role": "system", "content": f"你是一个 wiki 知识库助手。以下内容是用户 wiki 中的相关页面：\n\n{context}"},
                {"role": "user", "content": question}
            ],
            "temperature": 0.3
        }
    )
    return response.json()["choices"][0]["message"]["content"]
```

**工作量：2 小时**（封装一个 client 类，处理重试/流式/错误）

**方式 2：Hermes Agent Skill（Phase 2）**

写一个 Hermes skill `wiki-meld`，注册 `wiki_graph_search` 和 `wiki_page_read` 工具。Hermes 自动处理记忆、多轮对话、工具编排。这是更优雅的方案，因为 Hermes 已经是你整个系统的「大脑」。

```yaml
# wiki-meld skill (Phase 2)
name: wiki-meld
description: "查询和探索 WikiMeld 知识图谱"
tools:
  - wiki_graph_search: 搜索图谱节点和关系
  - wiki_page_read: 读取指定页面完整内容
  - wiki_compare: 对比两个或多个页面
```

**工作量：8 小时**（含测试和调试）

#### 集成方式：「壳」的哲学

核心约束：**不改动现有 wiki 的任何文件。**

实现方式：
1. WikiMeld 服务以**只读方式**读取 `/mnt/i/hermes/wiki/` 下的 .md 文件
2. 图谱信息存储在 `wiki/_wikimeld/` 目录（新目录，Git 可 ignore）
3. 入口：一个 `hermes skill` 或一个本地 HTTP 服务
4. 前端：静态文件，用 `file://` 或 nginx 或简单 HTTP server 即可访问

**为什么能不改文件？**
- 关系信息已经在 `[[wikilinks]]` 和 frontmatter 里了
- 不需要额外标注
- LLM 自动补全隐含关系，但写回图谱缓存，不是写回原文件

### 3.3 与 Hermes Agent 的关系

| 能力 | Hermes Agent 能提供的 | WikiMeld 自己做的 |
|------|----------------------|-------------------|
| 自然语言理解 | DeepSeek API 调用 | 上下文拼装 |
| 工具编排 | wiki-meld skill 编写 | 技能逻辑 |
| 微信推送 | Hermes 微信渠道 | 推送内容生成 |
| 记忆 | Hermes 记忆系统存储查询历史 | 图谱缓存 |
| 定时触发 | 已有 cron 体系 | 检测脚本 hook |

**最佳实践：Hermes 是「大脑」，WikiMeld 是「神经系统」——Hermes 知道该问什么，WikiMeld 知道去哪找答案。**

## 4. MVP 路线图

### 4.1 Phase 1：最小可行（2 周）

**目标：** 一个能在浏览器里打开的交互式 wiki 页面，能搜、能浏览、能看到图谱。

**交付物：**
- ✅ 静态站点生成器：将 170 个 .md 文件转为可交互 HTML
- ✅ 图谱视图：vis-network 力导向图，节点 = 页面，边 = wikilinks
- ✅ 文章视图：Markdown 渲染 + wikilinks 可点击跳转
- ✅ 卡片视图：按类型/标签筛选页面
- ✅ 全文搜索：Lunr.js 前端搜索
- ✅ 不需要后端服务器，一键刷新即可

**不做：**
- ❌ AI 问答
- ❌ 矛盾检测
- ❌ 更新推送
- ❌ Hermes Skill

**技术栈：**
- Python 脚本（解析 .md → 生成 JSON 索引）
- Vite + React (TS) 前端
- vis-network 图谱
- Lunr.js 搜索
- 输出为静态文件

**详细计划：**

| 天 | 任务 | 产出 |
|----|------|------|
| 1-2 | 写 Python 解析器：遍历 wiki 目录，解析 frontmatter、wikilinks、标签 | `wikimeld_parser.py`，输出 `index.json` |
| 3-4 | 搭建 Vite + React 项目，实现文章渲染器 | 能打开一个 .md 页面 |
| 5-6 | 实现图谱视图（vis-network 力导向图） | 看到所有节点和边，点击跳转 |
| 7-8 | 实现卡片视图和全文搜索 | 按标签筛选 + 搜索框 |
| 9-10 | 实现时间线视图 + 对比视图 | 按时间排序 + 对比渲染 |
| 11-12 | 美化 UI + 响应式适配 | 手机能打开 |
| 13-14 | 测试 + 部署（放 /mnt/i/hermes/output/wikimeld/） | 可访问的静态站 |

**总工作量：约 14 天 × 2-3 小时/天 = 28-42 小时**

### 4.2 Phase 2：核心功能（1 个月）

**目标：** 能「问」问题，能自动检测矛盾。

**交付物：**
- ✅ AI 问答界面：输入问题，DeepSeek 基于图谱上下文回答
- ✅ 矛盾检测管道：每次 ingest 后自动运行
- ✅ 微信推送：检测到矛盾 / 关注页面更新时推送
- ✅ WikiMeld 后端服务（Python FastAPI 轻量服务）
- ✅ Hermes Skill `wiki-meld`（基础版，支持查询）

**技术栈：**
- FastAPI 后端（serve JSON + AI 接口）
- DeepSeek API 调用封装
- Sentence-transformers + FAISS 本地 embedding
- Hermes Skill 注册

**详细计划：**

| 周 | 任务 | 产出 |
|----|------|------|
| 1 | 写 FastAPI 后端，提供图谱查询 + 页面内容 API | 前端可以问 API 拿数据 |
| 2 | 实现 AI 问答管道（RAG，用 DeepSeek） | 问答界面可用 |
| 3 | 实现矛盾检测 + 微信推送 | 新内容入库后自动检测 + 通知 |
| 4 | 写 Hermes `wiki-meld` skill + 整合测试 | 全链路通 |

**总工作量：约 30 天 × 1-2 小时/天 = 30-60 小时**

### 4.3 Phase 3：完整产品（3 个月）

**目标：** 成为一个真正「活」的知识系统。

**交付物：**
- ✅ 多用户支持（可选，如果有分享需求）
- ✅ 知识溯源：每条回答都标注「根据 X 页面第 Y 段」

## 6. 风险与对策

### 6.1 技术风险

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| LLM 幻觉导致问答不可靠 | 中 | 高 | Chain-of-thought + 严格引用溯源 + 每条回答标注置信度 |
| 图谱构建效果差（关系漏/错） | 中 | 中 | 先在 10 个文件上验证，合格再全量跑；设计快速修正接口 |
| 前端性能（170 个节点的力导向图） | 低 | 中 | vis-network 支持聚类，超过 100 节点自动分组 |
| DeepSeek API 不稳定/限流 | 低 | 中 | 实现请求重试 + 本地 fallback（用离线 embedding 兜底） |
| 解析器兼容性（有特殊格式的 .md） | 低 | 低 | 优雅降级：解析失败的文件跳过，标注为「未解析」 |

**最大技术风险：LLM 幻觉。** 用户如果对 AI 回答产生误信，比没有 AI 还糟。
**对策：** 所有 AI 回答必须标注引用来源（"根据 XXX.md 第 Y 段"），并显示置信度标签（High/Medium/Low）。

### 6.2 时间风险

| 风险 | 概率 | 影响 | 对策 |
|------|------|------|------|
| 每天只有 1 小时，3 个月可能拖到 6 个月 | 高 | 中 | Phase 1 两周内先出可用的东西，看到成果才有动力继续 |
| 卡在某个技术点上停滞 | 中 | 中 | 设定「2 小时原则」：一个技术问题超过 2 小时无解，降级方案 |
| 与日常工作和家庭冲突 | 高 | 高 | 固定每天/每周的时间窗口（如早上 7:00-7:45），雷打不动 |

**时间管理建议：**
- Phase 1 用「冲刺模式」：两周内每天固定 2 小时，周末 4 小时
- Phase 2-3 用「常速模式」：每天 45 分钟，像每天刷牙一样
- 不要追求完美。Phase 1 的「最小可行」意思是：它可以丑、可以慢、可以有 bug，但它必须**能跑起来让你看到图谱**

### 6.3 放弃风险

这是最大的风险。不是做不了，是不想做了。

**为什么可能放弃：**
- 新鲜感消退：规划阶段最兴奋，写到第 3 天发现「也就那样」
- 完美主义反噬：想着「图谱应该有智能聚类」，结果光调布局就花了一周
- 已有工具替代心态：「Obsidian 的图谱也可以啊，干嘛自己写」
- 看不到早期反馈：写了代码没人用，不知道好不好

**对策：**

1. **Phase 1 必须两周出成品。** 不是两周才开始，是两周就结束。先跑起来，再优化。谱视图哪怕丑到炸，能点开页面就算赢。

2. **第一天就放个截图发朋友圈。** 社交反馈是持续动力的核心燃料。先承诺，后交付。

3. **明确「不做清单」。** 写一份 DONTs.md，上面写着 Phase 1 不做什么、Phase 2 不做什么。完美主义是项目杀手，不做清单比待办清单更重要。

4. **跟已有工具对比，不要自欺欺人。** Obsidian 的图谱只是看「谁链接谁」，WikiMeld 能做的是 AI 问答 + 矛盾检测 + 主动推送。不要因为 Obsidian 也有图就怀疑自己——功能深度差很多。

5. **设定「庆祝节点」。** Phase 1 完成 → 吃顿好的；AI 问答第一次成功 → 发条公众号；矛盾检测抓到第一条冲突 → 截图保存。这些纪念物是维持动力的锚点。

## 附：一句话做 vs 不做的判断

**做，如果：**
- 你每天至少一次在 wiki 里翻找信息且感到烦躁
- 你觉得「知识多了反而不知道怎么用」这个矛盾值得解决
- 你想有一个拿得出手的全栈 AI 项目作为个人品牌资产

**不做，如果：**
- 你的 wiki 只有你自己用，且你对自己脑内拼图的速度满意
- 你只是想要一个好看的图谱——那装个 Obsidian 就够了
- 你最近三个月有更优先级的事情（比如家庭、重要项目、健康）
