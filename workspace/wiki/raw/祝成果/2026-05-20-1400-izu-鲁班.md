## izu Round 2: 鲁班
### 工程可行性（产品侧）

基于子产的需求判断和韩信的远景，评估产品方案在Hermes上的工程可行性。

### 1. 当前Hermes产品化的差距

| 需求 | 当前状态 | 差距 |
|------|---------|------|
| 委托式交互 | 纯命令行+自然语言 | 缺少"委托确认"环节和操作预览 |
| 信任信号 | 无（直接输出结果） | 无置信度/不确定性/能力边界表达 |
| 可逆操作 | git revert类手动操作 | 无一键撤销机制 |

### 2. 三阶段产品工程方案

**阶段A：信任信号注入**（3-5天）
```
Day 1-2: 在Agent输出中增加置信度标注
  - 每项回答附带(置信度: 确定/较确定/不确定/不知道)
  - 不确定时增加"我需要更多信息：..."
  
Day 3-5: 在输出首行增加能力边界声明
  - "我能做到：[具体列表]"  
  - "我不能做到：[具体列表]"
  - "你可能需要手动做：[列表]"
```

**阶段B：委托式交互流**（1-2周）
```
设计：
1. 用户输入任务
2. 系统生成执行计划预览
3. 用户确认/修改/拒绝
4. 系统执行（显示进展）
5. 系统输出结果
6. 用户评分/反馈

实现：
- workdir/plan_preview.md 作为确认中介
- Command: /plan (生成并显示计划)
- Command: /go (确认执行)
- Command: /cancel (拒绝)
```

**阶段C：可逆操作机制**（2-3周）
```
- 每次Agent执行的关键操作，在操作前创建快照
- 实现 /undo 命令（回退到最后一次关键操作）
- 实现 /revert <操作ID> 命令（回退到指定操作）
- 操作日志：workdir/actions.log 保存最近20次操作
```

### 3. ITA-izu协同工程

ITA验证器（阶段一）→ 产品化为信任信号（izu阶段A）
- ITA验证器返回的完整度评分 → 直接作为置信度标注
- 验证器的缺失项 → "不确定"信号 + 追问理由

### 4. 不做的边界

| 不做什么 | 理由 |
|----------|------|
| 不建独立UI/Web界面 | 当前Hermes以命令行为主，投入UI产出比低 |
| 不做Agent个性化配置文件 | 用户画像需要大量数据积累，当前用户不足以支撑 |
| 不做实时GUI dashboard | 与命令行输入模式不兼容 |
