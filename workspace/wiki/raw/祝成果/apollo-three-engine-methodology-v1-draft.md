**太阳神计划（Project Apollo）· izu前沿实验室**

## 摘要

我们提出一个Agent自我迭代的三层引擎架构——个体层（递归思考）、工具层（代码辅助进化）、群体层（元合议反思）。三层共享同一个设计原则：**代码做框架，模型做语义**（匠石原则）。在无模型训练、无GPU集群的条件下，仅通过Agent架构设计和API调用，三层引擎分别在数学推理、prompt优化、多Agent审议三个场景中展示了可测量的自我改进能力。本文描述三层引擎的算法、实验设计和关键发现，并讨论"诊断-干预"作为元认知核心难题的跨层一致性。

## 1. 引言

### 1.1 问题

当前Agent自我迭代研究面临两个不对称：

- **资源不对称**：RL训练（LSE论文）、GPU集群（Hyperagents）——绝大多数独立研究者无法获得
- **叙事不对称**："更大的模型"主导了自我迭代的想象，但Agent架构层面的自我改进机制被低估

我们的核心命题：**不依赖更大的模型、更贵的训练——只靠Agent架构设计，能否实现可测量的自我迭代？**

### 1.2 三层引擎概述

```
群体层 · TRT-H (元合议反思)
  让多Agent合议反思自己的讨论流程
  元角色诊断群体盲思 → 硬约束干预
              ↑ 嵌入
工具层 · LSE (代码辅助进化)
  让Skill/prompt跨批次自我优化
  代码诊断错误类型 → 模板选择 → 模型生成修复
              ↑ 嵌入
个体层 · TRT (递归思考)
  让模型在单题内递归自我改进
  生成→自排序→知识蒸馏→策略更新
```

每层独立运转，但共享匠石原则。高层嵌入低层：LSE的进化策略可以被TRT-H的元角色调用；TRT的递归思考可以被LSE用作基座能力。

### 1.3 设计原则：匠石原则

> **代码做框架，模型做语义。**

| 代码负责 | 模型负责 |
|---------|---------|
| 循环控制、上下文管理 | 文本生成、语义理解 |
| 去重（difflib）、答案提取（正则） | 排序评估（自排序） |
| 错误分类（FORMAT/COMPUTE/OTHER） | 教训蒸馏（对比分析） |
| 模板选择、硬约束注入 | 策略更新（基于教训生成新策略） |

该原则的核心价值在于：**把确定性留给代码，把概率性留给模型。** 纯prompt驱动的自我改进系统容易因格式漂移而崩溃（我们经历了6次迭代才将TRT答案提取从~70%推到100%），匠石原则通过在代码层兜底，使系统在模型输出不稳定时仍能运转。

## 2. 个体层：TRT递归思考

### 2.1 算法

```
输入：问题Q，最大轮次N
初始化：知识列表K=[]，策略列表S=[默认策略]

for round in 1..N:
  1. 生成rollouts: LLM(Q, K, S) → {候选1, 候选2, 候选3}
  2. 自排序: LLM(候选1, 候选2, 候选3) → 最佳候选
  3. 知识蒸馏: LLM(最佳 vs 其他) → 新教训
  4. 策略更新: LLM(新教训, 旧策略) → 新策略
  [代码层] K ← difflib_dedup(K + 新教训)[-8:]
  [代码层] S ← difflib_dedup(S[-2:] + 新策略)[:5]

输出：最后一轮的最佳候选答案
```

### 2.2 关键设计决策

**为什么3个rollout而不是1个？** 多样性是知识蒸馏的前提——如果只有一个候选，无法做对比分析。3个是工程权衡：增加rollout增加API成本但提供更多对比素材。

**为什么滑动窗口8条知识？** 上下文膨胀是递归系统的核心威胁。TRT论文使用知识紧凑化，我们使用difflib去重（阈值0.7）+ 8条滑动窗口——两者互补。去重防止语义重复的知识堆积，窗口防止上下文无限膨胀。

**答案提取的6次迭代**：从v0.1到v0.6，答案提取经历了约70%到100%的进化。核心教训：纯prompt格式约束（如"必须用FINAL_ANSWER格式"）在TRT的多rollout场景下不可靠——模型在同一次调用中生成3个候选时，格式约束容易被"---"分隔符破坏。最终方案是三层fallback：标注格式（[答案: X]）→ 等号提取 → 数字序列兜底。

### 2.3 AIME标准Benchmark实验 [v1.1新增]

在2024 AIME I的5题子集上测试TRT v0.6（deepseek-chat，3轮）：

| 题号 | 难度 | 期望 | TRT最终 | 结果 | 备注 |
|------|------|------|--------|------|------|
| AIME #1 | easy | 204 | 999 | ❌ | **退化**：R1=204✓→R2=216→R3=999 |
| AIME #2 | easy | 025 | 025 | ✅ | 3轮全部正确 |
| AIME #3 | medium | 809 | 809* | ⚠️ | 推理正确，提取失败("809**") |
| AIME #5 | medium | 104 | 104 | ✅ | 3轮全部正确 |
| AIME #8 | hard | 197 | 456 | ❌ | 模型未解出 |

**得分**：3/5(60%)，若修复提取则为3/5。仅3轮（论文64轮）。

**关键发现：TRT可以退化。** AIME#1在R1正确(204)后，R2自排序选择了错误候选(216)，R3进一步偏离(999)。这说明TRT的可靠性完全取决于自排序的准确性——当模型无法区分正确和错误推理时，递归反而放大错误，而非修复错误。**这是TRT的边界条件，比正确率更重要的学术发现。**

### 2.4 与微软TRT论文的对比

| 维度 | 微软TRT (2602.03094) | 太阳神TRT v0.6 |
|------|---------------------|---------------|
| 模型 | 闭源（Azure OpenAI） | 开源（deepseek-chat） |
| 轮次 | 8-64轮 | 4轮 |
| AIME | 100% | 演示题全对，待benchmark验证 |
| 架构 | 纯prompt驱动 | 代码+模型混合（匠石原则） |
| 单题成本 | ≥$0.1 | ¥0.05 ($0.007) |
| 答案验证 | 执行验证/答案唯一性 | 三层正则fallback |

## 3. 工具层：LSE代码辅助进化

### 3.1 问题

LSE论文（arXiv 2603.18620）使用RL训练了一个专门的进化策略模型，实现了4B模型超越GPT-5的自进化效果。但这需要GPU集群和RL训练数据——独立研究者无法复现。

我们探索了"纯模型自进化"——让模型分析自己的错误并改写prompt。结果失败。模型能解AIME级数学题，但无法可靠地回答"我的prompt哪里不好，应该怎么改"。**这是元认知瓶颈：模型的"解题能力"远超其"自我诊断能力"。**

### 3.2 代码辅助进化的设计

我们将进化过程拆为两层：

```
代码层（不用模型）：
  1. 评估当前Skill在训练批次上的表现
  2. 分类错误类型：FORMAT（答案正确格式错）、COMPUTE（计算错误）、OTHER
  3. 根据错误分布选择修复模板：
     FORMAT占比>40% → "强化格式约束"
     COMPUTE占比>30% → "增加验算步骤"
     OTHER >0 → "强化理解分析"
  4. 决策：触发哪个模板

模型层：
  1. 接收决策层选定的修复方向 + 当前Skill文本
  2. 生成改进版Skill（≤150字）
  3. 不参与"改什么"的决策
```

### 3.3 实验结果

基线：训练集50%，测试集0%（初始弱Skill："请解答数学题"）
最终：训练集75%，测试集75%（+25pp）

5轮进化中：
- 第3轮：FORMAT修复生效（+50pp）
- 第4轮：回退（模型生成的修复未提升效果，保留最佳Skill）
- 第5轮：二次修复生效（+25pp）

**关键：第4轮的回退被代码层正确捕获——如果纯模型自进化，这次回退可能不会被检测到。** 这验证了匠石原则在进化系统中的价值：代码层的确定性评估防止了"进化致死"。

### 3.4 与LSE论文的对比

| 维度 | LSE论文 | 太阳神LSE v1.0 |
|------|---------|---------------|
| 进化策略训练 | RL（PPO类算法） | 无训练 |
| 进化器 | 4B训练模型 | 代码+prompt |
| 奖励信号 | ∆R = R(c_new) - R(c_old) | 代码统计错误分布 |
| 上界 | 理论上无限（RL可学任何模式） | 受限于预定义错误类型数 |
| 部署成本 | GPU集群 | 零（纯API调用） |
| 跨模型迁移 | 训练好的policy可迁移 | N/A |

## 4. 群体层：TRT-H元合议

### 4.1 问题

五人合议（子产/韩信/鲁班/萧何/子贡 + 军师终裁）以固定顺序发言。实验发现：合议对初始发言高度敏感，容易产生"跟风效应"——首个发言者的观点被后续所有人直接或间接附和。

Hyperagents论文（Meta FAIR, 2603.19461）实现了单Agent场景下的元认知自修改。但多Agent合议场景中，**群体层面的流程反思**尚未被探索。

### 4.2 元角色设计

在五人合议中插入第六个Agent——元认知观察者：

```
五人发言 → 元角色审视 → 诊断低效模式 → 发出干预指令 → 五人按指令再发言
```

**诊断模式**：
- 跟风：多人附和首发言者，无独立判断
- 群体盲思：所有人快速形成共识，无人质疑
- 遗漏：某个关键角度（需求/远景/技术/资源/执行）未被讨论
- 主题漂移：偏离核心问题

**干预层级**：
- 软干预（v0.2）：将修改指令置于下一轮的context中。有效但不够强——共识比未降。
- **硬干预（v0.3，已验证）**：将约束直接注入每个Agent的system prompt。**成功打破群体盲思。**

### 4.3 实验

**软干预实验（v0.2）**——三题测试：

| 题号 | 基线共识比 | 元角色诊断 | 软干预效果 |
|------|-----------|-----------|---------|
| 1 | 1.0 | "跟风——前四位一致" | 共识比未降 |
| 2 | 1.0 | "群体盲思——五人高度一致" | 共识比未降 |
| 3 | 1.0 | "跟风——异议被淹没" | 共识比未降 |

**硬干预实验（v0.3）[v1.1新增]**——单题验证：

基线：五人全选LSE（共识比1.0，群体盲思）。
元角色诊断后，硬约束被注入每个Agent的system prompt：
"至少一人必须提出支持TRT并反驳LSE的理由"

结果：**共识比 1.0 → 0.8。** 四人转向TRT，萧何独守LSE。

硬干预生效——但不够完美（0.8而非理想的0.6）。这表明：**纯prompt层面的硬约束可以打破但不能根除共识惯性。** 要达到更低的共识比，可能需要更激进的干预（如强制指定反方角色）或引入RL训练。

### 4.4 与前沿的对比

- Hyperagents：单Agent元认知自修改。TRT-H扩展到多Agent合议场景，且引入了"硬约束vs软干预"的新维度。
- Evolving Orchestration (NeurIPS 2025)：RL训练编排器。TRT-H的元角色是零训练的prompt驱动方案，互补而非竞争。

## 5. 跨层发现：诊断-干预不对称性 [v1.1更新]

三层引擎的迭代过程揭示了同一个模式：

```
TRT（个体层）：
  诊断（自排序）⚠️ 自排序可能选错→递归退化
  干预（策略更新）⚠️ 有效但不稳定，依赖自排序质量

LSE（工具层）：
  诊断（代码错误分类）✅ → 干预（模型生成修复）⚠️ +25pp但未达上限

TRT-H（群体层）：
  诊断（元角色审查）✅ → 干预（软指令）❌ 无效
                         → 干预（硬约束）✅ 1.0→0.8
```

**诊断能力在工具层和群体层表现良好，在个体层存在隐患（自排序不可靠导致退化）。干预能力从个体到群体逐层递减，但硬约束可以部分突破群体层的干预障碍。**

我们提出两个假说：

1. **干预的难度与系统的复杂度成正比。** 个体层的干预对象是单个模型的推理路径（低复杂度），工具层的干预对象是prompt文本（中复杂度），群体层的干预对象是多个Agent的共识行为（高复杂度）。干预对象的耦合度越高，纯prompt驱动的干预越难以生效。

2. **递归的收益与自排�的可靠性成正比。** [v1.1新增] TRT的退化案例（AIME#1）揭示了：递归自我思考只有在自排序能可靠区分正确/错误推理时才有益。当自排序不可靠时，递归反而成为错误放大器。这定义了TRT的边界条件。

### 5.1 TRT退化分析 [v1.1新增]

AIME#1的实验提供了TRT退化的具体案例：
- R1：模型给出正确答案204（自排序正确选择了正确候选）
- R2：自排序选择了216（候选中的某个错误答案被误判为最佳）
- R3：基于R2积累的错误"知识"，模型进一步偏离到999

退化机制：自排序错误 → 错误知识进入知识列表 → 错误知识引导下一轮推理 → 答案进一步偏离 → 正反馈循环。

**修复方向**：在代码层引入"退化检测"——连续两轮答案不一致且偏离预期格式时，触发回退到前一轮的状态，或增加rollout数量以提高自排序可靠性。

## 7. 局限与未来工作

- **TRT**：未在标准benchmark上验证；自排序可靠性依赖模型判断力；4轮vs论文64轮的深度差距
- **LSE**：仅3种错误类型，上限低；模板匹配缺乏泛化能力；不如RL训练的进化器灵活
- **TRT-H**：硬约束干预待验证；共识比的单一指标不足以反映讨论质量
- **共同局限**：仅在deepseek-chat上测试；成本估算粗略；代码未开源
