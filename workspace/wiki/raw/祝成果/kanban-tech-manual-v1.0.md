## 第一章 概览与核心理念

### 1.1 什么是看板方法

看板方法（Kanban Method）是一种**渐进式改进的知识工作管理方法**。它通过可视化工作流、限制在制品数量、管理流动来帮助组织更有效地交付价值。

> **核心定义**（Kanban University）：看板方法是一套通过识别组织当前状态、定义期望的未来状态、然后以最小的阻力逐步演进的管理方法。

### 1.2 起源：从丰田到知识工作

看板的物理形式——"信号卡"——诞生于 1940 年代后期的丰田生产系统（Toyota Production System, TPS）。大野耐一（Taiichi Ōno）注意到美国超市的补货机制——货架空出来才补货，而不是按计划大量推送——由此创造了"拉动式生产"。

在看板系统中，下游工序消耗了零件，才会向上游发出"看板"信号要求补货。这套机制的核心洞见是：**只有被消费掉的东西才应该被生产。** 这彻底颠倒了传统的"推送"逻辑。

| 时期 | 里程碑 |
|------|--------|
| 1940s | 大野耐一在丰田工厂引入物理看板卡片 |
| 1953 | 丰田正式在总厂机械车间部署看板系统 |
| 2004 | David J. Anderson 在微软 XIT 部门首次将看板应用于 IT 服务管理 |
| 2007 | Anderson 首次用"看板"描述其在 Corbis 的软件开发实践 |
| 2010 | Anderson 出版《Kanban: Successful Evolutionary Change for Your Technology Business》 |
| 2011 | Kanban University 成立，发布《Kanban Method》蓝皮书 |
| 2016 | 《Essential Kanban Condensed》发布，确立六项核心实践 |
| 2020-2025 | 看板方法从 IT 扩展到市场营销、HR、医疗、教育、个人生产力 |

### 1.3 核心理念：变化的哲学

看板方法建立在两个基础之上：

**A. 变更管理三原则（Change Management Principles）**

1. **从现状开始（Start with what you do now）**——不推翻现有流程，不要求重整。在现有基础上改进。
2. **同意追求渐进式、演化式变革（Agree to pursue incremental, evolutionary change）**——大爆炸式的变革失败率太高。看板的承诺是"今天比昨天好一点"。
3. **鼓励各层级的领导行为（Encourage acts of leadership at all levels）**——改进不只在管理层的会议室里发生。任何看到问题的人都可以发起改进。

**B. 服务交付三原则（Service Delivery Principles）**

1. **理解并聚焦于客户的需求和期望**
2. **管理工作，让人们围绕工作进行自组织**
3. **定期审查服务网络和相关政策以改善成果**

### 1.4 看板 vs Scrum vs Waterfall

| 维度 | Waterfall | Scrum | Kanban |
|------|-----------|-------|--------|
| **节奏** | 一次性交付 | 固定时间盒（Sprint, 1-4周） | 连续流，无固定迭代 |
| **角色** | PM, BA, QA... | PO, SM, Dev | 无强制角色 |
| **变革方式** | 推翻重来 | 革命式（每个 Sprint 都可能大改） | 演化式（从现状渐进） |
| **计划变更** | 抵制变更 | Sprint 内不鼓励变更 | 随时可调整优先级 |
| **度量重点** | 偏差 vs 计划 | 速率（Velocity） | 流动效率、周期时间、吞吐量 |
| **适用场景** | 需求极稳定的项目 | 需求可分批交付的产品开发 | 连续流动的服务/运维/支持类工作 |
| **核心约束** | 范围固定 | 时间固定 | WIP（在制品）固定 |

> **看板不是 Scrum 的替代品，是 Scrum 的补充。** Vanguard 的案例证明：看板可以帮助 Scrum 团队突破"Scrum stall"——在达到一定成熟度后，Scrum 团队的交付速度反而开始下降的困境。Vanguard 团队在引入看板后，交付吞吐量提升 4 倍，平均交付时间缩短至原来的 1/4。（来源：Kanban University Case Study — Vanguard）

### 1.5 一个关键类比：高速公路

把工作想象成高速公路上的车流：

- **Waterfall**：一条车道，所有车排队走，一辆慢所有人都慢。
- **Scrum**：每两周放一批车上去，两周后清空再放下一批。
- **看板**：多车道但**限流**——每条车道最多并排走 3 辆车（WIP 限制）。车走了一辆才能上一辆。不存在整批堵住的情况。

看板的洞见：**大多数工作问题不是"做得太慢"，而是"做了太多"**。

## 第二章 看板系统搭建指南

### 2.1 设计你的第一块看板

**工具选择矩阵：**

| 工具 | 适合场景 | 优点 | 缺点 |
|------|---------|------|------|
| 物理白板 + 便利贴 | 同地办公团队（≤10人） | 可见性极强，零学习成本 | 无法远程，无数据统计 |
| Trello | 小团队，轻量需求 | 免费版足够，拖拽直观 | 高级分析需付费 |
| Notion | 需要文档+看板一体 | 灵活，可定制 | 学习曲线中等 |
| Jira | 研发团队 | 集成开发工具链 | 重，小团队杀鸡用牛刀 |
| Linear | 追求速度的产品团队 | 极快，键盘优先 | 扩展性有限 |
| SwiftKanban / Kanbanize | 严肃的看板实践 | 原生 CFD、WIP 告警 | 需付费 |
| Lark (飞书) 多维表格 | 中国企业生态 | 与钉钉/企微互通 | 看板功能偏弱 |

### 2.2 看板的解剖学

一块完整的看板包含以下组成部分：

**A. 列（Columns）= 工作状态**

最简形式：
```
待办 → 进行中 → 完成
```

推荐的最小真实看板：
```
需求池 → 就绪 → 开发 → 测试 → 部署 → 完成
```

每一列代表工作项在当前流程中所处的状态。列的设计原则：**一列 = 一个明确的"完成标准"切换点**。从一列移到下一列，意味着工作项的质量/状态发生了质变。

**B. 泳道（Swimlanes）= 工作类型或优先级**

横向泳道用于区分不同类型的工作流或优先级：
- 按类型：常规需求 / 紧急修复 / 技术债务
- 按优先级：P0 / P1 / P2
- 按团队：前端 / 后端 / 数据

**注意**：初学时不建议立即引入泳道。用同一套列跑两周，等看清楚了瓶颈再分。

**C. 卡片（Cards）= 工作项**

每张卡片至少包含：
- 标题（一句话说清楚）
- 负责人（可选，取决于团队文化）
- 状态（由所在列决定）
- 阻塞标记（如果被 blocked）

推荐额外信息（看情况加）：
- 预计周期时间 / 截止日期
- 依赖标记（"在等XX完成"）
- 标签（功能 / 修复 / 改进）

### 2.3 WIP 限制的设定

**WIP（Work In Progress，在制品）限制** 是整个看板系统最核心的参数。

> **WIP 限制的物理学原理（利特尔法则）**：
> 平均周期时间 = WIP 数量 ÷ 吞吐率
>
> 即：同时做的事越多，每件事完成得越慢。

**初始 WIP 限制的经验公式：**

| 方法 | 公式 | 示例（5人团队） |
|------|------|----------------|
| 人数法 | WIP = 人数 × 1~1.5 | 5~8 |
| 列限制法 | 每人同时在 1-2 件 | 开发列 = 3~5 |
| "少一个"法 | 当前同时进行数 - 1 | 如果现在同时做 6 件 → 先设 5 |

**设定 WIP 限制的铁律：**

1. **从宽松开始**——设一个你现在基本能做到的数字
2. **只有超过 80% 的时间都能遵守时，才收紧**
3. **发生阻塞时先解决阻塞，不要先放宽 WIP**
4. **每列单独设，不要只设一个全局 WIP**

### 2.4 服务等级（Classes of Service）

并不是所有工作项都同等重要。看板通过**服务等级**来区分不同工作项的流动策略：

| 服务等级 | 说明 | WIP 分配策略 | 典型占比 |
|---------|------|------------|---------|
| **加急（Expedite）** | 不处理会造成重大损失 | 预留 1 个槽位或按需触发 | <5% |
| **固定交付日期（Fixed Date）** | 有硬性截止日 | 基于截止日倒推，用延迟成本来排优先级 | 10-15% |
| **标准（Standard）** | 默认等级，FIFO | 正常的拉动策略 | 60-75% |
| **无形（Intangible）** | 做了好但不做也不会死的 | 只在没有标准类工作可拉取时做 | 10-20% |

> **加急不等于紧急。** 加急是"不做损失非常大"，紧急是"有人喊的声音大"。区分的关键：用延迟成本（Cost of Delay）来量化。

## 第三章 看板界面与核心机制

### 3.1 拉动式系统运作逻辑

看板是**拉动系统（Pull System）**，不是推送系统。工作项不是被"分配"给成员的——成员在有能力处理下一项工作时，从上游"拉取"。

**拉动机制的三个触发条件：**

1. 下游出现空闲容量（WIP 未满）
2. 上游有待处理的工作项
3. 按优先级（最高优先级优先）拉取

> **类比**：寿司回转带。厨师把做好的寿司放上传送带。你只拿你想吃的。如果你不拿，传送带上的寿司会越来越多——这就是 WIP 堆积的信号。厨师看到没人拿金枪鱼，就知道该少做金枪鱼。

### 3.2 工作项的生命周期

```
[创建] → [就绪] → [开发中] → [评审中] → [测试中] → [部署中] → [完成]
                                        ↑____________↓
                                          (返工回路)
```

**每一个列都应该有明确的"完成定义"（Definition of Done, DoD）：**

| 列 | DoD 示例 |
|----|---------|
| 开发中 → 评审中 | 代码已提交，单元测试通过，自测完成 |
| 评审中 → 测试中 | 至少一人 Review 通过，无阻塞性意见 |
| 测试中 → 部署中 | 所有验收条件通过，无 P0/P1 缺陷 |
| 部署中 → 完成 | 已上线生产环境，监控正常 |

### 3.3 阻塞处理与标记

阻塞（Blocked）是看板方法中最需要被"可视化"的状态。一项工作被阻塞时：

- 在卡片上标记"阻塞"（通常用红色标签或🔴）
- 在这个阻塞被解决之前，该卡片**不计入 WIP 限制**——你不能因为一个外部依赖让整个流程卡住
- 记录阻塞发生的时间和原因

**阻塞分类：**

| 类型 | 示例 | 处理策略 |
|------|------|---------|
| 外部依赖 | 等第三方 API 上线 | 升级到负责人层面推动 |
| 内部依赖 | 等另一个团队产出 | 看是否可以先绕过 |
| 信息缺失 | 需求不明确 | 立即挂起，优先获取信息 |
| 能力不足 | 团队不会某项技术 | 培训 or 外援 or 换人 |

> **军师的建议**：每天站会第一件事不是"你昨天做了什么"，而是看阻塞栏。一个阻塞卡了超过 3 天就需要升级。

### 3.4 统计与可视化

**累积流图（Cumulative Flow Diagram, CFD）**

CFD 是看板最强大的诊断工具。一张 CFD 图告诉你：

- 每列在不同时间点有多少卡片
- 哪一列在持续膨胀（瓶颈所在）
- WIP 整体趋势（上升=承诺过多）
- 平均周期时间（两条曲线间水平距离）
- 平均交付率（"完成"曲线的斜率）

**解释 CFD 的快速指南：**

| CFD 信号 | 意味着什么 |
|----------|---------|
| 某列面积在扩大 | 该列是瓶颈，WIP 在堆积 |
| "开发"很宽"测试"很窄 | 开发产出远大于测试吞吐——需要平衡 |
| "完成"曲线斜率下降 | 整体速率变慢，可能疲劳或堆积过多 |
| 多列同时膨胀 | 全局 WIP 过高，需要整体收紧 |

## 第四章 实战：从零搭建一个看板系统

### 4.1 场景设定

你负责一个小型运输公司的调度和安全管理。日常工作包括：

- 处理客户运输订单（每天 5-15 个）
- 司机排班和管理（8 个司机）
- 车辆维修和安全检查
- 季度报表和合规文件
- 偶尔的客户投诉处理

你一个人干这些，有时加上兼职帮忙的。事情不大但很杂，经常漏掉。

### 4.2 Step-by-Step 搭建

**Step 1：列出现有流程**

先别急着画看板。拿一张纸，列出你现在处理工作的步骤：

```
客户下单 → 排车 → 通知司机 → 跟车 → 签收 → 对账
维修 → 报修 → 安排维修 → 取车
报表 → 收集数据 → 做表 → 提交 → 存档
```

你会发现，你的工作不是"一件接一件"，而是**三股并行但速度不同的流**。

**Step 2：合并为统一的列**

把三条流合并为一个看板。用一个看板管所有事情，而不是三块看板——你只有一个人。

```
待处理 → 处理中 → 等待别人 → 完成
```

解释：
- **待处理**：所有新进来的事，包括新订单、新维修需求、新报表
- **处理中**：你正在做的事
- **等待别人**：你做了你的部分，在等司机回电/等客户回复/等修车厂打电话
- **完成**：这件事完了

**Step 3：设定 WIP 限制**

因为你只有一个人 + 偶尔帮忙的——"处理中"设 WIP = 3。"等待别人"不设限（因为那不是你在等，是工作在等）。

**Step 4：运行第一周**

每天早上花 3 分钟看一眼看板：
1. "处理中"有 3 件吗？没满就拉一件新的。
2. "等待别人"里有没有超过 3 天的？有就催一下。
3. 新来的事直接丢进"待处理"——别打断正在做的事。

### 4.3 第一周的真实结果预测

| 指标 | 用看板前 | 用看板后（预计） |
|------|---------|----------------|
| 每天焦虑次数 | 5-8（"我忘了什么来着"） | 1-2（只需扫一眼） |
| 被遗漏的事项 | 1-2 件/周 | 0（全在板子上） |
| 被阻塞事项的发现时间 | 几天到几周 | 当天或次日 |
| 完成事项的可见性 | 感觉自己"什么都没干" | 能看到"完成"列慢慢增长 |

## 第五章 核心参数详解

### 5.1 周期时间（Cycle Time）

**定义**：从工作项**开始处理**到**完成交付**的时间。

周期时间 = 完成时间 - 开始处理时间

**注意区分**：周期时间 ≠ 交付时间（Lead Time）。交付时间从**请求提出**开始算。周期时间从**开始动手**开始算。中间的时间差是你"还没开始做"的时间——往往是最大的浪费。

**目标**：对于知识工作（写代码/写文档/设计），单个工作项的目标周期时间通常为 **2-5 天**。超过 10 天的需要检查：不是事太大就是被阻塞了。

### 5.2 交付时间（Lead Time）

**定义**：从**客户提出需求**到**需求被满足**的总时间。

Lead Time = 完成时间 - 需求提出时间

> **看板的终极目标**：缩短 Lead Time，提高可预测性。

**利特尔法则（Little's Law）在这两个指标上的应用**：

```
平均 Lead Time = 平均 WIP ÷ 平均吞吐率
```

这意味着：**要缩短交付时间，要么减少同时做的事（降 WIP），要么提高完成速度（升吞吐率）。前者远比后者容易。**

### 5.3 吞吐率（Throughput）

**定义**：单位时间内完成的工作项数量。

吞吐率 = 完成的工作项数 ÷ 时间段

**看板不度量"工作量"，度量"完成量"。** 10 张卡片"进行中"不代表你干了 10 件事——只代表你打开了 10 个未完成的承诺。只有"完成"列里的才算数。

### 5.4 WIP 限制的科学

WIP 限制不是管理手段——是**物理约束**。大脑能同时追踪的复杂任务不超过 2-3 个（认知心理学中称为"工作记忆容量"，Miller's Law 指 7±2 但对于需要深度思考的复杂任务，实用上限是 2-3）。

**WIP 过高的信号：**

| 信号 | 说明 |
|------|------|
| 周期时间持续上升 | 每件事都做得很慢 |
| 大量工作在"等待"状态 | 上下文切换成本太高 |
| 完成的事项质量下降 | 注意力分散导致错误 |
| 团队成员焦躁 | 心理负担过重 |
| 吞吐率反而下降 | 多任务并行的边际收益变负 |

> **数据验证**：Kanban University 2024 年报告显示，强制实施 WIP 限制的团队，交付速度平均提升 37%。（来源：Kanban University, State of Kanban Report 2024）

### 5.5 累积流图（CFD）的深度解读

CFD 不是一个"看看就好"的报表。它是你的**流程诊断仪**。

**CFD 健康信号检查清单**：
- [ ] 所有带状区域的宽度都在缩小或保持稳定（没有某一列在无限扩大）
- [ ] "完成"区域稳步上升（吞吐率一致）
- [ ] 各列之间的色带平行（流动稳定）
- [ ] 整体宽度（总 WIP）没有突然跳升

### 5.6 WIP 老化（Aging）

**定义**：工作项在当前状态停留的时间。

WIP Aging 是比平均周期时间更精细的信号。平均周期时间可能看起来不错，但中间混了几张卡了很久的卡片——平均值抹平了异常。

**WIP Aging 的实践**：
- 卡片旁边标注"当前状态第X天"
- 第 3 天：黄色（关注）
- 第 7 天：橙色（需要讨论）
- 第 14 天：红色（必须升级，考虑是否终止或拆分）

## 第六章 进阶技术详解

### 6.1 STATIK：系统化引入看板的方法

**STATIK（Systems Thinking Approach to Introducing Kanban）** 是看板大学推荐的系统化引入方法论。它不是"先画个板子再说"，而是**先理解系统再设计看板**。

**STATIK 六步法：**

| 步骤 | 做什么 | 产出物 |
|------|--------|--------|
| 1. 识别服务 | 你的团队/组织提供什么服务？ | 服务清单 |
| 2. 理解客户 | 谁在消费这些服务？他们关心什么？ | 客户画像+满意度指标 |
| 3. 理解当前系统 | 绘制当前工作流（不是理想的，是真实的） | "照镜子"流程图 |
| 4. 识别需求源和类型 | 工作任务从哪里来？有几种类型？ | 需求类型+占比 |
| 5. 发现不满意之处 | 当前系统哪里让客户/自己不满意？ | 痛点清单 |
| 6. 设计看板系统 | 基于以上信息设计列、WIP限制、服务等级 | 看板设计文档 |

> **关键陷阱**：人们倾向于跳过第 3 步（照镜子），直接跳到第 6 步（设计一个"理想"的看板）。结果是设计出来的看板和现实脱节，没人用。

### 6.2 看板节奏（Kanban Cadences）

看板有七种标准会议节奏（Kanban Cadences），用来建立反馈回路：

| 节奏 | 频率 | 参与者 | 目的 |
|------|------|--------|------|
| **每日站会（Daily Standup）** | 每天 15 分钟 | 团队 | 同步流动状态，识别阻塞 |
| **补货会议（Replenishment）** | 每周或按需 | 团队+产品负责人 | 决定下批做什么 |
| **交付规划（Delivery Planning）** | 按交付周期 | 团队+利益相关者 | 确认交付内容和时间 |
| **服务交付评审（Service Delivery Review）** | 每两周 | 团队+客户/业务方 | 评审已交付成果，收集反馈 |
| **运营评审（Operations Review）** | 每月 | 团队+管理层 | 审视流程指标，决策改进方向 |
| **风险管理（Risk Review）** | 每月 | 团队 | 识别和管理交付风险 |
| **战略评审（Strategy Review）** | 每季度 | 领导层 | 长期方向调整和重大投资决策 |

**不要一次性引入全部七种。** 从每日站会 + 补货会议开始。运行两个月稳定后再加。

### 6.3 看板成熟度模型（Kanban Maturity Model, KMM）

KMM 定义了看板实践的七个成熟度级别，帮助组织理解自己的位置和下一步方向：

| 级别 | 名称 | 特征 |
|------|------|------|
| 0 | **受挫（Oblivious）** | 不知道有问题，或拒绝承认 |
| 1 | **团队聚焦（Team-focused）** | 单团队在使用看板，可视化已建立 |
| 2 | **客户驱动（Customer-driven）** | 围绕客户需求设计服务，有了服务等级概念 |
| 3 | **适应能力（Fit-for-purpose）** | 团队能主动适应市场变化，数据驱动决策 |
| 4 | **稳健（Built to Last）** | 组织级别的最佳实践，文化牢固 |
| 5 | **行业引领（Market Leader）** | 在行业内处于领先地位 |
| 6 | **生存能力（Antifragile）** | 不仅能承受变化，能从变化中变强 |

> **BBVA 案例**：拥有 30,000+ 员工的国际银行 BBVA 利用 KMM，从"团队聚焦"级别推进到"适应能力"级别。关键动作是将聚焦点从"团队做得怎么样"转移到"客户需求被满足得怎么样"。（来源：Kanban University — BBVA Case Study）

### 6.4 Flight Levels（飞行高度）

Flight Levels 是 Klaus Leopold 提出的看板分层模型，用于解决"每个团队都有自己的看板但整体交付还是一团糟"的问题：

| Flight Level | 聚焦 | 典型看板粒度 |
|-------------|------|------------|
| **Level 1: 运作层** | 单团队的工作执行 | 任务级卡片 |
| **Level 2: 协调层** | 多团队之间的端到端协调 | 需求/特性级卡片 |
| **Level 3: 战略层** | 组织级别的投资组合管理 | 史诗/项目级卡片 |

> **核心洞见**：只优化 Level 1 没有用——如果 Level 2 协调烂，单个团队再快也是在错误的赛道上冲刺。

### 6.5 延迟成本（Cost of Delay）

延迟成本是将"做完这件事的紧迫性"量化为经济指标的方法：

**延迟成本分类（Don Reinertsen 模型）：**

| 类型 | 描述 | 示例 |
|------|------|------|
| **紧急（Urgent）** | 每延迟一周，损失固定金额 | 监管合规截止日，过期罚款 |
| **时间敏感（Time-sensitive）** | 延迟越久→损失越大，但非线性的 | 节日促销功能，过了节就没价值 |
| **信息敏感（Info-sensitive）** | 延迟的损失是不确定性 | 市场调研——早做早知道方向 |
| **标准（Standard）** | 延迟的成本相对平稳 | 常规功能优化 |

**WSJF（Weighted Shortest Job First）排序公式**：

```
WSJF = 延迟成本 ÷ 工作量（或周期时间）
```

在"延迟成本差不多"的情况下，**优先做周期时间短的事**——能更快交付价值。

## 第九章 避坑指南

### 坑 1：把看板当成"把便利贴贴墙上"

**现象**：画了三栏，贴了一堆便利贴，但没有任何规则——WIP 不设限，卡片随手拖，站会不开。

**原因**：以为看板的威力来自"可视化"。错。可视化只是第一步——核心是限制 WIP 和管理流动。

**修复**：
1. 先从设一个 WIP 限制开始（哪怕只设"进行中 ≤ 团队人数 × 1.5"）
2. 一周后查看：有人绕过 WIP 了吗？为什么？
3. 三个月后再引入 CFD

### 坑 2：WIP 限制太松 → 形同虚设

**现象**：设了 WIP = 15，团队只有 6 个人。限制永远不被触发。

**原因**：怕设太低影响交付。这是一种"保护幻觉"——高 WIP 并不保护你，它只是让你的瓶颈不可见。

**修复**：
1. 先设一个"你觉得有点不舒服"的数字
2. 如果两周内从未触发 WIP 限制，调低 20%
3. 重复直到 WIP 限制每周被触发 1-2 次

### 坑 3：没有阻塞处理机制

**现象**：卡片卡了三个 Sprint，静静地躺在"进行中"栏，没人提。

**原因**：阻塞没有成为"团队关心的指标"。

**修复**：
1. 在每日站会第一个问题改成："有没有被阻塞的卡片？"
2. 阻塞超过 3 天的卡片自动变成红色
3. 阻塞超过 7 天的卡片自动升级到主管/PO

### 坑 4：看板变成了"状态展示板"，不是"管理工具"

**现象**：看板上的信息每天更新一次（站会时），其余时间没人看、没人拖。

**原因**：团队把看板当成"汇报工具"而非"自主管理工具"。

**修复**：
1. 确保每个人都能在自己完成一项工作后**自己拖卡片**（不需要等站会）
2. 把看板放在最显眼的位置（物理白板挂在墙上；数字板设为首屏）
3. 把"是否在看板上反映真实状态"纳入团队规范

### 坑 5：加列太多 → 流程碎片化

**现象**：看板有 12 列——"收集需求"→"初评"→"复评"→"等待审批"→"准备开发"→"开发"→"等待 QA"→"QA"→"等待 UAT"→"UAT"→"等待部署"→"部署"→"完成"。

**原因**：误以为列越多代表流程建模越精确。

**修复**：
1. 从 3-5 列开始
2. 只有当一列中的卡片超过 7 张且内部状态确实不同时，才拆分
3. "等待XX"类列是一个危险信号——如果一列叫"等待"，它通常在掩盖一个没有解决的流程问题

### 坑 6：用看板来微管理（Micromanagement）

**现象**：管理者把看板当监控工具——"我看你那张卡片两天没动了"。

**原因**：混淆了"可视化"和"监控"的区别。

**修复**：
1. 看板的数据是团队的镜子，不是管理者的鞭子
2. CFD 和周期时间用于团队自省，不用来考核个人
3. 如果一个卡片两天没动，可能是：在深度思考 / 被阻塞 / 需要帮助。**先问"你需要什么帮助"，不是问"你为什么没动"**

### 坑 7：卡片太大 → 一张卡片做两周

**现象**：一张卡片在"进行中"从周一待到下周五，最后变成"精神负担"。

**原因**：工作项粒度太粗。

**修复**：
1. 拆卡原则：**一张卡片应该在 1-3 天内可完成**
2. 如果一张卡预计超过 5 天 → 拆成 2-3 张
3. 拆分方法：按模块拆、按步骤拆、按用户场景拆

### 坑 8：没有"完成"的定义

**现象**：一张卡片被拖到"完成"，但第二天又拖回来了——因为其实没做完。

**原因**：没有明确的"完成定义"（Definition of Done）。

**修复**：
1. 每一列之间的切换都必须有明确的 DoD
2. DoD 写成清单，而不是一句话
3. 最先从"进行中→完成"这一跳开始定义

### 坑 9：忽视数据 → 凭感觉改进

**现象**：团队运行看板六个月，但从来没有看过 CFD 或周期时间。改进全是"我觉得我们应该..."。

**原因**：觉得看数据太专业了，或者不知道怎么读。

**修复**：
1. 先从最简单的开始：每周看"完成"列里的卡片数（吞吐率）
2. 第二个月引入 CFD（大多数数字看板工具自动生成）
3. 第三个月引入 WIP Aging

## 第十章 进阶技巧与最佳实践

### 10.1 个人看板（Personal Kanban）

Jim Benson 在《Personal Kanban》中将看板简化为两条规则：

1. **可视化你的工作**
2. **限制你的 WIP**

个人看板的推荐结构：

```
本周待办 → 今天 → 进行中 → 完成
           ↑
       (WIP ≤ 3)
```

个人看板特别适合：
- 自由职业者和远程工作者
- 同时处理家庭+工作+学习的人（如本文读者）
- 需要管理"多角色生活"的人

### 10.2 看板 + OKR 结合

OKR（Objectives and Key Results）和看板可以互补：

- **OKR 回答"要去哪"**——目标是什么，怎么衡量
- **看板回答"现在到哪了"**——哪些工作在推进、哪些被卡住了

结合方式：
1. 每个 KR（关键成果）作为一张 Epic 级卡片
2. 将 KR 拆分为任务级卡片，放入看板
3. 每周通过看板的"完成"列来追踪 KR 进度
4. 看板的 CFD 告诉你：按现在的流动速度，这个 OKR 能按时完成吗？

> 数据支持：2023 年 State of Agile 报告显示，32% 的组织将 OKR 链接到 Epic 级别进行交付度量，比 2022 年增长 5%。（来源：17th State of Agile Report）

### 10.3 看板的"五分钟规则"

从 Jim Benson 的 Personal Kanban 衍生：

> **如果一件事五分钟内能做完——直接做，不要建卡片。**

反面的规则是：**如果一件事需要超过 30 分钟——建一张卡片，放入看板。**

这个规则防止两个极端：为了看板而看板（什么事都建卡片），或者因为"懒得建卡片"把事情忘掉。

### 10.4 学习路线：从 Day1 到 Week4

| 周 | 学习目标 | 实践任务 | 阅读材料 |
|----|---------|---------|---------|
| Week 1 | 理解基本概念 | 搭建个人看板，运行一周 | Kanban University 入门文章 |
| Week 2 | 掌握 WIP 限制 | 收紧 WIP，观察对周期时间的影响 | 《Personal Kanban》前 3 章 |
| Week 3 | 理解流动指标 | 开始看 CFD 和周期时间 | 《Kanban in Action》前 5 章 |
| Week 4 | 引入团队看板 | 与至少一个同伴分享看板 | 《Kanban: Successful Evolutionary Change》 |

### 10.5 持续改进的 PDCA 循环

看板的演进采用科学的 PDCA（Plan-Do-Check-Act / 计划-执行-检查-行动）循环：

| 步骤 | 在看板中的应用 |
|------|-------------|
| **Plan** | 基于 CFD/周期时间数据，提出一个改进假设——"如果我们把 WIP 从 5 降到 3，周期时间会缩短" |
| **Do** | 实施变更，运行至少两周 |
| **Check** | 对比变更前后的数据——周期时间真的缩短了吗？ |
| **Act** | 如果有效，标准化新规则。如果无效，回滚并尝试新假设 |

> **关键**：一次只改一个变量。如果你同时收紧 WIP、增加列、改变会议频率——你就不知道哪一个产生了效果。

### 10.6 看板的工具自动化

现代看板工具提供的自动化能力：

| 自动化类型 | 示例 | 工具 |
|-----------|------|------|
| 自动移卡 | "代码提交→自动从开发移到测试" | Jira Automation, GitHub Projects |
| WIP 超标告警 | "开发列超过 5 张卡→Slack 提醒" | Kanbanize, SwiftKanban |
| CFR 自动计算 | 周期时间超出阈值→标记"需关注" | Businessmap, Linear |
| 定期报表 | "每周五自动发送吞吐率报告" | Notion Automation, Lark |
| AI 辅助建议 | "你已有 4 张卡在开发中，建议先完成某某再拉新卡" | Lark AI Kanban Template |

## 第十一章 未来展望

### 11.1 看板方法的去 IT 化趋势

看板诞生于制造业，发展于软件业，但**未来最大的增量在非 IT 行业**。

数据表明看板在非 IT 领域的采用年增长率达 18%。市场营销、HR、医疗、教育、法律、建筑设计——这些领域的从业者正在发现自己的问题不是"技术落后"，而是"流动管理差"。

我们可以预见的趋势是：**看板的"去科技化"**。未来五年内，将出现专门为特定行业定制的看板变体——比如"医院看板"（从挂号→分诊→检查→诊断→取药的端到端流动）、"律所看板"（案件从受理→调查→上庭→结案的看板）、"学校看板"（学生从入学→课程→实习→毕业的看板）。

### 11.2 AI 在看板中的角色演进

2025-2026 年，AI 在看板工具中出现，目前主要处理：

- 自动分类和标签
- 异常检测（"这张卡片已经卡了 8 天"）
- 预测交付日期（基于历史周期时间数据）

但真正的变革还没来。未来 3-5 年，我预见的 AI 看板能力：

**Level 1（现在已实现）**：数据可视化和告警
**Level 2（1-2年内）**：预测式看板——AI 在项目开始前就预测哪些工作项会成为瓶颈，并建议提前行动
**Level 3（3-5年内）**：自主看板——AI 代理自动处理可模式化的工作项（自动分配、自动跟进、自动升级阻塞），人类只处理需要判断力的例外情况

> 这不是科幻。如果 AI 能写代码，那 AI 就能管理写代码的流程。

### 11.3 混合方法论的一大统趋势

SAFe 的使用率暴跌超过 50%（从顶峰时的 53% 跌到 26%），34% 的组织选择"创建自己的框架"。这背后是**去标准化**的趋势。

定制化的混合方法（看板 + Scrum + Waterfall 的碎片组合）将成为 2026-2030 年的主流。看板在这个趋势中占据天然优势——因为它从来就不是一个"全有或全无"的框架。看板的核心理念"从现状开始"最适配混合方法。

**一个激进的预测**：到 2030 年，"纯粹的方法论"（纯 Scrum、纯 SAFe、纯看板）将成为少数派。多数组织会说："我们用了看板的核心（WIP 限制 + 可视化），但节奏是 Scrum 的，大型项目仍用一部分 Waterfall 的阶段关口。"

### 11.4 从"管理项目"到"管理注意力"

看板解决的是"工作看得见"，但下一个时代的问题是"注意力看得见"。

认知科学告诉我们：人类的多任务能力是幻觉。每多一个并发任务，效率就下降 20-40%（来源：APA 多任务研究报告）。看板的 WIP 限制无意中触达了一个更本质的问题——**我们如何管理人类有限的认知资源**。

未来的"看板 2.0"可能不再叫"看板"——它可能演进为整个数字生活的注意力管理界面：

- 不只是工作任务，还包括学习、社交、家庭事务
- 不只追踪"完成"，还追踪"能量消耗"和"认知恢复"
- 不只服务于团队，而是作为个人的"第二大脑"工作流界面

这和本手册读者的需求高度重合——一个人同时管理家庭、工作、学习的多角色生活。看板不是给你的"工作"用的，是给你的"人生"用的。

### 11.5 看板在中国

中国市场对看板方法的采用正在加速，但有三重特殊性：

1. **工具生态绑定**：钉钉、飞书、企业微信的看板功能成为大多数中国企业的入口。这不是好事也不是坏事——它意味着看板的实践质量受限于这些平台的功能成熟度。

2. **文化适配**：看板的"各层级领导行为"原则在中国企业层级文化中面临阻力。"改进建议从基层来"这种模式需要文化建设，而不只是工具部署。

3. **制造业回流**：看板的源头是制造业——中国作为制造业大国，天然适合将看板从 IT"回流"到制造业。中国制造 4.0 的智能化改造中，看板方法有巨大的未被发掘的潜力。
