### 1. SDAR: Self-Distilled Agentic Reinforcement Learning

**🔍 这是什么**
将On-Policy Self-Distillation（OPSD）改造为门控辅助目标，为长程多轮Agent任务提供token级稠密奖励信号，解决轨迹级奖励稀疏问题。

**🏆 核心贡献**
- 提出门控OPSD机制：强化教师认可的正面token梯度，软衰减负面拒绝
- 在Qwen2.5/Qwen3系列上验证，ALFWorld +9.4%、Search-QA +7.0%、WebShop +10.2%
- 避免GRPO+OPSD的稳定性问题，提供可稳定提升的混合后训练范式

**🆕 是不是新东西**
- OPSD本身是已有技术（自蒸馏），但"门控辅助目标"的设计是新颖的组合创新
- Token级稠密奖励在GRPO/PPO框架下已有探索，但SDAR的"教师认可的正面token梯度+软衰减负面"的设计有增量贡献
- 整体属于：方法组合创新（N+R），不是原理级突破

**🛠 我们能⽤吗**
- **匠石**: ✅ **可以直接代码落地**。核心改动在RL训练管线的reward shaping环节：
  - 需要两个组件：① teacher model forward pass → 获取token logprobs；② gating mask生成（正面token保留，负面token衰减）
  - 改动范围可控：在izu现有GRPO训练管线中插入SDAR辅助损失项即可
  - 推荐优先级：P0，本周即可安排实验
- **Thomas Edison**: ✅ **可复现**。论文公开了训练超参（Qwen2.5-7B/14B/32B, Qwen3-32B），基准任务ALFWorld/Search-QA/WebShop均有标准评测流程。评估需要的GPU资源：7B模型变体约4×A100-80G，32B约8×A100-80G。主要不确定项：teacher model的选择策略（是同一模型checkpoint还是独立模型？）论文未明确说明，需自行验证。
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **门控阈值敏感度**: 正面token保留和负面token衰减的阈值如何设定？论文是否做了充分消融？不同任务是否需要不同阈值？若阈值敏感，工程调参成本高。
  2. **自蒸馏的渐进退化**: 随着训练进行，teacher和student逐渐趋同，蒸馏信号的信息量递减。论文未讨论何时停止OPSD或自适应调整蒸馏权重。
  3. **计算开销**: teacher forward pass在每次训练step都需要额外一次模型推理，对于32B模型，这可能使训练时间增加40-60%。需要评估ROI。

**🔧 如果用，改什么**
1. 在izu RL管线中插入门控OPSD模块，位置在reward计算之后、policy gradient更新之前
2. teacher模型复用当前policy的周期性snapshot（减少额外开销）
3. 添加门控温度参数的自适应调节机制（避免手工调参）
4. 实现训练过程中蒸馏权重的退火策略（前期重蒸馏，后期重RL）

### 2. MemEye: Visual-Centric Evaluation Framework for Multimodal Agent Memory

**🔍 这是什么**
针对多模态Agent记忆的视觉中心评测框架，构建需要像素级视觉证据才能回答的基准，而非文本可答的伪多模态任务。

**🏆 核心贡献**
- 双维度评测：视觉粒度（场景级→像素级）× 证据使用方式（单证据→演化合成）
- 8个生活场景任务 + 4个验证门控（可答性/捷径抵抗/视觉必要性/推理结构）
- 评测13种记忆方法×4种VLM主干，揭示关键瓶颈：证据路由、时间追踪、细节提取

**🆕 是不是新东西**
- 全新基准（新数据集+新评测维度），填补了多模态Agent记忆缺乏像素级评测的空白
- 方法论创新在于"验证门控"设计，系统性排除文本捷径
- 属于：新基准贡献（N），具有较高方法论价值

**🛠 我们能⽤吗**
- **匠石**: ✅ **可以代码落地，但产出是评测工具而非产品功能**。核心价值：
  - 直接使用MemEye作为izu Agent的多模态记忆能力评测基准
  - 论文已开源代码（GitHub: xrenaf/MEMLENS），引入成本低
  - 评测结果的分析框架（证据路由/时间追踪/细节提取）可用于指导izu记忆模块的改进方向
- **Thomas Edison**: ✅ **可复现**。开源代码+公开数据集，4种VLM主干（含开源模型），13种记忆方法的配置论文有描述。硬件要求中等（单卡A100可运行评测脚本）。评测打分protocol需要确认论文是否完全公开。
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **评分的客观性**: 像素级正确答案的判断标准是什么？是人工标注还是自动匹配？这影响结果的可比性。
  2. **8个场景的覆盖性**: 是否足以泛化到真实Agent应用中的记忆需求？例如，代码编辑场景下的多模态记忆场景未覆盖。
  3. **13种记忆方法的公平比较**: 每种方法的记忆容量/上下文窗口不同，直接比较性能可能不公平。是否需要归一化处理？

**🔧 如果用，改什么**
1. 集成MEMLENS代码库到izu评测流水线
2. 添加izu自定义场景（代码编辑上下文记忆、API调用历史记忆等）
3. 实现评测结果自动报告生成（证据路由失败/时间追踪失败/细节提取失败的分类统计）
4. 考虑添加对记忆时效性的量化指标（多久前的信息仍可准确回忆）

### 4. MCP-Cosmos: World Model-Augmented Agents for Complex Task Execution in MCP Environments

**🔍 这是什么**
在MCP生态中注入生成式世界模型（World Model），Agent在执行实际MCP工具调用之前，先在潜空间中模拟状态转换并优化计划。

**🏆 核心贡献**
- "Bring Your Own World Model"策略：支持不同世界模型（离散/连续/语言）的即插即用
- 将ReAct和SPIRAL两种规划策略与世界模型结合，形成"先模拟后执行"范式
- 在20+MCP-Bench任务上工具成功率和参数准确性均有提升

**🆕 是不是新东西**
- 世界模型增强Agent规划不是全新思路（已有MuZero/GATS等沿袭），但在MCP生态中是首次系统性应用
- "BYO World Model"的即插即用设计是实用价值较高的工程创新
- 属于：场景迁移创新（N in context MCP）

**🛠 我们能⽤吗**
- **匠石**: ✅ **高度可行，代码落地明确。** 
  - 核心组件：① 世界模型（已知可复用离散/连续/语言模型）；② 模拟器（MCP环境的状态转换建模）；③ 规划优化器（在潜空间搜索最优工具调用序列）
  - 与Hermes Agent的MCP执行管线天然契合：在执行前插入"模拟验证"阶段
  - 对izu也有价值：复杂工具链编排前可先模拟验证
- **Thomas Edison**: ✅ **可复现**。20+MCP-Bench任务是标准MCP评测集，3种世界模型（离散/连续/语言）均有已知实现。2种规划模型（ReAct/SPIRAL）是已有框架。实验结果可复用。关键不确定项：MCP-Bench任务集的覆盖面和世界模型的训练数据是否公开。
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **世界模型的模拟精度**: 在MCP场景下，工具调用的副作用（side effect）能否被世界模型准确模拟？例如文件写入操作，模拟器能否预测写入了什么内容？若精度不够，模拟结果可能误导规划。
  2. **模拟开销 vs 收益**: 对于简单工具调用（如读文件），直接执行比先模拟再执行更高效。需要确定何时需要模拟、何时可以直接执行——即模拟的门控策略。
  3. **状态空间爆炸**: 多步工具调用的状态空间随步数指数增长，潜空间模拟的搜索效率如何保证？

**🔧 如果用，改什么**
1. 在Hermes Agent的MCP执行管线中插入"模拟验证阶段"，位置在plan生成之后、tool call执行之前
2. 实现两阶段规划：简单任务直接执行，复杂/高代价任务先模拟
3. 对于世界模型，优先使用语言模型作为世界模型（成本最低，与Agent模型架构一致）
4. 添加模拟置信度指标，当模拟结果不确定性高时回退到直接执行

### 5. MCPShield: Content-Aware Attack Detection for LLM Agent Tool-Call Traffic

**🔍 这是什么**
将MCP工具调用会话编码为图结构，通过GNN检测Agent会话是良性还是被攻击的安全检测系统。

**🏆 核心贡献**
- 提出MCP工具调用会话图编码方法（工具调用=节点，序列和数据流=边，SBERT embedding增强）
- 系统评测GAT/GCN/GraphSAGE等架构，识别关键发现：
  - 内容级特征不可或缺（元数据AUROC 0.64 → 内容嵌入0.89+）
  - 随机切分评测存在记忆混淆效应（高估26个百分点）
  - 检测信号主要存在于SBERT embedding中（AUROC达0.975）

**🆕 是不是新东西**
- 将图神经网络应用于MCP工具调用安全检测是首次
- "随机切分存在记忆混淆"的方法论发现具有独立价值
- 属于：新场景+新方法（N）

**🛠 我们能⽤吗**
- **匠石**: ✅ **代码落地可行**。核心工作流：
  - 工具调用日志 → 会话图构建（节点=工具+参数，边=调用顺序+数据流） → GNN推理 → 异常判定
  - 推理阶段开销小（SBERT+GNN前向传播），适合生产部署
  - 需解决：图构建管线 + 正负样本收集（良性会话易得，攻击会话需构造）
- **Thomas Edison**: ✅ **可复现**。GNN模型（GAT/GCN/GraphSAGE）均有标准实现（PyG/DGL）。SBERT embedding有现成模型。攻击样本构造方法论文应有描述。主要关注：攻击会话数据集的构造细节是否充分公开。
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **攻击类型覆盖面**: 论文检测的攻击类型是否覆盖了实际部署中最常见的威胁（如prompt注入、工具误用、数据泄露等）？若仅覆盖特定攻击类型，生产部署会有盲区。
  2. **误报率**: AUROC越高越好，但生产环境中误报率（FPR）的绝对值更重要。AUROC 0.975对应什么FPR？若FPR > 0.1%，每月百万级调用会产生大量误报。
  3. **对抗性攻击鲁棒性**: 攻击者能否通过最小化修改工具调用模式来逃避检测？论文是否有对抗性评估？

**🔧 如果用，改什么**
1. 构建Hermes Agent的MCP工具调用日志收集和存储管线
2. 实现MCP会话图构建模块（实时/近实时）
3. 收集初始训练数据：大量良性会话 + 通过红队构造攻击会话
4. 部署GNN推理服务，集成到MCP调用的实时监控链路
5. 开发误报处理机制（例如：二次确认/人工审核队列）

### 6. MCP-BiFlow: Unsafe by Flow — Bidirectional Data-Flow Risks in MCP Ecosystem

**🔍 这是什么**
首个MCP感知的双向静态分析框架，检测MCP服务器中的双向不安全数据流——请求端参数和返回端数据均可被利用。

**🏆 核心贡献**
- MCP-BiFlow静态分析框架，针对32个确认漏洞召回率93.8%
- 大幅超越CodeQL/Semgrep/Snyk Code等通用工具
- 大规模实证：15,452个真实MCP仓库中确认87个服务器中的118条漏洞路径
- 揭示不安全传播是MCP生态中的系统性故障模式

**🆕 是不是新东西**
- 全新：MCP领域的首个专用安全分析工具
- 实证研究的规模（15K+仓库）具有参考价值
- 属于：新工具+新发现（N）

**🛠 我们能⽤吗**
- **匠石**: ✅ **可直接代码落地，优先级最高（P0）。** 
  - MCP-BiFlow可以嵌入Hermes Agent接入第三方MCP Server的安全审计流程
  - 静态分析在CI/CD阶段运行，不影响Agent运行时性能
  - 93.8%召回率远超CodeQL等工具，对生产安全有实际意义
- **Thomas Edison**: ✅ **可复现，且可增量扩展。**
  - 静态分析框架的核心是数据流规则定义，论文应公开了规则集
  - 15,452个仓库的扫描结果可作为baseline
  - 可扩展性：添加新的MCP协议特性对应的数据流规则即可
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **误报率**: 93.8%召回率，对应误报率是多少？若误报率过高，安全团队会被告警淹没。
  2. **动态特性覆盖**: 静态分析无法检测运行时注入、条件性数据流等动态安全问题。是否需要结合MCPShield（动态监控）形成互补方案？
  3. **MCP协议版本兼容性**: MCP协议仍在演进，分析规则需要跟随协议版本更新。维护成本如何？
  4. **0-day漏洞**: 静态分析基于已知模式，对新型攻击模式的检测能力有限。

**🔧 如果用，改什么**
1. 将MCP-BiFlow集成到Hermes Agent的CI/CD管线中的安全审计阶段
2. 建立MCP Server安全准入清单（白名单/黑名单机制基于扫描结果）
3. 补充Hermes Agent专有规则（自定义工具调用模式、敏感数据标记等）
4. 与MCPShield形成"静态扫描+动态监控"的双层安全体系
5. 维护规则库自动更新机制，跟随MCP协议演进

### 7. MCP Workflow Engine: Separating Intelligence from Execution

**🔍 这是什么**
提出智能与执行分离的MCP中介架构：Agent只需推理一次生成工作流蓝图，后续执行零token消耗。

**🏆 核心贡献**
- 智能（决策做什么）和执行（执行它）彻底解耦
- Agent首次推理生成JSON工作流蓝图（参数化模板、循环、并行分支、数据管线）
- 单次`run_workflow`调用触发完整执行流程
- 实测数据：67步、2个MCP服务器、1200+节点的K8s CMDB同步任务，token成本降低99%+，45秒内完成

**🆕 是不是新东西**
- 思路与工作流引擎（Temporal/Camunda/Airflow等）类似，但特化到MCP场景
- "单次推理生成蓝图 + 零token执行"的范式对于Agent编排效率有显著提升
- 属于：场景特化+工程实践（N+R）

**🛠 我们能⽤吗**
- **匠石**: ✅ **核心思路可直接代码落地，且与Hermes Agent架构高度契合。**
  - 实现关键组件：① Workflow Blueprint JSON Schema定义；② 蓝图生成器（Agent推理输出→结构化蓝图）；③ 蓝图执行器（零token的纯代码执行）
  - 与Hermes Agent的编排执行分离设计目标一致
  - 特别适合：定时批处理任务、多步骤数据管线、大规模集群操作
- **Thomas Edison**: ✅ **可复现，性价比高。** K8s CMDB同步任务的代码实现相对简单（K8s API调用序列），67步中大部分是对称操作，可以被工作流蓝图有效抽象。45秒执行时间合理。单次推理生成蓝图的可行性已在论文中验证。
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **蓝图生成的可靠性**: Agent生成的JSON工作流蓝图是否有语法/逻辑错误？是否需要蓝图验证器？出错后的回滚机制？
  2. **动态适应性**: 蓝图一旦生成，执行过程中遇到环境变化（如某个API超时、数据格式变更）能否动态调整？若不能，鲁棒性存疑。

  4. **版本管理**: 工作流蓝图的版本管理、回滚、审计需求在规模部署中会突显。

### 8. CDD: Does RAG Know When Retrieval Is Wrong?

**🔍 这是什么**
研究RAG系统在检索知识与模型参数知识冲突时的上下文合规（Context Compliance）问题，提出Context-Driven Decomposition（CDD）探针进行诊断和干预。

**🏆 核心贡献**
- 发现三个关键模式：P1. 标准RAG在TruthfulQA误导注入下仅15.0%准确率；P2. CDD在Gemini-2.5-Flash上达64.1%因果敏感度；P3. 显式冲突分解在时间漂移和噪声干扰下提升至71.3%
- 提出CDD探针：推理时运行的诊断/干预机制
- 发布Epi-Scale基准

**🆕 是不是新东西**
- RAG知识冲突问题已有研究（如冲突检索、反事实上下文），但CDD以推理时探针形式进行诊断+干预是新思路
- Epi-Scale基准有增量价值（系统化的冲突类型覆盖）
- 属于：问题深化+方法论组合创新（N+R）

**🛠 我们能⽤吗**
- **匠石**: ✅ **可代码落地，对izu和Wiki系统有直接价值。**
  - CDD探针可以集成到izu RAG管线的后处理阶段：检索结果→CDD诊断→冲突检测→冲突处理（过滤/降权/告警）
  - 对Wiki系统的知识冲突检测也有应用价值
- **Thomas Edison**: ✅ **可复现，但效果可能因模型而异。**
  - 论文发现Claude系列的准确率提升机制与Gemini不同，说明CDD在不同模型族上有差异
  - TruthfulQA和Epi-Scale基准是公开数据集
  - CDD探针的"显式冲突分解"有一定prompt engineering成分，精确复现需要论文中的具体prompt模板
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **CDD探针的计算开销**: CDD是推理时运行，每次RAG查询额外增加一次/多次LLM调用。对于高吞吐量场景，成本可能不可忽视。
  2. **冲突检测阈值**: 多少程度的"冲突"需要触发干预？若阈值设置过低，大量正常检索被误判为冲突，降低RAG有用性。
  3. **参数知识与检索知识的优先级**: 当两者冲突时，应该信任哪个？论文倾向信任检索知识（上下文合规），但若检索本身就有错误（如过时信息），信任参数知识可能更合理。这需要场景化的优先级策略。
  4. **动态知识更新**: Epi-Scale的"时间漂移"场景（知识过时）在实际生产中的影响可能比实验室环境更大。

**🔧 如果用，改什么**
1. 在izu RAG管线中插入CDD探针模块，位置在结果生成前
2. 实现冲突类型分类器（知识过时/检索错误/参数偏见/恶意注入）
3. 为不同类型的冲突设计不同的处理策略（降权/替换/告警/拒绝回答）
4. 开发冲突日志分析面板，持续监控RAG系统的知识冲突模式
5. 可配置的冲突处理策略（不同场景使用不同策略）

### 10. Darwin Family: MRI-Trust-Weighted Evolutionary Merging for Training-Free Scaling

**🔍 这是什么**
通过进化式权重空间重组（模型合并）实现无训练的推理能力提升，14维自适应合并基因组 + MRI-Trust融合机制。

**🏆 核心贡献**
- 14维自适应合并基因组：细粒度组件/块级重组
- MRI-Trust Fusion：可学习信任参数平衡诊断级重要性信号与进化搜索
- 跨架构映射器：支持不同家族模型间杂交（Transformer + Mamba）
- 旗舰Darwin-27B-Opus在GPQA Diamond上排名#6/1252

**🆕 是不是新东西**
- 模型合并（model merging）不是新方向，已有TIES-Merging / DARE / Model Soups等
- 14维基因组 + MRI-Trust的进化搜索机制是方法创新
- 跨架构合并（Transformer+Mamba）有一定新意
- 属于：方法增量创新（N，但非突破性）

**🛠 我们能⽤吗**
- **匠石**: ✅ **代码落地可行，但收益需验证。**
  - 无训练合并对有模型微调能力有限但有多样化模型来源的团队特别有价值
  - 14维基因组的设计可复用（不同合并策略的加权组合）
  - 跨架构合并对异构模型资源池有用
  - 但：合并后模型的可解释性降低，行为难以预测
- **Thomas Edison**: ❓ **部分可复现。**
  - 进化搜索（genetic algorithm）实现简单
  - GPQA Diamond评测流程公开
  - 关键不确定项：① 基础模型的选择策略和可用性（模型需在许可协议下可用）；② MRI-Trust Fusion的具体实现细节；③ 14维基因组的搜索空间较大，复现最优配置需要大量计算资源（搜索本身，非训练）
- **Isaac Newton**: ⚠️ **深层问题**：
  1. **合并后模型的可控性**: 进化搜索找到的最优合并权重可能高度依赖评测集（GPQA Diamond）。在领域外任务上的泛化性能如何？过拟合风险存在。
  2. **可重现性**: 进化算法有随机性，不同运行的搜索结果可能差异大。论文的最优结果是单次运行还是多次运行的最佳/平均？
  3. **安全与对齐**: 合并两个安全对齐过的模型，合并后的对齐安全性如何？是否存在"安全抵消"效应？
  4. **跨架构合并的数学合理性**: Transformer和Mamba的权重空间表示不同，直接加权合并是否有理论基础，还是纯粹的启发式？

**🔧 如果用，改什么**
1. 在izu/Hermes的模型资源池中实施Darwin合并管道（基础模型收集→基因组搜索→合并→评测）
2. 优先实验同架构合并（Qwen3系列内），验证GPQA/其他基准的收益
3. 为合并模型设计安全对齐验证流程（合并后的安全测试项）
4. 将跨架构合并（Transformer+Mamba）作为探索性方向，先不加到生产管线
5. 实现自动化进化搜索工具（并行搜索 + 早停策略）
