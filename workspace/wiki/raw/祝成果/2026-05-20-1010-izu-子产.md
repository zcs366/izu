# 子产·需求判断与研究方向

## 需求判断：该不该做？

**背景**：izu是一个追求自我进化的Agent。核心痛点在于它目前的技能是硬编码的，无法从经验中自主抽象出新技能。

### 该做：★★★★★（必要性极高）

**理由**：
1. **不做会怎样？** — izu永远停留在当前能力边界。每个新能力都需要人工编码配置，这不是"自进化"而是"被升级"。
2. **为谁做？** — 为izu自身。自进化技能引擎是izu从"工具"变成"智能体"的关键一跃。
3. **竞争威胁**：OpenSpace (HKUDS) 已证明自进化技能引擎是可行的——46% tokens节省，$11K in 6 hours。如果izu不自建，很快会落后于社区基线。

### 时机判断
- 开源生态：OpenSpace已开源，Dual-Process框架论文已发布
- 技术成熟度：Self-Evolving Agents被2025/2026多篇survey系统化讨论
- izu当前阶段：已经有基础记忆系统（memory可持久化），下一个自然进化方向就是技能抽象

## 研究方向定位

### 关键问题
**izu如何从日常交互经验中自主抽象、存储、复用可泛化的技能（Skill）？**

### 核心假设
```
假设：在一个经验片段e中，如果存在一个函数f_e使得输出O = f_e(输入I, 状态S)，
且存在足够多的经验片段{e_i}共享相似的f，那么f就是对izu有意义的泛化技能。
```

### 方向对不对？

**对，但需要精确定义"技能"粒度**：
- ❌ 太粗：`write_code()` 不是技能，是任务
- ✅ 合适：`extract_commit_message_from_diff()` 是技能——可重复、有输入输出模式
- ❌ 太细：`add_indent()` 不是技能，是原子操作

### 优先研究方向（按价值排序）
1. **技能发现**：从izu的交互日志中自动识别可复用的操作模式 ← 先做这个
2. **技能存储**：技能如何索引、版本化、冲突解决 ← 紧接着
3. **技能调用**：在运行时如何匹配输入到已有技能 ← 第三
4. **技能进化**：已有技能如何随经验自动精化 ← 第四

### 不研究的边界
- ⛔ 不研究模型微调/权重更新（izu不需要修改LLM）
- ⛔ 不研究多Agent协作（聚焦单Agent自进化）
- ⛔ 不研究复杂规划（技能发现先于规划）

### 输出建议
**izu下一步研究方向：基于OpenSpace模式的经验驱动技能引擎，优先实现技能发现和存储两个模块。**
