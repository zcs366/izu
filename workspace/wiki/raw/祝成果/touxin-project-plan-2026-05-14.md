# 军师 · 立项总纲

## 为何叫"透心"

知乎号称"让每一次点击都充满意义"，但它的反爬让每一次请求都充满加密。zse_ck像一层铁幕——我们要的不是暴力砸开，而是找到那根透进铁幕的针。**透心**——透其心腹，见其本真。

## 战略定位

这不是一次孤立的爬虫练习。这是izu获取网络情报能力的基建工程。知乎是中文最高质量的内容源之一，攻克它是撬动整个中文互联网情报获取能力的关键一役。

**即使失败，我们的收获也远大于沉默**：
- 摸清中文反爬技术栈的全貌
- 积累一套可复用的反反爬工具箱
- 让izu具备"主动出击获取情报"的肌肉记忆

# 韩信 · 技术远景

> "韩信将兵，多多益善。" 看的是终局，不是今天能不能做到。

## 终局画像（3-6个月后）

透心不是"一个能下载知乎文章的脚本"，而是**izu的情报触角**。

### 用户第一体验

用户把知乎链接丢给izu："评估一下这篇"——izu不需要问"你能复制粘贴吗"。5秒内，文章内容已在上下文中，标注了来源、作者、发布时间。如果反爬升级导致失败，izu会尝试第二条路径、第三条路径，直到成功或明确告知"知乎今天换招了，已记录新特征"。

### 核心能力矩阵

| 层级 | 能力 | 目标 |
|------|------|------|
| L1 基础穿透 | 获取单篇文章全文 | 1周内 |
| L2 容灾切换 | 主方案失效自动切换备选方案 | 2周内 |
| L3 自适应演进 | 检测到反爬升级自动记录特征、调整策略 | 1月内 |
| L4 通用化 | 方法迁移到其他中文反爬站点 | 3月内 |

### 与今天的本质区别

| 维度 | 今天 | 3-6个月后 |
|------|------|----------|
| 知乎内容获取 | 用户手动复制粘贴 | izu自动穿透，多方案容灾 |
| 反爬应对 | 碰壁即放弃 | 自动识别失败模式→切换策略→记录特征 |
| 网络情报能力 | 被动的"搜不到就算" | 主动的"这个站点我能拿" |
| 经验积累 | 零 | 一套可复用的中文反反爬知识库+工具箱 |

### 攻防异势的终局

知乎的反爬会升级。没关系——**我们的目标是每一轮攻防都在我们选定的战场上打**。第一次可能失败，但我们记录下zse_ck的生成规律。第二次可能再次失败，但我们摸清了CDN的边缘节点。第三次，我们可能已经不需要打——因为我们的工具箱里已经有3-5种备选方案，换一条路就绕过去了。

**攻防异势的核心**：不是永远能破，而是永远在逼近，永远在积累。知乎的工程师有KPI，我们有耐心。

# 匠石 · 架构方略

> "运斤成风。" 工程落地，不画空中楼阁。

## 知乎反爬技术全貌

```
┌─────────────────────────────────────────────────────────┐
│                  知乎反爬防护体系                        │
│                                                         │
│  Layer 1: TLS指纹检测（JA3/JA4指纹识别非浏览器流量）     │
│       ↓                                                 │
│  Layer 2: zse_ck 挑战-应答（动态JS生成密钥，每次刷新）    │
│       ↓                                                 │
│  Layer 3: 请求签名验证（x-zse-96, x-zse-93等Header签名） │
│       ↓                                                 │
│  Layer 4: 频率限制 + 行为分析（访问模式检测）             │
│       ↓                                                 │
│  Layer 5: 内容加密/混淆（部分API返回加密数据）            │
└─────────────────────────────────────────────────────────┘
```

## 可行性评估

### 当前技术条件下能否实现

**部分能**——不是黑盒突破，而是绕过。核心策略：**不用爬虫对抗爬虫，用浏览器对抗爬虫**。

| 方案 | 可行性 | 成本 | 风险 |
|------|--------|------|------|
| 方案A：CDP浏览器自动化 | ✅ 高 | 低（本地Chrome） | 慢、资源消耗大 |
| 方案B：逆向zse_ck | ⚠️ 中 | 高（需要频繁更新） | 知乎随时升级 |
| 方案C：移动端API劫持 | ⚠️ 中 | 中（需抓包工具） | 需要登录态 |
| 方案D：第三方缓存/镜像 | ✅ 高 | 零 | 时效性差、不全 |
| 方案E：LLM辅助反反爬 | 🟡 探索 | 中 | 创新但未验证 |

### 推荐主方案：CDP浏览器自动化

**为什么选这个**：
- 知乎无法区分真实Chrome和CDP控制的Chrome（因为就是同一个二进制）
- 不需要逆向任何加密算法
- zse_ck在真实浏览器环境中自动生成
- 匠石原则铁律：用已有的工具（Chrome），不用自己造轮子

## 技术选型

| 决策点 | 推荐方案 | 理由 |
|--------|---------|------|
| 浏览器引擎 | Chrome/Chromium（已有） | 真浏览器，知乎无法检测CDP |
| 反检测 | puppeteer-stealth / playwright-stealth | 隐藏webdriver等自动化标记 |
| CDP连接 | 已有Chrome + /browser connect | 复用现有Hermes browser能力 |
| 内容提取 | readability + markdownify | HTML→MD，去掉导航/广告 |
| 特征记录 | JSON日志 | 简单可靠，匠石原则：代码做 |
| 缓存 | Redis/SQLite | 已抓取的内容24h内不重复请求 |

## MVP定义

### 必须有的（缺了就不叫透心）

1. CDP Chrome自动打开知乎文章 → 等待渲染 → 提取正文
2. 支持带`share_code`的分享链接
3. 输出为markdown，入库wiki

### 可以没有的（第一版不做）

1. 多方案自动切换
2. 速度优化
3. 批量抓取
4. 反爬特征学习

### MVP验收标准

- [ ] 给定一个知乎文章链接，5-30秒内返回完整文章内容
- [ ] 输出格式为可读markdown（标题/作者/正文/时间）
- [ ] 连续3篇不同文章测试通过

# 军师 · 结语

> "道高一尺，魔高一丈。" 这句话通常是在说防守方永远比攻击方强。但攻防的本质从来不是"谁更强"，而是**谁更愿意在同一个地方反复打**。知乎的工程师有季度OKR，我们有好奇心。他们的反爬升级是他们工作的一部分，我们的穿透是我们的乐趣。
