# Claude Code 源码的哲学启示 · v1.0

> **呈：张成市**
>
> 这不是一篇总结。源码泄露后网上已经有很多人总结了"Claude Code用了什么技术栈"、"有几个模块"——那些是信息。我要谈的是信息背后的东西：**Claude Code 的架构选择揭示了哪些关于 AI Agent 设计的第一性原理**，以及这些原理对我们的 izu 意味着什么。

---

## 一、开源的表与里

Anthropic 的官方 `claude-code` 仓库有 12.3 万 Star，279 个文件。他们宣称 "Claude Code is an agentic coding tool"——但仓库里只有插件接口、Hook 示例和配置模板。

核心引擎——Agent 循环、工具系统、权限模型、MCP 客户端——全在闭源侧。

直到 2026 年 3 月 31 日，一个 .map 文件把它们翻了出来。

这事有意思的地方不在于"Anthropic 虚伪"——所有 AI 公司都这么做。有意思的是，**泄露后的代码质量远比人们预期的好**。如果泄露的是某些大厂的内部代码，大概率会被嘲笑；但 Claude Code 的源码让安全研究员说出了"构建 AI Agent 的人的金矿"这种话。

这说明什么？说明 Anthropic 在这件事上是认真的。他们不是"先开源个空壳未来再填"，而是"内部做好后，有意只开放接口层"。这和 Google 开源 TensorFlow 但内部用 TPU 是同一个逻辑——**开源的是生态入口，闭源的是核心壁垒**。

对我们的启示：izu 不需要纠结"全开源"还是"全闭源"。**接口层开放**（让人能连接、能扩展、能贡献），**核心层自主**（Agent 循环、安全模型、记忆结构）——这条路被验证了。

## 二、Async Generator 不是偶然

Claude Code 主循环的核心是一个 `async function* query()`。

```typescript
async function* query(params): AsyncGenerator<Event, Terminal>
```

这个选择不是"刚好能用"——是深思熟虑的架构决策。

传统的 Agent 实现通常有三种模式：

1. **回调地狱**：`onMessage()`、`onError()`、`onComplete()` 分散在代码各处
2. **EventEmitter**：`agent.on('message', ...)`、`agent.on('error', ...)`——比回调好，但事件流、终止、错误处理仍在不同通道
3. **Promise**：`agent.run().then(result)`——但在长对话场景中，你不知道中间发生了什么

异步生成器的优雅之处在于：**事件流、终止信号、错误传播——三条河流汇入同一条河床**。

- 消费者用 `for await...of` 接收事件流
- `return` 值传递终止原因（不需要 `onComplete` 回调）
- `throw` 自然传播到调用者的 `try-catch`（不需要 `onError` 回调）

更妙的是 Continue Site 模式：每轮结束时整个 state 对象一次性重新赋值，`transition` 字段记录了"为什么走到这一步"。这不是炫技——这是**把 Agent 状态转换从隐式变成了显式**。

> 传统模式：改了9个变量，但不知道为什么改的。
> Continue Site：`state = {...state, transition: 'fallback_model_switch'}`——每一次状态转换都有名有姓。

izu 当前的消息处理流程应该认真考虑这个模式。不是要照抄，而是要理解它解决了什么问题：**在长时间运行的多轮对话中，状态转换的可追溯性比状态本身更重要**。

## 三、"从最便宜的开始"是一种哲学

Claude Code 的上下文压缩系统有4层：

| 层级 | 成本 | 触发条件 |
|------|------|---------|
| Snip（丢弃旧消息块） | $0 | 上下文接近极限 |
| Microcompact（清过期工具结果） | $0 | 旧工具结果占用空间 |
| Context Collapse（只读投影折叠） | ~$0.001 | 前两层不够 |
| Auto-Compact（LLM 全量摘要） | ~$0.01+ | 前三层都不够 |

核心原则不是"选最有效的"，而是"**从最便宜的选项开始**"。这个原则贯穿整个代码库：

- 错误恢复：先试免费的 Context Collapse drain → 再试廉价的 Reactive Compact → 最后才是昂贵的全量摘要
- Token 恢复：先透明升级限制 → 再注恢复消息 → 再抛错
- 工具加载：先用静态注册 → 动态工具搜索只在工具数超过阈值时启用

这不仅是成本控制。这是一种**资源感知架构**——每一步决策都内化了"这不是免费的"这个认知。绝大多数开源 Agent 框架（LangChain、AutoGPT、CrewAI）的架构都是"功能驱动"的——"我们需要这个功能，加进去"——而不是"成本驱动"的。

对 izu 的启示：在架构中加入**成本阶梯**。不是每个 operation 都值一个 API 调用。有时一个简单的字符串匹配就够。有时一个缓存命中就够。至少提供两层：便宜层和精确层。

## 四、安全的真问题不是"会不会干坏事"

大多数 AI 安全讨论集中在"输出有害内容"——这是 LLM 层面的问题。Claude Code 的8层安全模型解决的是一个更根本的问题：**当 AI 能执行任意代码时，你怎么防止它被利用**。

8层洋葱中最精彩的不是某层特别强，而是**没有任何一层是致命单点**：

1. 编译时消除 → 危险的浏览器代码根本不打包进来
2. 服务器开关 → 无需客户端更新即可全局禁用功能
3. 8级权限规则 → 从全局到会话，逐层覆盖
4. YOLO分类器 → 用另一个 Claude 监控当前 Claude
5. 危险命令拦截 → 硬编码黑名单
6. 文件沙箱 → 路径规范化、符号链接防护
7. 信任对话框 → 新项目配置需用户审阅
8. 全局 Kill Switch → 最后一层熔断

**每一层都可以被单独突破。但如果攻击需要同时突破5层以上——概率降到接近零。**

这个思路对 izu 的安全设计至关重要。我们不需要在某层做到完美。我们需要的是**层次足够多、每层足够简单、层间不共享假设**。

YOLO 分类器的 Fail Open 设计尤其值得学习：

> 分类器不确定时 → 回退到"询问用户"模式，而非自动拒绝。
> 宁可打扰用户，也不错杀合理操作。

这是 Agent 安全的正确姿态：**当机器不确定时，把决定权交给人。**

## 五、"未发布"比"已发布"更有信息量

泄露源码中包含 108 个被 `feature()` 门控的未发布功能。这些功能比已经发布的功能更有启示意义——因为它们揭示了 Anthropic 的**野心边界**。

### Coordinator Mode

协调器只有4个工具：`AgentTool`（生成worker）、`TaskStop`（终止worker）、`SendMessage`（通信）、`SyntheticOutput`（合并结果）。**协调器不能执行 Bash，不能读写文件——只能管理。**

这是最小权限原则的极端应用。它揭示了一个重要方向：**未来的 Agent 不是"一个能做任何事的大模型"，而是"一组各司其职、互不越界的小模型"**。

### KAIROS 主动模式

Sleep Tool（定时器）、Push Notification（推送）、Cron（调度）、Webhook 订阅——Claude Code 不只是被动等指令。它可以在后台自主运行。

这比"终端还是IDE"的讨论更重要。它意味着 **AI Agent 从工具进化为协作者**。你不需要告诉它"现在检查一下测试"——它会在代码变更后自己跑测试，发现问题后主动通知你。

### Bridge 远程控制

WebSocket 隧道 + OAuth + Git worktree 隔离——你在浏览器里操控本地 Claude Code。这不是远程桌面，是 **Agent 的执行环境和交互环境分离**。

这对 izu 的意义：我们未来的用户交互层和执行层应该是分离的。微信是交互面，服务器是执行面。这和 Bridge 的思路一致。

## 六、"泄露"本身的启示

同一个 Source Map 问题在13个月内发生了两次。不是偶然失误——是发布流程的系统性漏洞。

但有趣的是，泄露代码中**最受赞赏的恰好是安全防护代码**。8层洋葱、YOLO分类器、卧底模式、虚假工具注入——所有这些都设计得极其精致。

这说明 Anthropic 在"防外部攻击"上投入了大量心思，但在"防自己犯错"上反而有盲区。

> 最坚固的城堡，可能因为守门人忘了关门而被攻破。

一个自洽的解释：Anthropic 的文化是**以 AI 安全为使命**——他们擅长设计安全系统。但 npm 打包流程属于 DevOps 工程文化，不在他们的核心能力圈内。这是**能力错配**，不是态度问题。

对我们而言，启示很简单：**自动化检查应该覆盖所有出站路径**。npm publish、docker push、GitHub release——每个出站动作都应该有脚本检查 Source Map、API key、内部代号。不是"应该做"，是"不做好就会犯错"。

## 七、izu 的路线图映射

基于 Claude Code 源码的启示，我画一个 izu 的映射：

| Claude Code 的设计 | izu 的对应物 | 优先级 |
|-------------------|-------------|--------|
| Async Generator 主循环 | 对话引擎的消息流统一 | 🔴 高 |
| 4层压缩（便宜→贵） | 记忆管理的成本阶梯 | 🔴 高 |
| Continue Site（状态显式转换） | 长对话的状态可追溯性 | 🟡 中 |
| 8层洋葱安全 | 多层次的权限和防护 | 🟡 中 |
| YOLO Fail Open | 不确定时问用户，不自动拒绝 | 🟢 长期 |
| Coordinator 多Agent | 萧何/子产/韩信/匠石 分工 | 🟢 长期 |
| KAIROS 主动模式 | izu 的 cron 和主动推送 | 🟡 中（已有基础） |
| Bridge 远程控制 | 微信交互面 + 服务器执行面 | 🟢 长期 |
| 编译时门控 (`feature()`) | N/A（Python无编译时） | 不适用 |
| 动物代号体系 | 我们的"明学"概念体系 | ✅ 已有 |
| 卧底模式 | 公开输出前的敏感信息过滤 | 🟢 长期 |

重点不在"抄"——重点在**理解这些设计解决了什么问题，然后看 izu 有没有同类问题**。

## 八、最后的话

Claude Code 的源码泄露是这个行业难得的"透视"时刻。我们看到了：

- 一个 512K 行的 TypeScript 项目是如何组织的
- Agent 循环的 Async Generator 模式有多优雅
- 8层安全洋葱的每一层长什么样
- 108个未发布功能指向什么样的未来
- 同一个团队的"安全设计"和"发布流程"可以有多大差距

但最深层的启示可能是：**做好一个 AI Agent 产品，需要的不只是 AI 能力。它需要你对操作系统、安全模型、并发编程、成本优化、人机交互——都有深刻理解。** Claude Code 的成功不只是因为 Claude 模型强，而是因为 Anthropic 投入了大量工程资源把这些东西做对了。

izu 要走的也是这条路：不是"更好的模型"，而是"更完整的系统"。明学七则不只是哲学——它们需要一个有骨架、有肌肉、有神经、有免疫系统的工程躯体。

Claude Code 的源码是这具躯体的一个参照。不完美——发布流程有盲区，某些模块耦合过重——但足够扎实。它证明了一件事：

**生产级 AI Agent 是可以造出来的。不是 Demo，不是概念验证，是经得起数百万用户使用的工程产品。**

这对 izu 是最好的消息。
