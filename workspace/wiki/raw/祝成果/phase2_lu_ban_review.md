# Phase 2 — 核战队终审

## 审阅人3：鲁班（双轨道工程可行性与整合评审）

### ITA轨道工程评估

**可执行性评级：★★★★☆（4/5）**

**优势**：
1. 实验设计具体、可操作——不需要突破性工程技术
2. 0成本启动路径明确（小模型复现 → 技术报告）
3. 分阶段预算设计合理

**风险**：
1. Apple论文使用专有谜题生成器——重建可能需要2周而不是1周（工程乐观估计）
2. 闭源模型hidden state探测受限——实验2在闭源模型上仅能获得logprobs，维度大幅缩减
3. 验证器实验的"互验证"问题：如果验证器也需要推理，在高度复杂度区域验证器+推理器的联合失效可能不是对称而是级联

**建议调整**：
- 实验2区分"强探测"（开源full hidden state）和"弱探测"（闭源logprobs）两种模式
- 先做弱探测→如果已有显著信号，强探测可有可无
- 实验4的验证器使用比推理器小一个级别的模型（而不是同级或更高级）→ 验证"廉价验证"的可行性

### izu轨道工程评估

**可执行性评级：★★★★★（5/5）**

**优势**：
1. 架构成熟、技术栈成熟——无任何new research risk
2. 单人可完成主体开发（7周MVP）
3. 开源→社区反馈闭环清晰

**风险**：
1. 竞品风险确实存在——LangChain等可能在6个月内集成类似功能
2. 用户采纳的关键不在工具本身，而在"Agent可靠性"是否已成为企业优先事项
3. Phase 2种子用户获取可能比预期困难（企业愿意分享Agent事故数据吗？）

**建议调整**：
- MVP阶段就加入"匿名数据上报"功能——用户允许的情况下收集评估结果 → 建立业界首个Agent可靠性数据库
- 这个数据库本身就是巨大的护城河（Network Effect：越多用户 → 越丰富的故障模式库 → 越好的评估 → 越多用户）

### 双轨道整合评审

**ITA ⇄ izu 的互相增益点**：

```mermaid
ITA (推理崩溃机制)                  izu (Agent可靠性工程)
     │                                    │
     ├─ 理解失败模式 ──────────────────→  评估指标设计的理论依据
     │                                    │
     ├─ 复杂度预测器 ──────────────────→  运行时的预判放弃
     │                                    │
     └─ 验证器校准 ──────────────────→   安全护栏的触发阈值
```

**最可落地的整合方案**：

1. **第一优先级（快赢）**：izu的离线评估工具——利用ITA的形式化框架作为评估指标的"why it matters"背书
2. **第二优先级（差异化）**：ITA的"推理复杂度评估器"——在Agent接受任务前预估任务是否超出模型阈值，作为izu Layer 2的预检组件
3. **第三优先级（长期）**：从ITA的推理崩溃研究到Agent运行时容错机制的系统性转化
