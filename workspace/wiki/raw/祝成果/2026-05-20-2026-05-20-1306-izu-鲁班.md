# 鲁班（工程可行官）

## 工程可行性判断：izu记忆系统

### 能不呢？——能，但有取舍

#### 核心方案：基于Mem0剪枝的轻量级记忆系统

**可行性：✅ 可行**

| 组件 | 方案 | 工程难度 | 代码量 |
|------|------|----------|--------|
| 记忆存储 | SQLite + 向量嵌入 | 简单 | ~200行 |
| 混合检索 | BM25(SQLite FTS5) + FAISS向量检索 | 中等 | ~500行 |
| 记忆衰减 | 定时任务 + 权重计算公式 | 简单 | ~100行 |
| 知识图 | JSON-based Property Graph | 中等 | ~300行 |
| 对话接口 | 基于zu系现有交互管道 | 简单 | ~200行 |

**总估算**：~1300行代码，1-2月开发

#### 有没有重复造轮子？

| 轮子 | 是否重复 | 决策 |
|------|----------|------|
| Mem0/GitMemory | 直接复用 | 取其架构思想，但独立实现（避免新增依赖） |
| FAISS | 引用库 | 标准向量检索库，无需重写 |
| BM25 (SQLite FTS5) | 标准功能 | SQLite内置，零依赖 |
| 记忆衰减算法 | 自主研发 | 文献中无现成方案（这是izu的创新点） |

**结论**：大部分组件复用成熟技术，唯一的创新点是"知识陪伴场景下的记忆衰减策略"。

### 造什么装备？

1. **记忆模块（Memory Module）**
   - 功能：写入、检索、更新、衰减、删除
   - API：`memory.write(key, content, context, importance)` / `memory.query(query, top_k=5)`
   - 存储：SQLite数据库 + 向量索引文件

2. **衰减调度器（Decay Scheduler）**
   - 功能：按时间/交互频率/重要性权重计算每个记忆的当前得分
   - 低于阈值的记忆自动归档或删除
   - 规则引擎（可配置）：用户可设定"不要忘记关于XX的事"

3. **对话记忆桥（Memory Bridge）**
   - 功能：将自然会话转化为记忆操作
   - 当用户说"你还记得上周说的那个项目吗？" → 检索相关记忆
   - 当用户说"这个很重要，记下来" → 标记高重要性
   - 需要LLM的NLI能力（复用zu系已有LLM接口）

### 工程限制

| 限制 | 说明 |
|------|------|
| 单机部署 | 不支持分布式，所有数据本地存储 |
| max记忆数 | 默认10万条上限（约500MB空间） |
| 检索延迟 | 混合检索<100ms（本地运行） |
| 首次启动 | 需要1-2天积累初始记忆 |

### 结论
**工程上可行。技术栈成熟，唯一的工程创新点在记忆衰减策略。** 建议在ITA实验的20天内（izu并行思考期）完成记忆模块的架构设计和原型编码。
