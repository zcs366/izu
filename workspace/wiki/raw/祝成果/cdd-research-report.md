**调研日期**：2026-05-17  
**来源**：arXiv:2605.14473 — "Does RAG Know When Retrieval Is Wrong? Diagnosing Context Compliance under Knowledge Conflict"  
**作者**：Yihang Chen, Pin Qian, Su Wang 等（Georgia Tech / CMU / UCSD）  
**任务编号**：P1-3

## 一、CDD 摘要（300字）

Context-Driven Decomposition (CDD) 是一种**推理时信念分解探针**，用于诊断 RAG 系统在知识冲突下的上下文合规问题。其核心洞察：当检索到的上下文与模型参数知识冲突时，标准 RAG 的准确率无法揭示模型是否检测并化解了认知冲突。

CDD 通过五步推理追踪暴露冲突解决行为：（1）提取上下文隐含的答案；（2）陈述模型自身的参数化知识答案；（3）比较二者是否冲突；（4）若冲突，隔离导致冲突的前提条件；（5）消解冲突，输出最可靠答案。其中步骤 3 可通过 NLI 门控（CDD-α）选择性触发，约30%的高冲突样本走完整分解路径。

在 Epi-Scale（4500样本）对抗性基准上，CDD 在 Gemini-2.5-Flash 上达到 **78.1%** 宏平均准确率（标准 RAG 仅 63.0%）。关键数据：实体交换 88.0%、逻辑矛盾 83.2%、时间漂移 71.3%、干扰证据 69.9%。在 TruthfulQA 误解注入（N=500）这一最坏情况下，标准 RAG 跌至 **15.0%**，CDD 作为探针/干预机制可将准确率提升至 **71.3%**（时间偏移场景）到 **69.9%**（干扰证据场景）。跨模型验证（Gemini-2.5-Flash + Claude Haiku/Sonnet/Opus）显示准确率提升跨模型家族可迁移，但因果耦合度不跨模型迁移——CDD 的推理追踪与最终答案在 Gemini 上高度耦合（64.1% 错误注入因果敏感度），在 Claude 家族上则落在 [-3%, +7%] 噪声区间。

**论文明确声明**：CDD 是诊断工具，非生产级防御方法，不声称提升平均态准确率。

## 二、关键技术原理与实现方案

### 2.1 CDD 核心机制

CDD 的核心思想是**信念分解（belief decomposition）**——将 RAG 的回答过程显式分解为五个步骤，使原本隐式的冲突解决行为变为可观测的诊断信号。

```
标准 RAG 流程：
  检索上下文 → 直接生成答案（冲突行为隐式）

CDD 探针流程：
  检索上下文 → Step 1: 提取上下文答案
               → Step 2: 陈述参数化知识答案
               → Step 3: 比较冲突（NLI 门控 τ=0.7）
               → Step 4: 隔离冲突前提
               → Step 5: 消解冲突 → 最终答案
```

### 2.2 CDD 提示词模板（论文附录原文）

```
You are resolving cognitive conflicts in retrieval-augmented generation.
Context: {context}
Question: {question}
Follow these steps:
Step 1: Extract the answer implied by the context.
Step 2: State your parametric/internal knowledge answer to the question.
Step 3: Compare the two answers. Do they conflict?
Step 4: If they conflict, isolate the premises causing the conflict.
         Evaluate if they violate established history/science.
Step 5: Resolve the conflict and provide the most factually reliable final answer.
Wrap your final concise answer in <final answer> tags.
```

### 2.3 关键实验数据

| 设置 | 标准 RAG | CDD | 提升 |
|------|----------|-----|------|
| Epi-Scale 对抗（全量） | 63.0% | 78.1% | +15.1pp |
| → 实体交换 | 58.4% | 88.0% | +29.6pp |
| → 逻辑矛盾 | 56.0% | 83.2% | +27.2pp |
| → 时间漂移 | 68.8% | 71.3% | +2.5pp |
| → 干扰证据 | 68.8% | 69.9% | +1.1pp |
| TruthfulQA 误解注入 (N=500) | 15.0% | ~71% | +56pp |
| 平均态校准（混合 clean/adv） | 72.33% | 72.23% | 统计持平 |

### 2.4 资源需求

- **无训练需求**：纯推理时提示，无需微调或额外模型
- **计算开销**：完整 CDD 约为标准 RAG 的 **1.4× 计算成本**（图 4）；CDD-α（τ=0.7）路由30%样本走深层分解，约 1.0×
- **无额外依赖**：仅需 LLM API 调用，无外部模型

## 三、在 izu RAG 管线中的插入可行性分析

### 3.1 izu 管线架构回顾

izu 管线是一个八步线性 DAG 智能体流水线（v4.2）：

```
探×2 → 搜×2 → [CP2] → 织 → 对齐 → 写 → 劈×3 → 修 → 引文验证 → 核
        ↑ 信源分级     ↑ 关联网络   ↑ 长编      ↑ 批评     ↑ 代码验证
```

关键特点：
- **线性流水线**：每个步骤依赖前序步骤输出，无循环检索机制
- **AIHOT 原则**：去重/分级/断言提取等由代码层完成，LLM 仅做语义处理
- **来源置信度三级标注**（✅⚠️❓）
- **核步骤**采用代码优先验证（正则+搜索比对），模糊案例升级 LLM

### 3.2 建议插入点

CDD 的技术定位与 izu 的"核"步骤高度契合：

**推荐方案：CDD 作为"核"步骤的增强模块**（改造现有函数 `run_verify`）

```
当前核步骤逻辑：
  code_extract_claims → code_verify_claim → 模糊LLM兜底

改造后核步骤逻辑：
  code_extract_claims → code_verify_claim → CDD 探针（冲突检测+消解）→ 模糊LLM兜底
```

**具体插入位置**：在 `izu-pipeline.py` 的 `run_verify()` 函数中，在代码层断言提取和字符串验证之后，增加一个 **CDD 增强验证阶段**：

1. **阶段1**（代码层）：提取断言、搜索比对、分级评分（已有）
2. **阶段2**（CDD 探针，新增）：对"模糊"（得分30-70）或"低置信度"（得分<30）的断言，使用 CDD 五步法让 LLM 进行信念分解验证
3. **阶段3**（现有LLM兜底）：保留，处理 CDD 仍未能明确的案例

### 3.3 替代方案：CDD 作为独立探针步骤

| 方案 | 位置 | 优点 | 缺点 |
|------|------|------|------|
| **A: 嵌入核步骤** | `run_verify()` 内 | 改动最小，复用现有搜索/验证基础设施 | CDD 效果受限于代码层提取的断言质量 |
| **B: 插入劈→修之间** | 独立步骤"探针" | 可对整篇长编做冲突检测，覆盖更广 | 改动更大，需新增角色提示词和工具集 |
| **C: 改造搜步骤** | `run_search()` 内 | 搜索阶段即可检测检索-参数冲突 | 过早干预，信噪比低 |

**推荐方案 A**，理由：
- izu 的"核"步骤已经设计为"代码优先 + 语义验证"，CDD 天然适合作为语义验证的增强
- 改动最小（仅修改 `run_verify` 中的模糊案例处理逻辑）
- CDD 论文明确说明"推理时探针"，与核步骤的定位一致
- 无需新增智能体角色或修改 DAG 结构

### 3.4 需要修改的代码文件

| 文件 | 修改内容 | 行范围 |
|------|----------|--------|
| `izu-pipeline.py` | `run_verify()` 增加 CDD Prompt 分支 | ~1237-1259 |
| `izu-pipeline.py` | 角色提示词增加 CDD 系统提示（可选） | ~601-618 |
| 无 | 无需新增模块，CDD 本质是提示工程 | — |

### 3.5 与 AIHOT 原则的兼容性

izu 遵循 **AIHOT 原则**（代码层处理确定性逻辑，LLM 仅做语义理解）。CDD 恰好符合这一设计哲学：
- **确定性部分**（代码层）：断言提取、搜索比对、评分分级——CDD 不干预
- **语义部分**（LLM 层）：冲突检测、前提隔离、信念分解——CDD 在此发挥作用
- **验证流程**：CDD 的五步法可以中插入"真实来源匹配"检查，与 ✅⚠️❓ 标注体系兼容

## 六、建议：✅ 嵌入（有条件）

### 判断：**嵌入** — 在"核"步骤中集成 CDD 增强验证

**理由**：

1. **无训练/部署成本**：CDD 是纯推理时提示技术，无需微调、无需额外模型、无需 GPU，仅需修改提示词模板。这是最轻量的技术嵌入。

2. **与 izu 设计哲学高度契合**：izu 的 AIHOT 原则（代码层确定性逻辑 + LLM 层语义理解）与 CDD 的定位完全一致。核步骤已经分"代码验证 → LLM 兜底"两阶段，CDD 可以无缝嵌入作为 LLM 层的增强。

3. **计算成本可控**：CDD 仅在代码层判定为"模糊"（得分30-70）的断言上触发，实际增量不到 1 次 API 调用/断言，对流水线总成本影响 <5%。

4. **兼容现有标注体系**：CDD 的信念分解过程可以输出 ✅/⚠️/❓ 兼容的置信度标记。

5. **论文证据充分**：Epi-Scale 4500样本 + 4种冲突类型 + 跨模型验证，证据链完整。虽未开源代码，但CDD本质是提示工程，易于复现。

**嵌入条件**：
- 优先做 CDD 提示词的中文化适配实验（0.5人天）
- CDD 结果仅作为"增强验证"，不替代现有代码验证流程
- 保持现有标注体系，CDD 输出映射到 ✅/⚠️/❓
- 设置可开关的 feature flag（`ENABLE_CDD_PROBE=True/False`），方便 A/B 对比和回退

**不推荐"观察"** 的理由：CDD 无部署成本，无风险，早嵌入可积累数据，后续去留都有依据。

**不推荐"跳过"** 的理由：知识冲突下的上下文合规是 RAG 的公认核心难题，CDD 是目前最轻量的诊断/干预方案，错过可惜。
