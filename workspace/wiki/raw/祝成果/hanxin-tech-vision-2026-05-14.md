## 一、终局画像（3-6个月后）

### 用户第一次打开izu时的体验

打开izu，用户看到的不是"一个对话窗口"。左侧是**Agent关系拓扑图**——实时显示哪些Agent在线、谁在和谁协作、负载分布；中间是**任务流实况**——当前任务被谁接了、进展到哪一步、预计完成时间；右侧是**知识图谱生长动画**——新知识自动挂载到已有节点上，关系线逐渐延伸。

用户不需要说"调用探Agent"——他说"研究这个主题"，系统根据关系拓扑自动匹配最优Agent组合。做完之后，验证Agent检查输出质量，进化引擎把这次的经验写入Agent的记忆。下次同类任务，效率提升一档。

### 核心交互循环

```
用户提需求
  → 关系拓扑层自动分配任务给最优Agent组合（而非固定流水线）
  → Agent协作过程中知识图谱实时增量更新
  → 验证Agent核对输出质量
  → 进化引擎记录"这次哪里做得不好"
  → 下次同类任务自动优化Agent选择+提示策略
```

### 与今天的本质区别

| 维度 | 今天（v0.2） | 3-6个月后（v1.0） |
|------|-------------|-----------------|
| Agent协作 | 固定流水线：探→搜→织→对齐→写→劈 | 动态拓扑：根据任务类型+历史表现自动选择Agent组合和调度顺序 |
| 知识管理 | wiki静态页面，手动入库 | 依赖解析驱动的自动图谱构建，实时挂载+去重+融合 |
| 自我改进 | 无 | 验证驱动进化：每次任务结束后自动评估→补短板 |
| Agent间关系 | 无关系建模，各自独立 | 显式社交图：谁擅长什么、与谁协作更高效、历史信任度 |
| 框架设计 | 代码即文档 | 学术级设计文档，以Agent框架设计决策维度为模板 |

### 一个典型用户的完整故事

**今天（v0.2）**：用户想深入研究"GraphRAG优化"，需要说"用izu研究GraphRAG"→军师触发三部曲→探→搜→织→对齐→写→劈→入库。每一步固定，不管主题是什么，流程都一样。

**3-6个月后（v1.0）**：用户说"研究GraphRAG优化"。izu自动判断：这个主题偏知识检索，最优Agent组合是探2个+搜3个（节省1个搜的预算），跳过织（已有大量成熟资料，不需要从头编织），直接对齐→写。同时，知识图谱模块用依赖解析自动构建GraphRAG相关节点，和已有的"RAG""知识系统"节点自动建立关系边。输出后，验证Agent检查引用准确性，发现两个断链，自动记录"下次优先检查arxiv链接"。下次研究类似主题，Agent自动跳过之前踩过的坑。

用户感受到的不是"AI更聪明了"——是**它记住我了**。

## 二、技术路线

### 2026年下半年AGI关键趋势

| 趋势 | 对izu的影响 |
|------|-----------|
| Agent从单体走向生态系统 | 单Agent能力快到天花板，竞争转移到多Agent协作效率和关系建模。izu必须第一个在开源Agent框架中内置关系拓扑层 |
| 自我进化从概念走向工程化 | ICLR 2026接收ReVeal（#7），说明"验证驱动进化"已从学术概念进入工业可用阶段。不跟进就是等别人开源后被动适应 |
| GraphRAG要从"好用"到"快建" | 构建成本是GraphRAG落地的最大瓶颈。依赖解析（#1）已将成本压到LLM方案的6%，这条路线半年内会成熟 |

### 我们的技术阶梯

```
现在（v0.2）
  能力：固定7智能体流水线 + wiki静态存储 + 手动词条入库
  ↓ 关键升级①：引入关系拓扑层（2-4周）
v0.3
  新增：Agent社交图 + 动态任务分配（基于历史表现而非固定顺序）
  ↓ 关键升级②：融合验证驱动进化（4-8周）
v0.5
  新增：每次任务结束后自动评估 + Agent短板补全 + 提示策略自优化
  ↓ 关键升级③：接入依赖解析GraphRAG（4-6周）
v1.0
  终局能力：自适应Agent组合 + 实时知识图谱 + 验证-进化闭环 + 关系拓扑可视化
```

### 技术债务预警

| 今天的决策 | 3个月后的问题 | 建议 |
|----------|-------------|------|
| wiki用markdown文件存储 | 图谱查询只能走文件搜索，无法做一跳遍历 | v0.3起同步建设Neo4j图索引层 |
| Agent流水线硬编码顺序（探→搜→织→对齐→写→劈） | 无法根据任务类型动态调整，瓶颈在织（浪费token） | v0.3关系拓扑层直接解决 |
| 没有质量评估环节 | 输出质量无法量化改进，进化没有基准 | v0.5验证模块是进化引擎的前提，必须提前设计评估维度 |
| 只有一个Agent定义文件（SKILL.md） | 无法记录Agent间的协作历史和信任度 | 关系拓扑层需要持久化Agent间关系数据 |

## 三、版本阶梯

### v0.3 — 关系拓扑层（目标：2-4周内完成）

**核心功能**：
- Agent社交图数据结构（每个Agent的擅长领域、与谁协作更高效、历史任务表现评分）
- 动态任务分配引擎（根据任务类型+Agent历史表现选择最优组合）
- 关系拓扑可视化（终端TUI中显示Agent在线状态和协作关系）

**验证什么**：
- 动态分配是否比固定流水线效率更高（token消耗+输出质量两个维度）
- 关系数据是否准确反映Agent真实能力

**不做**：不在此版本做进化引擎（那是v0.5的事）；不做Neo4j（先存JSON）

### v0.5 — 验证驱动进化（目标：4-8周内完成）

**核心功能**：
- 任务完成后自动生成评估报告（引用准确率、逻辑一致性、完整性）
- 评估结果写入Agent历史，触发提示策略微调
- 观察上下文压缩（借鉴#8），降低长期记忆膨胀

**验证什么**：
- 进化后的Agent是否在同类任务上表现提升
- 压缩策略是否丢失关键上下文

**不做**：不在此版本做GraphRAG大规模图谱化（那是v1.0的事）

### v1.0 — 终局体验（目标：3-6个月）

**完整形态**：
- 自适应Agent组合 + 关系拓扑可视化
- 依赖解析驱动的实时知识图谱（wiki入库→自动构建节点+边）
- 验证-进化-压缩融合的生命周期管理
- 学术级框架设计文档

**与v0.2的本质区别**：从"7个按照固定顺序工作的工具"变成"一个会自己调配兵力、会自己反思进步、会自己组织知识的活的系统"

## 四、定调判断

### 我们坚决做的

1. **关系拓扑层优先于所有其他特性。** 日报4篇指向同一个方向（#2 #8 #9 #10）——多Agent协作的下一个战场不是单Agent能力，是关系建模。先做关系拓扑，再做进化，再做图谱。顺序不能乱。
2. **验证驱动进化作为核心差异化。** ICLR 2026刚接受这个概念，工业界还没跟进。6个月内复现ReVeal并定制化为izu的进化引擎，抢占开源Agent框架的进化赛道。
3. **依赖解析驱动图谱构建。** 放弃"等有钱了买更好的LLM建图谱"的思路——#1已经证明依赖解析能达到94%效果。花2周实验验证，可行就上。
4. **以学术论文框架写设计文档。** 第9篇给了现成的维度模板。照这个模板写一份izu框架设计文档，既是内部决策依据，也可以发成技术博客建立社区影响力。

### 我们坚决不做的

1. **不等开源的通用进化框架。** 等别人做完再改，永远是追随者。ReVeal的论文+代码已经公开，直接复现定制。
2. **不追求图谱的100%准确率。** 94%够用了，剩下的6%由用户手动校正。追求完美图谱=永远做不出来。
3. **不在v0.3引入Neo4j。** JSON先跑通关系拓扑的设计和算法，验证有效后再切图数据库。过早优化是万恶之源。

### 我们保持观察的

1. **端侧Agent部署**：#8的终端Agent压缩策略可能引出新的部署模式（极轻量Agent跑在本地），待v0.5之后再评估
2. **多模态知识图谱**：今天所有GraphRAG论文都在文本域，多模态图谱是大厂的下一个方向。等大厂开源后再跟，不做前沿探索
3. **Agent框架标准化**：#9的框架分类一旦被社区广泛采用，izu需要快速对齐——但不急着做第一个
