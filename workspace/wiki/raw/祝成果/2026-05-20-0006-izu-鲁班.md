# 鲁班 · 工程可行官

【韩信的技术远景】
- 3个月：Mem0起步 → 记忆闭环跑通
- 6个月：自建知识节点系统 → 自进化雏形
- 现在：记忆分层 + 交互信号采集

## 工程可行性判断

### Mem0集成 → 完全可以（1-2天）
- Mem0有成熟的Python SDK，pip install mem0ai即可
- 提供add()查询/搜索/save/load接口，5行代码接入
- 当前izu的message handler中插入Mem0调用即可记录历史
- **唯一风险**：Mem0的免费层配额有限（约1000次/月），超出需付费（约$20/月）

### 知识节点系统 → 条件可行
**条件**：先跑通Mem0版本再切换
- 手动实现主体-客体-关系-置信度-时间戳-来源这6个字段的知识节点数据库
- Neo4j太重，建议用SQLite（结构化）+ Chroma（向量检索）混合存储
- 预估工时：30工时（从Mem0切换到自建系统）

### 记忆分层 → 现在就可以做
- episodic memory：最近的对话历史（Mem0自动管理）
- semantic memory：从对话中提取的知识节点（需2-3行LLM prompt做提取）
- procedural memory：skill库（CMDs和script的索引）
- **不需要大改架构**，在当前izu的message处理流中加入一个memory_hook即可

### 交互信号采集 → 1小时搞定
- 在izu的响应中加入埋点：记录每次对话的token数、用户主动发起标记、话题tag
- 用SQLite存储时间序列（timestamps → 指标值）
- 后续用简单统计分析即可得出陪伴质量指标

### 有没有重复造轮子？
- MemSkill的skill evolution机制很吸引人，但其代码基于LangChain，izu如果不用LangChain则适配成本高
- 建议：izu借鉴MemSkill的核心思想（RL-based skill selection），但实现自己的skill存储格式（izu的CMDs接口已有基础）
- 没有重复造轮子，因为izu的领域（个人知识陪伴）没有现成框架
