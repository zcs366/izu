### 1.3 与今天的本质区别

| 维度 | 今天（2026-05-15） | 3个月后终局 |
|------|-------------------|------------|
| 创建方式 | cronjob(name, prompt, schedule, ...) 需要想清楚所有参数 | `/loop [一句话]` → 自动推断参数，或从模板选择 |
| 防失控 | 无。cron无限跑、不设限 | Loop Contract: max_attempts/max_spend/stop_condition/scope 四重安全网 |
| 成本可见性 | 不知道哪个cron花了多少钱 | 每loop分级账单，预算自动暂停 |
| 链式调用 | context_from 手动指定job_id | 可视化"数据链"自动生成，一目了然 |
| 失败处理 | cron出错静默失败，或无限重试 | 按合约规则处理：重试/暂停/通知/归档 |
| 模板化 | 无。每个cron从零写prompt | 预置模板 → 选模板 → 填参数 → 完成 |
| 可视化 | 无从查看。只能 `cronjob list` | 浏览器dashboard + Telegram `/loops` 命令 |
| 命名 | 自己起名，不统一 | 标准化 `category/name` 命名规则 |

### 1.4 一个典型用户的完整故事

张成市周三晚上刷到一个GitHub仓库的更新——Hermes Agent支持了MCP原生客户端。他感兴趣，想追踪后续版本。

以前：他要写个cronjob，想定时、想失败策略、想什么时候通知他——想得太复杂，最后算了。

现在：他在Telegram输入 `/loop watch/hermes-releases 跟踪Hermes MCP功能发布，有新版本通知我`。

系统做了什么：
1. 推断这是一个「监听型loop」——每6小时检查一次
2. 自动设置 `stop_condition = new_version > current_version`
3. 分配 `max_spend = $0.10/天`（监听类默认低预算）
4. 从模板「版本监听」补全剩余参数
5. 立即执行第一轮——「当前版本：v3.2.0」
6. 回复张成市：**Loop已创建**，合约摘要，预计每周花费$0.07

三天后的凌晨3点，系统检测到Hermes v3.3.0发布，自动触发 `stop_condition` 条件满足——loop暂停，张成市早上看到一条通知：「Hermes v3.3.0已发布，发布说明摘要如下... 此loop已达目标，已自动归档。」

整个过程，张成市说了7个字。其余全部由系统自主完成。

## 三、与AGI方向的贴合论证

### 为什么这个方向是对的？

**核心判断：这不是在造一个"cron的UI界面"，而是在构建"Agent权限与自主度分级框架"。**

AGI的核心挑战之一是 **Agent的自主性与可控性的平衡**。今天的大模型已经足够聪明到可以自主完成任务——Cherny的 `/loops + Routines` 和刘飞的观点都验证了这一点。但问题是：

> 你怎么放心让一个Agent在你睡觉的时候替你做事？

Loop Contract 就是答案——它是一种 **Agent权限声明式契约**。

### 与AGI发展三条主线的贴合

| AGI关键趋势 | Loop Contract 的贴合处 |
|------------|----------------------|
| **Agent自治化**：Agent从"对话助手"进化到"自主工作者"，需要异步执行 | Loop让Agent在用户离线时持续工作，是Agent从"问→答"到"委托→交付"的必然形态 |
| **成本敏感化**：Token成本下降但用量爆炸，需要预算管理 | Loop Contract 的 max_spend 是Agent预算的原生能力——LLM成本每季度降50%，用量涨3x，没有预算合约的Agent系统会失控 |
| **能力「信任层」**：Agent当前仍会失败/幻觉/跑偏，需要安全网 | max_attempts / stop_condition 是Agent信任层的最低要求——先有安全网，才敢放手 |
| **多Agent协作**：不同Agent负责不同领域，需要标准化契约 | context_from 链 + 命名分类 = 多Agent协作的"数据水管"，比复杂的Agent间通信协商务实100倍 |

### 为什么不是追热点？

1. **不是Agent编排平台**。我们不造Kubernetes for Agents。我们在一个极简的cron系统上叠加合约安全层——每加一层都有明确的"张成市用得上"的场景。

2. **不是RAG增强**。不碰向量数据库、不搞知识图谱增强。我们解决的是"Agent干活时我怎么放心睡觉"这个非常具体的问题。

3. **不是Agent间通信协议**。子产已经砍了。我们不搞Agent协商、不搞角色间消息传递——就是data pipeline，通过context_from传递数据。

4. **贴合Cherny的实际验证**。Cherny的 `/loops + Routines` 已经验证了这个方向的用户价值：不是并发数，是"不用盯"。

### 半年后的竞争判断

| 可能的变化 | 对我们的影响 |
|-----------|------------|
| Claude Code支持类似Routines | 验证方向正确。我们的差异点在深度合约化（max_spend/stop_condition 层级更细）+ 成本极度敏感 |
| OpenAI Codex支持定时Agent | 同上。我们的优势在已有35个cron的实战负载和经验 |
| 开源Agent框架内置类似能力 | 拼的不是功能，是"张成市每天1小时"的实际场景适配 |
| LLM成本继续下降 | 利好！loop运行更便宜，更多场景可自动化 |

## 四、三句话定调

> **第一句：Loop Contract 不是cron的UI升级，是Agent从"玩具"到"员工"的授权契约。**  
> 没有合约的Agent你敢让它干活吗？Loop Contract 就是信任层。
>
> **第二句：我们不造Kubernetes for Agents，只做"睡觉时替我干活"这一个场景。**  
> 子产已经砍了集群和通信层。我们的核心不是并发数，是"不用盯"。
>
> **第三句：从终局倒推，第1个月先铺安全网，第2个月让用户能管，第3个月给用户看的界面。**  
> 没有safety net之前不谈可视化。没有可视化之前不搞推荐引擎。

## 六、风险与预警

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| 张成市每天1小时 → 第1个月可能无暇测试 | 合约设计脱离实际 | 每一步都产出最小可运行版本，在现有cron上直接测试 |
| 费用核算不准 | 预算控制失效 | 先用估算（token数×模型单价），后续逐步精确 |
| stop_condition 语义判断不准 | 该停的没停，不该停的停了 | 默认策略：模糊时偏向"继续运行" + 通知用户确认 |
| 模板滥用 | 大量相似loop浪费资源 | 模板创建时默认较低预算上限，用户手动提额 |
| 系统本身占用过多cron资源 | 治丝益棼 | Loop系统本身的数据存储用文件/DB，不额外跑cron |
| 张成市对改动抵触 | 全盘推倒 | 第1步安全网完全透明——用户不需要感知变化，系统默默接管 |
