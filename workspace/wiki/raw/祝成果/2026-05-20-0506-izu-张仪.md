# 张仪 · 最强攻击

## 单点失败分析

### 最致命的一个点：**self-improve循环的"信号坍缩"**

理由：
1. izu目前是一个单会话Agent（每次会话独立）。"自改进"需要在session之间传递改进信号。但如果session日志的覆盖率不够（用户只在特定场景使用izu），发现的"模式"可能是采样偏差而非真实模式。
2. **更致命的是**：如果自改进循环开始修改SKILL.md（skill_updater.py），但修改判断是错的，它会自我强化。坏skill → 更差表现 → 基于更差表现的log发现"失败模式" → 再次修改skill → 螺旋下降。这被称为**自改进循环的"反馈污染"**。
3. HyperAgents的成功（跨领域转移）是因为有独立的评估集。izu没有独立评估集——改进信号来自用户交互日志，而日志本身已被当前skill质量污染。这是个**因果循环**：skill质量影响用户交互质量，用户交互质量作为改进信号又决定下一版skill质量。

### 降级方案

**降级A：人工审核门禁（+每2天30min审查）**
```
自改进循环产生skill修改建议 → 生成diff → 存入建议队列
→ 张成市每2天审查一次 → 批准/拒绝/修改后批准
→ 批准后才生效
优点：避免反馈污染
缺点：依赖人工频率
```

**降级B：双倍采样（增加鲁棒性）**
```
每个模式发现需要：
- 同一模式出现≥3次才视为模式
- 模式出现跨≥2个独立session（避免单session噪声）
- 模式的正向/负向信号都有（有对比才有因果）
如果某条skill修改建议满足以上条件→可自动执行
否则→进入降级A的人工审核
```

**降级C：外部分层评估（终极方案）**
```
用LoCoMo基准定期评估记忆质量
用HumanEval基准定期评估代码能力
用自定义场景测试定期评估综合能力
这些外部基准不依赖于izu自身日志 → 避免了"信号污染"
自改进的内容必须以通过这些外部基准为条件
代价：每次基准测试2-3小时计算（可周期执行）
```

### 推荐方案
**降级A+B组合**：所有自动修改走人工审核门禁，但在审核前用降级B的3×2规则筛选。这样人工负担降到最低（每2天5-10分钟），同时消除反馈污染风险。
