# 📐 项目·工程·产品 · 用户操作指南 v1.0

> **你是写代码的人，还是管进度的人，还是决定做什么的人？——这三种身份的逻辑，完全不一样。**
>
> 写给：在科技/AI 领域做事的人，想搞清楚自己到底在干什么、下一步该往哪走。

---

## 一、三句话讲清本质

| 概念 | 一句话 | 核心问题 | 成功的标准 |
|------|--------|---------|-----------|
| **项目** | 在固定时间内把一件事**做完** | 还剩多少天？预算够不够？ | 按时、按预算、按范围交付 |
| **工程** | 把一件事**做对**，让它能扛住时间和规模 | 这代码三年后还能改吗？十万用户会崩吗？ | 可靠、可维护、可扩展 |
| **产品** | 把一件事**做对路**，让人愿意用、愿意付钱 | 用户真的需要这个吗？他们为什么选别人？ | 用户留存、口碑、商业回报 |

> 💡 一个比喻就懂：
> - **项目** = 装修队——"三个月内把这套房子装好，预算 20 万"
> - **工程** = 建筑师——"这栋楼要能扛 8 级地震，管线 30 年不坏"
> - **产品** = 开发商——"这片区域需要什么样的房子？谁会来买？卖多少钱？"

三者缺一不可。只有产品没有工程 = 好看的毛坯房。只有工程没有项目 = 永远在打磨但永远没交付。只有项目没有产品 = 准时交了一堆没人要的东西。

## 二、你在哪条线上？——快速自测

```
选一个最像你的：

□ 我每天最关心：Deadline、排期、阻塞项、谁在等谁
  → 你是项目思维型

□ 我每天最关心：架构、代码质量、技术债、性能、测试覆盖率
  → 你是工程思维型

□ 我每天最关心：用户反馈、竞品动态、需求优先级、数据指标
  → 你是产品思维型
```

**如果你三种都在操心**——你不是超人，你是小团队创业者或独立开发者。这种情况下，你需要**有意识地切换模式**，而不是混在一起。混在一起的结果：需求讨论会变成技术争论，技术决策被截止日期绑架，截止日期被"再加一个功能"无限推迟。

## 三、AI 时代的特殊碰撞

在传统软件开发中，这三个角色由不同的人担任：项目经理、工程师、产品经理。但在 AI 时代，边界正在模糊：

### 🟡 冲突 1：AI 项目的"不确定性问题"

```
传统项目：
  需求 → 设计 → 开发 → 测试 → 上线
  每一步都可预估

AI 项目：
  想法 → 数据准备 → 训练 → 评估 → 发现效果不够好
      ↑________________________________________↓
           回到数据准备，重新来（可能要绕好几圈）
```

**怎么办**：AI 项目不能用传统的"固定范围 + 固定时间"的项目管理。需要用**探索性里程碑**代替"完成XX功能"——

| 不要这样定 | 改成这样 |
|-----------|---------|
| "3月底完成推荐模型" | "3月底达到 AUC 0.85 或明确知道上限在哪" |
| "本周完成XX模块" | "本周跑通 3 种方案并选出最佳" |

### 🟡 冲突 2：工程思维遇上"概率性系统"

传统工程追求确定性——输入 A 必须输出 B。AI 系统是概率性的——输入 A **大概**输出 B，但有时输出 C。

```python
# 传统工程思维：断言确定性
assert add(1, 2) == 3  # 永远成立

# AI 工程思维：管理概率
result = model.predict(input)
assert accuracy > 0.95   # 只能保证统计上的正确率
```

**这给工程带来的挑战**：
- 怎么为概率性系统写测试？
- 怎么做 CI/CD（持续集成/部署）？模型"变坏"不像代码 bug 那样明显
- 怎么监控？传统的"服务是否在线"不够，还需要"模型输出质量是否在下降"

### 🟡 冲突 3：产品思维里的"新技术陷阱"

AI 领域有一个常见的病：**因为技术很酷所以要做**。产品思维要不断问：

| 产品思维该问的 | AI 工程师常说的 |
|-------------|---------------|
| "用户的问题是什么？" | "这个模型 SOTA 了！" |
| "不用 AI 能不能解决？" | "我们能不能用大模型？" |
| "精度提升 2% 用户感知得到吗？" | "我加了个新层精度提升了 2%！" |

## 五、你此刻该干什么——决策指南

### 如果你是个人开发者

```
你在什么阶段？

刚有想法，还没验证 → 产品思维先行
  ├── 写下：谁有这个问题？多少人？现在他们怎么解决的？
  ├── 做一个最简陋的版本（一天内能做完的那种）
  └── 给 5 个人用，听他们骂

有了初步验证，开始认真做 → 工程思维介入
  ├── 别急着重构！先确定这个方向是对的
  ├── 技术债可以欠，但要记账（写 TODO/FIXME）
  └── 关键路径（核心功能）上不能有技术债

产品有用户了，事情变多了 → 项目思维补上
  ├── 列清单：什么事必须在什么时候做完
  ├── 学会说"不"：不是每个功能请求都要做
  └── 留出"打磨时间"：工程不会自我修复
```

### 如果你是团队负责人

| 团队问题 | 大概率是哪种思维缺位 | 怎么办 |
|---------|-------------------|--------|
| 总是延期 | 项目思维弱 | 引入更小的迭代周期、站会、阻塞项可视化 |
| Bug 不断、改不动 | 工程思维弱 | 引入 code review、测试要求、技术债清理 Sprint |
| 做了很多但没人用 | 产品思维弱 | 强制每个需求关联用户反馈、引入用户访谈、看数据 |
| 争论不休、方向摇摆 | 三种都在但没对齐 | 明确决策权归属——产品决策归产品，技术决策归工程，排期归项目 |

### 如果你在选职业方向

```
你喜欢什么？

喜欢"把东西做完、打勾"的满足感 → 项目经理/技术主管
喜欢"把东西做完美、追求优雅"的满足感 → 工程师/架构师
喜欢"发现别人都没发现的需求"的满足感 → 产品经理/创业者

⚠️ 这三种满足感来自完全不同的源头。
不要因为"这个岗位工资高"选错——你会在一个你不喜欢的满足感里耗尽自己。
```

## 六、AI 领域的产品生命周期——和传统软件不一样

```
传统软件：
  立项 → 开发 → 发布 → 维护 → 下线
  （线性，可预测）

AI 产品：
  探索 → 做出来 → 发布 → 监控数据漂移 → 持续迭代或推倒重来
    ↑________________________________________↓
        发现效果不好/数据变了/出现新技术
```

**AI 产品的"产品死亡谷"**：很多 AI 产品死在从"探索"到"做出来"之间。模型在实验室效果好，上线就崩。不是因为工程不行，而是因为**产品假设在真实数据面前不成立**。

这个阶段的正确做法不是"加强工程"（加测试、加监控），而是**回到产品思维**——重新理解用户场景、数据分布、失败模式。

## 七、快速参考：当你说"我要做项目"时，你到底在说什么

| 你说的 | 你其实需要的 | 核心工具/方法 |
|--------|------------|-------------|
| "我要管好这个项目" | 项目管理 | 甘特图、看板、Scrum、里程碑、每日站会 |
| "我要把这个产品做好" | 产品管理 | 用户访谈、竞品分析、PRD、路线图、A/B 测试 |
| "我要把这个系统做扎实" | 工程管理 | 架构评审、code review、CI/CD、测试策略、技术债管理 |
| "我要带一个AI团队" | 三者都要 | 探索性里程碑 + 工程最佳实践 + 用户验证闭环 |

## 八、你可能会问的

**Q：小团队（<5人），还需要分这么清楚吗？**

A：不需要设三个岗位，但**思维要分清楚**。一个人可以半小时用产品思维选需求，半小时用工程思维写代码，十分钟用项目思维更新看板。关键是**不要在讨论需求时争论技术方案，不要在写代码时纠结需求优先级**。串行切换，不要并行混淆。

**Q：我最缺哪一种思维？**

A：问自己三个问题——
1. 有没有东西因为"没时间"而永远没做完？→ 缺项目思维
2. 有没有东西因为"写得太烂"而不敢改？→ 缺工程思维
3. 有没有东西做完了但没人用？→ 缺产品思维

**Q：AI 让这三种思维过时了吗？**

A：没有，但权重变了。AI 写代码越来越强（替代部分工程执行），但"判断什么值得做"（产品思维）和"怎么把一堆 AI 产出整合成可交付的东西"（项目思维）变得更加重要。**AI 放大了工程效率，但也放大了方向错误和协调失败的成本。**

**Q：项目经理、产品经理、技术负责人——谁说了算？**

A：看阶段。探索期产品说了算（做什么）。建设期工程说了算（怎么做）。交付期项目说了算（什么时候交）。**但最终用户说了算**——如果用户不买账，之前谁说了算都没用。

## 九、一句话总结

**项目管时间，工程管质量，产品管方向。**

三者缺一个，你就是在用另外两个弥补它的缺失——用加班补项目管理不善，用重构补工程欠债，用加班补产品方向错误。但这些弥补只是把问题藏起来，不是解决。

认清你现在最缺哪一个，比多学一个框架、多追一个热点重要十倍。
