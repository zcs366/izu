我把研究、写作、排版、发布塞进同一个对话框：知墨，给作者的 AI 原生写作 IDE

200 美元订一个月 Claude Max 20x[1]，Anthropic 那一档最贵的。两周，配额几乎被我打光。

配额打光这件事其实就是 vibe coding。我两周一直在用 Claude Code[2] 临门一脚地写一个写作工具，叫知墨。几个月的迭代到这两周临门一脚，把整套 Agent + Trace + Skills + 双平台发布跑通。Agent 和我每天反复对话几百次，配额自然在飞。说白了，上周三我刚发的那篇答案讲的是 vibe coding 翻车的坑，里面那些鬼打墙、token 浪费、上下文丢失，我们写知墨这几个月撞过一大半。

去年 12 月我才认真开始在知乎和公众号写起来。几个月下来攒了一堆痛点。Typora[3] 加公众号编辑器、Notion[4] 加知乎、Obsidian[5] 加自己写的 publish 脚本、ChatGPT[6] 写完直接粘出来，几种搭配我都试过。每个组合都有局部最优，全局都不舒服。

这一篇讲清楚知墨干了什么，没干什么。一句话先放在这里：它不是又一个"输入题目一键成文"的 AI 写作产品。它甚至刻意不做这件事。

一、5 个 Tab 的常态

上周三晚上九点，我开始写一篇关于 vibe coding 翻车的知乎答案，要把 METR 那份实测研究[7]、arXiv 那篇 Lost in the Middle[8]、GitClear 的代码质量报告[9]、Stack Overflow 2025 开发者调查几份资料串起来论证一个判断。打开浏览器，数了一下当前的 Tab。

第一个，知乎答案编辑器，里面是上周写到一半的草稿。第二个，公众号后台，等着把这篇改成公众号文章。第三个，ChatGPT[6]，让它帮我整理几份研究里的数据点。第四个，Notion[4]，里面是我自己之前积累的 AI 编程相关素材。第五个，arXiv[10]，刚打开了 Lost in the Middle 那篇论文。

写完那篇答案花了三个半小时。其中一个半小时不在写，在做这几件：把 ChatGPT 整理出来的研究数据挨个回到原文核对，怕引用偏差；几张 Mermaid[11] 流程图反复调，知乎渲染一套、公众号要做图导出又是一套；同一篇发到公众号时整篇排版重做一遍，公众号不支持知乎那套样式；翻几天前 ChatGPT 给我的一条引用，聊天历史翻了十分钟。

写作总时长 3.5 小时，其中"非创作环节"占 1.5 小时。这个比例大概率不是我一个人的事。

更细的分布：研究数据交叉核对花了大约 35 分钟（要确保 METR 的 19% 数字、Stack Overflow 调查的样本量、GitClear 报告引用的"代码变更率"这些数据点和原文一致）。Mermaid 图表导出公众号格式花了大约 15 分钟（公众号知乎都不支持 mermaid 嵌入，要先在编辑器里渲染成图再导出 PNG）。公众号样式重排花了大约 25 分钟（外加翻聊天历史找老引用 10 分钟）。剩下的 15 分钟在测试图片上传是否能正常通过公众号素材库审核。

这就是一个"在 5 Tab 之间反复横跳"的状态。每个工具都没问题，每个步骤都不复杂，但复杂藏在切换的缝里。你切到 ChatGPT 找数据，回到编辑器粘进去，又切到公众号后台核对样式，又切回 arXiv 原文核对引用。三个半小时下来，写作那 2 小时其实只是 5 个工具操作的胶水。

说白了，写作工具今天还停留在"编辑器加一个 AI 侧边栏"的形态。AI 在写作里能做的事早就超出了"侧边栏式辅助补全"。它能搜资料、能整理引用、能学风格、能改排版。但工具结构没跟上，AI 永远是个插件，永远在"切应用"的边界上摩擦。

我后来想清楚一件事，写在这里作为知墨整个设计的源头。

AI 在写作场景里，应该是"辅助写作"的第一公民，不是"写作"的第一公民。写作本身的第一公民永远是作者。观点、判断、立场、节奏感，AI 替不了。但"辅助写作"这件事（搜资料、整理引用、学风格、转排版、跨平台发布、文笔打磨建议），AI 应该坐头等舱，不是被塞进侧边栏当乘务员。

这两个第一公民的位置混淆了，产品就做错了。

二、AI 不替你写：那条线我画出来过两次

知墨开发名叫 markdown-publisher。这个名字暴露了最初的样子。没有 Agent，没有 Trace，没有 Skills，目标特别纯粹：把一篇写好的 markdown 草稿，快速发到知乎和公众号。仅此而已。

第一版就解决这一件事，因为这是当时最痛的一刀。后面几个月里，刀一边磨一边深。磨着磨着发现，光把发布解决干净，问题只少了三分之一。研究和写作的脱节是更上游的痛，AI 给的调研结果粘进编辑器后引用要重新整理是中段的痛。Research、Agent、Skills、Trace 一层层长出来。

但在 Agent 这一刀上，我走过两次路。

第一次是想让 AI 自动写文章。4 段式固定流水线：提纲、写、检查、排版。每一步一张卡片，作者点"下一步"推进。这个版本活了一周，我主动砍了。

技术没问题。LLM 能写、能改、能套模板，那个版本甚至跑通过两篇能直接发的答案。问题在产品哲学。AI 替你写出来那篇，永远缺一个东西，你自己的判断。

几个具体场景。AI 生成的"观点"是它训练语料的平均值，跟你的看法没关系。AI 的"事实陈述"永远要回头核对，省下的时间又还了回去。AI 写的最后一段永远像在凑字数，跟你这个人的论点拐弯方式无关。写到一半你想说"刚才那段用更冷静的语气重写"，4 段式流水线根本没接口让你提。

这里面最折磨人的是"AI 的事实陈述要回头核对"那一条。说白了，LLM 的幻觉率今天已经压到能用的程度，但对作者写文章的容错率来说还是高一个数量级。AI 引用错一条 arXiv 论文[10]、记错一个时间节点、误用一个术语，整段就废。你检查每一句引用、每一个数字的时间，等于自己重读一遍源资料。"AI 替你省下的写作时间"在核对环节又拿走了。从结果上看，AI 自动写文章对作者的真实收益逼近零。

另一个糟糕的事情藏在改文章这件事里。我每次写完一段 AI 生成的草稿，下意识想改它，因为"不像我说话"。改的过程比从头写还累。你要先看懂 AI 的逻辑链，再判断哪里要拆、哪里要并、哪里换词，等于在做翻译。纯写比"改 AI 输出"快得多，这一点直到亲身试过才会信。

最离谱的是，AI 给的草稿越长，作者越不敢动它，因为"反正写得也不差，改不动就发吧"。结果发出去的内容不再像你。读者评论里第一时间提到的，几乎都是"这跟你之前写的不像"。"写得好不好"反倒成了次要问题。社区作者的信用是慢慢攒的，攒了一年的语感，AI 一篇全清空。

用了一周我就明白，AI 自动写文章对重度作者是反向价值。它把"创作"换成了"润色 AI 输出"。这两件事根本不是一个工种。重度作者不愿意接受第二种工作。

我说的"重度作者"是这一类人。一周写几篇深度长文，单篇 3000 字以上，跨平台双发（知乎加公众号、或者再加 newsletter / 掘金），每篇都伴随大量调研。这是知乎专栏作者、公众号原创号、技术博客作者共同的特征。这群人对工具的需求和"偶尔记点东西"的轻度用户完全不同。轻度用户喜欢 AI 一键生成，因为他们写的内容本身就不要求强个人色彩。重度作者反过来，最不能丢的就是个人色彩，因为那是他们的招牌。AI 替这种作者写文章就是在拆招牌。市面上的写作工具，无论是 Notion AI、Jasper 还是国内一堆公众号外挂，绝大多数瞄准的是轻度用户的"快"，没有瞄准重度作者的"准"。知墨想填的就是这块空白。

砍掉之后，知墨 Agent 的能力被严格收回到几件事：

调研：主动搜资料、抓引用、整理时间线，把网上散乱的信息变成你能直接读懂的笔记
素材库：把研究结果存进项目，按你的标注体系组织，未来反复引用
文笔打磨：你写完一段，Agent 给修改建议（"这句太长"、"这个连接词重了"、"这一段开头是 AI 味"），留哪句是你的事
发布：知乎和公众号的双平台排版+发布，一气呵成

写文章本身，作者自己来。




注意第三条的边界。给建议，不是替你写。这是知墨愿意停的地方。AI 替你生成段落，作者就被替换了。AI 给建议加作者拍板，作者还在驾驶座。

做这个产品过程里我还砍过几个看起来好、实际站不住的功能。AI 自动配图试过一次，问题在于配图是创作语义的一部分，AI 选的图总差一口气，改成 Agent 给关键词、作者自己来。CRDT 多人协作做过一周，发现单人写作是绝大多数场景，多人引入的冲突解决加权限管理加网络层根本扛不住，砍。移动端最多看草稿，做不到深度创作，明确不做。每砍一项，知墨的定位就清晰一寸。

砍掉"AI 自动写文章"这一刀，是知墨从"AI 写作工具"变成"辅助调研工具加素材资料库加文笔伴侣"的分水岭。下面 §三到 §六，全是围绕这条线展开的。

三、调研侧：Deep Research，可见的研究过程

Agent 的第一个失败模式特别老套。看到题目直接搜，搜出来要么宽泛要么学术，离作者要的差很远。







S05：用户消息"把这篇文章补完" + Agent 第一回应"收到。这篇要把 attention 的 O(n²) 复杂度讲清楚..."。截图位置：autoplay 跑完 pushUserMessage + 第一次 pushAgentText 之后、proposePlan 之前。作用：证明 Agent 不是看到题目立刻搜，而是先把它对题目的理解说给作者听。

知墨做了一张 Research Plan 卡片。Agent 收到题目后先输出它打算搜什么，是一个 query 列表，每条 query 一个子问题。这张卡片可编辑。用户可以删掉不相关的、改写不准确的、补 Agent 没想到的。改完点"开始研究"，Agent 才真的去搜。







为什么这一步那么值？用户改一次 plan，能省 Agent 后续 5 次无效检索。这是一个看起来多此一举、实际收益很大的设计。

从用户视角，这是一个可以打断的研究助理，不是黑盒。

Perplexity[12] 我用过半年，最大的不适感就在这里。它的"deep research 模式"看起来很自动，但你只能等。等到它给你一份长报告，想改方向只能从头来。Cursor 的 deep research 同理，它替你下决心搜什么，决定之前不跟你商量。这种交互对工程师可能 OK，对作者很伤。作者真正要的是这种感觉：AI 先把想搜的方向列出来给我过一眼，再去搜。AI 直接把答案撞过来的那种模式，我用几次就放弃了。这个差异决定了 Research Plan 卡片这一步必须存在。

多源并行不复杂但感知很强。5 条 query 串行 40 秒，并行压到 10 秒。回填阶段做了三件：按 URL 和标题做模糊去重，多源经常返回同一篇内容；引用按出现顺序编号，不是按搜索时间；每条保留原始 URL，让作者最后人工核对。

Plan 卡片这一步在工程上看起来就是"多一次往返"，对体感的差别其实更深。作者改 query 这个动作，本质是把判断权前置。原本 Agent 跑完搜索你才发现搜偏了，要么忍着用要么从头来。Plan 阶段你已经在看"它想搜什么"，这一眼能拦住 80% 的偏方向。我跑过几次实验，把 Plan 阶段去掉，让 Agent 直接搜，结果 5 次里有 2 次的报告基本不能用，得手动调 query 重跑一遍。Plan 卡片上线之后，重跑率压到 5 次里不到 1 次。

UI 设计还有一个小细节值得讲。Plan 卡片支持就地编辑，每条 query 一个 textarea，点旁边的按钮可以删除或新增。改完不需要"保存草稿"，直接点"开始研究"。这种"轻交互"对作者来说成本极低。如果改 Plan 这一步要走"打开对话框 → 编辑 → 保存 → 关闭"四步，作者大概率懒得改，直接让 Agent 跑。产品体验就回到了 Perplexity 那种"我等你给我答案"的形态。

最关键的设计在衔接处。研究结果不是塞进一个独立的"研究面板"或者 RAG 黑盒。它作为一条条消息追加回 Agent 的对话上下文。后续 Agent 整理调研报告时，是真的"看到了"引用全文。报告里引用的位置、用法、转述都比较自然。你之后基于这份调研自己写文章时，引用是结构化的、可追溯的、容易复用的。

引用回填还有一个细节值得讲，因为很多产品在这一步偷懒。同一篇论文常常被几个不同的中转站转载，搜索结果里 URL 各不相同，但内容指向同一个原始 PDF。如果不做归一化，Agent 整理的报告里可能出现"引用 [3] 和 [7] 实际是同一篇"的尴尬。知墨的做法是按论文 DOI 或博客标题做模糊匹配，把同一来源合并成一个 citation。引用链最终保留最权威的那个 URL（论文优先指向 arXiv 或出版商页，博客优先指向作者原站）。这种工作在产品演示里看不出来，但作者发出去文章被人指出"引用重复"时，价值就显现了。






















这一节标题里写的是"研究员"。不是写手。

四、素材库：项目化 + Skills + MCP

Agent 调研完，结果放哪儿？散落在聊天历史里没法用。

每个项目根目录下有一个 .zhimo/ 文件夹。里面装：草稿、会话记录、发布状态（.publish.yaml，下一节展开）、项目级 Skills、MCP 配置。

项目化的真实意义在这里：一个连载等于一个目录等于一套大脑。我在写"拆解 Claude Code"那个连载（六篇起步）时，给那个项目专门挂了一个 style.md skill，里面写了我希望那个系列的语气，稍微学术、多用类比、不要太口语。这个 skill 只在那个项目里生效，下一个题目就换一套。

Skills 这套形态我从 Claude Code 偷的[13]。之前在我那篇 Claude Code Skills 架构拆解里写过细节，这里只讲适配。物理形态：Markdown 加 YAML frontmatter 的文件夹。三层挂载，优先级从高到低：项目级（.zhimo/skills/）、用户级（~/.zhimo/skills/）、内置。Capability Drawer 里三个按钮：从 git 安装、从 zip 安装、从本地目录安装。git 那个我用得最多，给一个仓库地址，知墨拉下来挂上。

MCP[14] 是 Agent 的硬能力。Skills 是 Agent 的软指令。两者一起才把扩展性铺开。

知墨支持完整 MCP 协议，stdio / SSE / HTTP 三种 transport 都能跑。用途举例：接一个本地数据库的 MCP server，Agent 就能在写文章时查你的数据库；接一个 GitHub MCP server，Agent 能从你的 issue 和 PR 里抓素材；接一个企业内部知识库的 MCP server，Agent 能引用内部资料。mcp.json 改完保存，连接自动重建。

下面这段是给极客读者的硬糖，其他读者可以跳。

现实问题：一个 MCP server 暴露 10 到 30 个工具，用户挂 5 个 server 就是 150+ 工具 schema。全塞 system prompt[15] 里，每次对话开头烧掉一大块 token，还没开始干活，订阅配额就在飞。

知墨做了一个 ToolSearch 元工具。默认情况下 system prompt 里只暴露这一个工具。Agent 觉得"我可能需要某种能力"时，先调 ToolSearch 关键词检索，找到候选工具列表，再决定加载哪个工具的完整 schema。




收益是一个数量级：单次对话的工具描述上下文从两万多 token 降到几千。对单个作者不显眼，对一个长期跑的 Agent 产品意味着订阅配额能撑更多次对话。这个优化让我那两周冲刺的 Claude Max 20x 配额没有更早爆。

MCP 这套生态里还有不少踩坑值得分享。stdio transport 在长跑场景下有一个典型问题：子进程偶尔会僵死，stdout 不再返回数据，但 OS 层进程还活着。Agent 在那里等着回包，整个流程被卡住。知墨的解决方法是给每个 MCP 调用加超时，超时后强制重启子进程，重新建立 stdio 通道。SSE transport 的问题主要是网络抖动断连，知墨用了一套指数退避加上限的重连策略，断了之后从 5 秒、10 秒、20 秒往上重试，到 60 秒还连不上就直接 fallback 到错误状态告诉用户。HTTP transport 最稳，但它没有 stateful 能力，每次调用都要带完整上下文，token 消耗最高。

Skills 三层挂载在实际使用里还有一个特别有意思的场景。我自己机器上 ~/.zhimo/skills/ 装了一个"article-fact-checker"。这个 skill 写完文章自动扫一遍，把每一条断言和我之前写过的文章对照，看有没有自相矛盾的地方。它的工作前提是"知道我之前写过什么"，所以挂在用户级，对所有项目生效。但项目级 skill 完全是另一种语境。比如"拆解 Claude Code"那个连载，project skill 就是"保持这个连载已经定下来的术语统一性"。所有提到 prompt 缓存的地方都用同一个名词，所有提到 context window 的地方都按同一种方式描述。这两类需求在不同层挂载，互不污染，是设计 Skills 三层时刻意保留的灵活度。

五、发布侧：Publish Card 一气呵成

第一版的发布流程是这样：内部有一个 DAG（有向无环图）[16]引擎，把"渲染公众号 HTML"、"上传图片到素材库"、"调用公众号草稿 API"这些拆成 15 个节点。我把 15 个节点全部暴露给用户，每个节点一张卡片，右键能重跑。

我当时觉得这是 power user 设计。两周后发现是灾难。

具体场景：流程走到第 7 步弹窗问"封面图选哪一张"，作者切回去找图，思路被打断。某一步红了，作者不知道是该重跑这一步还是回退两步重输。公众号 token 在一个面板，知乎 cookie 在另一个，图片 CDN 又是一个，Mermaid[11] 主题还是一个，没人记得住。

用了两周明白一件事：作者只想点一下"发布"，剩下的让工具搞定。

新版只有一张 Publish Card，五段式。前置条件检查（平台 token、文章合法性、必填字段）。平台选择（公众号、知乎，可一次发两个）。预检表单（所有需要的输入一次收齐：封面、摘要、Mermaid 主题、Excalidraw[17] 渲染选项、知乎专栏选择）。进度时间线（语义事件，不是节点名）。错误恢复区（失败时只展开相关步骤，提供重试 / 修改输入 / 跳过三个选项）。







老版的"DAG 全节点视图"作为高级模式保留，折叠在卡片底部 Debug Panel，懂的人能展开，新用户看不见。

为什么是两套渲染器而不是一套通用 HTML。这件事我前期想偷懒，撞了三次。公众号过滤大量 CSS，不支持 class 选择器，只支持 inline style，图片必须走素材库否则外链失效。知乎要求 KaTeX 公式转图片且 alt 文本要兼顾纯文本，引用语法是它自己的一套，代码块高亮也是它自己的一套。通用渲染器只能取交集，两边样式都很丑。知墨用两套独立渲染器（shared/converters/wechat-* 和 shared/converters/zhihu-*），代码量翻倍，效果差很多。宁可多代码，不要丢效果。

.publish.yaml 是我特别得意的一个小设计。每篇文章旁边放一个同名 yaml 文件，记发布元数据：上次发到哪些平台、平台返回的 ID、上次发布时间、用户填过的预检表单。断电恢复、二次发布预填表单、未来跨设备同步全靠它。这个设计让一个看似复杂的功能变得几乎不用做：你已经在用 iCloud[18] 或 Dropbox[19] 同步文件了，知墨只需要诚实地把状态放到文件里。

一个真实的 .publish.yaml 长这样：

# 发布配置
# 对应文件: 大型项目开发vibecoding痛点.md

# ─── 知乎 ───
zhihu-type: answer
zhihu-title: 大型项目开发vibecoding痛点
zhihu-toc: true
zhihu-question: "https://www.zhihu.com/question/2001613944238924246"

# 以下字段由发布流程自动维护
zhihu-link: 
zhihu-created-at: 
zhihu-updated-at: 

注释把"哪些字段是用户写的、哪些是发布流程自动写"标得清清楚楚。用户改完点发布，自动维护的字段会被知墨填回去。下次再发同一篇，知墨先读这个 yaml，知道"上次发到了哪里、用了什么参数"，预检表单一次性预填好。整个流程对用户不可见，但状态以人类可读的形式持久化在文件系统里。作者拥有自己的文件，这是知墨的核心承诺。不做云、不做账户体系、不做服务端存储。你拷走 .zhimo/ 目录到另一台机器，所有发布历史无缝继续。







错误分层的真实例子。可重试：图片上传到公众号素材库网络超时，直接点重试。需要调整：公众号摘要超过 120 字，高亮位置加字数加修改入口。致命：WeChat appsecret 错误，跳设置页加引导重新授权。老版把这三种错误用同一种红色弹窗呈现，作者看到红色就紧张。新版按紧迫度分层显示，绝大多数错误其实是"可重试"，作者扫一眼就处理掉。

实际跑了几个月还碰到一些细分场景。比如知乎风控偶尔 ban 当前 cookie，原因可能只是触发频率高了一点。知墨这边的处理是检测到 401 之后弹一个"会话已过期"的二维码登录卡，作者扫一下重新拿 cookie，整个流程不退回前置。公众号那边更怪：偶尔上传图片成功但素材库列表里查不到，原因是它的 CDN 同步有几十秒延迟。知墨遇到这种情况会做"乐观提交"，假设图片已经上传成功，先用临时 URL 渲染预览，等真正同步成功之后再替换为正式 URL。这些都是发布几十次之后才被磨出来的边角细节。

公众号一次只能发一篇但你可以排队预发布若干篇。知墨支持把多个 .publish.yaml 一次性提交，按顺序依次走 Publish Card 流程，中间任一篇出问题不影响其他。这个能力对连载作者特别有用。

技术料一句话。DAG 引擎在 Electron[20] 主进程，进度通过 IPC 事件流回渲染层。节点定义来自插件，公众号插件贡献 5 个节点，知乎插件贡献 4 个节点。将来加掘金或 Medium[21]，只是再写一个插件，不动核心。

六、可观测侧：自己评估自己才是及格线

做 Agent 产品的人都知道一件事。最大的不可控藏在那个怨念里：上次还好好的，今天怎么就变蠢了。

LLM 对 prompt 极其敏感，对模型版本极其敏感，对工具描述极其敏感。改一行 system prompt 可能让 5 个用户场景从能用变成不能用，你完全不知道。

代码工具这两年靠 lint[22]、test[23]、code review 兜底。AI 写错代码很快暴露。写作工具没这个机制。一篇 5000 字答案发出去，错的事实就是错的，错的判断就是错的，是你的署名。所以 AI 在写作场景里必须自带观测，把"凭什么这次这样写"暴露出来。

我决定把这一套自带进知墨，不接 Langfuse[24] 或者 Datadog[25]。三个理由。隐私（草稿、研究、引用是创作素材，上云不合适）。离线（写作环境经常没网）。包内集成（作者反馈"发布有点慢"，我能直接进 Trace Inspector 复盘，不用要 trace ID）。

代价是等同于做了一个独立产品的工程量。回头看值得。

OpenTelemetry GenAI semantic conventions[26] 是基础。知墨严格按它打 span，四种类型：workflow、agent、chat、tool。存储分两层，SQLite[27] 存元数据和 span 树，内容寻址 blob 存大型消息体（避免 SQLite 膨胀）。默认常开，30 天 / 2000 session / 2 GB 自动清理。Trace Inspector 是一个独立的 BrowserWindow，跟主编辑器分进程，互不影响。







四件套分别说一下。

OTel span 树本身就是 debug 利器。每条 LLM 请求、每次工具调用、每个 sub-agent 子流程都是一个 span。timeline 可视化打开，你能看到 Agent 这一次跑了 47 秒，哪一秒在等 LLM 返回，哪一秒在等本地工具，哪一秒在等 MCP 子进程。慢在哪一目了然。OpenTelemetry 这套 schema 是工程界的事实标准，Anthropic 自家 SDK[28] 也在往这个方向靠。我没另起炉灶。

标注队列是产品迭代的数据引擎。任意 trace 上：👍 / 👎 / 📝（备注）。被标注的 trace 进入 golden set，可以当回归测试的输入样本，可以当 LLM judge[29] 的"已知好 / 坏"参考，可以反过来训练新 skill。一个 Agent 产品如果用户的反馈只是星级评分，没法形成闭环。标注队列让每一次 👍 / 👎 都进数据库，反过来驱动迭代。

我自己用 golden set 的频率比想象高得多。每次准备改一个 prompt 之前，我都会先去标注队列里挑出 10 到 20 个相关 case 作为基线。这一步不到 5 分钟，但能保证"改动后的版本至少不比旧版在已知 case 上变差"。没有这一步，prompt 改动就是赌博。

更好玩的用法是反向找 prompt 问题。比如 Agent 最近一段时间在某类调研任务上表现下滑，我打开标注队列按时间倒序拉，看最近 20 条 👎 的备注是不是有共性。如果发现"5 条都在抱怨它没去看引用原文"，那就直接定位到 Agent 的 system prompt 里"请优先访问原文"那一段被改弱了。这其实是前两天我刚修过的一个改动。这种"用标注 + 备注定位 prompt 退化"的工作流，是知墨 dogfooding 出来最有用的副产物。

Fork & Replay 是调 Agent 的瑞士军刀。任一 span 上点"Fork from here"，知墨创建一个 fake provider，加载这次会话所有 LLM 响应作为录像。重放整次对话。fork 点之前用录像（确定性），之后照常请求 LLM。两个高频工作流靠它。"我改了 system prompt，从这一步开始效果会变好吗"，直接 fork 验证，前 N 步用录像保证起点完全一致。"Agent 在第 5 步选错了工具"，fork 到第 5 步前，看 prompt 是不是有问题，改了再 fork 一次，A/B 对比。AI 时代调试需要"快照重放"，因为每一次跑都不一样。

回归加 A/B Compare 解决"这次改动到底变好还是变坏"。golden set（来自标注队列）跑两次版本，三种 scorer 自动评分。exact_match 字面对比，适合工具调用结果。diff_distance (Levenshtein 编辑距离[30])，适合"格式相近但内容微调"。llm_judge 丢给独立的"裁判 LLM"做 pairwise 偏好打分。

LLM judge 这个 scorer 踩过三个坑值得记一下。位置偏见：裁判偏好第二个出现的答案，解法是双向对比（A vs B 跑一次，B vs A 跑一次，取平均）。风格偏见：裁判偏好更长、更"丰富"的答案，解法是判官 prompt 里明确"长度不是质量"。自评同源：裁判模型和被评模型同家会有家族偏好，解法是故意用不同家的模型当裁判，GPT 评 Claude，Claude[31] 评 GPT[32]。

知墨的 judge prompt 模板大致长这样（这里抽掉了占位符）：

你是一位严格的写作质量评审。请比较以下两份调研报告（pairwise）。

【背景】调研主题：{topic}
【报告 A】{output_a}
【报告 B】{output_b}

评审维度（每项独立打分，1-5）：
1. 事实准确性（错误的事实直接扣到 1）
2. 引用密度与可信度
3. 结构清晰度
4. 是否避免"模板化模糊表达"

注意事项：
- 长度不是质量。冗长的答案如果信息密度低，请打低分。
- 你不知道 A 和 B 哪个是新版、哪个是旧版，请按内容打分。
- 如果两份大致相当，请打"tie"。

这段 prompt 的设计有几个细节。把评审维度拆开打分，比"整体哪个好"更稳定，因为 LLM 整体感更容易被 surface feature 带跑。"长度不是质量"这一句是直接对抗 LLM 的偏好。最后的"你不知道 A 和 B 哪个是新版"是防止 LLM 用"求稳"心态投老版的票。

这种 prompt 在第一版里写了三轮才稳定。每轮都让我意识到一件事：人类写测试用例，LLM 也会"知道考点"在哪里。prompt 里随便露一点点偏向，结果就被带歪。判官 prompt 的写法本身就是一门工程。

Fork & Replay 有一个我个人最爱的工作流。调 prompt 的时候我会同时开三个 fork，分支 A 改 system prompt 的第一段，分支 B 改第二段，分支 C 改 tool description 的某一行。三个 fork 跑完进 Compare 视图，一次性看哪一支胜出。这种"我开几条修改路径同时验证"在传统软件里叫 A/B test，AI 时代因为响应不确定性更高，这种并行验证的价值更大。没有 Fork & Replay，调 prompt 就是猜，调一次跑一次，等半小时。有了之后，半小时能跑完 3 条假设，效率差不止 3 倍。

Compare 视图最后呈现：summary card 显示总胜负，逐条点开看 diff drawer。这一节标题写了一个判断：自己评估自己才是 Agent 产品的及格线。我不奢望所有作者会去用这个面板。我自己每周用三次以上，每次都能据此改进 prompt 或修 skill bug。少了这套面板，迭代就是玄学。

有一个观察值得记下来。Agent 可观测性在大型 SaaS 里是 SRE 工具，在 dogfooding 驱动的产品里其实是产品功能。SRE 视角下，Langfuse / Datadog 那类 SaaS 是工程师配置好让业务用户隐性使用的；产品功能视角下，知墨这一套是给重度作者直接看见的。同样的 Trace 数据，呈现形式是"作者能用来诊断 Agent 行为"的 UI，而非"运维盯指标"的 dashboard。这种身份的转换让"可观测"从"后台运维"变成"产品能力"。我们做知墨第二个月才意识到这一点，反过来把 Trace Inspector 当作面向用户的功能来设计。这是 dogfooding 驱动型产品的一个稀有红利。

七、价值升维：AI 应该停在哪里

代码工具圈这两年的故事，从 Copilot[33] 升级到 Cursor 起来，再到 Devin[34] 和 Manus[35] 各种尝试，最后落到的共识是 AI Pair，不是 AI Replace。工程师在驾驶座，AI 在副驾。

写作工具圈反着。各家 AI 写作产品的演示长得清一色："输入题目，一键成文"。看多了人会下意识把所有 AI 写作工具默认成这种形态。

具体举几个例子。Notion AI[36] 的 "continue writing" / "draft an article" 路线，整篇代写，作者最后变成 reviewer。Jasper[37]、Copy.ai[38] 这类专业写作 SaaS 更激进，输入标题加几个关键词，一篇文章就吐出来。国内公众号外挂里的"AI 一键写文"工具也是这条路。演示视频都很好看。用过几次的作者都明白一件事，AI 写出来的那一篇，你最多 review 一下，真正认领的瞬间没法发生。写作的精髓不光是产生文字，是从一个角度切进一个问题、一点一点把判断打出来的过程。那个过程被 AI 跳过，文章就只是"看起来像你写的字串"。

我做 iOS 也快十年，这两年看着代码工具的边界一点点磨清楚。该 AI 做的事（boilerplate、跨语言搜索、refactor 候选）越来越好用。该工程师做的事（架构判断、复杂取舍、生产事故复盘）AI 始终碰不到核心。两边各司其职，工具用起来才舒服。

Cursor[39] 这两年崛起的真正原因，倒不是它的 AI 模型最强。它的 Composer / Tab Complete / Cmd-K 这三件套，每一件都把"AI 该插进哪里、不该插进哪里"想得很细。你按 Tab 接受补全，但补全只在你光标附近发生，不会"主动改一整个文件"。Composer 才会跨文件改，但每一个 diff 都让你 review。这种克制是 Cursor 用户黏性的根。

Devin[34] 推出时号称"全自动 AI 工程师"，能从 issue 接单到 PR 提交。它一度被炒上天，但实际用过的工程师反馈都偏冷淡。原因正是它越过了边界：把"决定下一步做什么"完全交给 AI，工程师变成了一个旁观的 reviewer，跟前面讲的 AI 自动写文章是同一种翻车形态。

Manus[35] 短暂的火爆和回落，几乎是同一个故事的复刻。它把 Agent 自主性推到极致，结果在真实工作流里反复偏移用户意图。"自主性强"听起来像好事，对作者或工程师都是双刃刀，收得不好，自主性就是失控的代名词。

写作要走的也是这条路。

写作是判断，不是堆词。工程师写错代码，CI[40] 会报警，code review 会拦住，线上还有 Sentry[41] 兜底。作者发出去一篇文章错的就是错的。没有 lint。没有测试。没有 code review。只有作者自己。

所以 AI 在写作场景里应该比代码场景更克制。它该帮你把"非创作环节"压到最小（调研、引用整理、排版、发布、文笔检查），然后退出去，把驾驶座让给作者。

知墨整套设计的底层都是这一条边界。Research Plan 卡片可编辑，因为搜什么是作者的判断。Skills 和 MCP 是扩展，作者决定挂什么。Publish Card 把所有输入前置收齐，让作者在发布前看清楚每一个细节。Trace Inspector 把 Agent 的每一步都暴露给作者，让"凭什么这次这样写"是可追溯的，不是黑盒。

这条边界写进了产品架构里，不是事后才喊的口号。

八、现在能用到什么程度

几个月迭代下来。上面这些功能都跑得通，VS Code 式编辑器、Deep Research、Skills + MCP 调研生态、Publish Card、Trace Inspector 加 Fork & Replay、回归与 A/B Compare。

配置侧体感：AI key、双平台账号、渲染参数三块全部在设置页一处管理，不用再开 4 个 Tab。













第一次打开知墨会进入「演示模式」——不需要填任何配置，知墨会自己把"打开半成品草稿 → Agent 调研 → 起草 → 双平台预览"整条流程跑给你看一遍。上面那些截图（S01–S12）就是这条流程里的关键画面。看完亮点再决定要不要正式用。

知墨暂不开源。这是个产品决定，不是技术封闭。一是产品还在打磨，社区反馈优先级和我们作为重度作者群体本身的优先级不一定一致。二是 Skills + MCP + Trace 这套组合是核心差异化，过早开源会失去打磨节奏。未来产品稳定后，会考虑开放部分模块（Trace Inspector 或 Skills 框架）。

顺便讲一下当前已知的问题，避免被发现的时候大家觉得我藏着掖着。

第一，单平台聚焦。知墨目前只支持知乎和公众号双发。掘金、Medium、Substack 等其他平台都没做。原因是我自己只用这两个，没动力。等有人提需求、或者我自己换了渠道，会扩。

第二，Mac 优先。Windows 我打过包但用得少。已知有几个 IPC 时序在 Windows 上比 Mac 慢一些，是 Electron 跨平台的常见问题。Linux 完全没测过。

第三，单语言。所有 UI 文案、内置 skill 文案、Agent 默认 prompt 全是中文。海外作者用起来会很别扭。i18n 是确定要做的，但时间排在 marketplace 后面。

第四，订阅模型。Claude / OpenAI / 自定义 endpoint 都支持，用户填自己的 API key 或者订阅凭证。Anthropic 那边 Max 订阅的接入比较新，知墨支持但还在打磨。如果你用 GPT 系，配置上更稳一些。

第五，Trace Inspector 的 UI 在大量 session（超过 500）时会有点卡。SQLite 那边索引加过了，但前端虚拟滚动还没完全跑通。这是接下来一个月要修的。

补一句关于"为什么是 Electron[20] 桌面"。经常有人问能不能做成 Web 版。我的回答是不能。三个原因。第一，.zhimo/ 项目目录是产品的基石，文件系统直接访问 Web 端做不到，要做就得起一套服务端存储加同步协议，工作量翻三倍。第二，本地 SQLite 用来存 trace 数据，IndexedDB 撑不到 2 GB 级别（第一版我用过，性能崩了）。第三，MCP server 的 stdio transport 需要本机子进程，Web 端只能用 SSE / HTTP，会损失一大类本地工具能力（接本地数据库、跑本地脚本之类）。这个选型由产品形态决定，跟"图省事"无关。

Roadmap 一句话：Skills marketplace（雏形阶段）、跨设备草稿同步（基于已有 .zhimo/ 结构，几乎零成本）、Trace Inspector 前端虚拟滚动（修上面第五条问题）。

我最希望听到什么反馈。如果你是写作者：哪一段流程对你来说还是太麻烦？哪一段是你愿意为之付费的？你目前的 5 个 Tab 是什么，知墨能不能合并掉其中 3 个。如果你是工程师：Trace + Replay + Compare 这一套，你自己做 Agent 时有没有需要？Skills 和 MCP 的双层挂载机制，你看得出问题吗。

反馈我每条都会看，团队规模不大，但响应这件事还扛得住。

九、结尾

写作工具有一个悖论。做工具的人很少是重度作者，重度作者很少去做工具。知墨想做这个悖论的例外。团队里有重度作者，工具是自己人在用的，再慢慢敞开门让更多作者也用起来。

回到开头那个数字。两周打光 Claude Max 20x 配额，听起来是工程上的"烧钱"。但换个角度看，配额是被一种新工作方式吃掉的。这种工作方式具体来说，是作者和 Agent 反复对话、Agent 不断为作者跑调研和素材整理、然后作者拿着这些素材自己写。每一次对话都在为一篇文章的某一个具体环节服务。两周下来的成果是这一篇你正在读的长文，外加另外四五篇技术答案，外加 100+ 个被自动归档进素材库的引用、研究、笔记。配额没浪费，是花在了"非创作环节"被压缩这件事上。

这一篇文章里大量的调研、引用、知乎和公众号双平台发布，都是知墨自己跑通的。文字部分是我一字一句写的。但写完每一段之后，知墨会帮我看哪儿啰嗦、哪句可以更紧、哪个表达不像我。它不替我写，但一直在帮我把文笔磨细。

这是一条边界。AI 不生成你的文章，但 AI 帮你优化你的文笔。它和"AI 自动写作"那类产品最根本的区别，就在这一条线上。

致谢 Claude Code[2]、CodeMirror、Element Plus、MCP SDK、OpenTelemetry GenAI、Vue 3、Electron 这些项目。没有它们做不出来。

特别感谢 Anthropic[42] 和 OpenAI[32] 把 Agent 工具调用做到今天的成熟度。五年前一个小团队三个月也做不出这个产品。
