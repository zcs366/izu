## 一、多Agent架构（3篇）—— 直连 izu 流水线

### 1. The Orchestration of Multi-Agent Systems: Architectures, Protocols, and Coordination
- **arXiv**: 2601.13671 | 2026.01
- **分类**: 多Agent编排
- **核心发现**: 统一了多Agent系统的技术组成框架——通信协议、任务分配、冲突解决、状态同步。提出三层编排架构：战略层（任务分解）→ 战术层（Agent调度）→ 执行层（工具调用）。
- **与izu的关联**: izu的流水线是顺序编排。这篇提供的三层架构可以用于设计更复杂的条件分支和动态调度——比如织的关联网络密度不够时自动触发补充搜索。
- **一句话**: 多Agent编排的"TCP/IP协议栈"级统一框架。

### 2. AAAI 2026 Bridge: Advancing LLM-Based Multi-Agent Systems with AAMAS Concepts
- **arXiv**: 2511.17332 | 2025.11 → AAAI 2026
- **分类**: 学术社区桥接
- **核心发现**: 论证LLM-based Agent社区应该借鉴AAMAS（自主Agent与多Agent系统）社区30年的理论积累——特别是BDI模型（Belief-Desire-Intention）和协商协议。认为当前LLM Agent社区在"重新发明轮子"。
- **与izu的关联**: izu的角色设计（探/搜/织/写/劈/修/核）天然对应BDI的某个维度。每个角色有自己的Belief（领域知识）、Desire（任务目标）、Intention（执行计划）。值得对照BDI框架重审角色定义。
- **一句话**: 别重新发明轮子——AAMAS社区30年前就在研究多Agent协作了。

### 3. Large Language Model based Multi-Agents: A Survey
- **arXiv**: 2402.01680 | 2024.02
- **分类**: 综述
- **核心发现**: 最早的系统性LLM多Agent综述。覆盖Agent画像（角色/记忆/规划）、通信范式（层级/民主/辩论）、集体智能涌现。提出多Agent系统的四个核心挑战：幻觉传播、协调成本、评估缺失、安全对齐。
- **与izu的关联**: izu的×2 ×3冗余设计（探×2、搜×2、劈×3）属于"投票/辩论"范式的一个变体。这篇综述可以帮助系统化理解不同冗余策略的优劣。
- **一句话**: 多Agent领域必读综述，框架至今不过时。

## 二、Self-Evolving / 代码Agent（3篇）—— 直连 匠石原则

### 4. A Self-Improving Coding Agent
- **arXiv**: 2504.15228 | 2025.04
- **分类**: 自改进Agent
- **核心发现**: 证明一个配了基本编码工具的LLM Agent可以**自主编辑自己的代码**，并在benchmark上提升性能。关键设计：Agent修改自己的工具函数→运行测试→如果通过则保留修改→形成自改进循环。
- **与匠石的关联**: 这篇直接验证了匠石原则——Agent自己改代码比让模型重新生成更可靠。但风险也是显见的：自修改可能导致不可预期的行为。需要"代码沙箱+回滚机制"。
- **一句话**: Agent改自己的代码，实测有效——但需要护栏。

### 5. ReVeal: Self-Evolving Code Agents via Reliable Self-Verification
- **arXiv**: 2506.11442 | 2025.06
- **分类**: 生成-验证循环
- **核心发现**: 提出ReVeal框架——多轮强化学习中交错进行代码生成和自我验证。核心创新：验证不是让模型"自己看一遍"，而是**用工具执行+测试用例**做客观验证。在HumanEval上提升显著。
- **与匠石的关联**: "用工具执行验证，不让模型自己判断"——这就是匠石原则在代码生成场景的精确应用。与izu核的代码优先验证完全同构。
- **一句话**: 验证用工具，别让模型自己骗自己。

### 6. A Survey on Code Generation with LLM-based Agents
- **arXiv**: 2508.00083 | 2025.08
- **分类**: 综述
- **核心发现**: 全面综述LLM Agent在代码生成中的应用。核心观察：软件开发的焦点正从"生成代码"转向"验证代码"。Agent擅长生成，但在理解大型代码库的全局架构时仍然困难。
- **与匠石的关联**: "焦点从生成转向验证"——这正好是匠石原则的推论。代码生成是模型的事，验证应该（且越来越）是工具的事。
- **一句话**: 代码Agent的下半场不是生成，是验证。

## 三、知识系统 / GraphRAG（2篇）—— 直连 wiki/WikiMeld

### 7. Reliable Graph-RAG for Codebases: AST-Derived Graphs vs LLM-Extracted Knowledge Graphs
- **arXiv**: 2601.08773 | 2026.01
- **分类**: GraphRAG + 代码
- **核心发现**: 对比了两种知识图谱构建方式——AST（抽象语法树）自动提取 vs LLM提取。结果：AST提取的图在代码检索任务上**更可靠**（确定性、无幻觉），但覆盖范围不如LLM提取的图（缺少文档、注释中的语义关系）。建议**混合方案**：AST做骨架，LLM补充语义边。
- **与wiki/WikiMeld的关联**: 这直接对应WikiMeld的设计问题——知识图谱该用代码规则构建还是LLM构建？答案是：代码做确定性骨架（文件关系、引用关系），LLM补语义边（概念关联、主题聚类）。匠石原则的又一次应用。
- **一句话**: 知识图谱：AST/代码做骨架，LLM补血肉——不要反过来。

### 8. Knowledge Graph of Thoughts (KGoT)
- **arXiv**: 2504.02670 | 2025.04
- **分类**: 推理+知识图谱
- **核心发现**: 将LLM推理过程与动态构建的知识图谱交织——每步推理产生新节点，新节点触发知识图谱扩展，扩展结果反馈给下一步推理。比单纯Chain-of-Thought在复杂推理任务上提升显著。
- **与wiki的关联**: wiki的"织"角色本质上是构建知识关联网络。KGoT的"推理→图谱扩展→反馈"循环可以启发织的设计——不是一次性编织，而是迭代编织。
- **一句话**: 推理和知识图谱不应该是两个阶段，应该交织进行。

## 四、验证与可靠性（2篇）—— 直连 核/verify

### 9. Benchmarking Vector, Graph and Hybrid Retrieval Augmented Generation
- **arXiv**: 2507.03608 | 2025.07
- **分类**: RAG评估
- **核心发现**: 系统对比三种RAG架构（向量/图谱/混合）在多个benchmark上的表现。关键发现：没有一种方案在所有场景下最优。向量RAG在事实型查询上最好，图谱RAG在关系型查询上最好，混合方案在多数场景下是最稳妥的选择。
- **与izu的关联**: izu的搜索步骤目前只用关键词搜索（DDG）。这篇支持引入混合检索——向量检索（语义匹配）+ 图谱检索（关系追溯）。
- **一句话**: 没有万能RAG架构。混合方案最稳妥。

### 10. Gödel Agent: A Self-Referential Framework for Agents Recursively Improving
- **arXiv**: 2410.04444 | 2024.10
- **分类**: 自指涉Agent
- **核心发现**: 受哥德尔机启发，提出一个Agent框架，Agent可以检查自己的代码、发现低效、生成改进、验证改进——递归地自我完善。不是预定义规则，而是让Agent自己找到改进方向。
- **与匠石的关联**: 这是匠石原则的极限形态——Agent不仅遵循"代码优先"原则，还能**自动发现哪些环节应该从模型迁移到代码**。当前是概念验证，但方向与匠石完全一致。
- **一句话**: 匠石原则的终极形态——Agent自己学会"能用代码就别用模型"。
