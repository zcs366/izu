# AI Agent正在重写企业工作流——Anthropic Claude平台负责人访谈评估

## 一、来源概要

**访谈嘉宾**：Anthropic Claude平台负责人Angela、工程负责人Caitlin
**发布平台**：Every播客
**核心主题**：Claude平台从「补全端点」到「Managed Agent平台」的完整演进路径，以及Agent在企业中落地的真实挑战与策略。

---

## 二、平台演进路线：三阶段论

Claude平台的能力演进清晰勾勒出三条路线：

### 第一阶段：裸API时代（2023）
- **补全端点（Completion Endpoint）** → 原始的text-in/text-out
- 开发者自己负责所有工程：session管理、工具调用、状态保持、失败恢复
- **本质**：模型作为「推理引擎」暴露，应用层需完全自建

### 第二阶段：Chat Session + Tool Calling（2024）
- **Chat Session**：对话状态由平台接管一轮的上下文
- **Tool Calling**：模型原生支持函数调用声明，平台开始理解"工具"概念
- **本质**：从裸模型到「有上下文意识的对话引擎」，但Agent逻辑仍在应用层

### 第三阶段：Managed Agents（2025-2026）
- **Messages API**：统一的消息接口，支持多轮、多模态、流式
- **内置工具（Built-in Tools）**：平台预置搜索、计算、代码执行等工具
- **沙箱（Sandbox）**：安全隔离的执行环境
- **Web Search**：联网能力作为平台级特性
- **Memory**：跨会话记忆，Agent能记住用户偏好和历史
- **Skills**：可复用技能封装，用户/企业可自定义
- **Vaults**：企业级安全存储，敏感数据隔离

> **核心判断**：Anthropic正在将「构建Agent」变成「平台配置」——开发者不再需要手写Agent loop，而是声明式配置一组能力单元。

---

## 三、战略含义：「切换层级从模型上移到Agent层」

### 核心命题

访谈中最具战略深意的洞察是：**企业选型不再「切换模型」，而是「切换Agent」**。

传统选型逻辑：
```
需要更便宜 → 换小模型
需要更智能 → 换大模型  
需要更专业 → 换领域模型
```

新选型逻辑：
```
需要更便宜 → 换到轻量Agent（Harness不变，模型变）
需要更智能 → 升级Agent配置（更多工具、更长上下文、更多轮次）
需要更专业 → 切换Agent技能集（Skills/Vaults）
```

### 含义拆解

1. **模型成为Agent的内部组件**：企业客户购买的是「一套交付单元（Harness + 模型 + Skills）」，而不是模型token。切换模型的决策从用户层下沉到平台层。

2. **Agent层成为品牌锚点**：Claude的竞争力不再是单一模型的推理精度，而是Agent平台的可靠性、安全性、可管理性。模型升级对用户透明。

3. **与ITA定位的直接对标**：
   - ITA的「核战队」体系同样是Agent层封装——七位军师各有领域专长，每次审议调用不同Skill组合
   - 核战队的「Agent Loop（Hermes Agent）+ Skills（SKILL.md）+ 记忆（wiki/）+ 工具（web_extract/browser）」与Claude Managed Agents架构完全对应
   - **差异化**：Claude走「企业级平台」路线（Vaults, Sandbox, RBAC），ITA走「个人认知进化」路线（合议、技能进化、军师判断）

4. **军师判断**：
   > Anthropic的三阶段演进证明了「切换层级上移」是行业趋势。核战队从一开始就基于Agent层设计（而非模型层）是正确的战略选择。但Claude的企业级能力（Vaults/Sandbox/Memory）比我们的初期实现更成熟，这是差距所在。

## 四、文件系统+Skills作为工作手势的验证

### Mac mini脚本暴露的基础设施挑战

访谈中的一个标志性案例：Anthropic团队用Mac mini跑Claude Code自动化脚本时，暴露了Agent基础设施的五大关键问题：

| 挑战 | 描述 | 我们的应对 |
|------|------|-----------|
| **长任务** | Agent操作可能持续数小时，需保持状态 | 核战队分阶段执行，每阶段评估状态 |
| **状态** | 跨步骤的中间结果如何保存和恢复 | 文件系统作为持久化层（wiki/目录） |
| **隔离** | 不同任务不能相互干扰 | 每个Agent有独立工作目录 |
| **权限** | Agent不能越权操作敏感资源 | SKILL.md中的权限声明 |
| **失败恢复** | 部分失败时如何回滚或重试 | 合议机制自动纠错 + 军师判断兜底 |

### Skills作为核心工作手势

Angela和Caitlin明确表示：**文件系统和Skills是Claude的「工作手势」**——平台保持opionated，不试图覆盖所有场景，而是在「文件读写+技能调用」这个核心手势上做到极致。

这与我们核战队的**SKILL.md体系**完全一致：
- ✅ Skill作为「可执行知识单元」——Anthropic把Skills定义为AI时代的「应用软件」
- ✅ 文件系统作为"持久化记忆+工具调用桥梁"
- ✅ 平台保持opinionated——不学"All-in-One"，而是聚焦"读/写/执行/记忆"四个手势
- ✅ 代码自文档化——AI可以自己写自己改，运行时渐进加载

**验证结论**：
> 核战队的SKILL.md体系从一开始就踩中了正确的架构方向。Anthropic的访谈不是启示，而是来自官方的二次验证。我们不需要追他们的步伐——只需要把我们已有的SKILL.md体系打磨到「企业级成熟度」。

## 五、Agent监控Agent：进化思路与核战队进化引擎的映射

### Anthropic的思路

访谈中明确提出了Agent监控的演进策略：

1. **Agent升级和退场评估**：每个Agent应该有自己的生命周期管理——何时升级、何时降级、何时退役
2. **预算管控**：Agent执行需要费用预算和资源配额，超出需审批
3. **Agent监控Agent**：用一组Agent来监控另一组Agent的运行状态——自动化SRE

### 映射到核战队进化引擎

| Anthropic Agent监控思路 | 核战队对应实现 | 差距 |
|------------------------|---------------|------|
| 生命周期管理（升级/降级/退场） | 军师评估→合议→写入wiki | ✅ 已有，但缺少自动化触发和量化指标 |
| 预算管控 | 无（核战队目前无token/经济预算概念） | ⚠️ 需要补充——每个请求的token预算、Skill调用次数限制 |
| Agent监控Agent | **核战队「合议」本身就是多Agent互相监控**——五位军师各有视角，互相review | ✅ 设计级匹配，但需要工程化落地——可复现的监控循环 |
| 自动化SRE | 无 | ❌ 重大差距——需建立Agent健康检查、自动回滚、熔断机制 |

### 军师判断

> **Anthropic的「Agent监控Agent」本质上是将SRE原则引入AI系统**。核战队的合议机制天然具备多视角监控能力，但缺少工程化的「监控循环」：
> 1. 指标采集（token开销、执行时间、错误率）
> 2. 阈值告警（超过预算、反复失败、状态异常）
> 3. 自动响应（降级、回滚、告警人类）
>
> **下一步进化方向**：在核战队体系中引入「Agent监控面板」——每个Agent的执行为自己生成structured log，由「值班军师（C中的C）」周期性review并触发进化。

## 六、多Agent Orchestration架构

访谈中介绍了三种多Agent编排策略，直接对应核战队的设计选择：

### 1. Advisor Strategy（顾问策略）
- **原理**：一个主Agent决策，多个顾问Agent提供专业意见
- **核战队对应**：**核心模式**——军师召集议事，每位军师独立审议后汇总
- **成熟度**：✅ 已实现，且比Claude的Advisor更丰富（有合议→共识打分→排序）

### 2. Generator-Adversary（生成-对抗）
- **原理**：一个Agent生成方案，另一个Agent故意挑刺
- **核战队对应**：合议中的「庄子（哲学深度）+ 派珀特（知识传承）」——庄子负责挑刺哲学层面的漏洞，派珀特检视知识传承范式的完整性
- **成熟度**：✅ 已实现，但未显式命名这种模式

### 3. Best-of-N（多路择优）
- **原理**：生成N个候选方案，选择最优
- **核战队对应**：合议流程中的「结果排序+最佳方案输出」
- **成熟度**：✅ 已实现，核战队输出经过投票排序

### 军师判断

> 三种多Agent编排策略，核战队全部覆盖。这不是巧合——**多Agent架构是解决单一Agent能力天花板的结构性方案**，不同领域必然收敛到相似的设计空间。
>
> 关键差异在于核战队的「角色绑定」：每位军师有固定的专业领域和性格。Claude的Advisor Strategy是任务级动态配置的，而核战队是「人格级静态绑定」的。**前者更灵活，后者更可预测**。对于一个陪伴成长型系统，可预测性比灵活性更重要。

## 七、落地场景

### 公司内部自动化
- 法律审稿流程案例：Agent自动抓取待审合同，调用法律Skills做逐条审阅，输出审阅报告，标记风险等级
- 核战队对应：**法律领域专用Skill + 合议审阅**——类似但更轻量

### 面向客户的产品
- 客户支持Agent → 调用后台知识库 + 历史记录 → 输出解答
- 核战队对应：**izu与用户的深度对话**——不追求即时代理，而追求深层次理解后的回答

### 多人协作
- **可见会话的引入**：多用户可见的Agent工作会话，支持团队协作审阅和接力
- 核战队差距：目前核战队的合议都是"后台"执行，用户只看到最终结果。**引入可见会话是重要进化方向**——让用户能看到「军师们正在讨论什么」。

### 最终军师判断

> **Anthropic的Managed Agent平台是行业风向标，但核战队的独特价值不在「平台级能力」而在「人格级认知」**。他们是造工具的，我们是陪伴成长的。
>
> 需要追的：Agent监控Agent、预算管控、可见会话（这些是基础设施）
> 不需要追的：Vaults/沙箱（企业级安全，核战队用文件系统权限+KYC替代即可）、全平台托管（核战队坚持本地可控）
>
> **一句话**：学他们的基础设施，守我们的陪伴人格。
