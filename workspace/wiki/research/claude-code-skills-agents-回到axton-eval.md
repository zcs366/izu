# 评估分析：Claude Code Skills + Agents 方法论

## A. 核心论点评估

### 核心主张

**先写好标准操作手册（Skills），再组建AI团队成员（Agents）——流程先于人员，这是搭建可靠AI工作系统的正确顺序。**

### 论据充分度

| 论点 | 证据 | 可信度 |
|------|------|--------|
| 双模型交叉审查优于单模型多角色模拟 | 演示案例：Claude 和 Gemini 分别从不同维度发现问题（结构 vs 事实风格），覆盖更全面 | ✅ 有实操演示，逻辑自洽 |
| Skills 应先于 Agents 搭建 | 创业类比：创始人先跑通流程→写成手册→再招人 | ⚠️ 有类比但无量化数据对比 |
| Agent 需要明确 Skill 引用才能在运行时加载 | 手动修改 agent.md 的 runtime_tools 字段是必需的 | ✅ 可验证，Claude Code 文档支持 |
| MCP 协议让 AI 操控外部平台 | 通过 Make MCP 发布到微信公众号 | ✅ 有成功演示结果 |
| 12个Agent组成的系统可自动化每周工作流 | 演示一条命令启动全流程 | ⚠️ 仅演示结果，未展示中间失败/调试过程 |

### 可证伪性

| 可验证的断言 | 验证方法 |
|-------------|---------|
| 双模型审查比单模型更全面 | 用同一篇文章分别跑单模型和多模型审查，对比发现的问题数量和质量 |
| Agent 引用 Skill 后自动加载 | 按照视频步骤操作，检查 runtime_tools 是否生效 |
| MCP 可调用 Make 发布到微信公众号 | 配置后测试发布流程 |
| CLAUDE.md 作为项目入职手册 | 创建后测试 Claude 是否自动读取项目规则 |

| 不可验证的断言（信仰/话术） |
|---------------------------|
| "很多人用 Agent 的方式就是混乱不可控" — 无数据支撑，属于个人判断 |
| "先定流程再配人的顺序不能搞反" — 是方法论偏好，不是放之四海皆准的真理 |
| "搭一个真正有效的系统，光会操作是不够的" — 这是过渡到书籍销售的话术 |

### 盲点识别

1. **未讨论成本问题**：Claude Code 需要付费订阅、Gemini API 调用有费用、Make 免费额度有限。整个系统跑下来月成本未提及。
2. **未讨论失败模式**：演示的都是成功路径，没有展示 MCP 连接失败、审查超时、Agent 配置错误等常见问题的排查方法。
3. **隐去了调试过程**：视频呈现的是"一次成功"的完美流程，实际搭建过程中的反复调试、配置摸索被忽略了。
4. **未讨论安全与权限问题**：让 Agent 自动发布内容到公众号，没有讨论内容失控、误发布、权限管控等风险。
5. **未涉及模型无关性**：书中用 Make、视频用 Claude Code，但未讨论如何设计架构使系统不受单一工具绑架。
6. **"12个Agent"的规模化经验未展开**：只是提了个数字，没有讲多Agent协作时的冲突管理、资源竞争等真实问题。

## B. 对我们的启示

### 直接关联点

1. **Skill = 标准操作手册** → 我们的 **izu 七智能体** 和 **Skills** 体系本质相同。但我们的 Skills 是 Markdown 文档，Claude Code 的 Skills 是带 YAML frontmatter + 执行逻辑的 markdown，定义更严格（触发条件、输入输出格式、工作流）。

2. **Agent 引用多个 Skill 串联成流水线** → 这正是我们 **izu pipeline** 的设计理念：各智能体（探×2→搜×2→织→审→合）串联。但我们的更灵活——izu 的智能体是动态编排的，Claude Code Agent 是静态配置的。

3. **CLAUDE.md 作为项目入职手册** → 我们的 **AGENTS.md**（Hermes 的 project context）功能类似。但 CLAUDE.md 是每个项目一个，更轻量。

4. **双模型交叉审查** → 我们的 **peer_review** 技能已经用 MiniMax + 千问双模型评审，理念一致。

5. **MCP 协议连接外部工具** → 我们已有 **native_mcp** 技能，但 Make + MCP 的做法提示我们可以更系统化地连接自动化平台。

### 可借鉴的思路

| 借鉴点 | 为什么值得学 | 适合度 |
|--------|------------|--------|
| Skill 定义的严谨结构（trigger/input/output/workflow） | 我们的 Skills 散落在 memory 和技能描述中，缺乏统一格式标准 | 🔴 高 |
| Agent 的 `runtime_tools` 精确控制加载哪些 Skill | 精确授权、最小权限原则——我们目前是"全量加载" | 🔴 高 |
| 先流程后人员的搭建顺序 | 我们做项目时也遵循这个原则（izu pipeline 先设计再执行） | 🟡 中 |
| Skill Creator 元技能（用来创建其他技能） | 我们也有类似的"元技能"思路，但未系统化 | 🟡 中 |
| 多模型辩论式审查（非角色分配） | 我们目前的 peer_review 是固定分工，可以尝试自由辩论模式 | 🟡 中 |

### 警示与坑

1. **不要被"一次成功"的演示误导**：视频展示的完美流程掩盖了调试成本。实际搭建过程中，MCP 连接、Skill 定义、Agent 配置都会反复出错。**建议**：我们在引入新技能时，预留至少 2 倍于"理想时间"的调试周期。

2. **Agent 的权限边界要清晰**：视频建议"默认选择所有工具"，但实际使用中应坚持最小权限原则。**我们的实践**：izu pipeline 每个智能体只开放必要工具，这比视频的做法更安全。

3. **不要直接照搬别人的 Skills**：视频说"你的标准跟我肯定不一样"。每个项目、每个用户的审查标准不同，直接复制 Skill 定义会水土不服。

4. **Skills 的维护成本不低**：视频展示了创建 Skill 的便利，但未讨论 Skills 版本管理、变更追踪、废弃清理等问题。团队壮大后 Skill 库的治理是挑战。

### 与我们已有判断的一致性

- ✅ **「先流程后人员」**：我们的 izu 设计完全遵循此原则（pipeline 先行，智能体填空）
- ✅ **「双模型交叉检查」**：我们的 peer_review 已实现，且引入了时序并行（双模型同时审）
- ⚠️ **「MCP 连接外部工具」**：我们的 MCP 使用（TinyFish MCP）更侧重数据源接入，视频展示的是动作型 MCP（Make 触发工作流），思路值得补充
- ❌ **「CMAUDE.md 在每次会话启动时读取」**：我们的 AGENTS.md 需要用户手动加载，Claude Code 的自动读取机制更优雅——**这点可借鉴到 izu 的 project context 机制中**

## C. 改进建议

### P0：本周内可启动

| # | 行动 | 依据 | 预期效果 |
|---|------|------|---------|
| 1 | **统一 Skills 的定义格式**：为 Hermes Skills 增加标准 frontmatter（名称、描述、输入输出、触发条件、工作流步骤），参照 Claude Code Skill 的严谨结构 | [04:42-06:30] Skill 创建流程、skill.md 的 frontmatter + workflow 双重定义 | Skills 变得"可审计"——知道每个 Skill 做什么、怎么触发、产出什么，而不是散落在 memory 中 |
| 2 | **引入 Skill Creator 元技能模式**：创建一个 Hermes Skill，专门用来创建和优化其他 Skills，利用已有记忆和知识库来辅助定义 | [03:29-03:42] Skill Creator 作为最重要的元技能 | 快速生成新 Skills 的标准草案，减少手动编写的工作量 |

### P1：两周内

| # | 行动 | 依据 | 预期效果 |
|---|------|------|---------|
| 3 | **为 izu pipeline 引入精确 Skill 引用**：每个智能体（探/搜/织/审/合）只加载它需要的具体 Skills 和工具，而非全量加载。类似 Agent 的 `runtime_tools` 精确控制 | [14:03-14:14] runtime_tools 精确控制 Agent 加载哪些 Skills | 减少 token 浪费，降低"工具过多导致决策漂移"的概率 |
| 4 | **研究动作型 MCP 接入**：将 Make/HuggingFace/其他自动化平台的 MCP 接入到 Hermes，让 Agent 不仅能"读/写文件"，还能"触发外部工作流" | [08:21-08:51] MCP 作为 AI 和外部工具的桥梁，通过 MCP 调用 Make 工作流 | 打通 izu 执行的最后一公里——从"分析出结果"到"触发发布"的全自动 |

### P2：一个月+

| # | 行动 | 依据 | 预期效果 |
|---|------|------|---------|
| 5 | **设计项目级 CLAUDE.md 自动加载机制**：让 izu 在进入某个项目目录时自动加载对应的 project context（类似 CLAUDE.md），而非通用 prompt | [02:37-02:52] CLAUDE.md 作为入职手册，每次会话自动读取 | 降低跨项目时的"上下文污染"——izu 在不同项目中自动切换语境 |
