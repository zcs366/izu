# Agent Memory 架构本质 — 评估

## 一、核心论点

> Memory 不是简单的"蒸馏"或存储，而是一个 **write–manage–read 闭环系统**。核心挑战在于**治理**（谁获得对未来决策的影响力），而非容量。

## 二、核心概念澄清

| 概念 | 职责 | 易混淆点 |
|---|---|---|
| **Memory** | 跨session持续存在的结构化历史，带来源/作用域/时间权重/可修正性 | 不是蒸馏产物 |
| **State** | 当前session内的短期运行态，session结束即销毁 | 不是memory |
| **Policy** | 允许与禁止的安全规则，不应被memory动态修改 | memory可记录不定义 |
| **Profile** | 用户模型的低维快照层，是记忆的输出产物 | 不是记忆本身 |

## 三、四个建模对象

| 模型 | 内容 | 核战队对应 |
|---|---|---|
| **用户模型** | 偏好、风险偏好、沟通习惯、转变轨迹 | USER.md |
| **任务模型** | 方案否决记录、已确认结论、未完成承诺 | session_search |
| **世界模型** | 仓库结构、API约束、系统边界、组织规则 | AGENTS.md / wiki |
| **自我模型** | 失败路径、工具不稳定记录、暂定假设 | **缺失** |

> **关键洞察**：意图不是单独存储的字段，而是这四层长期耦合后浮现的上层能力。

## 四、三条链路

### 写入：预算分配

本质是 decision under budget。**行为证据比口头表态更值得写入预算。**

### 管理：最容易偷懒也最关键

五件事：整合→冲突处理→衰减与遗忘→来源追踪→权限治理

> 死的不是经验本身，而是那些失去了更新机制的经验。

### 读取：任务约束驱动

传统RAG的局限：假设相关性由表面语义决定。升级方向：
```
retrieve(query) → read(task_context, belief_graph)
```

## 五、对izu记忆系统的扫描

| 组件 | 当前状态 | 差距 |
|---|---|---|
| **MEMORY.md/USER.md** | Profile层 ✅ | 缺少scope标注、置信度、衰减机制 |
| **SQLite FTS5 session_search** | Read层基础实现 ✅ | 语义检索而非任务约束驱动 |
| **自我模型** | ❌ **缺失** | 没有Agent自己失败路径的持久记录 |
| **冲突检测** | ❌ **缺失** | 新旧记忆矛盾时不处理 |
| **衰减与遗忘** | ❌ **缺失** | 记忆只增不减 |
| **来源追踪** | ⚠️ 部分 | 知道来源但无结构化provenance |
| **权限治理** | ❌ **缺失** | 用户无法查看/编辑/删除记忆 |

## 六、军师判断

**级别：大**。这篇比我预期的深刻——它不是实操技巧，是**架构级原则**。

**三个对我们直接有用的洞察**：

1. **自我模型缺失** → Agent重复犯错。当前核战队没有"Agent自己踩过什么坑"的持久记录。这是最小投入高回报的改进点。

2. **衰减与遗忘** → 记忆只增不减。短期内不致命，但随着使用时间增长会越来越严重。建议设置简单的时间戳衰减机制。

3. **记忆=治理而非容量** → 我们一直担心context window不够大，但真正的瓶颈在治理——什么值得记住、什么该忘、什么有冲突。这个认知转变比任何技术升级都重要。

**建议行动**：
- P1: 给MEMORY.md加简单的time权重字段
- P2: 设计冲突检测机制（同一事实两个版本时报警）
- P2: 自我模型（Agent失败记录独立存储）
