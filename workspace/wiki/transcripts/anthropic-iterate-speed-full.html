[00:00] 开场：Anthropic 凭什么这么快

大家好，我是AI启示录。最近整个AI圈都在问同一个问题：Anthropic 到底是怎么做到的？

有人做过一张统计日历——2026年的前40天里，他们一口气发布了超过30个核心功能，平均每天都有新东西上线。要知道，在传统软件行业，一个功能从想法到落地往往要6个月甚至一整年的规划周期。但在 Anthropic，很多功能的开发周期已经从6个月压缩到一个月，有时候甚至只需要一天。

外界第一反应都是：他们肯定是内部用了还没正式发布的 Metheus[1] 大模型，靠超强的AI能力给自己提效。

但 Claude Code 和 CodeWork[2] 的产品负责人 Kat Wu，在最新的深度访谈里直接戳破了这个猜测：前沿模型确实有帮助，但这根本不是核心。真正让 Anthropic 跑赢行业的，是一场从产品哲学、组织流程到岗位定义的彻底重构。

这期视频我就把这场访谈里的核心洞见完整拆解给大家。不管你是产品经理、工程师、创业者，还是只是想在AI时代找到自己定位的从业者，这期内容都会给你一份可落地的生存指南。

[1]: Metheus — Anthropic 内部开发的前沿大模型，推测为 Claude 系列下一代模型。

[2]: CodeWork — Anthropic 的云端协作产品，与 Claude Code 配合使用。访谈中也称 Cowork。

[01:02] 核心人物：Kat Wu 和 Boris 的分工

先给大家介绍一下这次访谈的核心人物。Kat Wu，他是 Anthropic 云端编码与协作产品的负责人，和 Claude Code 的创造者、技术负责人 Boris[3] 搭档，是站在AI研发变革最中心的人。

两个人的分工非常有意思：Boris 负责定愿景，划三到六个月后产品的终局——也就是那个最贴合 AGI 发展方向的版本。而 Kat Wu 的核心工作，就是把这个愿景拆解成可执行的路径，协调市场、销售、财务、算力等所有跨部门团队，扫清从想法到发布的所有障碍。

两个人的想法重合度有80%，剩下的20%——谁更在意，谁就牵头推进，没有严格的权责边界。而这恰恰是他们能快起来的前提。

[3]: Boris — Claude Code 技术负责人，全名未在视频中确认，与 Kat Wu 搭档负责产品方向。

[01:45] 三个核心动作：可复制的流程设计

很多人最关心的问题是：一天发布一个功能，到底是怎么做到的？

Kat Wu 拆解了三个核心动作，没有任何玄学，全是可复制的流程设计。

动作一：极致清晰的目标，干掉大模型带来的模糊性

大模型的能力太通用了。如果你不锁死用户场景和核心问题，团队很容易就会迷失在各种可能性里。

比如 Claude Code 核心用户从一开始就锁定了企业里的专业开发者。有一个功能要解决的问题就是权限弹窗太多导致的用户疲劳。目标非常明确：让企业开发者能安全地实现零权限提示。就这一句话，直接排除掉了所有不相关的方案，团队不用再无休止地讨论，直接朝着这个目标推进。

动作二：Research Preview 机制，降低发布的承诺压力

Claude Code 的几乎所有功能，都是先以研究预览（Research Preview）的形式发布。他们会明确告诉用户：这是一个早期产品，只是一个概念验证，我们正在收集反馈，这个功能未来可能不会永久支持。

这么做的好处是什么？团队不用等到功能做到完美、打磨到极致再发布。最快一两周甚至一两天，就能把东西推到用户手里。

很多人对发布有执念，觉得必须做到100分才能见人。但在AI时代，用户的真实反馈比你在会议室里闭门造车的100分规划要值钱得多。

动作三：Evergreen Launch Room（长青发布室）

这就是 Anthropic 内部大名鼎鼎的 Evergreen Launch Room[4] 流程，也是 Kat Wu 作为 PM 给团队搭的最核心的提效基建。

工程师只要觉得功能已经就绪，并且完成了内部试用，就可以直接把它发到这个专属频道里。接下来，负责文档的团队、负责产品营销的团队、开发者关系的团队，会立刻同步介入——最快第二天就能完成所有对外发布的准备工作。

这套流程跑顺之后，任何一个工程师想发布一个功能，都没有任何摩擦和阻碍。而搭建这套让所有人都能顺畅发布的机制，就是AI时代产品经理最核心的工作之一。

[4]: Evergreen Launch Room（长青发布室） — Anthropic 内部的异步发布流程，工程师自助提交 → 文档/营销/开发者关系团队自动接管，实现零摩擦发布。

[03:35] 最大误解：不是靠最强大模型

这里必须澄清外界的一个最大误解。很多人觉得 Anthropic 能跑这么快，全靠内部能用最强的模型。但 Kat Wu 明确说：他们在新模型出来之前，就已经保持这个高速迭代节奏好几个季度了。内部的前沿模型确实给提效带来了一些帮助，但这绝对不是核心原因。

真正的核心是：他们从流程到团队预期的彻底重构。团队里的每一个人都相信，自己有权利也有责任，把一个想法在不到一周甚至一天之内，从雏形变成现实，推到用户面前。

[04:07] 产品经理岗位正在被彻底改写

聊完了表面的流程，我们再深入一层，看看这场速度革命背后真正正在发生的巨变：产品经理这个岗位正在被彻底改写。

Kat Wu 面试了几百个想进 Anthropic 做PM的候选人，他发现绝大多数人对AI时代PM这个岗位的理解，从根上就错了。

在AI出现之前，技术迭代的速度很慢。产品团队可以按6到12个月做长期规划。那时候写代码的成本很高，发布一个功能的周期很长。PM的核心价值很大一部分来自跨部门协调——确保各个团队的路线图对齐，让大家的功能能互相解锁。所以那时候，会写PRD、会协调资源、能推动跨团队合作，就是一个好PM。

但现在一切都变了。AI把工程开发的效率提升了几个量级，模型的能力几个月就会有一次跨越式的升级，用户的行为也跟着在快速变化。

PM的核心价值，已经不再是写一份漂亮的跨季度路线图，也不是做无休止的跨部门对齐，而是想尽一切办法，缩短从产生一个想法到把产品交到用户手里的时间。

[05:10] PM的新护城河：产品品位

那PM的护城河到底变成了什么？Kat Wu 给出了一个全场最核心的答案：产品品位（Product Taste）[5]。

当编写代码的成本变得越来越低，真正变得稀缺且值钱的，是决定"要写什么"的能力。是在成千上万条用户反馈、成百上千个 GitHub issue 里，判断出哪些东西真正值得做、哪些只是噪音。是判断一个功能到底应该做成按钮、命令、自动触发，还是根本就不该做。是定义什么是好的用户体验，什么是令人愉悦的产品交互。

这种产品品位，依然是这个时代最稀缺的技能。

在 Anthropic 内部，工程师、PM、设计师的边界已经变得非常模糊。他们更倾向于招聘有产品品位的工程师。团队里很多工程师完全可以独立完成——从在社交平台上看到用户反馈，到周末就把功能发布上线的全流程，几乎不需要传统PM的介入。

而团队里几乎所有的PM，要么之前就是工程师，要么现在就在直接参与 Claude Code 的代码交付。甚至连设计师之前都做过前端工程师。

为什么工程背景在当下这么重要？Kat Wu 解释说：因为有工程背景的人，能更准确地预判一件事做起来到底有多难。如果一个功能做起来非常简单，那就别在会议室里争论了，直接花一个小时把它做出来，用用户反馈说话。如果一个功能做起来难度很高，你提前就能预判到成本，就能更准确地做优先级排序。

[5]: 产品品位（Product Taste） — Kat Wu 定义的核心概念：在大量可能性中，判断什么值得做、什么不做的能力。不同于传统PM的协调能力，这是AI时代PM的护城河。

[06:31] PRD的死亡与重生

还有一个更深层的变化：PRD的死亡与重生。

很多人问，现在迭代这么快，PM还写PRD吗？

Kat Wu 说，他们团队做了两件事替代了传统的PRD：

第一件事：每周和全团队一起做严格的指标复盘，确保每一个人都深度理解业务的全貌——核心目标、数据趋势和背后的驱动因素。

第二件事：维护一份清晰的团队原则，明确核心用户是谁、为什么是这些人、我们愿意做什么样的取舍。

这么做的目的，是让团队里的每一个人都能自己做决策，而不是事事都要等PM或者领导来拍板。

当然，PRD并没有完全消失。对于那些特别模糊、失败模式很多、或者需要大量基础设施投入的长期项目，他们依然会写一份一页纸的PRD——写清楚目标是什么、理想的用户场景是什么、当前要解决的失败模式是什么。但对于绝大多数功能，PRD已经不再是必需品了。

[07:26] 使命驱动：AGI安全是最高优先级

聊到这里就不得不提一个问题：Anthropic 起步的时候，不管是资金、算力还是分发渠道都不占优势，为什么能在这么短的时间里成长为 OpenAI 最强劲的竞争对手？

Kat Wu 说，最核心的就是整个组织高度统一的使命：为全人类实现安全的AGI。

这个使命不只是一句写在官网的口号，而是他们所有商业决策、优先级判断的过滤器。如果有两个互相竞争的目标，他们只会问一个问题：哪一个对我们的使命更重要？一旦确定，整个团队都会全力支持——甚至愿意为了公司的整体目标，牺牲自己产品线的局部利益，牺牲自己团队的KR。

Kat Wu 说得很直白："如果 Claude Code 失败了，但 Anthropic 成功了，我会非常高兴。"整个团队都愿意为了这个核心使命做出这样的取舍。

这种使命感也让 Anthropic 保持了极致的专注。他们能抵御住做社交网络、做信息流产品的诱惑，把所有的资源倾斜在赋能专业开发者、提升模型能力这件事上。哪怕遇到源代码泄露、订阅政策争议这样的突发状况，整个团队依然能保持冷静——因为他们对核心目标有绝对的笃定。

[08:39] AI时代的人机协作新范式

接下来我们再聊聊这场变革里最关乎每个人的部分：AI时代人机协作的新范式，以及人类大脑真正不可替代的价值到底在哪里。

95%自动化是陷阱，最后5%才是关键

Kat Wu 提出了一个非常反常识的标准：真正的自动化必须达到100%的准确率。

现在很多人用AI做自动化，做到90%甚至95%的准确率就觉得已经成功了。但 Kat Wu 说，这恰恰是最大的效率陷阱。如果一个自动化流程只有95%的准确率，就意味着你依然需要花时间人工审核、修正错误——它根本就不是真正的自动化。只有把它优化到100%的准确率，你才能彻底解放双手，获得真正的时间杠杆。

最后那5%的优化，往往需要花更多的时间和精力，但这才是真正能给你带来质变的部分。

他举了自己用 CodeWork 做演讲幻灯片的例子：Slack、Gmail、Google Drive 全部和 CodeWork 连接，给他明确了演讲的主题和叙事逻辑。CodeWork 花了一个小时翻阅了所有的产品发布记录、内部讨论、用户反馈，直接生成了一份20页的、完全符合 Anthropic 设计系统的幻灯片草稿。他要做的只是做最终的决策——决定哪些内容要保留、哪些要删掉，给它反馈修正一些冗长的表达。

这就是AI时代人机协作最合理的分工：AI负责处理海量的信息、重复性的劳动、铺开所有的可能性；而人类负责做最终的决策、定义成功的标准、把控产品的品位。

人类不可替代的价值：常识与隐性知识

那在模型越来越强的今天，人类大脑的价值到底在哪里？

Kat Wu 说，依然是常识、情商和处理隐性知识的能力。任何一次产品发布，都有成千上万个细碎的环节，有无数可能出错的地方。模型依然很难判断：谁是关键的利益相关方？他们之间的关系是什么？他们的偏好是什么？用什么样的方式沟通才能让所有人保持协作？这些隐性的、需要常识和情商的知识，依然是人类不可替代的堡垒。

还有一个被严重低估的能力，就是构建评测集（Evals）[6]。PM的核心职责是定义什么是成功、什么是失败，而评测集就是把这个定义量化的工具。你不需要做几百个评测，只要十个核心的评估基准，就能帮整个团队明确目标、衡量进展、找到缺失的环节。

Kat Wu 自己的习惯就是：当他发现模型出现意料之外的行为时，会直接问模型"你为什么会这么做"，让模型对自己的行为进行反思。很多时候，模型会告诉你是系统提示词里的某段话让它困惑，或者是它把任务委派给了子智能体但没有检查结果。这些反馈会直接指向产品的改进方向。

[6]: Evals（评测集） — 用于量化PM对"成功/失败"定义的工具。Kat Wu 主张10个核心评估基准即可，而非几百个。

[11:08] 高速迭代的代价

当然，这种极致的高速迭代不是没有代价的。Kat Wu 非常坦诚地说：他们牺牲了一部分产品一致性。

在传统的产品开发里，因为写代码的成本很高，团队会精心规划整个产品套件——每个产品的边界、场景、集成关系都非常清晰，不会有功能重叠。但现在为了快速测试大量的想法，他们有时候会同时上线两个功能重叠的产品——因为内部有两种方案都很受认可，他们想让真实的用户来告诉他们哪一个更好。

代价就是：新用户进来之后，可能会不知道完成某件事的最佳路径是什么，也很难跟上每一个新功能的更新节奏。这也是为什么他们后来推出了 PowerApp[7] 内置引导功能——原本他们的产品哲学是"好的产品应该足够直观，根本不需要教程"，但当功能数量快速增长，用户需要有人告诉他们：上百个功能里，最该用的那十个到底是什么。

[7]: PowerApp — Anthropic 推出的应用内引导功能，帮助用户在大量功能中找到最佳路径。

[11:58] 回应两大争议

这里我们也客观地聊一聊这段时间外界争议最大的两件事，Kat Wu 也在访谈里给出了明确的回应。

争议一：Claude Code 源代码泄露

三月底，Claude Code 的完整源代码泄露事件。Kat Wu 说，他们第一时间就做了全面调查。这件事的本质是人为失误——一位工作人员在用 Claude 协作编写PR、更新软件包的发布流程时出了差错。哪怕这个PR经过了两层人工审核，最终还是出现了疏漏。

他们已经第一时间加固了流程，增加了更多的安全防护措施，避免未来再发生类似的事件。

而对于大家最关心的"这位工作人员是否还在 Anthropic"，Kat Wu 的回答非常明确：还在。因为这不是某个人的错误，而是流程的失败。最重要的是从中吸取教训，而不是追责个人。

争议二：限制第三方工具使用订阅额度

限制第三方工具 OpenCoder[8] 使用 Claude 订阅额度的决策，这件事在开源社区引发了非常大的争议。

Kat Wu 的解释是：Claude 的市场需求一直在高速增长，他们一直在努力扩展基础设施、优化 Token 效率。但订阅服务的额度原本就是为第一方产品设计的，第三方工具的使用模式和第一方产品完全不同，会给基础设施带来不成比例的压力。

他们花了很多时间寻找最平滑的过渡方案，最终还是做出了这个艰难的决定——优先保障第一方产品和API的稳定。当然，他们也给每个订阅用户附赠了一定的额度作为缓冲。

[8]: OpenCoder — 受限制的第三方工具名称，Whisper 转录为"OpenClock"，按上下文推断为某开源 Claude 客户端。

[13:16] Claude Code 未来三阶段演进

聊完这些，我们再看 Claude Code 和 CodeWork 未来的演进方向。Kat Wu 用搭积木的逻辑，把它拆成了三个阶段：

第一阶段：保证单个任务的成功率。你给它一个清晰的指令，它能不能持续产出你可以直接使用、直接合并的结果。

第二阶段：多任务并行。现在已经有越来越多的用户同时让 Claude 处理六个甚至更多的任务。

第三阶段：同时运行五十个甚至上百个 Claude 智能体。到那个时候，本地机器的性能已经无法支撑任务，会在远端运行。产品需要解决的是：怎么让用户清晰地知道哪些任务需要关注，怎么让智能体能自己验证工作结果，让用户看到"已完成"的时候能完全信任它。

[13:56] 模型会吃掉你的产品外壳

还有一个非常有意思的观察。Kat Wu 说，每次新模型发布，他们做的第一件事不是加功能，而是删功能。

比如 Claude Code 早期有一个待办清单功能。当时的模型做大规模代码重构时，经常改了几个调用点就停下来，所以团队做了这个功能，强制模型先列好所有要修改的点，再逐个完成。但到了新模型之后，模型自己就会主动列清单、逐个核对，根本不需要额外的功能提醒。这个待办清单就从一个必要的拐杖，变成了一个可有可无的辅助功能。

就像行业里说的那句话："模型会把你的产品外壳当早餐吃掉。" 你为了弥补模型能力短板做的所有功能，终有一天会被更强的模型直接淘汰。

所以 Kat Wu 给所有AI产品人的建议是：一定要提前去做那些现在还不能完全跑通的产品原型。你要先想清楚未来的产品应该是什么样的，先把原型打好。等新的模型出来，直接替换进去，看看能力的缺口有没有被补上。这样你才能永远比别人快一步。

[14:53] 给AI从业者的两个建议

最后，Kat Wu 给所有在AI时代焦虑的从业者提了两个最核心的建议。

建议一：不要只做一次性的原型

去开发那些你每天都会用的工具。只有你自己每天都在用，你才能真正发现产品的边界和问题，才能真正把AI变成自己的工作杠杆，而不是一个只会拿来炫技的玩具。

很多人沉迷于给工具加各种技能、各种MCP、各种复杂的工作流，花在定制工具上的时间比完成核心任务的时间还多——这完全是本末倒置。

建议二：找到重复且不喜欢的任务，交给AI

找到你工作中那些重复的、你不喜欢做的手动任务，把它交给AI，然后不断迭代，直到它能100%可靠地运行。AI最大的价值，就是帮你接管那些琐碎的苦差事，让你把时间和精力放在真正有创造性的工作上。

不要停在95%的自动化。最后那5%的打磨，才是真正能给你带来自由的部分。

[15:48] Just Do Things：只管去做

而他自己的座右铭只有一句话：Just do things——只管去做。

在很多公司里，岗位的边界划分得非常严格。PM只能做PM的事，工程师只能碰自己负责的代码。但在AI时代，最值钱的能力是你看到一个问题，不管它属于谁的职责范围，都愿意主动去解决它。

你只要理解了约束条件，想清楚了该做什么，就直接去执行。从错误中学习，做错了就道歉、修复。在这个变化快到让人眩晕的时代，行动永远比完美的规划更重要。

[16:20] 结语：在AGI风暴中心站稳脚跟

今天的AI行业，每天都有新的模型发布、新的功能上线。所有人都在被时代的洪流推着往前走。很多人都在焦虑——自己的岗位会不会被AI取代？自己到底该学什么才能不被淘汰？

但 Kat Wu 的这场分享给了我们一个最朴素的答案：AI能接管的是执行、是重复劳动、是代码的编写。但它永远无法替代的，是你的判断力、你的产品品位、你定义什么是好、什么是成功的能力，以及你直面混乱、只管去做的行动力。

在AGI的风暴中心，能让你站稳脚跟的，从来不是对旧规则的熟练掌握，而是你拥抱变化、重新定义自己的勇气。
