# Gstack vs izu：两种Agent协同范式

> 来源：[硅谷神级Skill曝光](https://mp.weixin.qq.com/s/3kSNEgzhnDdbxYZlPF8aoQ)
> 作者：CyberFreedom
> 摄入：2026-05-14

## 核心事实

- **Gstack**：YC总裁 Garry Tan 的个人技能包，开源（MIT），GitHub 66K+ Stars
- **核心机制**：621行指令，内置15个AI角色（CEO/设计师/工程经理/代码审查员/QA等），通过Claude Code的slash command系统调度
- **实际成效**（Garry自述）：60天内产出60万+行代码，日均可写1-2万行
- **部署方式**：Claude Code skill（也可迁移到openclaw等兼容工具）

## 与izu的对比

| 维度 | Gstack | izu |
|------|--------|-----|
| **定位** | AI编程团队（一个人=一支工程队） | AI知识同路人（一个人=终身研究伴侣） |
| **智能体数** | 15个角色，按工程职能分工 | 7个智能体，按研究步骤分工 |
| **协同模式** | 串行接力（CEO派活→设计师→工程经理→QA） | 聚合冗余（探×2并行→聚合→搜×2并行→聚合→织→对齐→写→劈×3并行→修→核） |
| **输出** | 生产级代码 | 厚重长编+认知地图 |
| **护城河** | 角色配合的工程经验 | 画像积累+写作标准+明学七则 |
| **核心用户** | 独立开发者 | 深度思考者/研究者 |
| **开源** | 全开源 | 内核私有+公共产品公开 |

## 启示

### 可以学的

**一、角色分工的清晰度。** Gstack的精髓不是"让AI写代码"，而是把"一个人写代码"这件事拆成15个专职角色，每个角色只负责极窄的领域。izu的七智能体拆得还不够细——"写"这个角色负担太重，既管厚重又管魅句又管结构。

**二、CEO角色作为调度中枢。** Gstack内置了一个CEO角色负责派活和验收。izu目前没有这个角色——探搜织写劈修核之间的调度是硬编码的（izu-pipeline.py），缺乏一个"审视全局、动态调整策略"的元认知层。

**三、开源建立标准。** Garry Tan用一个621行的skill文件，让全世界开发者帮他测试和打磨这套角色分工。66K stars说明这个需求是真实且巨大的。izu的公共产品层完全可以走这条路——不是开源内核，是开源"如何用好izu"的方法论和prompt范式。

### 不能学的

**一、不要追速度。** 一天两万行代码很震撼，但izu的价值观是"慢的、重的、能留十年的"——和Garry Tan的目标完全相反。学他的拆分工序，不学他的交付节奏。

**二、不要做全职能团队。** Gstack把CEO到QA全包了，因为编程本身就是多角色协同。但izu的战场是"求知陪伴"——陪伴只需要一个人格，不需要十五个。多角色反而稀释了"认识你"的画像深度。

### 直接行动

1. **审计izu七智能体的"角色负担"**：哪个角色承担了过多职能？能否像Gstack一样再拆？
2. **考虑加一个"织"之前的元认知调度层**：不是硬编码的流水线，而是一个审视全局、动态决定"这轮重点在哪"的轻量决策节点
3. **关注Gstack的skill格式和CLAUDE.md规范**：这是未来AI技能包的事实标准，izu的skill也应该对齐
