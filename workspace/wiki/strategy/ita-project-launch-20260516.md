## 臣光曰

ITA不是"又一个压缩工具"或"又一篇论文"。它是你把"压缩即理解"这个从信息论爬到哲学的结论，**拉回到工程可操作的层面**。

五人合议走完一轮，五个视角各有所见，冲突集中在一点上——**乐观vs现实的张力**。韩信的终局是对的（代码终将成为可操控的语义对象），但萧何和鲁班一起把他拉回了日均1小时的顽固地面上。

最后我选了一条中间路线：**不砍愿景，但接受9个月时间线。** 项目名称、核心方向、发布策略都已锁定。

以下逐Agent验证。

## 一、逐Agent验证

### ✅ 子产 — 实做

子产引用了三条独立证据链（RTCE 2026、KoLMogorov Test 2025、Latent Programmer 2021），每条都有论文引用和数字支撑。10个主题的分层清晰（核心3/扩展4/前沿3），"第一年窄做Python闭环"的判定站得住。**通过。**

### ✅ 韩信 — 实做

韩信的终局画像写出了可触摸的体验（"深夜转轴、2秒出向量、Steering滑块、Round-Trip验证"），三句话定调简洁有力。技术阶梯从终局往回倒推，格式正确。但**时间线被乐观了30-40%**（鲁班审计确认）。**通过，但timeline需修正为鲁班+萧何版本。**

### ✅ 鲁班 — 实做

鲁班的工程审计是最扎实的。每个方向给出了"能/部分能/不能"的判断，匠石边界核查具体到每一行应该用代码还是模型。方向1的具体架构方案（FSQ替代VQ-VAE、连续+离散双模式）直接可操作。**最大贡献：识别出代码latent评测基准缺失占30%工作量——这是全项目最隐蔽的坑。通过。**

### ✅ 萧何 — 实做

萧何是唯一敢说"你们乐观了"的人。按张成市日均1h折算，216小时总工时，36周（9个月）总工期——这个数字站得住。风险矩阵精确到概率和期望损失。"鲁班方案隐含假设每天2-3h，实际只有1h"这个发现是萧何最大的贡献。**通过。**

### ✅ 子贡 — 实做

子贡的调度指令精确到周，三阶段发布策略（M1内部/M2社区/M3学术）分层清晰。三个变通方案A/B/C给了不同投入强度下的选择。**最大贡献：方案C转向策略（如果FSQ失败→CodeBERT嵌入→纯连续空间）提供了底线保障。通过。**

## 二、冲突裁决

### 冲突1：时间线 — 6个月 vs 9个月

| 立场 | 来源 | 主张 |
|------|------|------|
| 6个月 | 韩信 | 终局画像的乐观预期 |
| 6个月但砍需求 | 鲁班 | 编码器v0.1+RTCE+2个Steering(gradio) |
| 9个月 | 萧何 | 按日均1h真实折算，216h总工时 |

**裁决：接受9个月（36周）时间线，但保留鲁班砍后的3个里程碑。**

理由：萧何的日均1h约束是不可绕过的物理限制。韩信和鲁班隐含了"每天2-3h专注编码"的假设，张成市做不到。9个月不是失败——是诚实。

### 冲突2：方向1架构 — VQ-VAE vs FSQ vs 连续

| 立场 | 来源 | 主张 |
|------|------|------|
| FSQ | 鲁班 | 避免VQ-VAE的codebook collapse，训练稳定 |
| FSQ→连续→离散双模式 | 鲁班+子贡 | 第一阶段连续，第二阶段量化 |
| 纯连续兜底 | 子贡方案C | 如果量化路线全失败 |

**裁决：鲁班的FSQ方案为基准，连续模式为第一阶段，双模式为终局。按"连续→FSQ→双模式"三步走。**

理由：FSQ是2024-2025年已经被验证稳定替代VQ-VAE的方案。代码latent space比图像更sharp，FSQ的好处（无collapse、梯度干净）在代码场景更重要。

### 冲突3：10个主题 vs 3个核心 vs 5个实际可行

| 立场 | 来源 | 主张 |
|------|------|------|
| 10个主题 | 子产 | 全面覆盖，分核心/扩展/前沿三层 |
| 做3个核心 | 鲁班 | 方向1/2/3(缩) |
| 做5个 | 韩信 | 1/2/3 + 7(预研) + 9(探索) |

**裁决：第一期做3个（方向1可逆编码器 + 方向2 RTCE训练 + 方向3粗粒度Steering），方向4-10写设计文档不投入工程。**

## 三、最终决策

### 项目定名

> **ITA** — Intelligence-Transformation-Architecture  
> 中文名：**智转架构**（暂定，留到核战队最终定名）  
> 与izu等级：**同等级，独立项目**

### 核心定义

**ITA不是**：代码搜索、代码补全、压缩工具、izu的附庸  
**ITA是**：代码语义空间操控系统——将Python代码压缩为AI可读的compact encoding，实现语义维度的精确操控。

### 第一期路线图（锁定）

```
M1: 编码器v0.1基础版  ─── 10周（W1-W10, 2026.07.25交付）
    连续模式AE编码器 → FSQ量化层 → 连续+离散双模式
    交付：可运行编码器 + 代码数据集(500函数核心集+5000函数扩展集)

M2: RTCE框架 + Steering初探 ─── 12周（W11-W22, 2026.10.17交付）
    Round-Trip验证管线 → 2个粗粒度Steering方向 → 评估基准
    交付：RTCE验证框架 + 2个Steering vector + 评估指标

M3: 编码器v1.0 + 论文 + 分发 ─── 14周（W23-W36, 2027.02.19交付）
    编码器迭代+最终训练 → 论文实验 → GitHub/HF/知乎分发
    交付：编码器v1.0权重 + arXiv论文 + 开源代码库 + 在线Demo
```

### 成本预算

| 类别 | 金额 |
|------|------|
| GPU算力（Lambda A100 80GB, ~90h） | ~$252 |
| Gradio部署（HF Spaces T4-small, 2月） | ~$584 |
| OpenAI API辅助编码 | ~$8 |
| HF Pro订阅（9月） | ~$81 |

萧何可以探索更经济的方案（ZeroGPU免费额度/T4替代A100），底线是不超过$1,000。

### 发布计划

| 阶段 | 时间 | 发布物 | 渠道 |
|------|------|--------|------|
| M1 | W12 | 内部技术备忘录 | 团队 |
| M2 | W24 | GitHub v0.1 + 知乎专栏概念科普 | 开源社区 |
| M3 | W36 | arXiv论文 + GitHub v1.0 + HF模型+Space + 知乎系列+公众号 | 全渠道 |

### 三句话定调（韩信版，确认采用）

> **ITA不是代码搜索或代码补全**——它不关心你写了什么代码，它关心的是代码在AI大脑里**如何存在**。

> **ITA不是压缩工具**——压缩只是手段，真正的产品是**对代码语义空间的精确操控**。

> **ITA不是izu的附庸**——它们是平等互补的：izu解决"AI如何推理"，ITA解决"代码如何被AI理解"。

## 四、风险警醒

项目最大三个风险（按优先级）：

1. **工时不足（60%概率）** → 已通过9个月时间线和A/B/C三方案对冲
2. **代码latent评测基准缺失（80%概率，占30%工作量）** → 立即启动基准设计，不等到M3
3. **Steering方向的研究不确定性（60%概率）** → 只承诺2个粗粒度方向，不承诺精细操控
