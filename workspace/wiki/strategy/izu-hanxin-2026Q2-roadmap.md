## 一、终局画像（3-6个月后的 izu）

### 用户第一次打开时的体验

张成市打开微信（或 CLI），输入一个问题。不是直接出答案——izu 先说一句话：

> "这个问题有三个方向可以挖。第一个方向你上周接触过类似的，第二个方向是新领域，第三个方向我看到一篇刚入库的论文和它有关。你想先走哪个？"

这不是选择题，是**观察反馈**——izu 在读你的意图之前，先告诉你它读到了什么。

然后，不是一次回答。是一段三十分钟到两小时的**陪伴式研究旅程**：izu 先出一份长编，末尾不是"以上"而是"这里留了三个还说不清的缝"。你追问 -> izu 深挖 -> 你又发现了新连接 -> wiki 自动入库 -> 明早的日报里有"昨晚你走岔的那个方向，今天有新进展"。

### 核心交互循环

```
你产生好奇心 → izu 给出长编（够大够整够深）
    → 你在缝隙处追问 → izu 深挖那个方向
    → 新认知自动进入 wiki → 第二天 izu 在日报里延续话题
    → 你的画像更新一次 → 下次的产出更贴合你的思维习惯
    → 你又产生新的好奇心（循环）
```

### 与今天的本质区别

| 维度 | 今天 | 3-6个月后 |
|------|------|----------|
| 流水线 | 七智能体单向传递，无交叉审核 | Spec + 交叉审核循环，每步有硬检查点 |
| 质量闭环 | 产出即结束，无反馈回传 | 每份长编有"读完了吗/有用吗/哪里跳过了"的信号回传 |
| 画像 | 会话即画像（理论） | 画像开始反哺——izu 基于画像主动推荐研究方向 |
| 工具链 | 七智能体各干各的 | 核心工具集（grep+chrome+wiki+code）被 Spec 锁定，不随意添加 |
| 跨会话 | 每次对话独立 | 上次留下的"缝"是下次开始的门 |

### 一个典型用户的完整故事

张成市看到一篇关于"Agent 交叉审核"的推文。他在微信发给 izu。

**第 0 天：** izu 从 wiki 中找到 specs-coding 和 autoresearch 的概念文件，两小时后出了一份长编《从 Vibe Coding 到 Spec Coding：Agent 开发的范式转移》。

长编末尾写道："交叉审核循环的量化评分机制，和你七智能体流水线的缺环，是对得上的。这周也许值得一试。"

**第 3 天：** 张成市试了交叉审核的第一个版本。izu 的日报里多了几行："昨晚流水线的'织'阶段有 3 次未通过审核被回滚。其中 2 次的根因是搜到的资料和问题不匹配——建议调高'搜'阶段的相关度阈值。"

**第 30 天：** izu 自动检测到过去一周的流水线回滚率达到 40%，判断其中一个 Agent 的能力边界到了。不是出报告，是直接说："'搜'这个角色最近有点吃力，考虑拆成'搜(宽)'和'搜(深)'两个 Agent，或者给它加一个 Chrome MCP 工具。"

**第 90 天：** 张成市提出一个极难的问题。izu 花了四十分钟，遍历了 wiki 中 200+ 页资料、用 Chrome MCP 做了三次实时验证、调用了四条不同的搜索链路。最后说："这个问题我在十个方向走了七条死路。另外三个方向——其中两个目前只有间接证据。第三个有戏，但我还需要跑一轮模拟。你先休息，明天早上出结果。"

这不是工具。这是一个**同行了三年的研究伙伴**。

## 二、技术阶梯

### 2026年下半年 AGI 关键趋势

| 趋势 | 对我们的影响 |
|------|------------|
| **LLM 推理能力快速提升**（Claude Sonnet 4.6/DeepSeek-R2 级） | DCI 模式更可行——LLM 自己能做更好的检索和综合，无需 embedding |
| **MCP 协议普及**（Chrome DevTools MCP 等） | Agent 工具集从"写多少装多少"变成"即插即用设备" |
| **Agent 交叉审核方法论成熟**（autoresearch 等） | 质量闭环有了现成的参考实现，不是从零发明 |
| **Spec Coding 取代 Vibe Coding 成为共识** | 先定规矩再写代码将成为主流，izu 的先哲学后行动定位更稳 |

### 我们的技术阶梯

#### 现在（v0.1）— 七智能体单向流水线

- **已做到的：** 探×2→搜×2→织→对齐→写→劈 的七角色流水线跑通，wiki 100+页，自动化管道（日报/转录/入库）稳定
- **核心缺失：** 交叉审核为零，中间交接靠信任传递，产出无反馈回传
- **工具集：** 七智能体使用能力未规范化，各 Agent 的边界未经过压测

```
  ↓ 关键升级：引入 Cross-Review Loop + Spec Coding 第一版
```

#### 2个月后（v0.5）— Spec Coding + 交叉审核闭环

- **新增能力：**
  1. 流水线每阶段出口设量化检查点（正确性/相关性/深度/可读性/来源完整性，各0-10分）
  2. "织"Agent 增设交叉审核职责——审核"搜"的结果再往下传
  3. "劈"Agent 在产出中自动标记"缝"（三个未解决的方向），供下次继续
  4. 首次压测各 Agent 能力边界——哪些情况回滚率↑→工具升级或角色拆分
- **验证什么：** 交叉审核能把流水线烂尾率降到多少？回滚成本 vs 质量收益是否可接受？
- **不做：** 复杂的 RAG 系统、用户画像模型、个性化推荐

```
  ↓ 关键升级：画像开始介入交叉审核 + Chrome MCP 加入工具链
```

#### 6个月后（v1.0）— 画像驱动的自适应流水线

- **完整形态：**
  1. 交叉审核循环已稳定运行3个月+，积累了足够多的"合格/不合格"样本
  2. 画像开始反哺：基于你的阅读偏好调节长编的"风格参数"（深度/广度/节奏/举例方式）
  3. Chrome MCP 作为"验证器"接入——当流水线产出需要交叉核验事实时，自动启动浏览器验证
  4. 跨会话记忆正式投入使用——上次留下的"缝"是下次流水线的输入
  5. 工具使用规范化：核心工具集（grep+wiki+chrome+code）被 Spec 锁定；测试实验性工具时自动隔离
- **与 v0.1 的本质区别：** 从"被动流水线"到"自适应同行者"——系统不仅执行任务，还主动调节行为

### 技术债务预警

| 今天的决策 | 3个月后的瓶颈 | 怎么办 |
|-----------|-------------|-------|
| 七智能体各用各的 Prompt 模板 | 交叉审核的标准不统一，A 的评分在 B 身上不适用 | 现在就开始统一"检查点标准"的定义格式 |
| 无 Agent 能力画像 | 不知道哪个 Agent 擅长什么、瓶颈在哪 | 2周内开始做"Agent 劳动日志"（每个任务记录耗时/回滚率/擅长领域） |
| 纯文本 wiki（已足够） | 开始需要结构化元数据（来源类型、入库时间、关联度） | 在 wiki 每篇入口加 YAML frontmatter（推荐：现在的 SKILL.md 格式就是好范例） |
| 全依赖 LLM 做路由判断 | LLM 越来越贵 | DCI 模式可零成本替代 70% 的检索场景 |

|--------|------|-----------|---------|-------|

## 四、定调判断

### 我们坚决做的

1. **Spec Coding 作为 izu 的开发哲学** —— 不是工具，是方法论。每个功能上线前，先写它的规范（检查点/交付标准/回滚条件）。这与"先哲学后行动""匠石原则"一脉相承，是 izu DNA 的自然延伸。
2. **交叉审核循环作为流水线的核心升级** —— 这是今天入库的7个概念中最关键的一个。有了它，izu 从一个"单向流水线"变成了一个"可自愈的系统"。优先级最高。
3. **DCI 模式替换 embedding 检索** —— 零成本、更高准、更符合匠石精神。grep 做检索，LLM 只做语义理解。这是"能用代码就别用模型"在检索层的极致实践。
4. **流水线每步出口加"缝"标记** —— 这不是功能，是哲学。祝白皮书说"每一份长编末尾都是一扇窗户，不是一堵墙"。缝标记就是这扇窗户的技术实现。

### 我们坚决不做的

1. **不建 embedding/向量索引** —— DCI 已证明这条路不必要的成本。grep+bash 在当前规模够用，且准确率更高。
2. **不替换 Hermes 底座** —— 不在 izu 上叠另一个 Agent 框架。MetacGPT 的思路要吸收（角色分工+SOP），但代码用不上。
3. **不是平替"做更好的 Deep Research"** —— 不优化检索速度和信息量，优化"让人还想知道"的能力。
4. **不在前三个月做用户画像模型** —— 先让交叉审核循环跑稳，画像的事让"会话即画像"自然发生，不急做主动预测。

### 我们保持观察的

1. **Chrome DevTools MCP** —— 当前对 izu 的研究流水线价值有限（izu 主要是线下研究，不是网页交互），但一旦"Agent 自己验证事实"场景成熟，就是必须。触发条件：izu 开始做需要交叉核验的事实判断，且准确率不够。
2. **agent-skills 的新 Skill 发布** —— 不用这个工具，但要追踪 Addy Osmani 的 Skill 分类。如果 Hermes Skills Hub 出现类似的"开发阶段→检查点"分类法，考虑借鉴。
3. **简单 RAG 方案** —— 虽然 DCI 在当前规模够用，但 wiki 到 500+ 页时，纯 grep 的精确度下降曲线需要压测。如果 grep 的 recall 跌破可接受的阈值，再考虑轻量方案。
4. **多 Agent 的"劳动分工"数据记录** —— 先不做 Agent 画像，但必须做 Agent 劳动日志（每个任务耗时/擅长的任务类型/回滚率）。这是后来做 Agent 画像的原始数据，现在不收集以后补不了。

## 五、具体改进建议：交叉审核循环 + Spec Coding 落地步骤

### 痛点定位

izu 当前流水线的最大痛点——**质量没有闭环**。具体来说：

1. "搜"的结果"织"直接拿来用，没有检查"搜没搜全、搜没搜对"
2. "写"出的长编"劈"直接发布，没有回头问"这长编好不好、用不用得上"
3. 一次流水线结束后，没有信号告诉系统下一次该改进什么
4. 每个 Agent 的"合格线"没定义，大家各凭感觉

### 落地步骤（按周排期）

#### 第1周：定义检查点标准

给七智能体流水线设定 5 个检查点：

| 阶段 | 检查点 | 评分维度 | 及格线 |
|------|-------|---------|-------|
| 搜→织 | 资料质量审核 | 相关性(0-10)/来源可信度(0-10)/覆盖面(0-10) | 7分三方面均通过 |
| 织→对齐 | 综合质量审核 | 逻辑一致性(0-10)/信息无矛盾(0-10) | 8分 |
| 对齐→写 | 方向确认 | 用户意图匹配度(0-10) | 8分 |
| 写→劈 | 输出质量审核 | 可读性(0-10)/深度(0-10)/有缝(0-10) | 7分/6分/5分 |
| 劈→发布 | 最终审核 | 留一句十年后还有人读的话（有/无） | 必须有 |

**注意：** 这些分数在一开始不用追求"客观"。它们的作用不是数学精确，是**强制每个交接点停下来问"行不行"**。回滚记录比分数本身重要。

#### 第2周：实现第一个交叉审核节点（最强的那个桥头堡）

从**"搜→织"**开始做，这是当前流水线最薄弱的环节——搜的结果质量决定了后续所有产出。

实现方案（参考 autoresearch 模式）：
```
"搜"Agent 提交搜索结果 → "织"Agent 兼做审核员
    → 按 3 维度（相关性/可信度/覆盖面）打分
    → 三个维度均 ≥7 分 → 放行到"织"的正式工作
    → 任一维度 <7 分 → 返回"搜"重做，附反馈说明
    → 回滚 3 次仍未达标 → 标记当前任务为"高风险"，通知张成市人工介入
```

**实现成本：** 每个 Agent 的任务模板尾部加一段"输出后，送交叉审核"的指令。不需要新代码，只需要改 Prompt 和加一个"是否回滚"的条件判断。

#### 第3周：新增"劈"阶段的缝标记

让"劈"Agent 在每份长编末尾强制输出以下结构：
```
## 三扇窗户
1. [未完全解决的方向A] — 因为缺XX资料/证据不够→建议何时回顾
2. [可能的新方向B] — 与主问题相关但未被深入→建议触发条件
3. [当前判断可能错的点C] — 如果有新证据可能会推翻当前结论
```

**这不是可有可无的附加。** 这是让跨会话记忆有了可存储的"接口"。缝标记自动入库 wiki 的 raw/ 目录，明日日报可以直接读取。

#### 第4周：建立回滚数据看板

不建 UI。在 wiki 中新增一个自动生成的页面 `logs/流水线回滚日志.md`，记录：

- 每次回滚：哪个环节、触发了什么检查点、回滚原因、纠正措施
- 每周统计：各环节回滚率、平均回滚次数、最常触发回滚的评分维度
- 异常标记：连续 3 天某环节回滚率 > 40% → 告警

**数据比感觉重要。** 没有数据，你永远不知道"搜"的覆盖面够不够、织的逻辑一致性有没有真的提高。一个月的数据就能告诉你：哪些检查点太松（从不回滚→提高标准）、哪些太严（总是回滚→可能是标准本身错了，不是 Agent 不行）。

#### 第5周：Spec Coding 标准化文档

出第一版 `izu-Spec.md`（建议放在 wiki 根目录），包含：

```yaml
# izu Spec v0.1
## 所有 Agent 共享的规范
- 输出必须标注信息来源
- 不确定的猜测必须标记 [推测] 而非陈述事实
- "不知道"是允许的输出——比编造好

## 各 Agent 特有规范
- 搜Agent：每次搜索结果必须包含"未覆盖的方向"说明
- 织Agent：必须检查搜的结果是否有内部矛盾
- 写Agent：每千字至少留一个"缝"
- 劈Agent：最终审核必须返回"通过/需修改/不合格"三档

## 工具使用规范
- 优先使用 grep+bash（DCI模式），embedding/向量检索为备选
- 测试新工具时使用--dry-run模式，不污染正式产出
- Chrome MCP 只在需要实时验证事实时启用
```

#### 第6-8周：压测与调优

- 选择 10 个历史任务，用旧流水线和加交叉审核的新流水线各跑一次，对比质量
- 记录"交叉审核"带来的额外成本（额外的 LLM 调用 + 回滚带来的重跑）
- 调优：哪些检查点太严导致过度回滚？哪些太松形同虚设？
- 产出第一版"交叉审核经济性报告"——回滚成本 vs 质量提升的实际数据

#### 第9-12周：扩展到全流水线

将交叉审核从"搜→织"扩展到全流水线：
- 织→对齐：逻辑一致性和无矛盾检查
- 对齐→写：用户意图匹配度检查
- 写→劈：输出质量（可读性/深度/有缝）检查
- 劈→发布：最终审核（必须有一句"十年后还有人读的话"）

此时izu从"单向流水线"变成了"闭环流水线"，完成了本次升级的核心目标。

## 六、产业定位

### 地图

```
        效率派（Deep Research/Perplexity）
         │
         │   [izu——在这里]
         │
         └──────────────────→ 陪伴派（izu是独一无二的）
              关系深度 →
```

### 为什么这个位置不可替代

- **大厂够不到：** Deep Research 追求"一次说全"，izu 追求"让你还想知道"。这是产品哲学的分叉，不是技术差距。大厂的组织惯性决定了它们不会为一个用户花一小时慢慢对话。izu 的"一个人+一个系统"模式反而在此有天然优势。
- **小厂做不了：** izu 的根本壁垒不是代码，是**张成市在用的**——一段时间的画像积累、wiki 知识库、七智能体流水线的实际调优经验。新来的人即使复制代码，也得从头积累这些"让它懂你"的资产。
- **我们恰好能：** 因为同时掌握三样东西——哲学（明学/匠石）、工具（Hermes/full tooling）、内容（wiki 100+页持续增长）。大多数团队只占一样。

## 七、后记

这份路线图的灵魂可以概括为三句话：

1. **让流水线可自愈**（交叉审核 Loop）—— 这是 v0.5 的核心，优先级最高
2. **让每份产出都留一扇窗**（缝标记）—— 这是跨会话记忆的接口
3. **让画像自己长出来**（不做主动预测，让会话即画像自然积累）—— 这是 v1.0 的方向

这三件事做完，izu 从"一个七步流水线"变成了"一个会在你走远之后回过头来看你的伙伴"。
