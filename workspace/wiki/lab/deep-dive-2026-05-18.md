# 🥇 深度一：MARS——单周期元认知自进化

> **论文**: *Learn Like Humans: Use Meta-cognitive Reflection for Efficient Self-Improvement* (arXiv:2601.11974)
> **方向**: 支柱1 · Agent自我迭代
> **关联项目**: 爱祝（izu）Agent能力升级

---

## 一、核心方法拆解

### 要解决什么问题？

现有自改进框架（如 Gödel Agent, MetaAgentSearch）采用**多轮递归循环**——Agent 反复尝试→失败→反思→再尝试，计算成本高昂。MARS 的核心洞察是：**人类的反思不是无限循环的，而是在单次思考中完成"原则抽象+程序总结"**。

### 怎么做到的？

MARS 在**单周期**内完成三步：

**Phase 1: 评估（Evaluation）**
对每个失败的题目 `q_i`，用分析器模型产出结构化失败档案 `(τ_i, T_i, ε_i, ρ_i, μ_i)`：
- 题目类型（事实/概念/计算/应用/分析/比较）
- 错误类型（6种分类，含粗心/概念混淆/推理缺失等）
- 根因分析
- 具体错误定位

**Phase 2: 失败归组（Failure Allocation）**
按 `(题目类型, 主题领域)` 分组。每组产出聚合错误画像 `Ψ_j = (错误类型集, 循环根因集, 难度因子)`。

**Phase 3: 增强生成（Enhancement Generation）**
每组生成三种增强变体：
- **简明版**：简短警告 + 关键点
- **推理版**：最小化提示（引导自我修正）
- **综合版**：两者结合

最后通过**基于验证集的混合策略**自动为每类题目选择最优增强类型。

### 关键创新

不是"又试一次"，而是**"想清楚刚才为什么错，下次就不会再错"**。这对应教育心理学中的**双路径元认知**：原则反思（抽象准则）和程序反思（步骤策略）。

## 三、对 izu Agent 的实战启发

### 可复用的架构模式

```
izu Agent Action Pipeline:
  执行 → 失败 → MARS反思器 → 结构化失败档案
          → 归组聚合 → 策略生成 → 注入Agent提示 → 下次行动
```

### 具体可做的三件事

1. **搭建 izu 的失败档案系统**
   - 当前 izu Agent 的每次执行失败，记录结构化档案（行动类型/错误分类/根因/上下文）
   - 对应 MARS 的 `(τ_i, T_i, ε_i, ρ_i, μ_i)` 结构

2. **实现单周期策略生成**
   - 不从零写提示模板，而是用 MARS 的"归组→聚合→混合策略选择"流程
   - 适合 izu 的日常任务类型分类（会议安排/知识检索/写作辅助等）

3. **Hybrid 策略选择器**
   - 对每类任务预配"简明/推理/综合"三种增强方式
   - 用小验证集自动选择最优 → 免人工调参

### 需要注意

- MARS 的评估器本身依赖一个分析器模型（论文中用 GPT-4 系），算力成本需要计入
- 对"创造性任务"（写文章/头脑风暴）的效果可能不如"事实性任务"明显
- 单周期反思的"记忆容量"有限——如果 Agent 的失败模式在时间上分散，归组效果会打折扣

# 🥈 深度二：MPAC——多主体协调协议

> **论文**: *MPAC: A Multi-Principal Agent Coordination Protocol for Interoperable Multi-Agent Collaboration* (arXiv:2604.09744)
> **方向**: 支柱2 · 多Agent协作架构
> **关联项目**: Hermes Agent 工具编排层

---

## 一、问题定位：现有协议的盲区

当前主流协议的分工：
- **MCP**（Anthropic）：Agent→工具的标准化对接
- **A2A**（Google）：单一主体下的Agent间任务委派

**盲区**：当**多个独立主体**（不同公司/不同人的Agent）需要在**共享状态**上协作时——比如：
- 两个工程师的编码Agent要同时编辑同一个Git仓库
- 多个家庭的旅行规划Agent要协调行程
- 跨组织的谈判Agent要共享谈判进展

没有协议能处理这种情况 → 退化为：ad-hoc 聊天 / 手动合并 / 静默覆盖。

**MPAC 就是来填补这个空白的。**

---

## 二、五层协议架构

MPAC 定义了一个**应用层协议**，显式处理多主体协作语义：

| 层 | 功能 | 关键设计 |
|----|------|---------|
| **1. 会话（Session）** | 建立和管理多Agent协调会话 | 会话ID、参与者列表、生命周期 |
| **2. 意图（Intent）** | Agent在执行前声明意图 | **先声明后行动**——核心原则 |
| **3. 操作（Operation）** | 执行带结构协调的动作 | 乐观并发控制 |
| **4. 冲突（Conflict）** | 冲突作为**一等对象** | 不是错误消息，是结构化冲突实例 |
| **5. 治理（Governance）** | 可插拔的人机协同仲裁 | 规则化/人工介入/自动化裁决 |

### 关键设计决策

- **意图声明是行动的前提条件**：任何Agent不能在没有声明意图的情况下修改共享状态 → 让冲突有机会被提前发现，而不是事后补救
- **冲突 = 一等对象**：有结构、有权重、有状态机转换表 → 可以被自动化处理，而不仅仅是抛异常
- **Lamport时钟因果水印**：事件排序不再依赖中心化时间戳
- **乐观并发控制**：假设低冲突时直接执行，冲突时回滚+重试

### 协议规格

- 21种消息类型
- 3个规范状态机（含状态转换表）
- 2种执行模型
- 3种安全配置文件

## 四、对 Hermes Agent 的实战启发

### 直接可用的设计模式

1. **意图声明机制**
   - Hermes Agent 当前的工具调用是"立即执行"模式
   - 引入 Intent Layer：Agent 先声明"我要用工具X做Y"，等待冲突检查后再执行
   - 适合场景：多个 Hermes Agent 实例协作时预防竞态

2. **冲突作为对象处理**
   - 当前 Heremes 的工具调用失败只是错误日志
   - 改为结构化冲突对象（谁/什么时候/什么资源/冲突类型/仲裁选项）
   - 可以自动化部分冲突解决（如时间冲突自动协商）

3. **治理层可插拔**
   - Hermes 的 Gateway 可以整合 Governance Layer
   - 轻度冲突→自动裁决；重度冲突→转人工

# 🥉 深度三：SDAR——门控自蒸馏强化学习

> **论文**: *Self-Distilled Agentic Reinforcement Learning* (arXiv:2605.15155)
> **方向**: 支柱1 · Agent自我迭代（训练管线）
> **关联项目**: 爱祝（izu）训练管线

---

## 一、问题拆解

### 已有的方案及其局限

**GRPO**（Group Relative Policy Optimization）：
- 只用**轨迹级**奖励信号 → 对长程Agent任务的监督过于粗糙
- 无法告诉Agent："你这一步对了，那一步错了"——只有"整条轨迹得分3.2/5"

**OPSD**（On-Policy Self-Distillation）：
- 引入**教师分支**（带特权上下文），提供**token级**密集指导
- 但在**多轮Agent场景**中失败，原因是：
  - 多轮不稳定性→监督信号也跟着不稳定
  - 技能相关的特权引导：当教师因为检索/使用不完美而给出**负向拒绝**时，OPSD 无法区分"这个负信号是有价值的批判"还是"噪声"

### SDAR 的解决思路

**把 OPSD 作为门控辅助目标（gated auxiliary objective），RL 仍然是主优化主干。**

关键组件——**Sigmoid门控**：
- 将教师端token级信号映射到 sigmoid 函数上
- **正差距**（教师认可的token）→ 门打开，强化蒸馏
- **负向教师拒绝** → 门软性衰减，但**不完全丢弃**（信息可能仍有价值）

---

## 二、技术细节

### 训练流程

```
主优化：GRPO（轨迹级奖励）
辅助优化：OPSD（token级指导）
     └─ Sigmoid门控：选择性强化/弱化
```

### 为什么有效？

1. **RL保持主导**：轨迹级奖励提供稳定的全局优化方向，不会因为辅助目标而偏移
2. **门控选择性**：不是"全盘接受教师指导"，而是只取有正价值的token级信号
3. **不完全丢弃负信号**："软衰减"而非"硬丢弃"——教师拒绝中可能含有有用信息（如"这不是最佳路径，但告诉你为什么"）

## 三、实验结果

| 基准 | GRPO | SDAR | 提升 |
|------|------|------|------|
| ALFWorld | 基线 | **+9.4%** | 稳定 |
| Search-QA | 基线 | **+7.0%** | 稳定 |
| WebShop | 基线 | **+10.2%** | 稳定 |

- 横跨 Qwen2.5 和 Qwen3 模型族验证
- 避免 naive GRPO+OPSD 的不稳定性
- 在所有模型规模上一致优于混合 RL–OPSD 基线

## 四、对 izu 训练管线的实战启发

### 可落地的位置

izu 如果想做 Agent 的自我迭代训练，SDAR 是**最低侵入性**的方案——它只是一个 loss 项的 add-on，不需要改整个训练管线。

### 具体实现思路

```
izu Training Pipeline:
  [原有] GRPO loss → 更新模型
  [新增] OPSD loss × Sigmoid gate → 加到总loss中
     ├─ 教师分支：用更强模型（如 Qwen3-70B）在"上帝视角"下标注
     └─ 门控：只强化教师认可的token级别的指导
```

### 需要注意

- 需要有一个**教师模型**（占用额外算力）
- 教师的"特权上下文"需要设计——什么信息是教师在推断时能看到但Agent在运行时看不到的？
- 门控的 sigmoid 温度参数需要调优

| 维度 | MARS | MPAC | SDAR |
|------|------|------|------|
| **解决的问题** | 自改进计算成本高 | 多主体协调无协议 | RL训练监督粗糙 |

| **izu适用阶段** | 推理时自改进 | 多Agent协作 | 训练管线优化 |
| **实现成本** | 低（单次调用） | 中（协议集成） | 中高（需教师模型） |
| **可复用性** | 架构模式 | 参考实现(2语言) | loss项add-on |

**组合使用建议**：
1. 先用 SDAR 优化 izu Agent 的**训练**（让基础能力更强）
2. 再用 MARS 让训练好的 Agent 在推理时**自反思**（补训练覆盖不到的错误模式）
3. 最后用 MPAC 的思路设计 Hermes Agent 的**多实例协作**（处理复杂的多Agent任务）
