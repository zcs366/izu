## 🥇 Deep Dive: Library Drift — 自进化技能库的静默杀手

**论文**：Library Drift: Diagnosing and Fixing a Silent Failure Mode in Self-Evolving LLM Skill Libraries
**链接**：https://arxiv.org/abs/2605.19576
**方向**：Agent自我迭代 · 直接关联izu

---

### 核心问题

自进化技能库（Self-evolving skill libraries）面临一个此前未被正式定义的失败模式——**库漂移（Library Drift）**：技能无限累积，但没有outcome-driven的生命周期管理，导致：

1. **检索退化**（Retrieval degradation）：技能越多，检索噪声越大，相关技能被埋没
2. **误注入**（False-positive injections）：低质量甚至有害的技能被注入库中
3. **性能停滞**（Performance stagnation）：技能数量增加但端到端性能不再提升

### 关键证据

引用SkillsBench的发现：LLM自撰写的技能带来 **+0.0pp**（零提升），而人工筛选的技能带来 **+16.2pp**。这说明问题不在"技能生成"本身，而在"技能管理"。

### 三个可复现的触发条件（Ablation验证）

| 场景 | 结果 |
|------|------|
| 关闭技能注入（flat floor） | +0.002，几乎无变化 |
| 强制技能提前退役（premature retirement） | 主动伤害 -0.019 |
| 正常自进化 | 性能先升后降，进入漂移状态 |

### 提出的修复方案：三层治理配方

```
1. Outcome-driven retirement（结果驱动退役）
   → 技能按贡献度自动淘汰，非LRU

2. Bounded active-cap（活跃上限）
   → 同时活跃技能数有硬上限，防止检索退化

3. Meta-skill authoring prior（元技能创作先验）
   → 新技能创作时注入"什么技能值得保留"的先验知识
```

**效果**：held-out pass@1 从 0.258 → 0.584（late-window mean），提升 +0.328。

### 对izu的直接意义

izu的Agent自进化机制正好面临这个问题——技能库在无人值守的情况下持续累积，迟早进入库漂移状态。这篇论文给了我们一个**现成的诊断+修复工具箱**：

1. **Trace-level诊断工具**：追加式证据日志（append-only evidence log），每条技能有贡献分数、归属判定、路由参与度指标——这些指标在端到端分数下降之前就能暴露问题
2. **现成的治理配方**：outcome-driven退役 + 活跃上限 + 元技能先验
3. **八组消融实验**：哪个机制是承重墙，哪个可以被替代，一目了然

### 行动建议

1. **立即接入**：在izu的技能库管理模块中实现evidence log，对标论文中的trace-level诊断
2. **设置活跃上限**：当前技能库若已有50+技能，立刻设active-cap
3. **实现outcome-driven退役**：每个技能绑定一个contribution score，定期评估、淘汰后10%
4. **元技能先验**：在izu的Wiki知识系统中，将"技能创作指南"本身作为meta-skill注入

## 🥈 Deep Dive: Discoverable Agent Knowledge — Agent如何"知道它能知道什么"

**论文**：Discoverable Agent Knowledge -- A Formal Framework for Agentic KG Affordances
**链接**：https://arxiv.org/abs/2605.19186
**方向**：多Agent协作 · 直接关联izu

---

### 核心洞察

当前知识图谱（KG）的元数据标准（VoID、DCAT）只能描述KG"有什么"（统计信息：实体数、三元组数、主题域），但**不说一个Agent能从中"证明什么"**。这个差距导致：

- Agent无法在规划阶段判断某个KG是否适合它的任务
- 空结果无法区分"真不存在"和"查询表达不当"
- 任务词汇表与Schema的对应关系没有显式建模
- 声明使用的推理体制与实际运行的推理体制可能不一致（epistemic failure）

### AAP：Agentic Affordance Profile

核心贡献是一个四维形式化框架：

| 维度 | 定义 | 意义 |
|------|------|------|
| **Epistemic** | Agent能从KG中证明什么？ | 区分"可证明为真"vs"不可证伪" |
| **Grounding** | Agent的任务词汇如何映射到Schema？ | 解决词汇表不匹配 |
| **Closure** | 空结果的假设是什么？ | CWA vs OWA vs 本地封闭世界 |
| **Entailment** | 实际推理体制与声明体制一致吗？ | 防止推理体制漂移 |

### 五点研究议程

1. **形式化**：将AAP定义为一阶逻辑的扩展
2. **计算**：AAP匹配的可判定性和复杂度
3. **工程**：在VoID/DCAT上叠加AAP层
4. **组合**：多个KG的AAP组合推理
5. **失效诊断**：当Agent选错KG时，AAP能否定位原因

### 对izu的直接意义

izu正面临一个实际困境：Wiki知识库中存储了大量Markdown/HTML文档，但Agent读取这些文档时：
- 不知道哪些文档能回答哪些问题（没有epistemic profile）
- 搜索返回空结果时，不知道是"没有相关内容"还是"搜索策略不对"
- 多个文档的联合推理没有形式化支撑

AAP框架提供了将izu Wiki知识库从"文件集合"升级为"Agent可发现知识源"的路线图。特别是：

1. **Wiki-AAP**：为每个知识条目生成一个轻量级AAP（能回答什么问题、不能回答什么）
2. **规划时选择**：Agent在开始推理前就选择正确的知识源
3. **空结果诊断**：区分"无知识"和"查询不当"

### 行动建议

1. **概念验证**：选择izu Wiki中的3-5个核心知识条目，手动编写AAP
2. **自动化AAP生成**：利用LLM为每个Wiki条目自动生成epistemic profile
3. **集成到izu路由**：在知识检索前增加AAP匹配步骤

## 🥉 Deep Dive: Trustworthy Agent Network — A2A网络的信任不能后补

**论文**：Trustworthy Agent Network: Trust in Agent Networks Must Be Baked In, Not Bolted On
**链接**：https://arxiv.org/abs/2605.19035
**方向**：多Agent协作 · 关联Hermes Agent

---

### 核心洞察

Agent从独立运行走向协作生态（A2A网络），带来了现有安全对齐技术无法解决的**系统性漏洞**：

| 漏洞类型 | 描述 |
|---------|------|
| **对抗组合**（Adversarial Composition） | 两个独立安全的Agent组合后产生不安全行为 |
| **语义错位**（Semantic Misalignment） | Agent之间对同一个指令的理解不一致 |
| **级联故障**（Cascading Operational Failures） | 一个Agent的故障通过协作链放大 |

### 四大设计支柱

1. **身份与认证**（Identity & Authentication）
   - 每个Agent有可验证的身份
   - 在多供应商环境中防止身份欺骗

2. **行为契约**（Behavioral Contracts）
   - Agent之间通过形式化契约约定行为边界
   - 契约可被运行时监控器验证

3. **运行时监控**（Runtime Monitoring）
   - 对跨Agent交互的实时监控
   - 偏离契约时的自动干预

4. **争议仲裁**（Dispute Resolution）
   - Agent间出现分歧时的仲裁机制
   - 可追溯至历史交互日志

### 与现有工作的关键区别

- 不是"在现有Agent框架上加一层安全"（bolted on）
- 而是"从A2A协调框架的架构设计第一天就内建信任"（baked in）

### 对Hermes Agent的直接意义

Hermes Agent的多Agent编排能力（Gateway、tool orchestration、MCP协议）正好处于A2A网络的架构层面。这篇论文提醒我们：

1. **当前风险**：Hermes的multi-agent编排没有信任机制——任意Agent可以调用任意工具
2. **内建时机**：现在还是在设计阶段，可以内建信任架构
3. **具体切入点**：
   - 在Gateway层实现Agent身份验证
   - 为每个skill/tool定义behavioral contract
   - 增加运行时拦截器（类似Guardrails但针对跨Agent交互）

### 行动建议

1. **审计当前架构**：排查Hermes Agent中哪些地方存在"信任后补"风险
2. **定义契约原型**：为izu Agent和Hermes Agent之间的交互定义behavioral contract
3. **优先实现运行时监控**：关注"一个Agent调用另一个Agent的tool"时是否有监控
4. **关注后续工作**：这篇是vision paper，预计会有具体实现跟进
