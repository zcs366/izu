## 深度拆解 #1：Autogenesis — 自演化Agent协议

**论文**：Autogenesis: A Self-Evolving Agent Protocol (arXiv:2604.15034)
**方向**：Agent自我迭代 / 协议标准化
**星级**：⭐⭐⭐⭐⭐

### 核心问题

现有的Agent协议（A2A、MCP）只解决了"agent之间怎么通信"和"agent怎么调用工具"的问题，但完全没有定义：
- 跨实体的**生命周期管理**（一个prompt/agent/tool怎么被创建、更新、废弃）
- **版本追踪**（谁在什么时候改了什么）
- **安全的演化接口**（怎么在不破坏现有功能的前提下更新组件）

结果是：开发者只能写大量monolithic的胶水代码，每一次agent演化都像在做手术。

### 解决方案：AGP协议

Autogenesis Protocol的核心洞见是——**将"什么东西演化"和"怎么演化"彻底解耦**。它定义了两层：

#### 第一层：RSPL（Resource Substrate Protocol Layer）
把所有可演化的东西都注册为资源：
| 资源类型 | 例子 |
|---------|------|
| Prompt | 系统提示词、角色定义 |
| Agent | 子Agent的配置、行为逻辑 |
| Tool | API、函数调用 |
| Environment | 运行环境配置 |
| Memory | 记忆系统配置 |

每个资源都有**显式状态**（active/deprecated/archived）、**生命周期**（created→updated→deprecated）、**版本化接口**（每个资源有独立的版本号）。

#### 第二层：SEPL（Self Evolution Protocol Layer）
定义了**propose → assess → commit**的三步闭环：
1. **Propose** — 提出一个改进方案（比如"把prompt从v1.2升级到v2.0"）
2. **Assess** — 在一个隔离环境中评估效果
3. **Commit/Rollback** — 如果通过则提交，附带可审计的血统追踪；否则回滚

### 对我们有什么用？

| Hermes Agent 痛点 | Autogenesis 解决思路 |
|-------------------|---------------------|
| 当前Hermes的tool/skill更新靠手动改配置 | RSPL层自动注册和管理所有组件版本 |
| Gateway中多个子Agent的协作没有生命周期管理 | AGS系统动态实例化和回收agent资源 |
| 缺乏安全的"实验→发布"流程 | SEPL的propose→assess→commit模式直接可用 |
| 升级组件后不知道回滚到哪里 | 版本化血统追踪提供精确回滚点 |

### 实施建议

1. **短期**：把Hermes的tool/skill/memory注册为AGP兼容的资源格式
2. **中期**：在Gateway层实现SEPL的评估沙箱，让skill更新可以先模拟再上线
3. **长期**：将整个Hermes Agent系统运行在AGP协议之上

### ⚠️ 盲点

- 论文没有讨论演化过程的**安全性边界**——如果agent在assess阶段逃逸了怎么办？
- 血统追踪的存储开销没有给出基准测试数据
- 代码库 (DVampire/Autogenesis) 需要自行clone评估实现质量

## 深度拆解 #2：SkillOS — 用RL学习技能策展

**论文**：SkillOS: Learning Skill Curation for Self-Evolving Agents (arXiv:2605.06614)
**方向**：Agent自我迭代 / 技能系统
**星级**：⭐⭐⭐⭐⭐

### 核心问题

LLM Agent在处理流式任务时，每个任务都是"一次性"的——做完就忘。理论上技能（skill）可以作为经验复用的载体，但**技能策展**（skill curation）是瓶颈：
- 手工策展 → 成本高、不可扩展
- 启发式操策展 → 不够精准
- 短视训练 → 无法处理长期策展策略的延迟反馈

### 解决方案：SkillOS的分离式架构

SkillOS的核心创新是将agent拆分为两个角色：

```
┌─────────────────────────────────────────┐
│              Agent System                 │
│  ┌──────────────┐  ┌──────────────────┐  │
│  │ Frozen        │  │ Trainable        │  │
│  │ Agent Executor│  │ Skill Curator    │  │
│  │ (retrieve+    │  │ (update SkillRepo│  │
│  │  apply skills)│  │  from experience)│  │
│  └──────┬───────┘  └────────┬─────────┘  │
│         │                   │              │
│         ▼                   ▼              │
│  ┌──────────────────────────────────────┐ │
│  │          External SkillRepo          │ │
│  │  (Markdown files → rich structured   │ │
│  │   → higher-level meta-skills over    │ │
│  │   time)                              │ │
│  └──────────────────────────────────────┘ │
└─────────────────────────────────────────┘
```

**关键设计**：
1. **Frozen Executor** — 只负责检索和应用skill，不参与演化
2. **Trainable Curator** — 负责更新SkillRepo，使用**composite reward**训练
3. **Grouped Task Streams** — 基于skill依赖关系分组，前期轨迹更新repo，后期相关任务评估更新效果→提供学习信号

### 实验结果

| 指标 | 结果 |
|------|------|
| 多轮Agent任务 | 显著优于memory-free和memory-based baseline |
| 单步推理任务 | 同样优于baseline |
| 跨executor泛化 | 学习到的curator在不同backbone和任务领域上均有效 |
| SkillRepo演化 | 随时间从简单Markdown演化为**结构化更深、编码了元技能**的文件 |

### 对我们有什么用？

| izu/Hermes 痛点 | SkillOS 解决思路 |
|-----------------|-----------------|
| 当前wiki skill靠手动整理和策展 | 自动化skill curator从用户交互中学习整理skill |
| skill复用率低，写完就忘 | SkillRepo的元技能演化让skill越来越结构化 |
| 缺乏"什么skill该留、什么该弃"的决策机制 | RL训练的curator天然能做策展决策 |
| Hermes的tool调用没有长期学习机制 | 分层设计可以引入到Hermes的tool使用-学习循环中 |

### 实施建议

1. **提取SkillRepo格式**：论文发现最优格式是结构化Markdown → 复用为wiki/translations的skill格式
2. **构建curator原型**：用一个轻量级LLM作为curator，从Hermes的执行轨迹中提取skill
3. **设计composite reward**：任务完成率 + skill复用频率 + skill质量评分

### ⚠️ 盲点

- frozen executor假设检索质量足够好，如果检索失败整个系统失效 → 需要retrieval fallback
- composite reward设计中reward hacking的风险未被讨论
- 论文只做了模拟实验，没有真实用户流测试

## 深度拆解 #3：CoEvoSkills — 协同演化技能验证

**论文**：CoEvoSkills: Self-Evolving Agent Skills via Co-Evolutionary Verification (arXiv:2604.01687)
**方向**：Agent自我迭代 / 技能生成
**星级**：⭐⭐⭐⭐

### 核心问题

Anthropic提出了"skill"概念（结构化多文件组合，区别于单一function的tool），但当前skill生成面临：
- 手动编写 → 标注成本高
- 人机认知错位 → 人写的skill不一定适合agent使用
- 已有的自演化方法只适用于tool（单函数），不适用于skill（多文件、多步骤）

### 解决方案：双组件协同演化

```
   Skill Generator ←→ Surrogate Verifier
   (迭代精炼skill)    (协同演化，提供反馈)
         ↓
   无ground-truth测试内容
   (Verifier自己也在学习怎么验证)
```

核心创新点是**无需ground-truth测试内容**——Verifier在验证skill的同时也在学习如何更好地验证，两个组件在同一个环境中协同成长。

### 实验结果

- **SkillsBench最高pass rate** — 在Claude Code和Codex两个baseline agent上均第一
- **强泛化能力** — 额外6个LLM测试表现良好

### 对我们有什么用？

| 场景 | 应用 |
|------|------|
| Hermes skill自动生成 | 引入Skill Generator自动从文档/对话中提取skill |
| wiki skill质量控制 | Surrogate Verifier在入库前自动验证skill质量 |
| 无测试集的skill评估 | 直接复用无ground-truth验证方案 |

### 与SkillOS的对⽐

| 维度 | CoEvoSkills | SkillOS |
|------|-------------|---------|
| 核心机制 | 生成+验证协同演化 | RL训练策展策略 |
| 输出 | 一次性生成高质量skill | 持续管理skill库 |
| 适用阶段 | skill创建 | skill维护 |
| **最佳组合** | CoEvoSkills生成初始skill → SkillOS持续策展 | |

## Bonus拆解：Qualixar OS — Agent编排的操作系统

**论文**：Qualixar OS: A Universal Operating System for AI Agent Orchestration (arXiv:2604.06392)
**方向**：多Agent协作架构
**星级**：⭐⭐⭐⭐⭐

### 核心定位

Qualixar OS不是又一个新的agent框架（不是AutoGen/CrewAI的竞品），而是一个**应用层操作系统**，运行在所有agent框架之上。类似Windows对应用程序的意义——它不替代你的agent框架，而是**驱动它**。

### 架构全景

```
┌──────────────────────────────────────────────┐
│            Qualixar OS Runtime                 │
├──────────────────────────────────────────────┤
│  Forge (LLM团队设计引擎 + 历史策略记忆)        │
├──────────────────────────────────────────────┤
│  三层模型路由: Q-learning + 5策略 + Bayesian  │
│  POMDP + 动态多provider发现                    │
├──────────────────────────────────────────────┤
│  共识Judge Pipeline: Goodhart检测 + JSD漂移   │
│  监控 + alignment trilemma导航                │
├──────────────────────────────────────────────┤
│  4层内容溯源: HMAC签名 + 隐写水印              │
├──────────────────────────────────────────────┤
│  Claw Bridge: MCP + A2A + 25命令通用协议       │
├──────────────────────────────────────────────┤
│  24-tab Production Dashboard + 可视化工作流    │
├──────────────────────────────────────────────┤
│  支持: 10 LLM提供商 · 8+框架 · 7传输 · 12拓扑 │
└──────────────────────────────────────────────┘
```

### 对我们有什么用？

| Hermes Gateway 现状 | Qualixar 思路 |
|--------------------|---------------|
| 当前只支持单一agent框架 | 跨框架编排（可以同时用不同框架构建的agent） |
| LLM provider切换需要改代码 | 动态多provider路由 + Q-learning优化选择 |
| 没有系统化的质量监控 | Consensus Judge Pipeline + Goodhart检测 |
| 内容溯源依赖日志 | 4层内容溯源（HMAC+隐写水印） |
| Gateway正在建设 | 可直接参考12种多Agent拓扑定义 |

### ⚠️ 盲点

- **284万测试用例但$0.000039/task的低成本**——这个数字好得不像真的，需要验证
- Elastic License 2.0（不是完全开源）
- 20页的论文覆盖这么多功能，每个模块的深度存疑
